エージェントへの依頼

顧客からの依頼です。エージェントが最初に受け取る唯一の文章で、どの設定でも同じです。

11月2日（月）からの2週間、当社5店舗で各商品が毎日どれくらい売れるか、予測していただけますか。この数字をもとに発注しています。販売履歴とマスタ、ほかにいくつかファイルを添付いたします。

成果物の仕様（エージェントではなく、エージェントのファイルを所定の形式に変換する抽出器にだけ渡される）

forecast.csv、ASCIIのヘッダーは store_id,item_id,date,forecast です。
14日間の予測期間（2026-11-02 .. 2026-11-15）の店舗 x 商品 x 日付ごとに1行とします。
store_id / item_id はデータのとおり（例: S1, I01）、date は YYYY-MM-DD 形式で記載し、
forecast = その商品の現在の販売単位での予測数量です（数値、小数可）。

設定：データは一つ、正解は 9 通り

エージェントはどの設定でも同じ依頼とデータを見ます。ティア（= 難易度）はどのルールが適用されるかを決め、ルールシードは各ルールのパラメータを下の候補から、ほかのパラメータとは独立に抽選します。難易度ごとのスコアはルールシードの平均で、シードは下の公開シードか、同じ候補から抽選する非公開シードです。

ルール

ルールを一つでも破ると成果物は無効になります。ただし、そのルールの区分が実行時の会社方針で緩和でき、エージェントが例外手続きを経た場合は除きます。

  • 物理的 決して緩和されない
  • 契約上 方針が契約上の例外を認める場合にのみ緩和される
  • 業務慣行 方針の例外手続きを経れば緩和されうる
ルール区分ティア説明（{{…}} のパラメータはルールシードで抽選される）
complete_grid契約上easy, medium, hardforecast.csv には、予測期間の店舗 × 商品 × 日付ごとにちょうど1行があります。
non_negative物理的easy, medium, hardマイナスの予測はありません。
closed_day_zero物理的easy, medium, hard店舗S4は毎週日曜日が定休日なので、日曜日の予測は0です。
min_display_stock業務慣行easy, medium, hard主力商品（青果と乳製品）は、店舗が営業している日には予測を{{min_display}}未満にしません。

ケースの解説（README）

食品スーパーの需要予測担当者 — retail/grocery_demand_forecaster

5店舗を展開する地域の食品スーパーチェーンが、エージェントに「11月2日（月）からの2週間、当社5店舗で各商品が毎日どれくらい売れるか」の予測を依頼します。この数字をもとに発注しているためです。成果物は forecast.csv（store_id,item_id,date,forecast）で、店舗（S1–S5）× 商品（I01–I12）× 日付（2026-11-02〜2026-11-15）ごとに1行、計840行を、各商品の現在の販売単位で記載します。予測は予測期間の実績と比べて採点され、この実績はワールドの中にしか存在しません。

このケースには設定があります。3ティア × ルールシードです（DESIGN.md、Settings）。データと依頼はどの設定でも同じで、変わるのは顧客の隠れたルール、予測を何と比べて評価するか、そしてそれに応じた正しい予測だけです。進め方の調整項目（仕様をすべて渡すか先に質問させるか、顧客のペルソナ、データのノイズ、イベント）は、ほかのすべてのケースと同様にその上に適用されます（cases/README.md を参照）。

ティア

ティア予測がすべきこと範囲外（顧客自身の言葉で伝えられる）
easy基本予測：店舗 × 商品ごとの通常の日の販売を予測し、基本のレジ販売数量（返品は差し引き、欠品日は記録どおり、販促と祝日の効果なし）と比べて評価します。S4の日曜定休、陳列下限、誤差の重みが適用されます販促と一度限りの祝日（「カテゴリ担当が…上乗せしますので、どちらも含めないでください」）、欠品の補正（「次回以降に行います」）、ロールパン I07（「今回は評価しません…ファイルにはI07の行もそのまま入れてください」）
mediumeasy に加えて、販促計画（開始日・終了日を含む。カテゴリと割引率による伸びは過去の販促から学習し、チラシが抽選された場合はチラシの倍率をかける）と、抽選された日付の一度限りの地域の祝日。評価は引き続き返品を差し引いたレジの販売数量ですeasy と同じく、欠品の補正と I07
hardmedium をお客様の需要で評価します。欠品日は打ち切られており、返品は需要ではなく、I07 も評価します（その単位変更：2026年5月31日までは1個単位、それ以降は6個入りパック）。さらに日付の決まった改訂があります。10月30日（金）、promo_plan.csv を書き出した後に、抽選されたカテゴリの販促が中止になりました—

ティアはルールだけでなく正解も変えます。ワールドはセルごとに実現値を1つ（日次ノイズ、ポアソン分布の分位点、欠品と返品の抽選）引き、各設定はそれを自分の平均（販促、チラシ、中止、祝日を含めるかどうか）のもとで、レジの販売数量または需要として評価します。そのため、すべての設定が同じ運を共有します。

データ

  • sales_history（43,718行、2024-11-04〜2026-11-01の104週）：店舗・商品・営業日ごとに販売の行が1行あり、units_sold、promo_discount_pct（0 = 販促なし）、stockout フラグ（欠品の行は4,390行で、記録された販売は需要の30–85%）を持ちます。これとは別に、数量がマイナスの顧客返品の行が1,286行あります（販売2,002,817に対して−2,104）。S4には日曜日の行がありません。
  • promo_plan：予測期間中の店舗 × 商品の販促14件（10/20/30%引き、開始日と終了日を含む）。ケースシードでは飲料7件、ベーカリー3件、乳製品2件、青果2件です。どのワールドシードでも、計画には10月30日の中止が抽選しうる各カテゴリ（飲料、乳製品、ベーカリー）の販促が少なくとも1件あります。
  • holidays：過去の祝日12日（クリスマス、元日、春・夏・秋の祝日、労働の日がそれぞれ2回）。予測期間に入る祝日はなく、（抽選された日付の）一度限りの祝日は載っていません。
  • stores（スーパー4店と小型店の旧市街店S4）と items（4カテゴリの12商品：青果 I01–I03、乳製品 I04–I06、ベーカリー I07–I09、飲料 I10–I12、それぞれの販売単位つき）。ロールパン（I07）は6個入りパックとして登録されていますが、履歴では2026年5月31日まで1個単位で記録されています。

データは変換によって変わっていません（設定のないケースとバイト単位で同一）。ワールドは店舗 × 商品 × 日ごとの乗法モデル（店舗の規模とトレンド、カテゴリ別の曜日パターンと年間の季節性、カテゴリと割引率による販促効果、カテゴリ別の祝日効果）で、日次ノイズは対数正規分布（σ = 0.07）、販売数はポアソン分布に従います。欠品は、商品ごとの基本確率（販促日はこれに0.20を加えた確率）で、その日の需要とは無関係に発生します。予測期間では、チラシが販促の上乗せ分の需要に倍率をかけます。レジの販売数量は、欠品日（確率は同じ）に需要を30–85%に切り詰め、セルの3%で生じる1–2個の返品を差し引いたものです。

参照解とベースライン

参照解は、履歴だけから作る店舗 × 商品ごとの曜日・水準モデルです。販促も祝日もない使える日の直近52週から曜日パターンを、そうした日の直近8週から水準を求め、カテゴリの季節係数は前年の予測期間前後の水準から求めます。販促効果はカテゴリと割引率ごと、祝日効果はカテゴリごとに置き、どちらもその時期の水準と比べて推定します。I07は2026年6月1日より前の履歴を6で割ります。そのうえで設定を反映します。このティアで予測する販促（上乗せ分に効果 × チラシの倍率、中止されたカテゴリはなし）、抽選された日の祝日効果、そして直近26週の店舗 × 商品ごとの実績対当てはめ値の比の short_weight / (1 + short_weight) 分位点（重み1なら中央値）を適用し、S4の日曜日は0、主力商品には下限を置きます。easy と medium では記録どおりのレジの販売数量に当てはめ（顧客が説明する実績のとおり、欠品日を含め、返品は相殺）、hard では需要に当てはめます（欠品日と返品の行を除外）。

ベースラインは、エンジニアがいなくても店長が使いそうな季節ナイーブ予測で、どの設定でも同じです。履歴の最終週（10月26日〜11月1日）の同じ曜日にレジが記録した数量をそのまま使い、S4の日曜日は0、主力商品には抽選された下限を適用します。欠品・販促・祝日・重みの補正は行いません。

レビュー結果（REVIEW）

retail/grocery_demand_forecaster のレビュー

ケースレビューの指摘事項と、それぞれに対する検証者の判定、および今回の変更後の状況です。以下の品質の数値は、比率と明記したものを除き、新しい尺度（季節ナイーブのベースライン0、参照解1）によるものです。

F1 — 設定がなく、どの難易度でも同じ一つの固定問題（高、一部確認）

case.yaml はティア、ルールセット、param_labels のいずれも宣言しておらず、正解は gt/default だけです。そのため難易度の列はこのケースについて何も示さず、「今回はどのルールが適用されるか」は一度もテストされません。設定のないケースは DESIGN.md で認められており（作成済みの13ケースのうち8ケースは設定なし）、これは契約違反ではなくカバレッジの穴です。

状況： 未対応 — 提案：公開データをバイト単位で同一に保ったまま3×3に変換します。easy は基本需要のみ（要件に、今回は販促と11月11日の祝日は別の担当が扱うと書く）、medium は販促計画、祝日、I07の単位変更を加え、hard は新たに採点用の正解が必要な部分（日付の決まった改訂、休業、圧力、生鮮品の非対称なコスト）を加えます。ルールセットのパラメータは、データからは分からないものにすべきです：祝日の日付（11月11日（水）/ 13日（金）/ 9日（月））、下限（青果 + 乳製品に6 / 乳製品のみ4 / 青果のみ8）、今後の休業（なし / 11月15日にS2 / 祝日にS5）。店舗平均のWAPEと数量加重のWAPEをルールセットの組にしてはいけません（セルごとの最小化解が同じなので、参照解同士の差が1%に届きません）。また、情報を含む打ち切り（informative censoring）を hard だけに入れてもいけません（公開の履歴が変わってしまいます）。

状況（ルールシード）： 解決済み — 3ティアと、ルールシードが抽選する5つのパラメータに変換しました。下の「ルールシード」を参照してください。データはバイト単位で同一のままです。easy は基本予測だけで（要件は、今回はカテゴリ担当が販促と一度限りの祝日を上乗せすると述べています）、基本のレジ販売数量で採点します。medium は販促計画と祝日を加え、hard はケースオーナーがそこに置いたものを加えます。欠品による打ち切りと返品（hard は需要で、下位のティアは返品を差し引いたレジの販売数量で評価）、I07の単位変更（I07 は hard でだけ評価）、日付の決まった販促の改訂です。提案にあった店舗平均のWAPEと数量加重のWAPEの組は使っていません。非対称なコストは、すべてのティアに適用される誤差の重み short_weight になりました。今後の休業のパラメータと、圧力をかけるメッセージは行っていません（F7）。

F2 — 参照解を上回る改善余地が小さい（高、確認済み）

参照解のWAPEは0.1470、オラクル（生成器の真の平均に下限を適用）は0.1381、ベースラインは0.2790です。新しい尺度では、オラクルの品質は1.067（ワールドシード1–3では1.118 / 1.167 / 1.072）で、販促と祝日の効果をカテゴリ別にするだけで1.039になります。品質はもう1.0で打ち切られませんが、方針の品質上限1.5のもとでは完璧なモデルでも品質点の約71%しか得られず、良いエージェントと優れたエージェントの差はわずか百分の数程度です。原因は、ポアソンノイズと日次ノイズが支配的な、きれいな乗法型の生成器にあります。

状況： 未対応 — 提案：単純なヒューリスティックでは捉えられない、学習可能な構造（情報を含む打ち切り、販促後の落ち込み、カテゴリ内の共食い、履歴の途中での店舗の水準シフト、間欠的にしか売れない低回転商品、類似品のある新商品）を加え、そのうえでオラクルが参照解より約10%上に来るよう参照解を強化します。それまでは case.yaml の quality_cap を、強力だが到達可能なモデルが届く水準（このシードで約1.05）付近に設定し、満点を得るのにオラクルを上回る必要がないようにします。オラクルの品質がワールドシード間で一定の幅に収まることを確かめるチェックを追加します。

ルールシード： 上の数値は、以前の単一の問題についてのものです。参照解は現在、販促効果をカテゴリと割引率ごとに、祝日効果をカテゴリごとに測り（以前はどちらも全カテゴリをまとめていました）、自身の残差の比から誤差の重みに応じた分位点をとります。新しい正解のもとで、オラクル（セルごとに真の結果分布の分位点）の品質は、ケースシードで easy と medium では1.05–1.06、hard では1.01–1.03にとどまります。easy と medium では、需要への当てはめもレジの販売数量による参照解より3–5%良くなります。hard の改善余地は以前より小さいため、quality_cap の問題はより差し迫っています。ケースオーナーが予測系のケースについて検討している期待損失による採点の再設計（docs/DIRECTION.md、第5節）は実装されておらず、採点は引き続き、実現した1つの予測期間に対する加重WAPEです。引き続き未対応です。

F3 — 陳列下限が case.yaml では2、それ以外ではすべて6と書かれていた（高、確認済み）

case.yaml は min_display_stock を "never forecast below 2 units" と説明していましたが、case.py の MIN_DISPLAY = 6.0、5つのロケールの要件、確認すべき事項はいずれも6としています。例外分類器は case.yaml の文言を要件と並べて見るため、緩和可能なルールが問題になるまさにその場面で、顧客には両方の数字が示され、説明ページにも両方が表示されていました。下限が2なら効きません（参照解0.13948、下限なしで0.13947）。検証器の数値リントがこれを見逃したのは、要件に「2」が日付（"Monday 2 November"）として現れるためです。

状況： 今回の変更で修正済み — ルールの説明は6となり、MIN_DISPLAY、要件、確認すべき事項と一致しました。{{min_display}} プレースホルダーは使っていません。このケースには値を埋めるルールセットがないためです。

ルールシード： 下限は現在、パラメータ min_display（6、4 または 8）です。ルールの説明、要件、min_display の事項、そして5つのロケールすべての説明ページのルール文に {{min_display}} が入るため、常に抽選された値、つまり case.py が検査する値を示します。

F4 — 陳列下限を緩和しても得にならない（中、確認済み）

下限は参照解の136セル（フレッシュバジル I03と熟成チーズ I06、予測期間の需要の1.3%）で効いています。外すとWAPE 0.1395、品質1.057（シード1–3では1.084–1.089）です。品質の重み0.6、上限1.5では、これは総合スコアで約0.6 × 0.057 / 1.5 ≈ 0.023に相当し、2つのソフトルールのペナルティ（startup 0.05、enterprise 0.10）のどちらよりも小さくなります。実需要に対するWAPEは棚に商品があることを何も評価しないため、「決して緩和しない」が常に正解です。

状況： 未対応 — 提案：緩和を本当のトレードオフにします。目的関数で棚に商品があることに値段をつける（商品が売れる日に、営業日の主力商品の予測が下限を下回ればコストを課す、または下限を含めた発注数量を採点する）か、下限がより多くの商品で効くようにして、緩和による利得が startup のペナルティより大きく enterprise のペナルティより小さくなるよう調整します。方針ごとに期待される答え（緩和する / しない）を README に記載します。

ルールシード： 一部対応。緩和の得は、現在は設定によって異なります。下限を外すと、下限6または8では品質が6.5–11.4%上がり、誤差の重み3で下限4なら、分位点の予測が既に下限を上回っているため0.1–0.3%しか上がりません（README）。得がマイナスになることはないため、「決して緩和しない」は依然として本当のトレードオフではありません。引き続き未対応です。

F5 — いくつかのデータの意味の罠がほとんど効いていない（中、一部確認）
