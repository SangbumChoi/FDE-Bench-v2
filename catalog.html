Case catalog

Cases live in cases/<field>/<role>/ and are addressed as <field>/<role> (e.g. finance/loan_underwriting_specialist). Each case is titled by the role the agent plays for the client; fields are listed with their names in all five locales in fields.yaml. Every case is authored natively in zh / en / ko / ja / es and must pass fdebench2 validate-case. Format: DESIGN.md §3.

Status: ✅ built and validated · ⭐ recommended first batch · (blank) planned

Deliverable: Batch = a file the agent produces (plan, decisions, forecast). Program = code the evaluator runs on hidden inputs (e.g. decide(application), answer(question)), isolated from the scorer (see DESIGN.md §3).

Data and answers on disk: every case keeps its generated data and ground truth in dataset/ (agent_view/<lang>/ as the agent receives it, hidden/ for inputs it never sees, gt/<tier>_s<seed>/ per public setting with the reference deliverable and its score). Regenerate with fdebench2 export-dataset; validate-case fails if the stored files drift from the generator.

Detailed, research-grounded specs for every unbuilt role are in docs/specs/.

Each row lists the hidden requirements the simulated client knows (examples, not exhaustive) and the business_policy rule a policy may let the agent bend.

Difficulty: one dataset, tiers and rule seeds

A case with settings keeps one dataset and one request, and varies only what the client wants (hidden requirements) and how the deliverable is scored:

  • Difficulty → content tier (easy / medium / hard): which rules apply and how strictly they are scored. The data does not change; a lower tier's requirements say which parts of it are out of scope this round.
  • Rule seed: draws the hyperparameters of those rules (caps, thresholds, which item a rule targets, scoring weights), each parameter independently from its candidates in case.yaml (params:); a harder tier may have harder candidates. Different draws have different correct solutions: a solution tuned to one is invalid or worse under another. A case's public rule seeds (rule_seeds:) are stored in dataset/ and shown in its explainer; any other int is a private seed, a fresh draw whose answer is published nowhere.
  • Evaluation: every difficulty is run under several rule seeds (the public panel, or private seeds) and reported as their mean, so results have one column per difficulty.
  • Same view: the agent's prompt and files are byte-identical in every setting (validate-case checks this), and campaigns run isolated in docker, so the only way to learn this setting's rules is to ask the client.

How the work is handed over is a separate axis, engagement (configs/engagement.yaml), the same for every difficulty in a comparison:
