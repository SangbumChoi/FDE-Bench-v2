案例说明（README）

BI 数据分析师 — data_knowledge/bi_data_analyst

一家向韩国、日本和美国客户销售订阅盒和单次购买商品的咖啡、茶订阅商店（总部在首尔，所有报表都以韩元计）给智能体发来订单数据库的 CSV 导出、一份简短的数据字典和管理层的十二个问题：“能麻烦您根据数据库导出的数据帮忙回答一下吗？……每个问题给一个数字就行。”交付物是包含所有问题编号的 answers.json（{"Q01": ..., ..., "Q12": ...}），每个值是一个数字或 null。null 表示“不知道”：CEO 的董事会材料中该数字显示为“暂无数据”。需求里没有提到任何决定这些数字的口径，也没有说错误的数字会带来什么代价。两者都在隐藏需求中，模拟客户只有在被问到时才会说明。

这个案例有九套标准答案：3 个层级 × 3 个规则集。智能体在全部九种设置下看到的需求和数据都相同（验证器会检查它的提示词和工作区逐字节一致）。变化的是本轮董事会材料需要哪些问题、客户的口径（财年、活跃时间窗口、取整单位），以及正确答案、“不知道”和错误答案各值多少。模拟客户依据该设置的隐藏需求作答，评估器也按该设置评分。因此这个案例衡量两件事：智能体能否找到口径并答对，以及在应当说“不知道”时是否会这样说（校准弃答，calibrated abstention）。与所有案例一样，交接方式的各项设置（给出完整需求还是先澄清、客户人设、数据噪声、事件）叠加在其上（见 cases/README.md）。

答案与得分

Q01..Q12 每个键都必须存在，值为有限数字或 null。缺少某个键，或者值两者都不是，就违反 answer_format（物理约束）。层级计分的每道题得到一份奖励：

错误不知道（null）正确
A012
B00.52
C01.52

目标值（最大化）是奖励总和除以 2 × 计分题数，取值在 [0, 1] 之间。全部答对的答卷得 1。全部回答“不知道”的答卷得 0.5、0.25 或 0.75。对层级不计分的题目作答或填 null 都没有影响。指标为 scored、answered、right、wrong、dont_know、accuracy_on_answered（right / answered）、coverage（answered / scored）、奖励总和 reward，以及答错的题目和答“不知道”的题目列表。

弃答阈值。 了解计分规则的答卷，只应在答对概率 p 胜过“不知道”时才作答：p × 2 > dont_know_reward，即 A 下 p > 50%，B 下 p > 25%，C 下 p > 75%。客户把这套规则作为业务事实说出来，它也是一个应问事项（answer_rewards，类型 missing）：“错误的数字一旦报到董事会，就得在下次会议上更正，也有损信誉；‘暂无数据’只是留下一个空白”，随后给出三个数值。

除金额容差外，正误判定与没有设置时的案例相同。Q03、Q04、Q05 和 Q10 必须完全一致。金额须在 0.5% 与取整单位一半（500、5,000 或 50 韩元）两者中较宽的范围内，因此按规则集要求取整后的精确值一定算对。Q11 须在 0.05 个百分点以内，Q08 和 Q12 须在 0.5% 以内。以小数而非百分数给出的比例也接受。violating_examples 断言：把精确答案按设置的单位取整后，在每个设置下、在验证器构建的每个世界上，都能无违规地得到 1.0。

参考解与基线数字（公开种子 20261026）

参考解是一位细心的分析师：使用该设置的口径，除了品类更名之外每个口径都处理正确——它只用 pantry 标签回答“食品储藏”那道题。层级不计分的题目它填 null。它的弃答策略有章可循且是确定性的：它的食品储藏数字只覆盖 2025-10 以后上架的商品，所以它认为这个答案对错各半，只有当 ½ × right_reward > dont_know_reward 时才保留。B 下成立（1 > 0.5），所以它作答并答错。在 A（1 = 1，打平则弃答）和 C（1 < 1.5）下它回答“不知道”。在 easy 和 medium 中 Q06 不计分，所以参考解在那里答对每一道计分题。

基线是没有分析师时财务部报出的结果：每道题都是“暂无数据”（null）。它在每道计分题上拿到该规则集的“不知道”奖励（A / B / C 下为 0.5 / 0.25 / 0.75），因此全部回答“不知道”在归一化尺度上得 0。表面值答卷是不采用客户任何口径、直接对导出数据求和的结果：按存储的 UTC 日期划分自然年期间、不论状态计入所有订单、收入 = 订单 total 减去日期落在该期间的退款、所有币种按 2026-09-30 的汇率换算、活跃 = 最近 30 天内下过单、“食品储藏” = pantry 标签。它回答每一道题，遵守客户无论如何都会执行的两条财务规定（排除测试账号、金额按设置单位取整），并在每个设置下都低于基线：它的错误数字一分不得。

评审结果（REVIEW）

评审 — data_knowledge/bi_data_analyst

案例评审的发现，已在公开种子（20261026）和世界种子 1–20 上对照代码重新核对。F1、F3、F8 和 F9 在第一次处理评审意见时（下文的“第一次改动”）已修复。F10 是案例负责人的要求：3 个层级 × 3 个规则集，答案可以是正确、“不知道”或错误，且奖励随规则集不同。它在第二次改动中完成，这次改动也推进了 F2、F4 和 F5。其余各项是留给案例负责人的待定提议。

F1 — 取整规则使 Q07 和 Q09 无法答对（高，部分确认）

金额答案必须是整千韩元，但评分时却要求在未取整数字的 0.5% 以内。对每单平均值来说这行不通：Q07 = 41,618 取整为 42,000（+0.92%），Q09 = 35,780 取整为 36,000（+0.62%）。因此遵守规则的答卷最多只能得 10/12，而保存的参考解得 9。取整后的精确答案在种子 1–20 中只有 35%（Q07）和 45%（Q09）能通过。放宽 report_rounding 反而能提高得分：使用 UTC 日期的答卷取整时得 7/12，不取整时得 9/12。

状态： 已在第一次改动中修复。现在金额答案与精确值的偏差只要在 0.5% 与 500 韩元两者中较宽的范围内即算对，因此精确值取整到千位后一定算对。五种语言区域中的“评判方式”一节和 report_rounding 事项都写明了这一点。violating_examples 现在断言：按财务要求取整的精确答案，在验证器构建的每个世界上都能无违规地得到 12/12；在种子 1–20 上确实如此。参考解从 9 升到 11（Q07 和 Q09 现在算对），遵守规则也不再丢题：使用 UTC 日期的答卷无论取整与否都得 9/12。核查人的异议仍然成立：没有加入“放宽从不带来好处”的通用检查，因为其他案例中可放宽的规则本来就设计成会牺牲目标值。第二次改动：取整单位现在是规则集参数（1,000 / 10,000 / 100 韩元），金额容差为 0.5% 或单位的一半，同样的断言（目标值 1.0、无违规）在全部九种设置下运行。

F2 — 参考解与上限之间没有余地（高，已确认）

参考解是漏掉了品类更名的 compute()。在旧的截断尺度下它得 9，任何答对 9 道及以上的答卷都拿满质量分。经过 F1 的修复和新尺度，问题反了过来：参考解得 11，基线得 0，所以完美答卷的归一化质量是 12/11 = 1.09。在政策上限 1.5 下，完美答卷只能拿到质量分的 73%，而更名（Q06）是把它和参考解区分开的唯一事实。

状态： 待定，并因第二次改动（F10）而有所变化。参考解仍然只漏掉更名，而 Q06 只在 hard 中计分。所以在 easy 和 medium 中，参考解答对每一道计分题，它本身*就是*上限：在这六种设置下，完美答卷的归一化质量都是 1.000。在政策上限 1.5 下，那里最好的答卷能拿到质量分的 67%。在 hard 中，完美答卷在公开种子下得 1.091（A）、1.125（B）和 1.091（C）：参考解在 A 和 C 下把 Q06 留作“不知道”，在 B 下答错。它的目标值在检查过的每个种子（1–20）上都是 0.958 / 0.917 / 0.979，基线对归一化数字的影响很小。先前的提议（quality_cap: 1.09）已不再合适。整个案例只有一个上限，无法让完美答卷在全部九种设置下都得满分：上限设为 1.0，会让达到参考解水平的答卷在 hard 中也得满分；上限高于 1.0，又会让 easy 和 medium 拿不满。所以第二次改动没有设置 quality_cap。提议：(a) 在框架中支持按层级设置 quality_cap（easy 和 medium 为 1.0，hard 为 1.10）；(b) 在每个层级给参考解留一个刻意的缺口，例如在 easy 和 medium 中各设一道参考解无法确定的题，让它在那里也弃答；(c) 按每道题所考查的、真正起作用的应问事项数量给题目加权，使每个隐藏事实的代价大致相同。
