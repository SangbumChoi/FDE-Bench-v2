# BI 数据分析师 — `data_knowledge/bi_data_analyst`

一家向韩国、日本和美国客户销售订阅盒和单次购买商品的咖啡、茶订阅商店（总部在首尔，所有报表都以韩元计）给智能体发来订单数据库的 CSV 导出、一份简短的数据字典和管理层的十二个问题：“能麻烦您根据数据库导出的数据帮忙回答一下吗？……每个问题给一个数字就行。”交付物是包含所有问题编号的 `answers.json`（`{"Q01": ..., ..., "Q12": ...}`），每个值是一个数字或 `null`。`null` 表示“不知道”：CEO 的董事会材料中该数字显示为“暂无数据”。需求里没有提到任何决定这些数字的口径，也没有说错误的数字会带来什么代价。两者都在隐藏需求中，模拟客户只有在被问到时才会说明。

这个案例有九套标准答案：3 个层级 × 3 个规则集。**智能体在全部九种设置下看到的需求和数据都相同**（验证器会检查它的提示词和工作区逐字节一致）。变化的是本轮董事会材料需要哪些问题、客户的口径（财年、活跃时间窗口、取整单位），以及正确答案、“不知道”和错误答案各值多少。模拟客户依据该设置的隐藏需求作答，评估器也按该设置评分。因此这个案例衡量两件事：智能体能否找到口径并答对，以及在应当说“不知道”时是否会这样说（校准弃答，calibrated abstention）。与所有案例一样，交接方式的各项调节（给出完整需求还是先澄清、客户人设、数据噪声、事件）叠加在其上（见 [cases/README.md](../../README.md)）。

## 答案与得分

Q01..Q12 每个键都必须存在，值为有限数字或 `null`。缺少某个键，或者值两者都不是，就违反 `answer_format`（物理约束）。层级计分的每道题得到一份奖励：

| | 错误 | 不知道（`null`） | 正确 |
|---|---|---|---|
| A | 0 | 1 | 2 |
| B | 0 | 0.5 | 2 |
| C | 0 | 1.5 | 2 |

目标值（最大化）是奖励总和除以 2 × 计分题数，取值在 [0, 1] 之间。全部答对的答卷得 1。全部回答“不知道”的答卷得 0.5、0.25 或 0.75。对层级不计分的题目作答或填 `null` 都没有影响。指标为 `scored`、`answered`、`right`、`wrong`、`dont_know`、`accuracy_on_answered`（right / answered）、`coverage`（answered / scored）、奖励总和 `reward`，以及答错的题目和答“不知道”的题目列表。

**弃答阈值。** 了解计分规则的答卷，只应在答对概率 p 胜过“不知道”时才作答：p × 2 > dont_know_reward，即 A 下 p > 50%，B 下 p > 25%，C 下 p > 75%。客户把这套规则作为业务事实说出来，它也是一个应问事项（`answer_rewards`，类型 missing）：“错误的数字一旦报到董事会，就得在下次会议上更正，也有损信誉；‘暂无数据’只是留下一个空白”，随后给出三个数值。

除金额容差外，正误判定与没有设置时的案例相同。Q03、Q04、Q05 和 Q10 必须完全一致。金额须在 0.5% 与取整单位一半（500、5,000 或 50 韩元）两者中较宽的范围内，因此按规则集要求取整后的精确值一定算对。Q11 须在 0.05 个百分点以内，Q08 和 Q12 须在 0.5% 以内。以小数而非百分数给出的比例也接受。`violating_examples` 断言：把精确答案按设置的单位取整后，在每个设置下、在验证器构建的每个世界上，都能无违规地得到 1.0。

## 规则集：客户的口径以及答案的价值

| 参数 | A | B | C |
|---|---|---|---|
| `fy_start`：财年从该月 1 日开始，以开始那一年命名 | 4 月 | 7 月 | 1 月 |
| `fy2025` / `fy2026_q1` / `fy2026_h1`：由此得出的期间（按文本中的写法） | 2025-04-01–2026-03-31 / 2026-04-01–06-30 / 2026-04-01–09-30 | 2025-07-01–2026-06-30 / 2026-07-01–09-30 / 2026-07-01–12-31，统计到 09-30 | 2025-01-01–12-31 / 2026-01-01–03-31 / 2026-01-01–06-30 |
| `active_days` / `active_from`：活跃 = 最近 N 天内有一笔有效订单 | 90，从 2026-07-03 起 | 60，从 2026-08-02 起 | 30，从 2026-09-01 起 |
| `rounding_unit`：金额报告时四舍五入到的单位 | 1,000 韩元 | 10,000 韩元 | 100 韩元 |
| `wrong_reward` / `dont_know_reward` / `right_reward` | 0 / 1 / 2 | 0 / 0.5 / 2 | 0 / 1.5 / 2 |
| 仅当 P(答对) 高于此值时作答 | 50% | 25% | 75% |

`case.py` 从 `fy_start` 和 `active_days` 推导出所有期间，并在 import 时检查文本所引用的 case.yaml 中的期间字符串与它实际计分所用的期间一致。每个规则集的参考解在同一层级的另外两个规则集下都无效或差得多（18 对中 18 对）：取整到 1,000 或 100 韩元的参考解违反 B 的 10,000 韩元规则，100 韩元的答卷还违反 A 的规则，而有效的交叉组合相对另一参考解只得 0.00–0.40。在每一对中，财年不同会改变 Q01、Q02、Q08 和 Q10，时间窗口不同会改变 Q03；此外，Q04 在 B 与其他两者之间变化，Q12 在 C 与其他两者之间变化，而用较细的单位给较粗单位的答案计分会让 Q07 或 Q09 出错（B 的 40,000 韩元数字在 A 和 C 下，A 的 Q09 在 C 下）。

## 规则

| 规则 | 类别 | 违反条件 |
|---|---|---|
| `answer_format` | 物理约束 | 缺少某个问题编号，或某个值既不是有限数字也不是 `null`（无论是否计分，十二道题都检查） |
| `exclude_test_accounts` | 合同约束 | 某个计分的计数或客户编号答案（Q03、Q04、Q05、Q10）等于包含测试账号时的数字（按韩国时间日期和该设置的期间），且该数字与排除测试账号时的数字不同 |
| `report_rounding` | 业务惯例（可放宽） | 某个计分的金额答案（Q01、Q02、Q06、Q07、Q09）不是该设置单位（1,000 / 10,000 / 100 韩元）的整数倍 |

## 包含的情境

- **隐藏事实：** 上面的十一个应问事项。数据的构造使每一项都会显现出来。测试账号 10027 上的 QA 压力测试（36 笔订单，每笔十台手摇磨豆机和五袋 1 kg 拼配豆，2025 年 4 月至 2026 年 3 月）使得在保留测试账号时，无论按哪种财年它都是净收入最高的客户。五笔测试订单落在 2026-07-01 大促开始后的头几分钟（韩国时间），按 UTC 仍是 2026-06-30。已付款的取消订单有付款记录。四个食品储藏商品以新标签上架，而四个较早的商品仍标为零食。9 月订单在 10 月发生的退款会让 Q11 变动约 3 个点（种子 1–3 下为 2–4）。
- **校准弃答：** 计分规则本身也是隐藏事实。没有找到某个口径、或者无法确定某个数字的智能体，应当把自己答对的概率与该规则集的阈值相比较。全部回答“不知道”得 0.25–0.75，这就是基线（质量 0）；全部按表面数字作答在公开种子下得 0–0.4，比基线更低。
- **带日期的事件、施压：** 案例本身没有（见 REVIEW.md F6）。messy 交接方式会加入框架的通用事件。

## 参考解与基线数字（公开种子 20261026）

**参考解**是一位细心的分析师：使用该设置的口径，除了品类更名之外每个口径都处理正确——它只用 `pantry` 标签回答“食品储藏”那道题。层级不计分的题目它填 `null`。它的弃答策略有章可循且是确定性的：它的食品储藏数字只覆盖 2025-10 以后上架的商品，所以它认为这个答案对错各半，只有当 ½ × right_reward > dont_know_reward 时才保留。B 下成立（1 > 0.5），所以它作答并答错。在 A（1 = 1，打平则弃答）和 C（1 < 1.5）下它回答“不知道”。在 easy 和 medium 中 Q06 不计分，所以参考解在那里答对每一道计分题。

**基线**是没有分析师时财务部报出的结果：每道题都是“暂无数据”（`null`）。它在每道计分题上拿到该规则集的“不知道”奖励（A / B / C 下为 0.5 / 0.25 / 0.75），因此全部回答“不知道”在归一化尺度上得 0。**表面值答卷**是不采用客户任何口径、直接对导出数据求和的结果：按存储的 UTC 日期划分自然年期间、不论状态计入所有订单、收入 = 订单 `total` 减去日期落在该期间的退款、所有币种按 2026-09-30 的汇率换算、活跃 = 最近 30 天内下过单、“食品储藏” = `pantry` 标签。它回答每一道题，遵守客户无论如何都会执行的两条财务规定（排除测试账号、金额按设置单位取整），并在每个设置下都低于基线：它的错误数字一分不得。

## 备注

- 数据是合成的。价格、税率、汇率走势、下单节奏和退款率都是虚构的；商店、客户和账号也都是虚构的。财年、本地日期、测试账号、净收入和更名这些口径，是在原始导出数据上做 BI 工作时常见的陷阱，而不是关于某家真实公司的事实。三套奖励方案是为了把弃答阈值设在 25%、50% 和 75% 而做的设计选择，并非实测的成本。
- 已知的简化（REVIEW.md F7）：所有美国订单统一按 7% 计税、周末也有汇率、已付款的取消订单没有冲正记录，以及注册记录从 2024-07-01 开始而订单历史从 2025-01-01 才开始。QA 测试账号 10027 在 2025 年 12 月才注册，却从 2025 年 4 月起就有压力测试订单。
- `validate-case` 检查每个设置：五种语言版本下的确定性数据、全部九种设置下智能体看到的内容相同、质量为 1.0 的参考解、比参考解差的有效基线、每条规则一个只违反该规则的交付物，以及各规则集之间互不相同的参考解。它会警告 A 和 C 下 medium 与 hard 的参考解逐字节相同：两者都把 Q06 填为 `null`，因为在 medium 中不需要，在 hard 中是“不知道”。它们的得分不同（1.0 对 0.958 和 0.979），所以层级仍然提供了区分度。
