### F1 — 端数処理のルールのせいで Q07 と Q09 に正解できなかった（高、一部確認）

**状況：** 一回目の変更で修正済み。金額の回答は、正確な値との差が 0.5% と 500 ウォンのうち広いほうの範囲内なら正解となったので、正確な値を千ウォン単位に丸めた回答は必ず正解になります。五つのロケールすべてで、「評価方法」の節と `report_rounding` の事項がその旨を述べています。`violating_examples` は、経理の求めどおりに丸めた正確な回答が、検証器の作るすべてのワールドで違反なしに 12/12 になることを確かめるようになり、シード 1–20 で実際にそうなります。参照解は 9 から 11 に上がり（Q07 と Q09 が正解に）、ルールに従っても質問を失わなくなりました。UTC の日付を使った回答シートは、丸めても丸めなくても 9/12 です。検証者の異議は引き続き有効です。ほかのケースの緩和可能なルールは目的値を犠牲にするよう設計されているため、「緩和しても得にならない」という一般的なチェックは追加していません。二回目の変更：端数処理の単位はルールセットのパラメータ（1,000 / 10,000 / 100 ウォン）になり、金額の許容誤差は 0.5% または単位の半分で、同じ確認（目的値 1.0、違反なし）を9つの設定すべてで実行します。ルールシード：単位は抽選されるパラメータ（候補 100 / 1,000 / 10,000 ウォン）になり、同じ確認を、すべての公開設定で、検証器が作るすべてのワールドに対して実行します（シード 1–20 で確認）。

### F10 — 回答で「わからない」と言えず、ケースの正解が一つだけだった（ケースオーナーの要望、対応済み）

ケースオーナーは、回答が正しい・「わからない」・誤りのいずれにもなりえ、報酬がルールセットごとに異なることを求めました。そのうえでベンチマークは、エージェントが「わからない」と言うべきときにそう言えるか（較正された回答保留）、そして答えるときには正しく答えられるかを測るべきだとしました。ケースには設定もありませんでした（F5）。

**状況：** 二回目の変更で対応済み。データ、依頼、質問一覧は変わっておらず、9つの設定すべてでバイト単位で同一です。ルールセット A での公開シードの数値は、設定のなかった頃のケースの数値と同じです。三回目の変更：固定された三つのルールセットは、今ではルールシードが抽選する候補です（「ルールシード」の節）。報酬の仕組み、ティアごとの質問の組、すべて `null` のベースライン、参照解の回答保留の方針は変わっていません。

- **回答。** `answers.json` は Q01..Q12 のすべての番号を数値または `null`（「わからない」）に対応づけます。キーが欠けている、または値が有限の数値でも `null` でもない場合は、採点の有無にかかわらず、どの質問でも `answer_format` に違反します。成果物の仕様、ルールの文言、五つのロケールの要件がそう述べています。抽出器には、エンジニアが数値を出さなかったところに `null` を書くよう指示しています。
- **得点。** 採点される質問ごとに、正しければ 2、`null` なら `dont_know_reward`、誤りなら 0 を得ます。目的値は合計 /（2 × 採点対象の質問数）で、[0, 1] の範囲です。指標：`scored`、`answered`、`right`、`wrong`、`dont_know`、`accuracy_on_answered`、`coverage`、`reward`、そして誤った質問と「わからない」とした質問の一覧。採点しない質問への回答や `null` は何の影響もありません。端数処理とテストアカウントのチェックは、採点される質問だけを確認します。
- **ルールセット。** A = (0, 1, 2)、B = (0, 0.5, 2)、C = (0, 1.5, 2) なので、報酬の仕組みを知っているエージェントは P(正解) が 50%、25%、75% を上回るときだけ答えます。ほかのパラメータは正解を変えます：会計年度の開始 4月 / 7月 / 1月、アクティブ期間 90 / 60 / 30日、端数処理の単位 1,000 / 10,000 / 100 ウォン。顧客はこの仕組みを業務の言葉で述べます：取締役会資料の誤った数値は次の会議で訂正しなければならず信用を損なうが、「集計中」は空欄が一つ残るだけだ、と。そのあとに三つの値が続きます。これは確認すべき事項です（`answer_rewards`、種類 missing）。
- **データの範囲を超える期間。** 7月始まりの会計年度では、FY2026 上半期は 2026年7月〜12月で、基準日を越えます。要件はどのルールセットでも、基準日にまだ終わっていない期間は基準日までで集計すると述べているので、B の上半期は 2026年7月〜9月です。生成器の日付範囲を変える必要はありませんでした。2025-01-01 からの注文が、三つの開始月すべてで FY2025 をカバーします。
- **ティア。** easy は Q01、Q03、Q04、Q10、Q12、medium は + Q02、Q05、Q07、Q08、Q09、Q11、hard は + Q06。顧客の要件は、今回の取締役会資料にどの質問が必要かを、顧客自身の言葉で述べています。Q01 には両方が必要なので easy も純売上と為替レートから自由ではなく、B では韓国時間が Q01 を左右します。10月の返金は medium から効いてきます。どの事実がそれぞれの設定でどの質問を失わせるかは、README.md の表にあります。
- **参照解。** 設定の慣行を適用した現行のロジックです。名称変更を見落とし、採点しない質問は `null` のままにします。Q06 では、pantry ラベルによる数値が正しい確率を五分五分とみなし、½ × 2 > `dont_know_reward` のときだけその回答を残します。そのため B では（誤って）答え、A（同点）と C では「わからない」と答えます。**ベースライン：** すべて `null` の回答シート（どこでも「集計中」）なので、回答保留だけなら 0 になります。額面どおりの回答シートは、どの設定でもそれを下回ります。
- **数値。** README.md を参照：参照解は easy と medium で 1.000、hard で 0.958 / 0.917 / 0.979。完璧な回答シートの正規化品質は easy と medium で 1.000、hard で 1.091 / 1.125 / 1.091 です。設定ごとに異なるため、`quality_cap` は設定していません（F2）。
- **検証器。** 実行すると、A と C では medium と hard の参照解がバイト単位で同一だという警告が出ます。どちらも Q06 を `null` にしています（medium では不要、hard では「わからない」）。得点は 1.000 に対して 0.958 と 0.979 なので、ティアは引き続き識別力を加えています。
- **未対応。** `validate-case` は、あとから追加する翻訳（`locales/<lang>/explainer.yaml`、`README.<lang>.md`、`REVIEW.<lang>.md`）がないために止まります。それ以外のチェックは、そのチェック一つだけを外して、ワールドシード 1–3（ワールドシードのチェックはシード 1–20）で実行し、通っています。
- **再確認。** 二回目のレビューで、手作りの回答シート（すべて正解、すべて `null`、`null` が一つと誤りが一つ、採点しない質問へのあらゆる種類の回答）による報酬、形式のルール（キーの欠落、文字列、真偽値、リスト、NaN、Infinity）、Q06 での回答保留のトレードオフ、ルールセット間の交差得点、README の表（目的値、一つの事実を誤った場合の表、hard ティアの回答）、シード 1–20 の範囲を計算し直し、すべて再現しました。修正したもの：float に収まらないほど大きな JSON 整数（例：400桁）が、`answer_format` 違反になる代わりに採点で例外を起こしていました。別のルールセットで動く質問を挙げた README の一覧が不完全でした（Q04、Q07、Q09）。スペイン語のテキストが「FY2025 = del …」となっていました。「B では回答保留のほうが誤った回答より得点が低い」というチェックは、文言どおりには成り立ちえません。どの仕組みでも `null` は誤った回答より多くを得るからです。成り立つのは、参照解の五分五分の確率での期待値です：B では答えるほうが保留より得で（1問あたり 1 対 0.5）、A では同じ、C では損です。

### ルールシード — ルールセット A / B / C がパラメータの候補になる（ケースオーナーの要望、対応済み）

ケースオーナーは、固定されたルールセットをルールシードに置き換えました。ケースは隠れたルールごとに候補値を宣言し、ルールシードはそれぞれを独立に抽選し、レポートはティアのルールシードの平均を出します。データ、依頼、質問一覧、エージェントの見え方は変わっておらず、どの設定でもバイト単位で同一です。

- **パラメータ。** case.yaml の `params:` には、どのティアでも同じ四つの候補があります：`fy_start` 1月 / 4月 / 7月、`active_days` 30 / 60 / 90、`rounding_unit` 100 / 1,000 / 10,000 ウォン（オーナーは報告の単位を、シードで抽選される隠れたルールにしたいと考えています）、`dont_know_reward` 0.5 / 1 / 1.5。これらは以前の A / B / C の値で、今では自由に組み合わされ、ティアごとに三つではなく81通りの組み合わせになります。`right_reward` 2 と `wrong_reward` 0 は固定で、テキストが引用する期間の文字列（`fy2025`、`fy2026_q1`、`fy2026_h1`、ロケールごとの言い回し）および `active_from` とともに `derive_params` から得られます。case.yaml には期間がもう書かれていないため、それがコードと一致するかを import 時に確かめるチェックはなくなりました。今はコードが期間を書きます。`admissible` は以前の安全策（報酬が誤り・わからない・正しいの順に大きくなる、基準日までに FY2026 が始まっている）に、期間がデータの範囲内にあることを加えたもので、現在の組み合わせはすべて通ります。
- **公開ルールシード。** `rule_seeds: [4, 12, 23]` は、すべての候補のすべての値が一度ずつ現れる最初の三つのシードです：s4 = 1月、60日、100 ウォン、1。s12 = 7月、30日、10,000 ウォン、0.5。s23 = 4月、90日、1,000 ウォン、1.5。設定は `easy/s4` … `hard/s23` で、`dataset/gt/<tier>_s<seed>/` に保存され、抽選された値と算出された値は `setting.json` にあります。s23 は、`null` の価値が 1 ではなく 1.5 のルールセット A です。以前の B と C は、そのままの形では公開ルールシードにありません（B はシード 21 で、C は 400 未満のどのシードにもありません）。
- **テキスト。** プレースホルダーは以前と同じで、期間についての以前のルールセットごとのラベルは、今では算出された値です。五つのロケールすべてに `<!-- when: -->` の箇所が三つあります。7月始まりの年度では、会計年度の注記に、FY2026 上半期は 2026-07-01 から基準日までしか経過しておらず第1四半期と同じ月だという一文が加わります。`null` の価値が 0.5 のとき、顧客は取締役会が空欄よりも数値を見たいと付け加え、1.5 のときは、前回までの2回の資料で訂正があったため誤った数値よりも空欄のほうがずっと良いと付け加えます。medium ティアのテキスト（と説明ページにあるその四つの翻訳）は、「ルールセット B では」ではなく「会計年度が7月始まりのときは Q02」と述べます。パラメータに対応する四つの事項（`fiscal_year`、`active_customer`、`report_rounding`、`answer_rewards`）が抽選された値を持ち、残りの七つの事項はどの値が抽選されても同じです。
- **コード。** `RULESETS` と `_check_rulesets` はなくなり、`derive_params` と `admissible` がそれに代わります。採点、参照解（名称変更を見落とし、Q06 には ½ × 2 > `null` の報酬のとき、つまり 0.5 のときだけ答える）、すべて `null` のベースライン、額面どおりの回答シート、違反例は変わっておらず、設定のパラメータを読み取ります。
- **数値。** 参照解は easy と medium で 1.000、hard で 0.958（s4）/ 0.917（s12）/ 0.979（s23）。ベースラインは 0.500 / 0.250 / 0.750。検証器の、パラメータが効くかの確認は `hard/s4` から四つのパラメータすべてで通ります。s4 と s23 では medium と hard の参照解がバイト単位で同一だという警告が出ます（どちらも Q06 が `null`）。README.md の一つの事実を誤った場合の表、hard ティアの回答、ワールドシードの範囲は、新しい公開ルールシードに合わせて計算し直しました。
- **未対応。** (a) 一部の非公開の抽選（1月始まりの年度、`null` の価値 0.5 または 1）では、額面どおりの回答シートがすべて `null` のベースラインを上回ります（上のベースラインについての注記を参照）。そのときは素朴な暦年の読み方が正しいので現実的ですが、そうした抽選では、何の工夫もない回答シートが最大 0.47 の正の品質を得ます。オーナーがこの回答シートをどこでも品質 0 にしたいなら、ベースラインを設定ごとに二つの回答シートのうち良いほうにすることができます。(b) hard 向けのより難しい候補は追加していません。候補はどのティアでも以前の値です。9月または10月始まりの年度（FY2026 の第1四半期が基準日を越えて続く）は、hard 専用の候補として自然でしょう。(c) README.<lang>.md と REVIEW.<lang>.md はまだルールセット A / B / C を説明しており、あとで翻訳し直します。
