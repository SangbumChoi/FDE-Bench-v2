# BI データアナリスト — `data_knowledge/bi_data_analyst`

韓国・日本・米国のお客様に定期便ボックスと単品商品を販売するコーヒーとお茶の定期便ショップ（本社はソウル、レポートはすべてウォン建て）が、注文データベースの CSV エクスポート、簡単なデータ辞書、経営陣からの12の質問をエージェントに送ります。「データベースのエクスポートから回答していただけますでしょうか。…質問ごとに数値をひとつずつお返しください。」成果物はすべての質問番号を含む `answers.json`（`{"Q01": ..., ..., "Q12": ...}`）で、それぞれの値は数値または `null` です。`null` は「わからない」を意味し、CEO の取締役会資料ではその数値が「集計中」と表示されます。依頼には数値を決める定義がひとつも書かれておらず、誤った数値がどれほどの損失になるかも書かれていません。どちらも隠れた要件に含まれており、シミュレーションの顧客は質問されたときにだけ答えます。

このケースには9通りの正解があります：ティア3つ × ルールセット3つ。**エージェントは9つの設定すべてで同じ依頼と同じデータを見ます**（検証器は、プロンプトと作業領域がバイト単位で同一であることを確認します）。変わるのは、今回の取締役会資料にどの質問が必要か、顧客の慣行（会計年度、アクティブ期間、端数処理の単位）、そして正しい回答・「わからない」・誤った回答それぞれの価値です。シミュレーションの顧客はその設定の隠れた要件に基づいて答え、評価器はその設定で採点します。したがって、このケースは二つのことを測ります。エージェントが定義を見つけて正しく答えられるか、そして「わからない」と言うべきときにそう言えるか（較正された回答保留、calibrated abstention）です。進め方の調整項目（仕様をすべて渡すか先に質問させるか、顧客のペルソナ、データのノイズ、イベント）は、ほかのすべてのケースと同様にその上に適用されます（[cases/README.md](../../README.md) を参照）。

## 回答と得点

Q01..Q12 のすべてのキーが必要で、値は有限の数値または `null` です。キーが欠けていたり、値がそのどちらでもなかったりすると、`answer_format`（物理的）に違反します。ティアが採点する質問ごとに報酬が得られます：

| | 誤り | わからない（`null`） | 正しい |
|---|---|---|---|
| A | 0 | 1 | 2 |
| B | 0 | 0.5 | 2 |
| C | 0 | 1.5 | 2 |

目的値（最大化）は報酬の合計を 2 × 採点対象の質問数で割った値で、[0, 1] の範囲の数です。すべて正しい回答シートは 1 になります。すべての質問に「わからない」と答えた回答シートは 0.5、0.25 または 0.75 です。ティアが採点しない質問への回答や `null` は何の影響もありません。指標は `scored`、`answered`、`right`、`wrong`、`dont_know`、`accuracy_on_answered`（right / answered）、`coverage`（answered / scored）、報酬の合計 `reward`、そして誤った質問と「わからない」とした質問の一覧です。

**回答保留のしきい値。** 報酬の仕組みを知っている回答シートなら、正解の確率 p が「わからない」を上回るときだけ質問に答えるべきです：p × 2 > dont_know_reward、つまり A では p > 50%、B では p > 25%、C では p > 75% です。顧客はこの仕組みを業務上の事実として述べ、これは確認すべき事項です（`answer_rewards`、種類 missing）。「誤った数値が取締役会に出ると次の会議で訂正が必要になり、信用も損ないますが、『集計中』は空欄がひとつ残るだけです」と述べたあと、三つの値が続きます。

正誤の判定は、金額の許容誤差を除けば設定のなかった頃のケースと同じです。Q03、Q04、Q05、Q10 は完全に一致しなければなりません。金額は 0.5% と端数処理単位の半分（500、5,000 または 50 ウォン）のうち広いほうの範囲内でなければならないため、正確な値をルールセットの求めるとおりに丸めた回答は必ず正解になります。Q11 は 0.05 ポイント以内、Q08 と Q12 は 0.5% 以内でなければなりません。割合をパーセントではなく小数で答えたものも受け付けます。`violating_examples` は、正確な回答を設定の単位に丸めると、すべての設定、そして検証器が作るすべてのワールドで、違反なしに 1.0 になることを確かめています。

## ルールセット：顧客の慣行と回答の価値

| パラメータ | A | B | C |
|---|---|---|---|
| `fy_start`：会計年度はこの月の1日に始まり、始まる年で呼ぶ | 4月 | 7月 | 1月 |
| `fy2025` / `fy2026_q1` / `fy2026_h1`：そこから決まる期間（テキストの記載どおり） | 2025-04-01–2026-03-31 / 2026-04-01–06-30 / 2026-04-01–09-30 | 2025-07-01–2026-06-30 / 2026-07-01–09-30 / 2026-07-01–12-31、09-30 まで集計 | 2025-01-01–12-31 / 2026-01-01–03-31 / 2026-01-01–06-30 |
| `active_days` / `active_from`：アクティブ = 直近 N 日間に集計対象の注文がある | 90、2026-07-03 から | 60、2026-08-02 から | 30、2026-09-01 から |
| `rounding_unit`：金額はこの単位に四捨五入して報告 | 1,000 ウォン | 10,000 ウォン | 100 ウォン |
| `wrong_reward` / `dont_know_reward` / `right_reward` | 0 / 1 / 2 | 0 / 0.5 / 2 | 0 / 1.5 / 2 |
| P(正解) がこれを上回るときだけ答える | 50% | 25% | 75% |

`case.py` はすべての期間を `fy_start` と `active_days` から導き、テキストが引用する case.yaml の期間文字列が実際に採点に使う期間と同じであることを import 時に確認します。各ルールセットの参照解は、同じティアのほかの二つのルールセットのもとでは無効になるか、はるかに悪い得点になります（18組中18組）。1,000 または 100 ウォン単位に丸めた参照解は B の 10,000 ウォンのルールに違反し、100 ウォン単位の回答シートは A のルールにも違反します。有効な組み合わせは、相手の参照解に対して 0.00–0.40 にとどまります。どの組でも、会計年度が違えば Q01、Q02、Q08、Q10 が、アクティブ期間が違えば Q03 が動きます。さらに Q04 は B とそれ以外の間で、Q12 は C とそれ以外の間で動き、粗い単位の回答を細かい単位で採点すると Q07 か Q09 を外します（A と C での B の 40,000 ウォンの数値、C での A の Q09）。

## ルール

| ルール | 区分 | 違反となる条件 |
|---|---|---|
| `answer_format` | 物理的 | 質問番号が欠けている、または値が有限の数値でも `null` でもない（採点の有無にかかわらず12問すべてを確認） |
| `exclude_test_accounts` | 契約上 | 採点される件数や顧客 ID の回答（Q03、Q04、Q05、Q10）が、テストアカウントを含めた数値（韓国時間の日付、設定の期間による）と一致し、かつその数値がテストアカウントを除いた数値と異なる |
| `report_rounding` | 業務慣行（緩和可能） | 採点される金額の回答（Q01、Q02、Q06、Q07、Q09）が設定の単位（1,000 / 10,000 / 100 ウォン）の整数倍でない |

## 含まれる状況

- **隠れた事実：** 上の11件の確認すべき事項。データはそれぞれの事実が表に出るように作られています。テストアカウント 10027 の QA 負荷テスト（ハンドグラインダー10台と1kgブレンド5袋の注文36件、2025年4月〜2026年3月）により、テストアカウントを含めると、どの会計年度でもこのアカウントがトップの顧客になります。テスト注文5件が 2026-07-01 のセール開始直後の数分（韓国時間）に入りますが、UTC ではまだ 2026-06-30 です。決済済みのキャンセル注文には決済行があります。パントリー商品のうち4つは新しいラベルで発売され、古い4つはまだスナックのままです。9月の注文に対する10月の返金は Q11 を約3ポイント（シード 1–3 では 2–4）動かします。
- **較正された回答保留：** 報酬の仕組みも隠れた事実です。定義を見つけられなかった、あるいは数値を確定できないエージェントは、正解の確率をルールセットのしきい値と比べるべきです。すべてに「わからない」と答えると 0.25–0.75 になり、これがベースライン（品質 0）です。すべてに額面どおり答えると公開シードで 0–0.4 となり、それを下回ります。
- **日付の決まったイベント、圧力：** ケース自体にはありません（REVIEW.md F6 を参照）。messy の進め方では、フレームワーク共通のイベントが加わります。

## 参照解とベースラインの数値（公開シード 20261026）

**参照解**は、設定の慣行に従い、カテゴリ名の変更を除くすべての定義を正しく扱う、注意深いアナリストです。「パントリー」の質問には `pantry` ラベルだけで答えます。ティアが採点しない質問は `null` のままにします。回答保留の方針は筋が通っていて決定的です。パントリーの数値は 2025-10 以降に発売された商品しか含まないため、その回答が正しい確率を五分五分とみなし、½ × right_reward > dont_know_reward のときだけ回答を残します。B ではこれが成り立つので（1 > 0.5）答えて誤ります。A（1 = 1、同点なら保留）と C（1 < 1.5）では「わからない」と答えます。easy と medium では Q06 を採点しないので、そこでは参照解は採点されるすべての質問に正解します。

**ベースライン**は、アナリストなしで経理チームが報告するもの、つまりすべての質問について「集計中」（`null`）です。採点されるすべての質問でルールセットの「わからない」の報酬を得るので（A / B / C で 0.5 / 0.25 / 0.75）、すべてに「わからない」と答えると正規化した尺度では 0 になります。**額面どおりの回答シート**は、顧客の定義をひとつも使わずにエクスポートをそのまま集計したものです：保存された UTC の日付による暦年の期間、ステータスにかかわらずすべての注文、売上 = 注文の `total` からその期間の日付の返金を差し引いたもの、すべての通貨を 2026-09-30 のレートで換算、アクティブ = 直近30日間に注文あり、「パントリー」= `pantry` ラベル。この回答シートはすべての質問に答え、顧客がいずれにせよ適用する二つの経理の方針（テストアカウントの除外、設定の単位での金額の丸め）は守り、どの設定でもベースラインを下回ります。誤った数値は何も得られないからです。

## 補足

- 合成データです。価格、税率、為替レートの推移、注文のリズム、返金率は作りものであり、ショップもその顧客もアカウントも架空のものです。会計年度、現地の日付、テストアカウント、純売上、名称変更に関する慣行は、生のエクスポートを扱う BI 業務でよくある落とし穴であって、実在の会社についての事実ではありません。三つの報酬の仕組みは、回答保留のしきい値を 25%、50%、75% に置くための設計上の選択であり、実測したコストではありません。
- 既知の単純化（REVIEW.md F7）：すべての注文に一律7%の米国の税、週末にもある為替レート、取消行のない決済済みのキャンセル注文、そして注文履歴は 2025-01-01 からなのに 2024-07-01 からある会員登録。QA 用のテストアカウント 10027 は2025年12月に登録したにもかかわらず、2025年4月から負荷テストの注文があります。
- `validate-case` はすべての設定を確認します：五つのロケールでの決定的なデータ、9つの設定すべてで同じエージェントの見え方、品質 1.0 の参照解、参照解より悪い有効なベースライン、ルールごとにそのルールだけに違反する成果物ひとつ、ルールセット間で互いに異なる参照解。A と C では medium と hard の参照解がバイト単位で同一だという警告が出ます。どちらも Q06 を `null` にしているためで、medium では不要だから、hard では「わからない」だからです。得点は異なる（1.0 に対して 0.958 と 0.979）ので、ティアは引き続き識別力を加えています。
