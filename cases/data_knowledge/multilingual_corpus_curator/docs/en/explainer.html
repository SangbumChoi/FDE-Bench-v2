At a glance

What the AI has to do

Write a Python program that the client runs once, offline, on its full shared drive: about 100 books in Chinese, English, Korean, Japanese and Spanish, with the same mix of files as the sample but other books. It builds a clean library (one UTF-8 text file per book holding only its description, at a path made of its year, title and author) and a manifest of what went where, and sets aside every book it cannot file, with a reason code, for the client's team.

What the AI is given

  • The client's request: the material of about 100 books is scattered over files from the regional offices, the scanning team and the rights desk; they want a program for the full drive that files one description file per book the way their catalogue team wants, writes a manifest, and sets aside anything it cannot file instead of guessing.
  • corpus/, a sample of the drive copied as is: about 120 files for 100 books, most of them in inbox/, misc/ and the office folders (london/, madrid/, 北京办公室/, 東京オフィス/, 서울지사/). A book's title, authors, years and description are spread over one to three files: JSON, ONIX XML, EPUB, DOCX, PDF, HTML, Markdown or plain text, some in old encodings.
  • corpus/catalogs/: two catalog exports with one book per row, catalog_export_2023.csv (English headers) and 東京_目録.csv (Japanese headers); corpus/archives/: two zip files, inbox_archive_2020.zip and laptop_export_2018.zip, with two more books each. The full drive has the same kinds of files under other names.
  • corpus/scans/: four image-only PDFs with no text (two copy a book that also has a readable file, two are a book's only material). Junk is spread over the other folders: .DS_Store, Thumbs.db, desktop.ini, an Office lock file and empty text files.
  • archivist_notes.txt: a short note saying the sample is copied as is, who put files there (including old archives and catalog exports), and that the real run gets the full drive laid out the same way.

What the AI must find out by asking the client

  • The folder layout of the library, depending on the version: library/<year>/<title>/<author>.txt, library/<year>/<author>/<title>.txt or library/<author>/<year>_<title>.txt.
  • Which year goes in the path, depending on the version: the year of first publication or the year of the edition the client holds. A book with only one year uses it for both.
  • Which script titles and author names are written in, depending on the version: the original script, or the romanized form paired with it in the book's metadata (this matters for the Chinese, Korean and Japanese books).
  • How a co-authored book is named, depending on the version: only the first author, or all authors in order joined with " & ".
  • What the spaces in a title or a name become in a file name, depending on the version: _, - or a plain space.
  • How many characters of a title or a name are kept, depending on the version: 40, 48 or 60 on easy, 32, 40 or 50 on medium, 24, 32 or 40 on hard; spaces, dots and separators left at the ends are removed.
  • What a library file holds (the same in every version): only the book's description, with no title, author or year lines.
  • Which reason code a book set aside gets (the same in every version): one of UNREADABLE, NO_TITLE, NO_AUTHOR, NO_YEAR, NO_DESCRIPTION and CONFLICT, the first that applies.
  • On hard only: what happens to a book with no author anywhere, depending on the version. It goes to review as NO_AUTHOR, or it is shelved under the author name "Unknown" or "Anonymous".
  • On hard only (the same in every version): a book with no description anywhere goes to review as NO_DESCRIPTION, never with an invented or placeholder text; two exports of the same rank that disagree on the year send the book to review as CONFLICT; a meaningful file name counts as a title but a generic one such as doc_0042 or an ISBN does not (NO_TITLE).

How it is scored

Scores 0 if the deliverable…

  • Writes a library file or manifest.csv that is not valid UTF-8.
  • Writes a file or folder name that contains \ / : * ? " < > | or a control character, is . or .., ends in a space or a dot, or is longer than 255 bytes.
  • Gives a book more than one library file (its copies in other formats or folders must be merged into one).
  • Has a manifest row marked review with no reason code, or with one outside the six.
  • Has a manifest that is not the index of the library: a library file without exactly one placed row giving its path, a placed row whose path is no library file or that names no file of the drive as its source, or a source named in two rows.
  • Sends a book to review without copying its files of the drive under _review/.
  • On hard, gives a library file to a book with no description anywhere, or writes a library file that is empty or holds made-up or placeholder text instead of a description taken from the files.
  • On hard, shelves a book under a title or a year its files do not settle: no title other than a generic file name, no year anywhere (file dates are not publication years), or two exports of the same rank that disagree on the year.
  • On hard, where the client's policy sends books with no author to review: shelves such a book anyway, unless the company policy lets this rule bend and the AI asked the client for an exception first (then it goes under "Unknown").
  • On hard, where the client's policy shelves books with no author under a name: sends such a book to review, or shelves it under another name.

If it is valid, quality is…

Higher is better: points out of 100, the average credit per counted book. A book earns 1 at exactly the right path with its description, or when it is set aside with the right reason code (0.7 for a book with no author when the client's policy sends it to review); its description at a wrong path is misfiled and earns 0.4. A missing or wrong manifest row takes off a fifth, and on medium and hard each library file that is no book costs 0.5. The client's own way (score 0) files only the books with a complete UTF-8 JSON record and leaves the rest (about 9 to 17 points); the reference solution (score 1) reads every format and handles every exception, so it files every book as the client's catalogue does (100 points, 99.4 on hard when the policy sends the two books with no author to review). It is also the best possible, so a program as good as it earns full credit.

The same in every case

  1. Valid or not. Breaking any rule above makes the deliverable invalid and the run scores 0. A rule the company policy lets bend counts only if the AI asked the client for an exception.
  2. Quality. The result is placed on a scale where the client's own way without an engineer is 0 and the reference solution is 1. Better than the reference goes above 1; full credit at the policy's cap (1.5).
  3. Final score. Quality, plus how well the AI asked (did its questions uncover the facts above?), how it communicated (the client's language, a NOTES.md) and how efficient it was, weighted by the company policy.
  4. Several versions. The data stays the same; only the client's exact values (a threshold, a unit, a date) change from one version of the case to another. A difficulty's score is the average over several versions, so memorising one answer does not help.

What the AI is asked

The client's request: the only text the AI gets at the start. It is the same in every version of the case.

Our shared drive holds the material of about a hundred of our books, in Chinese, English, Korean, Japanese and Spanish, and nobody has kept it in order: titles, authors, years and blurbs are scattered over all kinds of files from the regional offices, the scanning team and the rights desk. A sample of the drive is attached (corpus/).

We need a program we can run on the full drive that builds a clean library from it: one text file per book with the book's description, filed the way our catalogue team wants, plus a manifest of what went where. Anything it cannot file should be set aside for our team to look at, not guessed.

Deliverable spec (the program interface)

A program/ directory with organize.py defining organize(task); task = {"corpus_dir": <a folder laid out like
data/corpus>, "out_dir": <an empty folder>}. It reads corpus_dir (never changes it) and writes only inside out_dir:
  out_dir/library/...    one UTF-8 .txt file per book holding the book's description (the folder layout and
                         file naming follow the client's catalogue rules)
  out_dir/_review/...    the material of books that cannot be placed
  out_dir/manifest.csv   header source,status,path,reason; a row per book (source = its corpus-relative file
                         path(s), ";"-separated) and per skipped file; status placed | review | skipped
It is run once, offline, on the client's full drive (same structure and mix as the sample, about 100 books).
Python standard library only; at most 5 minutes.

Settings: one dataset, 9 answers

The AI sees the same request and data in every version. The difficulty decides which client rules apply; the rule seed picks the exact values of those rules (a threshold, a unit, a date) from the candidates below. A difficulty's score is the average over rule seeds.

Case notes (README)

Multilingual Corpus Curator — data_knowledge/multilingual_corpus_curator

A small publisher keeps the material of about a hundred books (Chinese, English, Korean, Japanese, Spanish) on one messy shared drive: each book's title, authors, publication years and description are spread over one to three files of mixed formats, next to scans, archives, catalog exports and junk. The agent delivers a program, program/organize.py with organize(task), task = {"corpus_dir": "$INPUT_DIR", "out_dir": "$OUTPUT_DIR"}, that builds a normalized library:

out_dir/library/<the drawn layout>.txt   one UTF-8 file per book: the book's description only
out_dir/_review/...                      source files of books that cannot be placed
out_dir/manifest.csv                     source,status,path,reason (placed | review | skipped)

The agent sees a visible sample (data/corpus/, 100 books, ~120 files) and the program is scored on a hidden corpus built by the same recipe with another seed (same size and mix of kinds, other books, other archive, catalog and numbered file names), identical in every setting. Everything is synthetic: titles, names and blurbs are generated from invented vocabularies written natively in each language. Only the standard library is needed to read every format.

The case is audited (audited: true): dataset/audit.json holds its ground truth audit, GT.md the ground truth in five parts generated from it (client facts, validity checks, objective, reference and bounds, diagnostic cases), and CLIENT_REVIEW.md the passages the simulated client answers each target from, in all five locales, for a human reviewer. Both are written by gt_report.py.

Settings: one corpus, tiers × rule seeds

A setting is a tier and a rule seed. The world, the visible corpus, the hidden corpus and the request are the same in every setting (the validator checks that the agent's view is byte-identical). The tier decides which books are scored, which rules apply and which candidate pools the rule seed draws from; the rule seed draws the client's library rules, each parameter on its own, so the correct library differs from seed to seed. The public panel is rule seeds 11, 18 and 21 (nine settings, stored in dataset/answer/ and checked by the validator); any other seed is a private draw whose answers are published nowhere.

What an agent must ask

Twelve targets, one fact each (GT.md part 1 shows that misreading any one of them alone loses at least a tenth of the credit in every measured setting where it is in force):

  • drawn per rule seed (param:): layout, year_basis, script, co_authors, separator, max_len and, in hard, missing_author (the no-author policy and its fallback name);
  • the same under every draw: content (the file holds the description only), review_codes (the six codes) and, in hard, no_description (no description: NO_DESCRIPTION, never a placeholder), conflict (same-rank years that disagree: CONFLICT) and generic_titles (a generic file name is not a title: NO_TITLE).

The earlier targets precedence, encodings, year_notations, author_variants, duplicates, containers, scoring and the parts of exceptions not listed above are no longer targets: they are data facts the sample shows, or concern too few books to matter (GT.md lists the bound for each; REVIEW.md, Ground truth audit). They stay in requirements.md, and the client answers them when asked.

Value of asking (audit, public world): a program that never asks (robust_solution: the reference's reading of every fixed fact, the first candidate of each drawn rule, the longest name limit, and no review rows since it cannot know the codes) earns a mean credit of 0.31 / 0.34 / 0.36 in easy / medium / hard, so asking is worth 0.69 / 0.66 / 0.64 of the credit.

Scoring

Per scored book: 1 for the exact library path with the right description; 0.4 for the right description at any other path (misfiled: the team has to find and move it); 0.2 for the right path holding any other text. A book that belongs in review earns 1 when every manifest row naming one of its files says review with the right reason code (0.4 when they agree on another code; under the review policy a NO_AUTHOR book earns 0.7 in review); rows that disagree, or a library file for the book as well, earn nothing. A book that belongs on the shelf earns nothing in review; under a shelving policy that includes the author-less books, whose expected author is the drawn fallback name. Each book's manifest row is checked too (the only row naming the book's files, all of them and nothing else; placed with the book's library path, or review with its files copied byte for byte under _review/; a scan that copies a readable file may be in the row, listed as skipped or left out): a missing or wrong row costs a fifth of the book's credit. Medium and hard subtract 0.5 per library file that is no book. Objective = 100 × credit / books scored (maximize); quality is normalized between the baseline (0) and the reference (1), and quality_cap is 1.0 (the reference is the best possible). Descriptions are compared after NFKC with whitespace removed, so wrapping does not matter. In hard, no_fabrication also fires on a non-empty library file that holds no whole description paragraph of any book and is not a piece (20+ characters) of one: placeholders and invented blurbs; a stray heading or a dropped paragraph only loses credit.

The rules that make the outputs mandatory: manifest_rows (every library file is the path of exactly one placed row, every placed row's path is a library file and its source names at least one file of the drive, an archive member or a catalog row, written !, /, :, # or | after the archive or catalog path; no source is named in two rows) and review_copies (every file of the drive named in a review row is copied under _review/). no_guessing (hard) makes the request's "not guessed" a hard gate: a book whose title or year the sources do not settle (NO_TITLE, NO_YEAR, CONFLICT) is not placed.

score() also reports enforced and evidence per target in force: the diagnostic, computed from the same run of the program on the hidden drive (GT.md part 5). Degenerate programs (shortcuts() in case.py, GT.md part 2) are invalid or score at most 0.42: reviewing everything, spamming review rows, placeholders or whole files at the right paths, a header-only manifest, a manifest whose placed rows have an empty source or their own library path as the source, review without copies, every book under all three layouts, copying the drive through, and a flat library/<title>.txt. The diagnostic also tells these from a correct program: a flat path counts against layout, a placeholder at the right path against content, and an author-less book that is neither shelved nor in review against missing_author; in hard, a program that writes no review row at all is not enforced on review_codes (in easy and medium no scored book belongs in review, and it stays None). A stray library file that holds one book's whole description with more around it (a card at a path no rule gives) is still no book's file for the score, but the diagnostic reads it as that book's, so a program misreading two facts is flagged on both. The audit also tries the diagnostic on deliverables that are neither the reference nor an ablation (the answer key, the baseline, robust_solution; GT.md part 5, REVIEW.md "Diagnostics on other deliverables"). The case has no lazy diagnose() hook: the diagnostic is cheap and computed in score().
