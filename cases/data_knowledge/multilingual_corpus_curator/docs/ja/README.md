# 多言語コーパスキュレーター — `data_knowledge/multilingual_corpus_curator`

小さな出版社が、約100冊の本（中国語・英語・韓国語・日本語・スペイン語）の資料を、散らかった共有ドライブ1つに置いています。各本の書名、著者、刊行年、紹介文は形式の異なる1〜3個のファイルに分かれていて、その横にはスキャン、アーカイブ、目録の書き出し、不要ファイルが並んでいます。エージェントは**プログラム** `program/organize.py`（`organize(task)`、`task = {"corpus_dir": "$INPUT_DIR", "out_dir": "$OUTPUT_DIR"}`）を納品し、このプログラムが正規化されたライブラリを作ります。

```
out_dir/library/<抽選されたパス構成>.txt   1冊につき UTF-8 のファイル1つ：その本の紹介文だけ
out_dir/_review/...                        ライブラリに並べられない本の元ファイル
out_dir/manifest.csv                       source,status,path,reason（placed | review | skipped）
```

エージェントにはサンプル（`data/corpus/`、100冊、約120ファイル）が見え、プログラムは同じ作り方で別のシードから作った**採点用のコーパス**（AIには渡さない）で採点されます。採点用のコーパスは規模と種類の構成がサンプルと同じで、本は別、アーカイブ・目録・番号付きのファイルの名前も別で、どの設定でも同一です。すべて合成データで、書名、人名、紹介文は各言語でネイティブに書いた架空の語彙から生成しています。どの形式も標準ライブラリだけで読めます。

このケースは**監査済み**です（`audited: true`）。`dataset/audit.json` に正解の監査の結果があり、`GT.md` はそこから生成した5部構成の正解（顧客だけが知っている事実、有効性のチェック、目的値、模範解答と限界値、直接の検査の事例）です。`CLIENT_REVIEW.md` は、シミュレーションの顧客が各事実に答えるときのもとになる文章を、人が確認できるよう5つのロケールすべてについて示したものです。どちらも `gt_report.py` が書き出します。

## 設定：コーパスは一つ、ティア × ルールシード

設定はティアとルールシードの組です。ワールド、エージェントに見えるコーパス、採点用のコーパス、依頼はどの設定でも同じです（エージェントの見え方がバイト単位で同一であることを検証器が確認します）。ティアは、どの本を採点するか、どのルールを適用するか、ルールシードがどの候補プールから抽選するかを決めます。ルールシードは顧客のライブラリ規則をパラメータごとに別々に抽選するので、正しいライブラリはシードごとに異なります。公開ルールシードは **11、18、21** です（9つの設定。`dataset/answer/` に保存され、検証器が確認します）。それ以外のシードは非公開の抽選で、その正解はどこにも公開されません。

### ティア（コーパスは同じで、範囲、厳しさ、候補プールが異なる）

| | easy | medium | hard |
|---|---|---|---|
| **採点する本**（採点用のコーパス） | 形式の整った本30冊：1ファイル、UTF-8、メタデータ完備、ふつうの4桁の年 | 66冊：+ 読めるすべての本 | 100冊：+ 例外 |
| **加わる内容** | 各形式、パス構成、名前の規則、紹介文の抽出、年の基準、ローマ字の対 | 古いエンコーディング（GB18030、CP949、Shift_JIS、CP1252）；`令和元年`、`昭和50年`、`民國98年`、`단기 4342년`、`二〇〇九年`、`MMIX`；全角の書名とアクセントが分解された書名；パスに使えない文字；同じ著者のいくつものローマ字表記（正式な対はその著者のほかの本にだけある）；形式やフォルダをまたぐコピーの統合；情報源の優先順位（埋め込みメタデータ > 扉ページ > ファイル名） | 欠けた著者・書名・紹介文を別のファイルから補う；意味のあるファイル名から書名；`©` の行から年；理由コードを付けて確認に回す：`NO_TITLE` / `NO_YEAR` / `NO_DESCRIPTION` / `CONFLICT`（同じ段階の情報源で年が食い違う）/ `UNREADABLE`（画像だけのスキャン）；著者のない本についての顧客の方針（`NO_AUTHOR` で確認に回すか、代替の著者名で並べる）；読めるファイルと重複するスキャン；不要ファイル（`.DS_Store`、`Thumbs.db`、`desktop.ini`、`~$` ロックファイル、`__MACOSX/._*`、空のファイル）；zip アーカイブの中の本；複数の本を収めた目録 CSV（英語と日本語のヘッダー） |
| **名前の長さのプール**（`max_len`） | 60、48、40：副題付きの書名を値ごとに異なる位置で切る | 50、40、32：+ 32 では共著者の並びと、地名の入った長い書名も | 40、32、24：+ 中くらいの長さの書名と共著者の並び |
| **著者のない本の方針**（`no_author`） | 抽選しない（該当する本は範囲外） | 抽選しない | 確認に回すか、「Unknown」または「Anonymous」の名前で並べる |
| **ルール** | `utf8_output`、`safe_names`（物理的）；`one_file_per_book`、`review_reason`、`manifest_rows`、`review_copies`（契約上） | 同じ | + `no_fabrication`、`no_guessing`（契約上）；確認方針では `missing_author_review`、配架方針では `missing_author_shelved`（業務慣行） |
| **採点の追加要素** | 範囲外の本は無視 | 本でないライブラリのファイル1つにつき −0.5 | 確認方針：著者がなく確認待ちの本は0.7（「Unknown」で並べると1だが、承認された例外が必要）；配架方針：そうした本もほかの並べる本と同じように採点；どの情報源にもない文章を収めたライブラリのファイルは `no_fabrication` 違反 |
| **要件が範囲外とするもの** | 「ドライブのほかのファイル（古いエンコーディング、複数形式のコピー、壊れた・不完全な資料、アーカイブ、目録、スキャン）はまだ確認しませんが、それが原因でプログラムが止まってはいけません」 | 「例外（項目の欠落、スキャン、アーカイブ、目録、不要ファイル）はまだ採点しませんが、本でないものをライブラリに入れてはいけません」 | なし |

ルールシードはどのティアでもプールの同じ位置を抽選します（抽選はティアに左右されません）。ただし `max_len` はティアごとにプールが異なり、`no_author` は hard にしか候補がありません。そのため同じシードでも、ティアが難しくなるほど名前の長さの上限が厳しくなり、hard では著者のない本の方針が変わることがあります。3つのティアの模範解答はどの公開シードでも互いに異なり、それぞれを別のティアで採点すると、そのティア自身の模範解答より低い点になります（下の表）。

### パラメータ

ルールシード s は、候補が n 個ある各プールから位置 `Random("data_knowledge/multilingual_corpus_curator|<name>|s").randrange(n)` を、ほかのパラメータとは独立に抽選します。最初の5つのプールはどのティアでも同じです。どのパラメータも、AIが確認すべき事実1つの内容です（`locales/en/targets.yaml` の `param:`）。

| パラメータ | プール | 変わるもの（採点用のコーパス、公開ワールド、範囲内で並べる本 easy / medium / hard） | 事実 |
|---|---|---|---|
| `layout` | `library/<年>/<書名>/<著者>.txt`、`library/<年>/<著者>/<書名>.txt`、`library/<著者>/<年>_<書名>.txt` | 並べるすべての本のパス（30 / 66 / 88–90） | `layout` |
| `year_basis` | 初版の刊行年、この版の刊行年（年が1つしかない本はその年を両方に使う） | 2つの年が異なる本（15 / 37 / 44） | `year_basis` |
| `script` | 原語の文字、ラテン文字（メタデータで対になっているローマ字） | 中国語・韓国語・日本語の本（18 / 40 / 58） | `script` |
| `multi_author` | 筆頭著者のみ、全著者を `" & "` でつなぐ | 著者が2人の本（10 / 23 / 30） | `co_authors` |
| `sep` | `_`、`-`、半角スペース | 空白を含む名前（原語の文字では 18 / 40 / 53、ラテン文字ではすべての本） | `separator` |
| `max_len` | easy 60、48、40；medium 50、40、32；hard 40、32、24 | 上限より長い名前：easy 5–6；medium 13、13、15–17；hard 15、17–19、21–38（幅は文字と共著者の規則による） | `max_len` |
| `no_author` | easy と medium は `review`；hard は `review`、`Unknown`、`Anonymous` | 著者のない本2冊（hard）：`review` なら緩和可能な `missing_author_review` のもとで `NO_AUTHOR` として確認に回し（各0.7）、名前ならその著者名でほかの本と同じように並べ（各1）、そのとき `missing_author_shelved` により、確認に回すか別の名前で並べると無効 | `missing_author` |

`derive_params` は、テキストが引用する名前 `fallback_author` を加えます。配架方針では抽選された名前、確認方針では「Unknown」（承認された例外で使う名前）です。実行不可能な組み合わせはありません。生成器はどちらの文字でも、すべての書名が先頭24文字（最も厳しい上限）の中で互いに異なるようにしているので、どの組み合わせでも並べる本2冊が同じパスになることはなく、このケースは `admissible` を定義しません。

どの設定にも共通の名前の規則：NFKC、`\ / : * ? " < > |` と制御文字はそれぞれ空白に、連続する空白は区切り文字に、`max_len` 文字で切り詰め、両端の空白・ピリオド・区切り文字を除去。上限が厳しいほど多くの名前にかかるので、この手順の順番を誤ると失点する機会が増えます。アクセントが分解されたスペイン語の書名を NFKC の前に切ると残る文字が減り、切った位置が区切り文字に当たると、除去すべき区切り文字が1つ残ります。

### 公開ルールシード

公開ルールシードにはすべてのプールのすべての候補が現れます。シード11、18、21を合わせると、候補が3つのプールは3つの値すべてを（どのティアでも）、候補が2つのプールは両方の値を出します。シード11が先頭なのは、validate-case がこのシードからパラメータの影響をチェックするためです。その hard の抽選は著者のない本を並べるので、方針のチェックでは、有効な配架方針の模範解答を、それが違反することになるほかの方針と比べます。

|---|---|---|---|---|---|---|---|---|---|---|
| easy/s11 | author/year_title | first | latin | all | `" "` | 40 | review (Unknown) | 100.00 | 16.67 | 100.00 |
| easy/s18 | year/title/author | first | latin | first | `-` | 48 | review (Unknown) | 100.00 | 16.67 | 100.00 |
| easy/s21 | year/author/title | edition | original | first | `_` | 60 | review (Unknown) | 100.00 | 16.67 | 100.00 |
| medium/s11 | author/year_title | first | latin | all | `" "` | 32 | review (Unknown) | 100.00 | 13.03 | 100.00 |
| medium/s18 | year/title/author | first | latin | first | `-` | 40 | review (Unknown) | 100.00 | 13.03 | 100.00 |
| medium/s21 | year/author/title | edition | original | first | `_` | 50 | review (Unknown) | 100.00 | 13.03 | 100.00 |
| hard/s11 | author/year_title | first | latin | all | `" "` | 24 | Unknown | 100.00 | 8.60 | 100.00 |

目的値は公開ワールドシード（20261027）の採点用のコーパスでのものです。「限界値」は `objective_bound` で、有効なプログラムが取れる最高の点です（`expected_output` がこの点を取ります）。非公開シードはそれ以外のどの組み合わせも抽選します。たとえばシード101は `author/year_title`、first、original、first、`-`、60 / 50 / 40、すべてのティアで review、シード102は `year/author/title`、first、original、first、`_`、40 / 32 / 24、hard で `Unknown` です。

### エージェントが確認すべきこと

AIが確認すべき事実は12個で、それぞれ1つの事柄だけを扱います（GT.md の第1部は、どれか1つだけを読み違えると、それが適用される測定したすべての設定で、品質点の少なくとも10分の1を失うことを示しています）。

- ルールシードごとに抽選されるもの（`param:`）：`layout`、`year_basis`、`script`、`co_authors`、`separator`、`max_len`、そして hard では `missing_author`（著者のない本の方針とその代替の名前）。
- どの抽選でも同じもの：`content`（ファイルには紹介文だけを入れる）、`review_codes`（6つのコード）、そして hard では `no_description`（紹介文がない：`NO_DESCRIPTION`、仮の文は決して入れない）、`conflict`（同じ段階の年が食い違う：`CONFLICT`）、`generic_titles`（汎用的なファイル名は書名ではない：`NO_TITLE`）。

以前の事実 `precedence`、`encodings`、`year_notations`、`author_variants`、`duplicates`、`containers`、`scoring` と、`exceptions` のうち上に挙げなかった部分は、もうAIが確認すべき事実ではありません。サンプルに見えるデータ上の事実であるか、関わる本が少なすぎてスコアを左右しないからです（GT.md にそれぞれで失う点数の上限を載せています。REVIEW.md の「正解の監査」も参照）。これらは requirements.md に残っており、尋ねられれば顧客は答えます。

**質問の価値**（監査、公開ワールド）：一度も尋ねないプログラム（`robust_solution`：固定の事実はすべて模範解答と同じ読み方、抽選されるルールはそれぞれ最初の候補、名前の上限は最も長いもの、そしてコードを知りえないので確認行はなし）は、easy / medium / hard で品質点の平均 0.31 / 0.34 / 0.36 を得ます。したがって質問の価値は品質点の 0.69 / 0.66 / 0.64 です。

## ファイル形式と例外の種類

| 種類 | 情報のある場所 |
|---|---|
| JSON | `title`、`title_latin`、`authors[{name, name_latin}]`、`first_published`、`edition_year`、`description`（medium では年が元号などの文字列のことがある） |
| ONIX 風の XML（名前空間 `ns.editeur.org/onix/3.0`） | `TitleText`（+ `textscript="Latn"`）、`Contributor/PersonName` + `AlternativeName` または `PersonNameInverted`、`PublishingDateRole` 01 = この版、11 = 初版、`TextContent/Text` |
| EPUB（zip + OPF） | `dc:title`、`alternate-script` / `file-as` の補足が付いた `dc:creator`、`dc:date`（この版）、`first-published` の meta、`dc:description`；`dcterms:modified` は罠 |
| DOCX（zip + XML） | `docProps/core.xml` の title と creator（`dcterms:created` は罠）；複数の run に分かれた本文の段落 = 扉ページ + 紹介文 |
| PDF（圧縮していないテキストストリーム） | Info の `/Title`、`/Author`（UTF-16 の16進文字列；`/CreationDate` は罠）；ページのテキストは UTF-16 の `Tj` 文字列で、扉ページの行は折り返さず、紹介文の行は折り返している |
| スキャン PDF | 画像だけのページで、テキストも書名もない：読めない |
| HTML | `<title>`、`<meta name="author">`；本文の `h1`、`p.latin`、`p.byline`、`p.edition`、`h2`、紹介文の段落；`<meta charset>`（medium では Shift_JIS / CP949） |
| Markdown | フロントマター（`title`、`title_latin`、`author`、`author_latin`、`first_published`、`edition`）+ 本文の扉ページ |
| プレーンテキスト | 扉ページ（書名、`(ローマ字書名)`、`名前（ローマ字） 著` / `지음` / `by` / `por`、版の行、任意の `©` の行）、見出し（`内容简介`、`内容紹介`、`책 소개`、`About this book`、`Sinopsis`）、紹介文（固定位置での改行、CRLF、古いエンコーディングのこともある） |
| 目録 CSV | 1行1冊；英語か日本語のヘッダー；`source` = `file.csv#row` |
| zip アーカイブ | それぞれ2冊と AppleDouble の `__MACOSX/._*` 項目1つ；`source` = `archive.zip!inner/path`（採点用のコーパスではフォルダが1段深い） |

各コーパスの構成（件数は固定、言語は一部ランダム）：easy 30冊；medium はエンコーディング7、年の表記6、全角・分解アクセントの書名4、禁止文字5、ローマ字の揺れ5、複数ファイルのコピー6、優先順位の衝突3；hard は著者の補完3、著者なし2、ファイル名からの書名2、書名なし2、紹介文の補完2、紹介文なし2、著作権表示の年3、年なし2、同じ段階の衝突2、スキャンのみ2、読めるコピーのあるスキャン2、zip の中の本4、目録の行6；ほかに不要ファイル8。easy の英語とスペイン語の本は1冊おきに、ほかの本は60%が長い副題を持ちます（`The Silent Lighthouse — Stories from the Northern Coast and the Keepers Who Stayed Behind`）。本の30%は著者が2人です。アーカイブと目録の名前は小さなプールから選ばれ、番号付きのファイル名（`doc_0391`、`scan_0414`）はコーパスごとにランダムなオフセットから始まります。公開ワールドでは、採点用のドライブがサンプルと共有するパスは不要ファイルの4つだけで（以前は12）、ワールドシード 1-3 ではそれ以外に共有するのはせいぜいアーカイブの名前1つです（中身は別）。採点用のドライブには、昭和の年（和暦の本）と、フォルダが1段深い zip の中身も必ず入っています。

## 採点

採点する本ごとに：正しいライブラリのパスに正しい紹介文があれば **1**、正しい紹介文がほかのパスにあれば **0.4**（置き場所の誤り：チームが探して移す必要がある）、正しいパスに別の文章があれば **0.2** です。確認に回すべき本は、その本のファイルのどれかを挙げる一覧の行がすべて `review` で理由コードが正しければ1（すべて同じ別のコードなら0.4、確認方針では `NO_AUTHOR` の本は確認で0.7）で、行どうしが食い違う場合やその本のライブラリファイルもある場合は0です。ライブラリに並べるべき本は、確認に回すと0点です。配架方針では著者のない本もこれに当たり、その本の期待される著者は抽選された代替の名前です。各本の一覧の行も確認します（その本のファイルを挙げる唯一の行で、ファイルをすべて挙げてほかは挙げないこと。`placed` とその本のライブラリのパス、または `review` とファイルの `_review/` 以下へのバイト単位のコピーがそろっていること。読めるファイルと重複するスキャンは、その行に入れても、skipped として載せても、省いてもかまいません）。行がない、または誤っている場合は、その本の点数の5分の1を失います。medium と hard では本でないライブラリのファイル1つにつき0.5を引きます。目的値 = 100 × 点数 / 採点する本の数（最大化）で、品質は従来のやり方（0）と模範解答（1）の間で正規化し、`quality_cap` は1.0です（模範解答が達成できる最高だからです）。紹介文は NFKC のあと空白をすべて除いて比べるので、改行位置は影響しません。hard では、空でないライブラリのファイルが、どの本の紹介文の段落も丸ごとは含まず、紹介文の断片（20文字以上）でもない場合にも `no_fabrication` が発動します。仮の文や作った紹介文がこれに当たり、見出しが1つ残っていたり段落が1つ抜けていたりするだけなら点数を失うだけです。

出力を必須の成果物にするルールは2つです。`manifest_rows`（ライブラリのファイルはどれもちょうど1つの placed 行のパスで、placed 行のパスはどれもライブラリのファイルであり、その行の source はドライブのファイル、アーカイブ内の項目、目録の行のうち少なくとも1つを挙げる。アーカイブ内の項目と目録の行は、アーカイブや目録のパスのあとに `!`、`/`、`:`、`#`、`|` のどれかを付けて書く。同じ情報源を2つの行に挙げない）と、`review_copies`（確認行に挙げたドライブのファイルは、すべて `_review/` の下にコピーする）です。`no_guessing`（hard）は、依頼の「推測せず」を必須条件にします。情報源から書名や年が決まらない本（`NO_TITLE`、`NO_YEAR`、`CONFLICT`）は並べません。

`score()` は、適用中の事実ごとに `enforced` と `evidence` も報告します。これが直接の検査で、採点用のドライブでのプログラムの同じ実行から計算します（GT.md の第5部）。極端に単純なプログラム（case.py の `shortcuts()`、GT.md の第2部）は、無効になるか最高でも0.42です：すべてを確認に回す、確認行を大量に書く、正しいパスに仮の文やファイルの全文を置く、ヘッダーだけの一覧、placed 行の source が空か自分のライブラリのパスである一覧、コピーなしの確認、すべての本を3つのパス構成すべてで置く、ドライブをそのままコピーする、平らな `library/<書名>.txt`。直接の検査は、これらを正しいプログラムとも区別します。平らなパスは `layout`、正しいパスの仮の文は `content`、並べても確認に回してもいない著者のない本は `missing_author` が反映されていないとみなされます。hard では、確認行を1行も書かないプログラムは `review_codes` が反映されていないと判定されます（easy と medium では確認に回すべき採点対象の本がないので、None のままです）。1冊の紹介文を丸ごと含み、そのまわりにほかの文章もあるライブラリの余分なファイル（どのルールも与えないパスに置いたカード）は、スコアの上ではやはりどの本のファイルでもありませんが、直接の検査はそれをその本のファイルとして読みます。そのため2つの事実を読み違えたプログラムは、両方の事実について「反映されていない」と判定されます。監査は、模範解答でも事実を一つだけ取り違えた解答でもない成果物（正解キー、従来のやり方、`robust_solution`）でも直接の検査を試します（GT.md の第5部、REVIEW.md の「ほかの成果物での直接の検査」）。このケースには、必要なときだけ計算する `diagnose()` フックはありません。直接の検査は軽いので `score()` の中で計算します。

採点用のコーパスでのプログラムの出力はプログラムのダイジェストをキーにキャッシュされるので、各設定、違反例、パラメータの影響のチェックとティア間のチェックは、異なるプログラムごとに1回だけ実行されます（既定のワールドシード 1–3 で `validate-case` は約3分、`audit-case` は約8〜10分かかります）。

## 模範解答と検証済みの数値（シード 20261027、採点用のコーパス）

従来のやり方（`reference/baseline.py` + 同じ `config.json`）は、顧客がエンジニアなしで書けるスクリプトです。完全な UTF-8 の JSON 書き出し（書名、著者、ふつうの4桁の年、紹介文）がある本だけを目録の規則どおりにライブラリに並べ、同じ ISBN の ONIX 書き出しもある JSON の記録はチームに残し（2つのどちらが正しいか判断できないため）、ほかのファイルもすべてチームに残します（ほかの形式、古いエンコーディング、元号の年は扱わず、コピーを統合せず、確認エリアもありません）。どの設定でも有効です。

模範解答（`reference/organize.py` + その設定の `config.json`）は完全な整理プログラムです。すべての形式と zip の中の項目、コーパス自身の UTF-8 文字統計による古いエンコーディングの判定、すべての年の表記（元号、民国紀年、檀紀、漢数字、ローマ数字、`©` の行）、NFKC で正規化したパス名（スラッグ）、正規化した書名によるグループ化、本のすべてのファイルにまたがる項目ごとの優先順位、ドライブのどこかにある各著者の正式な名前の対、同じ段階の年の衝突、スキャン、不要ファイル、目録に対応し、抽選された著者のない本の方針に従います。採点用のコーパスのどの本も `expected_output` とまったく同じように並べるので、どの設定でも `objective_bound` に達し、`quality_cap` は1.0です。これまでに見つかった最善の解答（`best_known_solution`、監査用）は、正解キーそのものをプログラムで書き出したもので、やはり限界値に達するオラクルです。模範解答とは別の、すべてを知っている2つ目の成果物で、直接の検査がこれを反映されていないと判定することがあってはなりません。

| ティア | 採点する本 | 従来のやり方の目的値 | 模範解答の目的値 = 限界値 |
|---|---|---|---|
| easy（s11、s18、s21） | 30 | 16.67 | 100.00 |
| medium（s11、s18、s21） | 66 | 13.03 | 100.00 |
| hard、確認方針（s18） | 100 | 8.60 | 99.40（例外ありで100） |
| hard、配架方針（s11、s21） | 100 | 8.60 | 100.00 |

従来のやり方が正確に並べるのは 5 / 9 / 9 冊です。medium と hard ではそのうち2冊（コピー）が、ほかにもファイルがあるのに一覧の行に JSON しか挙げていないため5分の1を失います。ワールドシード 1、2、3 では、従来のやり方は 3.33–20.00（easy）、2.73–19.70（medium）、3.80–14.00（hard）で、模範解答は100.00（確認方針では99.40）です。確認方針のもとで `missing_author_review` を緩和する（著者のない2冊を「Unknown」で並べる）と、緩和が認められる場合は有効で、hard/s18 で100.00（正規化品質 1.007）になります。

## 補足

- エージェントに見えるコーパスはどの設定・どのロケールでもバイト単位で同一です（`content_dirs: [corpus]`）。ローカライズされているのは、コーパスの外にある整理メモだけです。
- `write only inside out_dir` と `never modify the corpus` はランナーが強制し（プログラムはコーパスのコピーを受け取り、docker では読み取り専用）、採点はしません。

## 保存されたデータセット（`dataset/`）

`python -m fdebench2.cli export-dataset cases/data_knowledge/multilingual_corpus_curator` で書き出します。`validate-case` が再生成し、生成器とずれていれば失敗します（約 2 MB、小さなファイル約2,300個）。`audit-case` が `dataset/audit.json` を書き出します（export-dataset はこれを残します）。

```
dataset/
  agent_view/<lang>/corpus/...       エージェントのサンプルドライブ（どのロケールでもバイト単位で同一）+ 整理メモ
  hidden/corpus/...                  organize() が受け取るそのままの採点用のドライブ（どの設定でも同じ）
  audit.json                         正解の監査（公開ワールド）：事実を一つだけ取り違えた解答、近道、質問の価値、
                                       限界値、直接の検査。GT.md はここから生成
  answer/<tier>/s<seed>/             easy/s11 ... hard/s21、公開ルールシード
    setting.json, score.json         抽選されたパラメータ（+ 導出された fallback_author）と、採点用のコーパスでの
                                       模範解答のスコア（従来のやり方の目的値と両方の正規化品質を含む）
    reference/program/               模範解答の成果物（organize.py + その設定の config.json）
    reference_output/                模範解答が採点用のコーパスで書き出すもの（library/、_review/、manifest.csv）
    expected_output/                 この設定で採点する本についての正しい out_dir（採点用のコーパス）：
                                       library/... 並べる本ごとに紹介文のファイル1つ、その設定のパスに
                                       _review/<REASON>/<パスの / を __ にした名前>  確認に回す本の元ファイル
                                       manifest.csv  placed / review の行（理由付き）と、hard では JUNK の skipped 行
    books.csv                        正解キー（採点用のコーパス）：各本の種類、ティア、採点対象か、期待される状態、
                                       パスと理由、正規の書名・著者・年、元ファイル
    expected_score.json              評価器による expected_output のスコア：easy と medium は100、hard は
                                       確認方針で99.4（NO_AUTHOR の2冊が確認で0.7；緩和したルールはない）、
                                       配架方針で100
```

正解キーがあるのは採点用のコーパスだけです。エージェントに見えるサンプルはエージェントが学ぶための材料で、そこではスコアを計算しません。期待される出力のツリーにはそのティアで採点する本（30 / 66 / 100）だけが入っており、ティア外の本はその設定の正解に含まれません。顧客のメールや SQL の書き出しは追加していません。ドライブにはすでに顧客自身の目録の書き出しがあり、新しい周辺資料を加えるとこのケースが試すものが変わってしまうからです。
