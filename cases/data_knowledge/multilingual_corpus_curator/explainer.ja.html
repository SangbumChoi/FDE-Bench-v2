ひと目でわかる概要

AIがすること

AIは、顧客が共有ドライブ全体（中国語・英語・韓国語・日本語・スペイン語の本およそ100冊。ファイルの種類はサンプルと同じで、本は別）に対してオフラインで1回実行する Python プログラムを作ります。プログラムは整理されたライブラリ（1冊につき紹介文だけを収めた UTF-8 のテキストファイル1つ、パスは年・書名・著者で組み立てる）と、どのファイルをどこに置いたかの一覧（manifest.csv）を作り、整理できない本は理由コードを付けて、顧客のチームが確認できるよう別にしておきます。

AIに与えられるもの

  • 顧客の依頼：本およそ100冊分の資料が各地のオフィス、スキャン担当、版権チームのファイルに散らばっているので、ドライブ全体で実行して1冊につき紹介文のファイルを1つ目録チームの決まりどおりに並べ、一覧を残し、整理できないものは推測せずに別にしておくプログラムがほしい、という内容です。
  • corpus/ は、整理せずにそのままコピーしたドライブのサンプルです。100冊分でファイルはおよそ120個あり、多くは inbox/、misc/ と各オフィスのフォルダ（london/、madrid/、北京办公室/、東京オフィス/、서울지사/）にあります。1冊の書名・著者・年・紹介文は、JSON、ONIX XML、EPUB、DOCX、PDF、HTML、Markdown、プレーンテキストの1〜3個のファイルに分かれていて、古いエンコーディングのものもあります。
  • corpus/catalogs/ には1行1冊の目録の書き出し catalog_export_2023.csv（英語のヘッダー）と 東京_目録.csv（日本語のヘッダー）が、corpus/archives/ にはさらに2冊ずつ入った zip アーカイブ inbox_archive_2020.zip と laptop_export_2018.zip があります。ドライブ全体には同じ種類のファイルが別の名前であります。
  • corpus/scans/ には、文字がなく画像だけの PDF が4つあります（2つは読めるファイルが別にある本のコピー、2つはその本の唯一の資料）。不要ファイルはほかのフォルダに散らばっています。.DS_Store、Thumbs.db、desktop.ini、Office のロックファイル、空のテキストファイルです。
  • 整理メモ.txt は短いメモです。サンプルは整理せずにそのままコピーしたこと、誰がファイルを置いたか（古いアーカイブや目録の書き出しも含む）、本番では同じ構成のドライブ全体を渡すことが書かれています。

顧客に聞かないとわからないこと

  • ライブラリのフォルダ構成です。ケースのバージョンごとに変わり、library/<年>/<書名>/<著者>.txt、library/<年>/<著者>/<書名>.txt、library/<著者>/<年>_<書名>.txt のどれかです。
  • パスに入れる年が初版の刊行年か、顧客の手元にある版の刊行年かです（バージョンごとに変わります）。年が1つしかない本は、その年を両方に使います。
  • 書名と著者名を原語の文字で書くか、メタデータで対になっているローマ字表記で書くかです（バージョンごとに変わります。中国語・韓国語・日本語の本で違いが出ます）。
  • 共著の本の著者を筆頭著者のみにするか、全著者を順番どおり " & " でつなぐかです（バージョンごとに変わります）。
  • 書名や名前の空白をファイル名で何にするかです。_ か - にするか、半角スペースのまま残します（バージョンごとに変わります）。
  • 書名や名前を先頭から何文字残すかです。easy は40・48・60文字、medium は32・40・50文字、hard は24・32・40文字のどれかで（バージョンごとに変わります）、切ったあと両端に残った空白・ピリオド・区切り文字は除きます。
  • ライブラリのファイルに何を入れるかです（どのバージョンでも同じです）。その本の紹介文だけで、書名・著者・年の行は入れません。
  • 別にしておく本にどの理由コードを付けるかです（どのバージョンでも同じです）。UNREADABLE、NO_TITLE、NO_AUTHOR、NO_YEAR、NO_DESCRIPTION、CONFLICT のうち最初に当てはまるものです。
  • hard のみ：どこにも著者のない本の扱いです。NO_AUTHOR で確認に回すか、著者名「Unknown」または「Anonymous」でライブラリに並べます（バージョンごとに変わります）。
  • hard のみ（どのバージョンでも同じです）：どこにも紹介文のない本は NO_DESCRIPTION で確認に回し、作った文や仮の文は決して書きません。同じ段階の2つの書き出しで年が食い違う本は CONFLICT で確認に回します。意味のあるファイル名は書名になりますが、doc_0042 のような汎用的な名前や ISBN はなりません（NO_TITLE）。

評価方法

こうなると0点（無効）

  • ライブラリのファイルか manifest.csv が正しい UTF-8 ではありません。
  • 書き出したファイル名やフォルダ名が \ / : * ? " < > | や制御文字を含むか、. や .. であるか、空白やピリオドで終わるか、255バイトを超えています。
  • 1冊の本のファイルがライブラリに2つ以上あります。ほかの形式やフォルダにあるコピーは1つにまとめなければなりません。
  • review とした一覧の行に理由コードがないか、6つ以外のコードが書かれています。
  • 一覧がライブラリの索引になっていません。ライブラリのファイルにそのパスを書いた placed 行がちょうど1つないか、placed 行のパスがライブラリのファイルでないかその行の情報源にドライブ上のファイルが1つもないか、同じ情報源が2つの行に挙がっています。
  • 本を確認に回したのに、ドライブにあるその本のファイルを _review/ の下にコピーしていません。
  • hard：どこにも紹介文のない本にライブラリのファイルがあるか、ライブラリのファイルが空であるか、ファイルから取った紹介文ではなく作った文や仮の文が入っています。
  • hard：ファイルから決まらない書名や年で本を並べています。汎用的なファイル名のほかに書名がない、どこにも年がない（ファイルの日付は刊行年ではない）、同じ段階の2つの書き出しで年が食い違う、のいずれかです。
  • hard で、顧客の方針が著者のない本を確認に回すと決めている場合：著者のない本をそのままライブラリに並べています。ただし、AIが顧客に申請して例外の承認を得ていれば「Unknown」で並べられます。
  • hard で、顧客の方針が著者のない本をある名前で並べると決めている場合：そうした本を確認に回すか、別の名前で並べています。

有効なら、品質は…

数えた本1冊あたりの平均点を100点満点で表します。正しいパスに紹介文とともに置いた本や、正しい理由コードで確認に回した本は1点（顧客の方針が確認に回すものなら、著者のない本は0.7点）、紹介文は正しいがパスが違えば置き場所の誤りで0.4点です。一覧の行がないか誤っている本はその点数の5分の1を失い、medium からは本でないライブラリのファイル1つにつき0.5点を引きます。従来のやり方（0点）は完全な UTF-8 の JSON 記録がある本だけを並べて残りはそのままにします（約9〜17点）。模範解答（1点）はすべての形式を読み、すべての例外を扱うので、どの本も顧客の目録どおりに並べます（100点。hard で著者のない2冊を確認に回す方針なら99.4点）。これが達成できる最高でもあるので、模範解答と同じだけ良いプログラムは満点になります。

難易度ごとの違い

難易度求められること
easy形式の整った30冊（1冊1つの UTF-8 ファイル、メタデータがそろい、年はふつうの4桁）だけを数え、名前は40・48・60文字のどれかで切ります。
medium残りの読める本を加えて66冊を数えます。古いエンコーディング（GB18030、CP949、Shift_JIS、CP1252）、令和元年・民國98年・단기 4342년・MMIX のような年、全角やアクセントが分解された書名、ファイル名に使えない文字、いくつものローマ字表記で出てくる著者、まとめるべきコピー、情報源の優先順位が加わり、名前は32・40・50文字のどれかで切り、本でないライブラリのファイルは1つにつき0.5点引かれます。
hard例外を加えて全100冊を数えます。別のファイルで補うか理由コードを付けて確認に回すべき書名・著者・年・紹介文の欠落、© の行の年、食い違う年、画像だけのスキャン、不要ファイル、zip アーカイブ、目録 CSV、紹介文を作らず年や書名を推測しないこと、著者のない本についての顧客の方針が加わり、名前は24・32・40文字のどれかで切ります。

すべてのケースに共通

  1. 有効かどうか。上のルールを一つでも破ると成果物は無効で0点です。会社の方針が緩めることを認めたルールは、AIが顧客に例外を申請した場合にだけ認められます。
  2. 品質。結果を「エンジニアなしで顧客がしていたやり方 = 0点、模範解答 = 1点」の尺度に換算します。模範解答より良ければ1を超え、方針の上限（1.5）で満点です。
  3. 最終スコア。品質に加えて、AIの質問の良さ（質問で上の事実を引き出せたか）、コミュニケーション（顧客の言語、NOTES.md）、効率を、会社の方針の重みで合わせます。
  4. 複数のバージョン。データは同じままで、顧客ルールの具体的な値（基準値、単位、日付など）だけがケースのバージョンごとに変わります。難易度ごとのスコアは複数のバージョンの平均なので、答えを一つ覚えても点にはなりません。

AIへの依頼

顧客からの依頼です。AIが最初に受け取る唯一の文章で、ケースのどのバージョンでも同じです。

共有ドライブには当社の本およそ100冊分の資料が、中国語・英語・韓国語・日本語・スペイン語で入っていますが、誰も整理してきませんでした。書名、著者、年、紹介文が、各地のオフィスやスキャン担当、版権チームが置いていったさまざまなファイルに散らばっています。ドライブのサンプルを添付します（corpus/）。

ドライブ全体に対して実行できるプログラムが必要です。1冊につき紹介文を収めたテキストファイルを1つ、目録チームの決まりどおりに並べたきれいなライブラリを作り、何がどこへ行ったかの一覧も残してください。整理できないものは推測せず、当社のチームが確認できるよう別にしておいてください。

成果物の仕様（プログラムのインターフェース）

program/ ディレクトリに、organize(task) を定義した organize.py を置きます。task = {"corpus_dir": <data/corpus と
同じ構成のフォルダ>, "out_dir": <空のフォルダ>}。corpus_dir は読むだけで（決して変更しない）、書き込むのは out_dir の中だけです：
  out_dir/library/...    1冊につき、その本の紹介文を収めた UTF-8 の .txt ファイル1つ（フォルダ構成と
                         ファイル名の付け方は顧客の目録ルールに従う）
  out_dir/_review/...    ライブラリに並べられない本の資料
  out_dir/manifest.csv   ヘッダー source,status,path,reason。1冊につき1行（source = その本の corpus からの
                         相対ファイルパス、";" 区切り）、スキップしたファイルごとにも1行。status は placed | review | skipped
顧客のドライブ全体（サンプルと同じ構成・同じ種類のファイルで約100冊）に対して、オフラインで1回実行されます。
Python 標準ライブラリのみ、最長5分です。

設定：データは一つ、正解は 9 通り

AIはどのバージョンでも同じ依頼とデータを見ます。難易度はどの顧客ルールが適用されるかを決め、ルールシードはそのルールの具体的な値（基準値、単位、日付など）を下の候補から選びます。難易度ごとのスコアは複数のルールシードの平均です。

ルール

ルールを一つでも破ると成果物は無効（0点）です。例外は一つだけで、会社の方針が緩めることを認めたルールについて、AIが先に顧客へ例外を申請した場合です。

  • 物理的 決して緩和されない
  • 契約上 方針が契約上の例外を認める場合にのみ緩和される
  • 業務慣行 方針の例外手続きを経れば緩和されうる
ルール区分ティア説明（{{…}} のパラメータはルールシードで抽選される）
utf8_output物理的easy, medium, hardlibrary/ のすべてのファイルと manifest.csv は正しい UTF-8 です。
safe_names物理的easy, medium, hard出力するファイル名・フォルダ名は \ / : * ? " < > | や制御文字を含まず、. や .. ではなく、空白やピリオドで終わらず、255バイトを超えません。
one_file_per_book契約上easy, medium, hard1冊の本が library/ に持つファイルは最大1つです。別の形式やフォルダにある同じ本のコピーは、そのファイルにまとめます。
review_reason契約上easy, medium, hard一覧（manifest.csv）で status が review の行には、すべて理由コード UNREADABLE、NO_TITLE、NO_AUTHOR、NO_YEAR、NO_DESCRIPTION、CONFLICT のいずれかを付けます。
manifest_rows契約上easy, medium, hardmanifest.csv はライブラリの索引です。ライブラリのファイルはどれもちょうど1つの placed 行の path で、placed 行の path はどれもライブラリのファイルで、その行の source にはドライブ上のファイル（またはアーカイブ内の項目、目録の1行）が少なくとも1つ挙がっており、どの情報源（ファイル、アーカイブ内の項目、目録の1行）も2つの行に挙げません。
review_copies契約上easy, medium, hardreview の行に挙げたドライブのファイルは、すべてそのまま _review/ の下にコピーします（アーカイブ内の項目と目録の行は不要）。

多言語コーパスキュレーター — data_knowledge/multilingual_corpus_curator

小さな出版社が、約100冊の本（中国語・英語・韓国語・日本語・スペイン語）の資料を、散らかった共有ドライブ1つに置いています。各本の書名、著者、刊行年、紹介文は形式の異なる1〜3個のファイルに分かれていて、その横にはスキャン、アーカイブ、目録の書き出し、不要ファイルが並んでいます。エージェントはプログラム program/organize.py（organize(task)、task = {"corpus_dir": "$INPUT_DIR", "out_dir": "$OUTPUT_DIR"}）を納品し、このプログラムが正規化されたライブラリを作ります。

out_dir/library/<抽選されたパス構成>.txt   1冊につき UTF-8 のファイル1つ：その本の紹介文だけ
out_dir/_review/...                        ライブラリに並べられない本の元ファイル
out_dir/manifest.csv                       source,status,path,reason（placed | review | skipped）

エージェントにはサンプル（data/corpus/、100冊、約120ファイル）が見え、プログラムは同じ作り方で別のシードから作った採点用のコーパス（AIには渡さない）で採点されます。採点用のコーパスは規模と種類の構成がサンプルと同じで、本は別、アーカイブ・目録・番号付きのファイルの名前も別で、どの設定でも同一です。すべて合成データで、書名、人名、紹介文は各言語でネイティブに書いた架空の語彙から生成しています。どの形式も標準ライブラリだけで読めます。

このケースは監査済みです（audited: true）。dataset/audit.json に正解の監査の結果があり、GT.md はそこから生成した5部構成の正解（顧客だけが知っている事実、有効性のチェック、目的値、模範解答と限界値、直接の検査の事例）です。CLIENT_REVIEW.md は、シミュレーションの顧客が各事実に答えるときのもとになる文章を、人が確認できるよう5つのロケールすべてについて示したものです。どちらも gt_report.py が書き出します。

設定：コーパスは一つ、ティア × ルールシード

設定はティアとルールシードの組です。ワールド、エージェントに見えるコーパス、採点用のコーパス、依頼はどの設定でも同じです（エージェントの見え方がバイト単位で同一であることを検証器が確認します）。ティアは、どの本を採点するか、どのルールを適用するか、ルールシードがどの候補プールから抽選するかを決めます。ルールシードは顧客のライブラリ規則をパラメータごとに別々に抽選するので、正しいライブラリはシードごとに異なります。公開ルールシードは 11、18、21 です（9つの設定。dataset/gt/ に保存され、検証器が確認します）。それ以外のシードは非公開の抽選で、その正解はどこにも公開されません。

エージェントが確認すべきこと

AIが確認すべき事実は12個で、それぞれ1つの事柄だけを扱います（GT.md の第1部は、どれか1つだけを読み違えると、それが適用される測定したすべての設定で、品質点の少なくとも10分の1を失うことを示しています）。

  • ルールシードごとに抽選されるもの（param:）：layout、year_basis、script、co_authors、separator、max_len、そして hard では missing_author（著者のない本の方針とその代替の名前）。
  • どの抽選でも同じもの：content（ファイルには紹介文だけを入れる）、review_codes（6つのコード）、そして hard では no_description（紹介文がない：NO_DESCRIPTION、仮の文は決して入れない）、conflict（同じ段階の年が食い違う：CONFLICT）、generic_titles（汎用的なファイル名は書名ではない：NO_TITLE）。

以前の事実 precedence、encodings、year_notations、author_variants、duplicates、containers、scoring と、exceptions のうち上に挙げなかった部分は、もうAIが確認すべき事実ではありません。サンプルに見えるデータ上の事実であるか、関わる本が少なすぎてスコアを左右しないからです（GT.md にそれぞれで失う点数の上限を載せています。REVIEW.md の「正解の監査」も参照）。これらは requirements.md に残っており、尋ねられれば顧客は答えます。

質問の価値（監査、公開ワールド）：一度も尋ねないプログラム（robust_solution：固定の事実はすべて模範解答と同じ読み方、抽選されるルールはそれぞれ最初の候補、名前の上限は最も長いもの、そしてコードを知りえないので確認行はなし）は、easy / medium / hard で品質点の平均 0.31 / 0.34 / 0.36 を得ます。したがって質問の価値は品質点の 0.69 / 0.66 / 0.64 です。

採点

採点する本ごとに：正しいライブラリのパスに正しい紹介文があれば 1、正しい紹介文がほかのパスにあれば 0.4（置き場所の誤り：チームが探して移す必要がある）、正しいパスに別の文章があれば 0.2 です。確認に回すべき本は、その本のファイルのどれかを挙げる一覧の行がすべて review で理由コードが正しければ1（すべて同じ別のコードなら0.4、確認方針では NO_AUTHOR の本は確認で0.7）で、行どうしが食い違う場合やその本のライブラリファイルもある場合は0です。ライブラリに並べるべき本は、確認に回すと0点です。配架方針では著者のない本もこれに当たり、その本の期待される著者は抽選された代替の名前です。各本の一覧の行も確認します（その本のファイルを挙げる唯一の行で、ファイルをすべて挙げてほかは挙げないこと。placed とその本のライブラリのパス、または review とファイルの _review/ 以下へのバイト単位のコピーがそろっていること。読めるファイルと重複するスキャンは、その行に入れても、skipped として載せても、省いてもかまいません）。行がない、または誤っている場合は、その本の点数の5分の1を失います。medium と hard では本でないライブラリのファイル1つにつき0.5を引きます。目的値 = 100 × 点数 / 採点する本の数（最大化）で、品質は従来のやり方（0）と模範解答（1）の間で正規化し、quality_cap は1.0です（模範解答が達成できる最高だからです）。紹介文は NFKC のあと空白をすべて除いて比べるので、改行位置は影響しません。hard では、空でないライブラリのファイルが、どの本の紹介文の段落も丸ごとは含まず、紹介文の断片（20文字以上）でもない場合にも no_fabrication が発動します。仮の文や作った紹介文がこれに当たり、見出しが1つ残っていたり段落が1つ抜けていたりするだけなら点数を失うだけです。

出力を必須の成果物にするルールは2つです。manifest_rows（ライブラリのファイルはどれもちょうど1つの placed 行のパスで、placed 行のパスはどれもライブラリのファイルであり、その行の source はドライブのファイル、アーカイブ内の項目、目録の行のうち少なくとも1つを挙げる。アーカイブ内の項目と目録の行は、アーカイブや目録のパスのあとに !、/、:、#、| のどれかを付けて書く。同じ情報源を2つの行に挙げない）と、review_copies（確認行に挙げたドライブのファイルは、すべて _review/ の下にコピーする）です。no_guessing（hard）は、依頼の「推測せず」を必須条件にします。情報源から書名や年が決まらない本（NO_TITLE、NO_YEAR、CONFLICT）は並べません。

score() は、適用中の事実ごとに enforced と evidence も報告します。これが直接の検査で、採点用のドライブでのプログラムの同じ実行から計算します（GT.md の第5部）。極端に単純なプログラム（case.py の shortcuts()、GT.md の第2部）は、無効になるか最高でも0.42です：すべてを確認に回す、確認行を大量に書く、正しいパスに仮の文やファイルの全文を置く、ヘッダーだけの一覧、placed 行の source が空か自分のライブラリのパスである一覧、コピーなしの確認、すべての本を3つのパス構成すべてで置く、ドライブをそのままコピーする、平らな library/<書名>.txt。直接の検査は、これらを正しいプログラムとも区別します。平らなパスは layout、正しいパスの仮の文は content、並べても確認に回してもいない著者のない本は missing_author が反映されていないとみなされます。hard では、確認行を1行も書かないプログラムは review_codes が反映されていないと判定されます（easy と medium では確認に回すべき採点対象の本がないので、None のままです）。1冊の紹介文を丸ごと含み、そのまわりにほかの文章もあるライブラリの余分なファイル（どのルールも与えないパスに置いたカード）は、スコアの上ではやはりどの本のファイルでもありませんが、直接の検査はそれをその本のファイルとして読みます。そのため2つの事実を読み違えたプログラムは、両方の事実について「反映されていない」と判定されます。監査は、模範解答でも事実を一つだけ取り違えた解答でもない成果物（正解キー、従来のやり方、robust_solution）でも直接の検査を試します（GT.md の第5部、REVIEW.md の「ほかの成果物での直接の検査」）。このケースには、必要なときだけ計算する diagnose() フックはありません。直接の検査は軽いので score() の中で計算します。

採点用のコーパスでのプログラムの出力はプログラムのダイジェストをキーにキャッシュされるので、各設定、違反例、パラメータの影響のチェックとティア間のチェックは、異なるプログラムごとに1回だけ実行されます（既定のワールドシード 1–3 で validate-case は約3分、audit-case は約8〜10分かかります）。

模範解答と検証済みの数値（シード 20261027、採点用のコーパス）

従来のやり方（reference/baseline.py + 同じ config.json）は、顧客がエンジニアなしで書けるスクリプトです。完全な UTF-8 の JSON 書き出し（書名、著者、ふつうの4桁の年、紹介文）がある本だけを目録の規則どおりにライブラリに並べ、同じ ISBN の ONIX 書き出しもある JSON の記録はチームに残し（2つのどちらが正しいか判断できないため）、ほかのファイルもすべてチームに残します（ほかの形式、古いエンコーディング、元号の年は扱わず、コピーを統合せず、確認エリアもありません）。どの設定でも有効です。

模範解答（reference/organize.py + その設定の config.json）は完全な整理プログラムです。すべての形式と zip の中の項目、コーパス自身の UTF-8 文字統計による古いエンコーディングの判定、すべての年の表記（元号、民国紀年、檀紀、漢数字、ローマ数字、© の行）、NFKC で正規化したパス名（スラッグ）、正規化した書名によるグループ化、本のすべてのファイルにまたがる項目ごとの優先順位、ドライブのどこかにある各著者の正式な名前の対、同じ段階の年の衝突、スキャン、不要ファイル、目録に対応し、抽選された著者のない本の方針に従います。採点用のコーパスのどの本も expected_output とまったく同じように並べるので、どの設定でも objective_bound に達し、quality_cap は1.0です。これまでに見つかった最善の解答（best_known_solution、監査用）は、正解キーそのものをプログラムで書き出したもので、やはり限界値に達するオラクルです。模範解答とは別の、すべてを知っている2つ目の成果物で、直接の検査がこれを反映されていないと判定することがあってはなりません。

レビュー — data_knowledge/multilingual_corpus_curator

ケースレビューの指摘事項（F1–F9）と、今回の変更でそれぞれにどう対応したかをまとめます。特に断りがない限り、数値はシード 20261027 の採点用のコーパス（AIには渡さない）でのもので、ルールセット A、B、C で同じです。未対応の提案へのコメントを歓迎します。その後の変更で、3つのルールセットは、ライブラリ規則をそれぞれプールから抽選するルールシードに置き換えられました（末尾の「ルールシード」の節）。この変更は F3、F4、F9 に関わり、「ルールシード」で始まる補足にその公開ルールシード（シード11、18、21）での数値を示します。
