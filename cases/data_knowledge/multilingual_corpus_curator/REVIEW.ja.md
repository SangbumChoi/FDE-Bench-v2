# レビュー — `data_knowledge/multilingual_corpus_curator`

ケースレビューの指摘事項（F1–F9）と、今回の変更でそれぞれにどう対応したかをまとめます。特に断りがない限り、数値はシード 20261027 の採点用のコーパス（AIには渡さない）でのもので、ルールセット A、B、C で同じです。未対応の提案へのコメントを歓迎します。その後の変更で、3つのルールセットは、ライブラリ規則をそれぞれプールから抽選するルールシードに置き換えられました（末尾の「ルールシード」の節）。この変更は F3、F4、F9 に関わり、「ルールシード」で始まる補足にその公開ルールシード（シード11、18、21）での数値を示します。

### F1 — 確認行を大量に書けば確認の点数が取れる（高、確認済み）

以前は、確認に回すべき本は自分のファイルのどれかに触れる `review` 行のうち最も良い点数を得て、ライブラリに並べるべき本の行は無視され、確認に回すべき本がライブラリにも並んでいても何も失いませんでした。hard でコーパスのファイルごとに6つの理由コードを1行ずつ書くと、確認行を除いた `expected_output` が88.0から99.4（取りうる最高の値）に、確認ロジックを除いた模範解答が76.2から87.6に上がり、模範解答自身の85.6を上回りました。`(scan).pdf` のコピーを確認に回しても代償はありませんでした。

**状況：** 今回の変更で修正済み — 一覧の source は完全な参照（`path`、`archive.zip!member`、`catalog.csv#row`）として照合するようになりました。確認に回すべき本が点数を得るのは、そのファイルを挙げるすべての行が `review` で同じ1つのコードを付けている場合だけで（1、別のコードで一致していれば0.4、`NO_AUTHOR` は0.7）、行どうしが食い違う場合やその本のライブラリファイルもある場合は0です。ライブラリに並べた本のファイルが別の行にも出てくると、その本は点数の5分の1を失い（F5）、重複スキャンを確認に回した本も同様です。確認行を大量に書く試験提出（プローブ）は現在、hard で71.6（`expected_output`）と62.16（確認ロジックを除いた模範解答）、easy と medium ではすべての本が5分の1を失います（`expected_output` 80.0、模範解答 80.0 / 74.18）。5つのロケールすべての文書で、確認行の判定方法を説明しています。未対応：スパム提出に対する検証器のチェック（プローブは README.md にあります）。

正解の監査：解決済みで、確認もしました。確認行のスパムが無効になるようにケースを変えました。`manifest_rows`（契約上、すべてのティア）が同じ情報源を2つの行に挙げることを禁じるので、近道 `review_spam`（模範解答に、ドライブのファイルごとに確認行を6つ加えたもの）は、測定した45設定すべてでこのルールに違反します。

### F2 — 仮の紹介文で60%が取れ、どのルールにも違反しない（高、確認済み）

以前は、正しいパスに誤った文章があるファイルが0.6を得て、`no_fabrication` が発動するのは紹介文のない本と空のファイルだけでした。`expected_output` のライブラリファイルすべてに `x` と書くと、違反なしで 60.0 / 60.0 / 64.2 になり、中心となる内容の課題である紹介文の抽出には1冊の40%の価値しかありませんでした。

**状況：** 今回の変更で修正済み — 正しいパスに別の文章がある場合は0.2になりました（`WRONG_DESC_CREDIT`）。hard では、空でない正しい UTF-8 のライブラリファイルが、どの本の紹介文の段落も丸ごとは含まず、20文字以上の紹介文の断片でもない場合にも `no_fabrication` が発動します。仮の文、作った紹介文、文字化けしたデコード結果の大半はルール違反になり、見出しが1つ残っていたり段落が1つ抜けていたりするだけなら点数を失うだけです。`x` のプローブは現在 20.0 / 20.0 で、hard では無効です。5つのロケールすべてで、要件、AIが確認すべき事実、ルールの文言にそのことを書きました。違反例 `fabricate` と `utf8` は引き続き自分のルールだけに違反します（UTF-8 でないファイルが、作った文としても数えられることはありません）。

正解の監査：解決済みで、確認もしました。`x` のプローブは近道 `placeholder_text`（すべての本を正しいパスに置き、仮の文を入れる）で、有効な場合（easy と medium）の最高の品質は0.080、hard では無効です。各本の最初のファイルの全文を書く近道（`whole_text`）も同じスコアです。置き場所の誤りを一律の点数にしても（下記）、正しいパスに別の文章がある場合は引き続き0.2です。

### F3 — 模範解答は意図的に弱く、ティアごとに加わるスキルが報われていなかった（高、一部確認）

このレビューは品質が1.0で頭打ちになっていた時点で書かれ、完璧なプログラムも模範解答も1.0でした。新しい尺度は従来のやり方（0）と模範解答（1）の間で正規化し、1を超えても切り捨てないので、改善余地が見えるようになりました。取りうる最高の出力ツリー（`expected_output`）の正規化品質は easy で1.00、medium で1.09、hard で1.18（`NO_AUTHOR` の例外ありで1.19）です。その結果、逆の問題が生じます。方針の品質上限が1.5だと、完璧なプログラムでも品質点の最大 0.67 / 0.73 / 0.79 しか得られず、easy には改善余地がまったくありません（模範解答がすでに完璧なため）。

**状況：** 未対応 — 提案：ケースは自分の最善解を知っているので、そこから `quality_cap` を決めます。ケース全体で1つの値では easy（1.00）と hard（1.18）の両方には合わないため、フレームワークがティアごとの上限に対応するか、ケースが1.18に設定して easy と medium が満点に届かないことを受け入れるかのどちらかです。easy については、名前の長さの切り詰めや共著者の扱いが必要な形式の整った本を数冊加えて、模範解答が最初から完璧にならないようにするか、easy は質問による要件確認の力だけを測ると明記します。模範解答を完全な仕様（zip、ローマ数字と漢数字の年、著作権表示の年、衝突、著者の対応表）まで強化すると、DIRECTION が求める改善余地がなくなるため、推奨しません。
ルールシード：内容は変わりません。取りうる最高の出力ツリーは、easy と medium ではどの設定でも 1.00 / 1.09 に達し、hard では著者のない本の2つの方針のどちらでも1.18です（確認方針：模範解答の85.60に対して99.40、配架方針：86.20に対して100.00）。medium と hard のより厳しい長さのプールは改善余地を生みません。模範解答が切り詰めを正しく適用するからです。引き続き未対応です。

正解の監査：解決済み。上の立場を改めました。フレームワークは今では `quality_cap` をこれまでに見つかった最善の解答から決めるので、より良いプログラムに報いるために模範解答の上に改善余地を残す必要はもうありません。また、弱い模範解答のために、品質の尺度も、事実を一つだけ取り違えた解答も、間違った基準点から測られていました。模範解答は今ではすべての穴をふさぎ（zip の中の項目、ローマ数字と漢数字の年、`©` の行、同じ段階の衝突、ドライブ全体の著者の対応表）、採点用のコーパスのどの本も `expected_output` と同じように並べます。測定した45設定すべてで `objective_bound`（証明された上限）に達し、これまでに見つかった最善の解答であり、`quality_cap` はどのティアでも1.0です。そのため、ケース全体で1つの上限を使うことによる easy と hard の食い違いはなくなりました。

### F4 — 唯一の誘惑（`missing_author_review` の緩和）が厳密に劣った選択で、イベントも圧力もない（中、確認済み）

著者のない2冊を代替の著者名で並べると hard で86.20（正規化1.008、上限1.5で品質点が +0.005）で、それを許す方針のもとでの `soft_rule_penalty` は0.05–0.1です。プログラムは1回しか実行されず、ケースには日付の決まったイベントも、緩和を迫るステークホルダーもいません。

**状況：** 未対応 — 提案：緩和を本当のトレードオフにします。たとえば発売日を控えた営業担当者が、不確かな本や著者のない本を6–10冊並べるよう求め、`startup_velocity` のもとでは利得がペナルティを上回りうるようにします。あるいは `NO_AUTHOR` の確認を1.0で採点し、誘惑を `CONFLICT` の年の推測に移します。日付の決まったイベントを少なくとも1つ加えます。版権チームからの修正版 ONIX 書き出しや、目録チームがやり取りの途中で共著者の規則を変えることなどで、プログラムが変更を取り込まなければならないようにします。
ルールシード：著者のない本の方針は hard で抽選されるパラメータになったので（`no_author`：確認に回すか、「Unknown」または「Anonymous」の名前で並べる）、エージェントは今回の方針が何かを確認しなければならず、`missing_author_review` は確認方針のもとでだけ適用されます（公開ルールシードでは hard/s18）。その方針のもとでは、緩和は依然として劣った選択です（86.20 対 85.60、正規化1.008）。日付の決まったイベントや圧力は加えていません。どちらも今回の変換の範囲を超えるコーパスやフレームワークの変更が必要です。引き続き未対応です。

正解の監査：引き続き未対応。著者のない本の方針は今では両方の方針のもとで hard のルールです（配架方針のもとでは `missing_author_shelved` により、確認に回すか別の名前で並べると無効）。そのためエージェントは hard のどの設定でもこれを尋ねなければなりません。確認方針のもとでは、緩和は依然として劣った選択です（100.00 対 99.40、正規化品質1.007）。日付の決まったイベントや圧力は加えていません。

### F5 — 一覧と `_review/` はほとんど採点されていなかった（中、確認済み）

以前は `manifest.csv` の列名だけを確認し、読むのは `review` 行だけでした。ヘッダーだけの一覧で `_review/` フォルダもない `expected_output` が 100 / 100 / 88.0 になり、並べた行の source と path をすべてでたらめな値に置き換えても 100 / 100 / 99.4 でした。

**状況：** 今回の変更で修正済み — 採点する本ごとに一覧の行を確認します。その本のファイルを挙げる唯一の行であり、ファイルをすべて挙げてほかは挙げず（読めるファイルと重複するスキャンは、その行に入れても、`skipped` として載せても、省いてもよい）、`placed` とその本のライブラリのパス、または `review` とすべての元ファイルの `_review/` 以下のどこかへのバイト単位のコピーがそろっていなければなりません。行がない、または誤っている場合はその本の点数の5分の1を失い（`MANIFEST_SHARE`）、これによりライブラリそのものが引き続き主要な成果物となります。プローブは現在 80.0 / 80.0 / 70.4（ヘッダーのみ）と 80.0 / 80.0 / 81.8（でたらめな placed 行）です。模範解答は何も失わず（行が正しいため）、`expected_output` は引き続き 100 / 100 / 99.4 で、指標 `manifest_rows_wrong` が該当した本を数えます。不要ファイルの `skipped` 行は、要件で任意とされているので引き続き採点しません。

正解の監査：解決済みで、ルールとして直接強制しています。一覧と確認エリアは、今ではどのティアでもルールによる必須の成果物です。`manifest_rows`（ライブラリのファイルはどれもちょうど1つの placed 行のパスで、placed 行のパスはどれもライブラリのファイルであり、同じ情報源を2つの行に挙げない）と `review_copies`（確認行に挙げたドライブのファイルは、すべて `_review/` の下にコピーする）です。近道 `no_manifest`（ヘッダーのみ）と `no_review_copies` は、測定した45設定すべてで無効です。以前は、失うのはせいぜい1冊の点数の5分の1でした（品質は hard で0.97、確認に回す本が範囲外の easy と medium では1.0）。

監査の敵対的チェック：上のでたらめな source のプローブは、まだ未対応でした。模範解答のライブラリと、パスはそのままで source が空の（または自分のライブラリのパスを source にした）placed 行を使うと、一覧は `manifest_rows` を通り、プログラムの品質は 0.76 / 0.77 / 0.80 でした。監査がふさいだヘッダーだけの一覧と同じ点数です。`manifest_rows` は今では、どの placed 行の source もドライブのファイル（またはそのアーカイブの実在する項目か、その目録の実在する行）を少なくとも1つ挙げることも求めます。2つのプローブはどちらも近道（`sourceless_manifest`、`path_as_source`）で、測定した45設定すべてで無効です。

### F6 — 韓国語：ぎこちないパラメータの差し込み位置と、3つのものを指す1つの語（中、確認済み）

レンダリングした韓国語の要件には `<연도>는 초판이 처음 나온 연도이며`（同語反復）、`<저자>는 첫 번째 저자만입니다`、`모든 저자를 순서대로 " & "로 연결입니다`（非文）、`밑줄 _(으)로`、`일반 공백 하나(공백 유지)(으)로`、`"Unknown"로` がありました。`목록` が一覧（manifest）、目録 CSV、出版社の目録のすべてを指し、`목록팀` は不自然で、`Markdown 머리말` は「序文」と読めてしまいました。

**状況：** 今回の変更で修正済み — 韓国語のラベルは、テンプレートがそのまま文を終えられる完結した節になりました（`첫 번째 저자만 씁니다.`、`모든 저자를 순서대로 " & "로 이어 씁니다.`、`원래 문자로 씁니다. …`、`로마자로 씁니다. …`）。年の基準は `초판 발행 연도` となり、区切り文字は自分の助詞を伴い（`밑줄 _ 하나로`、`하이픈 - 하나로`、`일반 공백 하나로(공백은 그대로 둠)`）、代替の著者名は `라고` で引用するので、助詞が値に左右されません。用語は 매니페스트（manifest.csv）、카탈로그 CSV（目録 CSV、整理メモでも同じ）、저희 도서 목록（出版社の目録）に統一し、`도서 목록 담당팀` と `프런트매터` が `목록팀` と `머리말` に代わりました。9つの設定すべてをレンダリングして読みましたが、ネイティブスピーカーによる確認はまだ行う価値があります。

正解の監査：変更なし（新しい事実、ルール、概要の文を除いて韓国語の文言には手を加えておらず、それらも同じ用語 매니페스트、카탈로그 CSV、저희 도서 목록 で書きました）。

### F7 — ありそうにない紀年表記、何でも知っている顧客、AIが確認すべき事実として採点されるデータ上の事実（中、確認済み）

檀紀の年が2014年と2025年の本の JSON の項目に現れ、民国紀年が北京オフィスの簡体字中国語の本に、ローマ数字が出版社のメタデータに現れます。「誰も整理してこなかった」ドライブの顧客が、コードページ、不要ファイルの名前、行の決まりをすべて挙げてみせます。AIが確認すべき事実の `encodings`、`year_notations`、`duplicates`、`containers` はサンプルで見えるので、質問せずデータから見つけたエージェントは Ask-F1 を失います。ISBN は979にランダムな数字を続けたものです（検証者がレビューを訂正しました：採点用のコーパスの ISBN 36件のうち6件は 979-0 の ISMN の範囲にあり、大半は割り当てのない979のグループにあります）。

**状況：** 未対応 — 提案：紀年表記はもっともらしい場所にだけ残します（日本語の奥付の和暦、民國は台北オフィスの繁体字中国語の本だけ、檀紀やローマ数字はせいぜい古い扉ページや © の行に限り、JSON の書き出しには入れない）。顧客が知っていることは方針と好み（パス構成、年の基準、確認の方針、衝突）に限り、データから見つけられる4つの事実は targets.yaml から外すか確認のみの事項として印を付け、データから対処したエージェントを審査役が減点しないようにします。ISBN の接頭辞には 978- か 979-8 以上を使います。これらはコーパスとAIが確認すべき事実を変えるので、ケースオーナーが判断することです。

正解の監査：事実については解決、コーパスについては未対応。`encodings`、`year_notations`、`duplicates`、`containers` はもうAIが確認すべき事実ではなく（背景として requirements.md に残っています）、`author_variants` と `precedence` も同様です。この2つが関わるのは5冊と3冊で、hard で品質点の10分の1を失うことはありえません。残る事実は顧客だけが知っていることです（ライブラリの規則、ファイルの中身、6つのコード、著者のない本の方針、推測してはいけないこと）。紀年表記のもっともらしさ、何でも知っている顧客、ISBN の接頭辞は変わっていません。

### F8 — 採点用のコーパスが同じ閉じた生成器から作られている（低、一部確認）

採点用のコーパスは `build_corpus(seed + 7919)` で、種類ごとの件数は同じに固定されています。120のパスのうち12がサンプルと共通です：zip 2つ、目録2つ、不要ファイル、スキャンだけの本2冊（`scans/scan_0107.pdf`、`scans/scan_0109.pdf`）。残る108のパスは異なるため、サンプルをハードコードして通用するのはこの12件だけです。

**状況：** 未対応 — 提案：種類ごとの件数を小さな範囲から抽選し、アーカイブ・目録・スキャンの名前とカウンタのオフセットをランダムにし、要件には書かれているがサンプルにはない変種をいくつか（昭和の年、3つ目の目録ヘッダーの形式、zip の中の入れ子のフォルダ）採点用のコーパスに入れます。

正解の監査：一部解決。アーカイブと目録の名前は小さなプールから選ばれ、番号付きのファイル名はコーパスごとにランダムなオフセットから始まります。公開ワールドでは、採点用のドライブがサンプルと共有するパスは12ではなく不要ファイルの4つだけになり（サンプルには `inbox_archive_2020.zip`、`laptop_export_2018.zip`、`catalog_export_2023.csv`、`東京_目録.csv`、採点用のドライブには `backup_2019.zip`、`old_drive_backup.zip`、`rights_desk_titles.csv`、`目録_2022.csv` があります）、ワールドシード 1-3 ではそれ以外に共有するのはせいぜいアーカイブの名前1つで、中身は別です。採点用のドライブには、昭和の年と、フォルダが1段深い zip の中身が必ず入っています。種類ごとの件数は引き続き固定です。件数を抽選すると、スコアを左右するかどうかのしきい値を測る基準であるティアの規模が変わってしまうからです。

### F9 — medium の範囲の文言、ほとんど効かないパラメータ、「ask」のヒント（低、一部確認）

medium の要件は例外を「まだ確認しない」としていましたが、本でないライブラリのファイル（不要ファイル、目録 CSV 丸ごと）は medium で0.5を失います。評価方法の節ではその減点を明かしていました。C の `max_len` 80 が効くのは 0 / 2 / 3 冊だけ、`fallback_author` は劣った緩和を通してしか意味を持たず、ルールセットどうしは一度に5–7個のパラメータが異なり、`deliverable_spec` には「the folder layout and file naming are the client's: ask」と書かれています。

**状況：** 文言は今回の変更で修正済み — medium は現在、5つのロケールすべてで、例外は「まだ採点しないが、本でないものをライブラリに入れてはいけない」と述べています。ほかの点は未対応 — 提案：どのティアでも効く `max_len` の値を選び（例：24 / 32 / 48、または長い副題を増やす）、ルールセットの1組はパラメータ1つだけが異なるようにして誤った前提の原因を特定できるようにし、`deliverable_spec` から「ask」を外し、実際の目録規則のように名前を単語の境界で切ることを検討します。
ルールシード：単語の境界での切り詰めを除いて修正済みです。`max_len` はティアごとのプールから抽選され、どの値も副題付きの書名のうち最も短いものより小さいので、すべての値が結果を左右します：easy 60 / 48 / 40（副題付きの書名3つを値ごとに異なる位置で切る）、medium 50 / 40 / 32（7–11冊）、hard 40 / 32 / 24（9–21冊）。hard/s11 で24の代わりに40文字の上限を使うと模範解答は86.20から81.60に、easy/s11 で40の代わりに60を使うと100.00から98.00になります。`fallback_author` はもう単独では抽選しません（2つの名前の間で模範解答の動きは0.4で、影響の基準1%に届かなかった）。代わりに、抽選された著者のない本の方針から導かれ、その方針は結果を左右します（hard/s11 から確認方針にすると模範解答が無効）。各パラメータは単独で抽選され、validate-case が1つずつチェックするので、誤った前提を1つのルールに帰することができます。`deliverable_spec` は現在、5つのロケールすべてで、パス構成とファイル名の付け方は「顧客の目録ルールに従う」と述べています。

正解の監査：パラメータについては解決。置き場所の誤りを一律の点数にし、副題と共著者を増やしたことで（下記）、抽選されるどのパラメータも、値が変わるすべてのティアの測定したすべての設定でスコアを左右します（それだけを読み違えると品質点の少なくとも10分の1を失う）。`no_author` は2つの方針のルールを通じてスコアを左右します。単語の境界での切り詰めは行っていません。

**従来のやり方：** `reference/baseline.py` は完全な UTF-8 の JSON 書き出しがある本だけを目録の規則どおりに並べ、ほかのファイルはすべてチームに残します。どのルールセットでも、模範解答の100.00に対して10.00（easy）、92.73に対して13.33（medium）、85.60に対して10.80（hard）です。ワールドシード 1–3 では 6.7–20.0 / 8.2–13.3 / 5.4–8.8 で、模範解答は 100.00 / 94.24–95.76 / 86.60–87.60 です。ルールシード：公開ルールシードのどの設定でも同じですが、配架方針のもとの hard の模範解答だけは異なります（公開ワールドで86.20、ワールドシード 1–3 で 87.20–88.20）。従来のやり方は著者のない本を並べないので、その数値は動きません。

## ルールシード

ケースオーナーは、固定のルールセット A / B / C をルールシードに置き換えました。case.yaml は顧客だけが知っているライブラリ規則ごとに候補プールを宣言し、ルールシードは各パラメータを独立に抽選し、レポートはティアごとにルールシードの平均を出します。変更点は次のとおりです。

- **プール。** `layout`（以前の3つのパス構成）、`year_basis`（first、edition）、`script`（original、latin）、`multi_author`（first、all）、`sep`（`_`、`-`、スペース）は以前の値を保ったまま、自由に組み合わされるようになりました（3通りではなく72通り）。`max_len` にはティアごとのプール 60 / 48 / 40、50 / 40 / 32、40 / 32 / 24 があり、難しいティアほど多くの名前にかかる厳しい上限を抽選します（F9）。`no_author` は新しいパラメータで、hard にだけ候補があります：`review`（以前の方針。例外が認められれば「Unknown」で並べる）、`Unknown` または `Anonymous`（目録担当チームが、著者のない本をその名前で並べることに同意した）。`fallback_author` はここから導かれます。これで easy と medium は216通り、hard は648通りの組み合わせになります。
- **公開ルールシード。** ルールシード11、18、21に、すべてのプールのすべての候補が現れます。（ティア、シード）ごとの抽選された辞書、模範解答、従来のやり方、取りうる最高の目的値は README.md にあります。3つのティアの模範解答はどの公開シードでも互いに異なるようになり（長さの上限、さらに hard/s11 と hard/s21 では方針）、ティアの模範解答がバイト単位で同一だという検証器の警告がなくなりました。それぞれの模範解答を別のティアで採点すると、そのティア自身の模範解答より1.8–6.6点低くなります。
- **テキスト。** 5つのロケールすべての要件と事実 `missing_author` には、2つの方針についての `<!-- when: no_author=... -->` の段落（方針の文、その採点、必須条件）があります。例外の一覧は、`NO_AUTHOR` を名指しする代わりに方針を参照するようになりました。`missing_author_review` には `when: {no_author: [review]}` があり、その違反例はその方針のもとでだけ存在します。ティアの説明とその翻訳は、ティアごとの長さのプールと、hard では方針を明記しています。
- **コード。** `_View.review_of` が、その設定での各本の確認コードを返します（配架方針では著者のない本は並べられるので、確認に回すと0点）。模範解答は config から `no_author` を読みます。以前の修正（F1、F2、F5、`no_fabrication` のチェック）はすべてそのままです。
- **チェック。** `validate-case`（ワールドシード 1、2、3）は警告なしで通ります。どのパラメータも hard/s11 から結果を左右し、すべての公開設定の模範解答は品質1.0、従来のやり方は0で、公開ワールドとワールドシード 1–20 では、プールのどの組み合わせでも並べる本2冊が同じパスになることはありません。

- **チェック担当者による確認。** ワールドシード 20261027、1、2、3 で、ルールシード4–10を公開ルールシードに加えて（120の設定）確認しました：どの設定でも模範解答は品質1.0で有効、従来のやり方は有効でそれより低くなっています（従来のやり方は模範解答の最大0.20）。エージェントの見え方は、公開ワールドの30の設定すべてで、5つのロケールすべてにわたりバイト単位で同一です。`multi_author: first` の中国語の文言は要件と事実で「`<作者>` 为只写第一作者」となっていましたが、ラベルは `第一作者（只写一位）` になりました。採点の設計上、引き続き未対応の点：配架方針どうしでは、2つの名前の違いは著者のない2冊の著者部分だけなので（0.4点、hard の模範解答の0.46%）、`Unknown` 対 `Anonymous` だけでは影響の基準1%を超えません。このパラメータは `review` を通じて結果を左右します。

## 正解の監査

ケースオーナーは、ケースを増やす前に正解（GT）と採点を強化するよう依頼しました。データと依頼がどの設定でもバイト単位で同一の1つのワールドを保ち、顧客だけが知っている要件が正しい答えを決める形はそのままです。このケースは今 `audited: true` です。`dataset/audit.json` がその監査（`fdebench2 audit-case`、公開ワールド、45設定：各ティアの公開ルールシードに、許容されるパラメータの組み合わせ12通りを加えたもの）、`GT.md` はそこから生成した5部構成の正解、`CLIENT_REVIEW.md` はシミュレーションの顧客が各事実に答えるときのもとになる文章です（状態：人による確認待ち）。どちらも `gt_report.py` が書き出します。上の F1-F9 の「正解の監査」の補足に、各指摘事項の新しい状況を示しています。

変更点を、作業した順に示します（模範解答を改善する前に近道をふさぎました）。

- **近道と必須の成果物。** `shortcuts()` は9つの極端に単純なプログラムを挙げます。3つはふさがれていませんでした。ヘッダーだけの一覧（easy で品質0.78）、コピーなしの確認（easy と medium で1.0、hard で0.97）、正しいライブラリの上に F1 のスパムを加えたもの（easy で0.78）です。一覧と確認エリアは、今ではどのティアでもルールによる必須の成果物です。`manifest_rows`（一覧はライブラリの索引：ライブラリのファイルはどれもちょうど1つの placed 行のパスで、placed 行のパスはどれもライブラリのファイルであり、同じ情報源を2つの行に挙げない）と `review_copies`（確認行に挙げたドライブのファイルは、すべて `_review/` の下にコピーする）です。9つとも今では、測定したすべての設定で無効になるか、最高でも0.42です（`flat_titles`、すべての本が置き場所の誤り）。
- **採点：置き場所を誤った本は0.4。** 以前は、正しい紹介文が誤ったパスにあると、0.4に、合っている要素1つごとに0.2を加えた点数でした。そのためライブラリの規則を1つ読み違えても1冊あたり0.2しか失わず、採点用のコーパスでは `co_authors` と `max_len` はどのティアでも品質点の10分の1を失うことがありえず、`year_basis` もかろうじて失う程度でした。誤った年の下に置かれた本は、誤った著者の下に置かれた本と同じように棚の上で見つからなくなり、チームが探して手で移さなければなりません。今では一律に0.4で、5つのロケールすべての評価方法の節にそう書いています。
- **コーパス：十分な数の本に関わる事実。** easy の英語とスペイン語の本は1冊おきに、ほかの本は60%が長い副題を持ち（以前は30%）、本の30%は著者が2人です（以前は18%）。そのため長さの上限と共著者の規則は、ティアごとに並べる本の5-38冊と10-30冊に関わります。書名は先頭24文字（最も厳しい上限）の中で互いに異なるままなので、どの組み合わせでも2冊が同じパスになることはありません。PDF の扉ページはもう折り返しません。著者が2人の中国語・韓国語・日本語の著者行は PDF の1行に収まる35文字より長く、折り返した行は正解に必要なローマ字表記を失っていました（共著者が多くなると、公開ワールドの採点用のコーパスで2回起きました）。F8：アーカイブ、目録、番号付きのファイルの名前はドライブごとに異なり、採点用のドライブには昭和の年と、フォルダが1段深い zip の中身があります。
- **事実：1つにつき1つの事柄で、どれもスコアを左右する（16 → 12）。** `name_rules` は `separator` と `max_len` に分けました。`manifest_review` は `review_codes` になりました（一覧の形式とコピーはプログラムのインターフェースにあり、今ではルールにもなっています）。`exceptions` は `no_description`、`conflict`、`generic_titles` に分けました。外したもの（背景として requirements.md に残す）：`encodings`、`year_notations`、`duplicates`、`containers`（サンプルに見えるデータ上の事実、F7）、`author_variants` と `precedence`（5冊と3冊：読み違えても hard で品質点の10分の1を失うことはありえない）、`scoring`（正しい成果物を何も変えない）、そして `exceptions` の残り（項目の補完、意味のあるファイル名、`©` の年：データの自然な読み方で、それぞれ2-3冊）。GT.md にそれぞれで失う点数の上限を載せています。抽選される7つの事実は en/targets.yaml に `param:` を持ち、ほかの5つには `ablations()` に読み違えがあります。
- **顧客の「推測せず」を必須条件にするルール（hard）。** `no_guessing`：情報源から書名や年が決まらない本（`NO_TITLE`、`NO_YEAR`、`CONFLICT`）は並べません。`no_fabrication` と合わせて、`conflict`、`generic_titles`、`no_description` の自然な読み違えは無効になります。依頼（「推測せず、当社のチームが確認できるよう別にしておいてください」）が含意するとおりです。`missing_author_shelved`（業務慣行、配架方針のときだけ）：著者のない本を確認に回さず、別の名前でも並べません。`missing_author_review` と対になるルールで、これにより `missing_author` は確認方針のときだけでなく、どの方針のもとでもスコアを左右します。従来のやり方は今では、食い違う年で本を並べる代わりに、同じ ISBN の ONIX 書き出しもある JSON の記録をチームに残します（どちらの書き出しが正しいか判断できないため）。
- **模範解答と限界値。** 模範解答は意図的に残していた穴をすべてふさぎ（zip の中の項目、ローマ数字と漢数字の年、`©` の行、同じ段階の衝突、ドライブ全体の著者の対応表）、公開ワールドとワールドシード 1-3 で、採点用のコーパスのどの本も `expected_output` とまったく同じように並べます。`best_known_solution` は模範解答です。`objective_bound` は証明された上限で（採点する本1冊につき1、確認方針のもとの著者のない本は0.7、ペナルティは引くだけ）、測定したどの設定でも限界値までの差は0です。`quality_cap` は1.0です（どの設定でもこれまでに見つかった最善の品質）。
- **直接の検査。** `score()` は、採点用のドライブでのプログラムの同じ実行から、適用中の事実ごとに `enforced` と `evidence` を返します。抽選されるルールについては、そのルールが決める各本について、プログラム自身が書いたパスを、候補のすべての読み方で読み直します。ほかの事実については、その事実が関わる本（または確認行）を見ます。模範解答はどこでも成果物に反映されていると判定され、スコアを左右する、事実を一つだけ取り違えた解答はどれも反映されていないと判定されます（12の直接の検査すべてが区別します）。
- **尋ねない解法。** `robust_solution` は、固定のどの事実も自然な読み方（紹介文だけ、何も推測しない）、抽選されるルールはそれぞれ最初の候補、名前の上限はそのティアで最も長いもの（平均して最良）とした模範解答のプログラムで、6つのコードを知りえないので確認行は書きません（並べられない本は skipped として載せます）。

主な数値（公開ワールド。表は GT.md にあります）：どの事実も、それが適用される測定したすべての設定でスコアを左右します（失う点数0.112-1.000。抽選されるルールは最も害の小さい誤った値で数える）。質問の価値は、easy で品質点の0.69（一度も尋ねないと0.31、固定の事実はすべて知っているが抽選されるルールは何も知らないと0.42）、medium で品質点の0.66（一度も尋ねないと0.34、固定の事実はすべて知っているが抽選されるルールは何も知らないと0.44）、hard で品質点の0.64（一度も尋ねないと0.36、固定の事実はすべて知っているが抽選されるルールは何も知らないと0.29）です。模範解答は45設定すべてで限界値に達し（差0）、未対応の指摘事項も免除された指摘事項もありません。ワールドシード 1-3 でも、長さの上限はどの組み合わせでも失う点数0.104-0.272で（どのティアでも）、共著者の規則は失う点数0.156-0.325でスコアを左右します。validate-case はワールドシード 1-3 で通ります。

これで解決する指摘事項：F1 と F2（確認済みで、スパムは今では無効）、F3（解決）、F5（一覧と確認エリアをルールとして強制）、事実についての F7、一部の F8（名前、変種。件数は固定のまま）、F9（どのパラメータもスコアを左右する）。未対応のまま：F4（日付の決まったイベントがなく、確認方針のもとでの緩和は依然として劣った選択）、F6（ネイティブスピーカーによる確認）、コーパスについての F7（紀年表記のもっともらしさ、何でも知っている顧客、ISBN の接頭辞）、F8 の固定の件数。

### 監査の敵対的チェック

2人目のエンジニアが、コードを実行して上の監査を崩そうとしました（公開ワールド、監査の45設定）。

- **新しい近道。** チェックのために11のプログラムを書きました。2種類がふさがれておらず、今はふさがれています。

### ほかの成果物での直接の検査

実行の「成果物に反映した」段階は、事実ごとの直接の検査をエージェントのプログラムに適用します。それは模範解答でも事実を一つだけ取り違えた解答でもないので、その2つを区別できるだけでは足りません。フレームワークの監査（バージョン3）は今では、ほかの成果物でも直接の検査を試します。有効なこれまでに見つかった最善の解答での False は誤った「反映されていない」判定（問題）、スコアを左右する設定の大半でほかの事実を「反映されていない」と判定させる取り違えた解答は、ほかの事実への波及（`cross_flags`）の警告、エラーで止まる `diagnose()` フックは問題で、従来のやり方と `robust_solution` の判定は傾向として記録します。公開ワールド（45設定）で、次の変更とともに再実行しました。

- **直接の検査を行うどの評価でも、直接の検査がエラーで止まっていた。** case.py 自身の `diagnose(corpus, view, ...)` が、フレームワークの、必要なときだけ計算する新しいフックと同じ名前だったため、`evaluate(..., diagnose=True)`（実行の採点と監査）がフックの引数でそれを呼び、どの成果物でも `TypeError` になっていました（監査の `diagnose_error` の問題）。`_diagnostic` に名前を変えました。このケースには、必要なときだけ計算するフックはありません。直接の検査はプログラムの1回の実行を読むだけで軽いので `score()` の中に残し、検証器と質問の価値の行列もそれを受け取ります。
- **確認行を1行も書かないプログラムで `review_codes` が None だった。** 採点する本のうち10〜12冊を確認に回すべき hard では、今は False です。そのようなプログラムが6つのコードを使ったはずはないからです（evidence：「none in this output, though N book(s) of this tier belong in review」）。easy と medium では None のままです。そこでは確認に回すべき採点対象の本がなく、正解キー自体にも確認行がないからです（最初に試したドライブ全体での数え方では、下のプローブの easy と medium の8つの見え方すべてで、正解キーを反映されていないと判定しました）。プログラムが書く確認行は、ルールと同じく、そのティアが採点しない本のものも含めてすべて数えます。確認行を書かない従来のやり方と `robust_solution` は、今では hard で15/15が False です（以前は None）。
- **これまでに見つかった最善の解答：模範解答ではなく正解キー。** 以前は模範解答だったので、誤った「反映されていない」判定のチェックは、区別のチェックを繰り返すだけでした。今は `expected_output` を書き出すプログラムです（設定のすべての事実を持つオラクル、`best_known_solution`）。模範解答と同じく45設定すべてで有効で限界値に達しますが、別の成果物です（そのティアが採点する本だけなので、easy と medium では確認行がない）。直接の検査は、適用中のどの事実についても、これを反映されている、または None と判定します。誤った「反映されていない」判定はありません。
- **余分なパスに置いたカードが、直接の検査から本を隠していた。** 2つの事実を読み違えた成果物（模範解答と、取り違えた解答 `placeholder`、`first_source`、`filename_titles` の出力を、カードにしたもの、別のパス構成に移したもの、その両方。easy/s18、hard/s18、hard/s21）でそれがわかりました。どのルールも与えないパスに置いたカードはどの本のファイルでもなかったので、中身とパス構成を読み違えたプログラムは、ライブラリのどの規則と `content` についても None でした。カードを書き、さらに年が食い違う本や汎用的なファイル名を書名にした本を並べたプログラムは、`conflict` / `generic_titles` について反映されていると判定されました（その本が並べられていないように見えた）。そして配架方針のもとでは、著者のない本を正しく並べてはいるが、別のパス構成でカードとして置いた場合に、`missing_author` が False でした。直接の検査は今では、余分なライブラリのファイルを、その紹介文を丸ごと含み、そのまわりにほかの文章もある1冊の本のファイルとしても読みます。スコアは変わりません（余分なファイルであることに変わりはない）。そのプローブの36の成果物のどれも、今では読み違えた事実にちょうど印が付きます。
