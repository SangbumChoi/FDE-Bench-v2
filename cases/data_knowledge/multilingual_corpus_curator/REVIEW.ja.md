# レビュー — `data_knowledge/multilingual_corpus_curator`

ケースレビューの指摘（F1–F9）と、今回の変更でそれぞれにどう対応したかをまとめます。特に断りがない限り、数値はシード 20261027 の隠れたコーパスでのもので、ルールセット A、B、C で同じです。未解決の提案へのコメントを歓迎します。

### F1 — 確認行を大量に書けば確認の点数が取れる（高、検証済み）

以前は、確認に回すべき本は自分のファイルのどれかに触れる `review` 行のうち最も良い点数を得て、ライブラリに並べるべき本の行は無視され、確認に回すべき本がライブラリにも並んでいても何も失いませんでした。hard でコーパスのファイルごとに6つの理由コードを1行ずつ書くと、確認行を除いた `expected_output` が88.0から99.4（最高可能値）に、確認ロジックを除いた参照解が76.2から87.6に上がり、参照解自身の85.6を上回りました。`(scan).pdf` のコピーを確認に回しても代償はありませんでした。

**状況：** 今回の変更で修正 — 一覧の source は完全な参照（`path`、`archive.zip!member`、`catalog.csv#row`）として照合するようになりました。確認に回すべき本が点数を得るのは、そのファイルを挙げるすべての行が `review` で同じ1つのコードを付けている場合だけで（1、別のコードで一致していれば0.4、`NO_AUTHOR` は0.7）、行どうしが食い違う場合やその本のライブラリファイルもある場合は0です。ライブラリに並べた本のファイルが別の行にも出てくると、その本は点数の5分の1を失い（F5）、重複スキャンを確認に回した本も同様です。スパムのプローブは現在、hard で71.6（`expected_output`）と62.16（確認ロジックを除いた参照解）、easy と medium ではすべての本が5分の1を失います（`expected_output` 80.0、参照解 80.0 / 74.18）。5つのロケールすべての文書で、確認行の判定方法を説明しています。未対応：スパム提出に対する検証器のチェック（プローブは README.md にあります）。

### F2 — 仮の紹介文で60%が取れ、どのルールにも違反しない（高、検証済み）

以前は、正しいパスに誤った文章があるファイルが0.6を得て、`no_fabrication` が発動するのは紹介文のない本と空のファイルだけでした。`expected_output` のライブラリファイルすべてに `x` と書くと、違反なしで 60.0 / 60.0 / 64.2 になり、中心となる内容の課題である紹介文の抽出には1冊の40%の価値しかありませんでした。

**状況：** 今回の変更で修正 — 正しいパスに別の文章がある場合は0.2になりました（`WRONG_DESC_CREDIT`）。hard では、空でない正しい UTF-8 のライブラリファイルが、どの本の紹介文の段落も丸ごとは含まず、20文字以上の紹介文の断片でもない場合にも `no_fabrication` が発動します。仮の文、作った紹介文、文字化けしたデコード結果の大半はルール違反になり、見出しが1つ残っていたり段落が1つ抜けていたりするだけなら点数を失うだけです。`x` のプローブは現在 20.0 / 20.0 で、hard では無効です。5つのロケールすべてで、要件、確認すべき事項、ルールの文言にそのことを書きました。違反例 `fabricate` と `utf8` は引き続き自分のルールだけに違反します（UTF-8 でないファイルが、作った文としても数えられることはありません）。

### F3 — 参照解は意図的に弱く、ティアごとに加わるスキルが報われていなかった（高、一部検証済み）

このレビューは品質が1.0で頭打ちになっていた時点で書かれ、完璧なプログラムも参照解も1.0でした。新しい尺度はベースライン（0）と参照解（1）の間で正規化し、1を超えても切り捨てないので、伸びしろが見えるようになりました。最高可能なツリー（`expected_output`）の正規化品質は easy で1.00、medium で1.09、hard で1.18（`NO_AUTHOR` の例外ありで1.19）です。その結果、逆の問題が生じます。方針の品質上限が1.5だと、完璧なプログラムでも品質の点数の最大 0.67 / 0.73 / 0.79 しか得られず、easy には伸びしろがまったくありません（参照解がすでに完璧なため）。

**状況：** 未解決 — 提案：ケースは自分の最善解を知っているので、そこから `quality_cap` を決めます。ケース全体で1つの値では easy（1.00）と hard（1.18）の両方には合わないため、フレームワークがティアごとの上限に対応するか、ケースが1.18に設定して easy と medium が満点に届かないことを受け入れるかのどちらかです。easy については、名前の長さの切り詰めや共著者の扱いが必要な形式の整った本を数冊加えて、参照解が最初から完璧にならないようにするか、easy は質問による要件確認の力だけを測ると明記します。参照解を完全な仕様（zip、ローマ数字と漢数字の年、著作権表示の年、衝突、著者の対応表）まで強化すると、DIRECTION が求める伸びしろがなくなるため、推奨しません。

### F4 — 唯一の誘惑（`missing_author_review` の緩和）が厳密に劣った選択で、イベントも圧力もない（中、検証済み）

著者のない2冊を代替の著者名で並べると hard で86.20（正規化1.008、上限1.5で品質の点数が +0.005）で、それを許す方針のもとでの `soft_rule_penalty` は0.05–0.1です。プログラムは1回しか実行されず、ケースには日付の決まったイベントも、緩和を迫る関係者もいません。

**状況：** 未解決 — 提案：緩和を本当のトレードオフにします。たとえば発売日を控えた営業担当者が、不確かな本や著者のない本を6–10冊並べるよう求め、`startup_velocity` のもとでは得点が罰則を上回りうるようにします。あるいは `NO_AUTHOR` の確認を1.0で採点し、誘惑を `CONFLICT` の年の推測に移します。日付の決まったイベントを少なくとも1つ加えます。版権チームからの修正版 ONIX 書き出しや、目録チームがやり取りの途中で共著者の規則を変えることなどで、プログラムが変更を取り込まなければならないようにします。

### F5 — 一覧と `_review/` はほとんど採点されていなかった（中、検証済み）

以前は `manifest.csv` の列名だけを確認し、読むのは `review` 行だけでした。ヘッダーだけの一覧で `_review/` フォルダもない `expected_output` が 100 / 100 / 88.0 になり、並べた行の source と path をすべてでたらめな値に置き換えても 100 / 100 / 99.4 でした。

**状況：** 今回の変更で修正 — 採点する本ごとに一覧の行を確認します。その本のファイルを挙げる唯一の行であり、ファイルをすべて挙げてほかは挙げず（読めるファイルと重複するスキャンは、その行に入れても、`skipped` として載せても、省いてもよい）、`placed` とその本のライブラリのパス、または `review` とすべての元ファイルの `_review/` 以下のどこかへのバイト単位のコピーがそろっていなければなりません。行がない、または誤っている場合はその本の点数の5分の1を失い（`MANIFEST_SHARE`）、これによりライブラリそのものが引き続き主要な成果物となります。プローブは現在 80.0 / 80.0 / 70.4（ヘッダーのみ）と 80.0 / 80.0 / 81.8（でたらめな placed 行）です。参照解は何も失わず（行が正しいため）、`expected_output` は引き続き 100 / 100 / 99.4 で、指標 `manifest_rows_wrong` が該当した本を数えます。不要ファイルの `skipped` 行は、要件で任意とされているので引き続き採点しません。

### F6 — 韓国語：ぎこちないパラメータの差し込み位置と、3つのものを指す1つの語（中、検証済み）

レンダリングした韓国語の要件には `<연도>는 초판이 처음 나온 연도이며`（同語反復）、`<저자>는 첫 번째 저자만입니다`、`모든 저자를 순서대로 " & "로 연결입니다`（非文）、`밑줄 _(으)로`、`일반 공백 하나(공백 유지)(으)로`、`"Unknown"로` がありました。`목록` が一覧（manifest）、目録 CSV、出版社の目録のすべてを指し、`목록팀` は不自然で、`Markdown 머리말` は「序文」と読めてしまいました。

**状況：** 今回の変更で修正 — 韓国語のラベルは、テンプレートがそのまま文を終えられる完結した節になりました（`첫 번째 저자만 씁니다.`、`모든 저자를 순서대로 " & "로 이어 씁니다.`、`원래 문자로 씁니다. …`、`로마자로 씁니다. …`）。年の基準は `초판 발행 연도` となり、区切り文字は自分の助詞を伴い（`밑줄 _ 하나로`、`하이픈 - 하나로`、`일반 공백 하나로(공백은 그대로 둠)`）、代替の著者名は `라고` で引用するので、助詞が値に左右されません。用語は 매니페스트（manifest.csv）、카탈로그 CSV（目録 CSV、整理メモでも同じ）、저희 도서 목록（出版社の目録）に統一し、`도서 목록 담당팀` と `프런트매터` が `목록팀` と `머리말` に代わりました。9つの設定すべてをレンダリングして読みましたが、ネイティブスピーカーによる確認はまだ行う価値があります。

### F7 — ありそうにない紀年表記、何でも知っている顧客、確認すべき事項として採点されるデータ上の事実（中、検証済み）

檀紀の年が2014年と2025年の本の JSON の項目に現れ、民国紀年が北京オフィスの簡体字中国語の本に、ローマ数字が出版社のメタデータに現れます。「誰も整理してこなかった」ドライブの顧客が、コードページ、不要ファイルの名前、行の決まりをすべて挙げてみせます。確認すべき事項の `encodings`、`year_notations`、`duplicates`、`containers` はサンプルで見えるので、質問せずデータから見つけたエージェントは Ask-F1 を失います。ISBN は979にランダムな数字を続けたものです（検証者がレビューを訂正しました：隠れた ISBN 36件のうち6件は 979-0 の ISMN の範囲にあり、大半は割り当てのない979のグループにあります）。

**状況：** 未解決 — 提案：紀年表記はもっともらしい場所にだけ残します（日本語の奥付の和暦、民國は台北オフィスの繁体字中国語の本だけ、檀紀やローマ数字はせいぜい古い扉ページや © の行に限り、JSON の書き出しには入れない）。顧客が知っていることは方針と好み（パス構成、年の基準、確認の方針、衝突）に限り、データから見つけられる4つの事実は targets.yaml から外すか確認のみの事項として印を付け、データから対処したエージェントを審査役が減点しないようにします。ISBN の接頭辞には 978- か 979-8 以上を使います。これらはコーパスと確認すべき事項を変えるので、ケースのオーナーが判断することです。

### F8 — 隠れたコーパスが同じ閉じた生成器から作られている（低、一部検証済み）

隠れたコーパスは `build_corpus(seed + 7919)` で、種類ごとの件数は同じに固定されています。120のパスのうち12がサンプルと共通です：zip 2つ、目録2つ、不要ファイル、スキャンだけの本2冊（`scans/scan_0107.pdf`、`scans/scan_0109.pdf`）。残る108のパスは異なるため、サンプルをハードコードして通用するのはこの12件だけです。

**状況：** 未解決 — 提案：種類ごとの件数を小さな範囲から抽選し、アーカイブ・目録・スキャンの名前とカウンタのオフセットをランダムにし、要件には書かれているがサンプルにはない変種をいくつか（昭和の年、3つ目の目録ヘッダーの形式、zip の中の入れ子のフォルダ）隠れたコーパスに入れます。

### F9 — medium の範囲の文言、ほとんど効かないパラメータ、「ask」のヒント（低、一部検証済み）

medium の要件は例外を「まだ確認しない」としていましたが、本でないライブラリのファイル（不要ファイル、目録 CSV 丸ごと）は medium で0.5を失います。評価方法の節ではその減点を明かしていました。C の `max_len` 80 が効くのは 0 / 2 / 3 冊だけ、`fallback_author` は劣った緩和を通してしか意味を持たず、ルールセットどうしは一度に5–7個のパラメータが異なり、`deliverable_spec` には「the folder layout and file naming are the client's: ask」と書かれています。

**状況：** 文言は今回の変更で修正 — medium は現在、5つのロケールすべてで、例外は「まだ採点しないが、本でないものをライブラリに入れてはいけない」と述べています。ほかの点は未解決 — 提案：どのティアでも効く `max_len` の値を選び（例：24 / 32 / 48、または長い副題を増やす）、ルールセットの1組はパラメータ1つだけが異なるようにして誤った前提の原因を特定できるようにし、`deliverable_spec` から「ask」を外し、実際の目録規則のように名前を単語の境界で切ることを検討します。

**ベースライン：** `reference/baseline.py` は完全な UTF-8 の JSON 書き出しがある本だけを目録の規則どおりに並べ、ほかのファイルはすべてチームに残します。どのルールセットでも、参照解の100.00に対して10.00（easy）、92.73に対して13.33（medium）、85.60に対して10.80（hard）です。ワールドシード 1–3 では 6.7–20.0 / 8.2–13.3 / 5.4–8.8 で、参照解は 100.00 / 94.24–95.76 / 86.60–87.60 です。
