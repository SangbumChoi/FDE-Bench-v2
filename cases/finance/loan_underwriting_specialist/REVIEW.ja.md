### F2 — 「refer」は理由コードから安く逃れる手段になっている（高、確認済み）
どの申込もコスト60で人の審査に回すことができ、コードが検査されるのは否決だけです。LOW_SCORE / LIMIT_EXCEEDED / CREDIT_RISK / SPLIT_APPLICATION の否決をすべて人の審査に回すプログラムは9つの設定すべてで有効のままで、目的値は 0.942–0.977 です。金額調整を加えると5つの設定で 1.0 以上に達します。模範解答は設定ごとに153–265件を CREDIT_RISK、31–82件を LIMIT_EXCEEDED で否決しているので、プログラムは最も間違えやすい計算、つまりその日の承認後に残る枠の計算を省けてしまいます。

**状況：** 未対応 — 提案：業務上の事実として人の審査を希少なものにします。1つの方法は、審査担当者の1日の処理能力を契約上のルールとすることで、たとえば義務である勤続・不一致の回付に加えて、裁量による回付は1日最大N件とします。別の方法は、明白な否決（延滞、基準点未満、枠の残りが1,000未満）を人の審査に回してはならないというルールを設け、人の審査のコストを担当者1時間分の水準（数百）に引き上げることです。あるいは、人の審査に回す場合にも理由コードを求めます。

**更新（正解の監査）：解決済み。** 依頼元が述べる業務上の事実で解決しました。ルールが求める人の審査への回付（勤続の慣行、hard では不一致の手続き）のほかに、審査担当者が受けられるのは1日最大3件です（`referral_capacity`、契約上、すべてのロケールの requirements.md に記載）。模範解答が否決する申込（延滞を除く）をすべて人の審査に回すと、測ったすべての設定でこのルールに違反し、すべてを回しても同じです（近道 `refer_declines`、`refer_everything`）。

### F3 — いくつかのルールセットのパラメータがほとんど効いていない（高、一部確認）

**状況：** 未対応 — 提案：スコアの分布をずらす（例：平均約760、標準偏差約90）か基準点を上げて、延滞のない申込者の10–20%がそれぞれの基準点を下回るようにします。実際のPDが部分的に B社のスコアにも従うようにして、一方の機関の基準点を下回る顧客の一部が収益を生むようにします。C の収入上限をDSRから導かれる上限より低く（例：90–100%）設定するか、賞与の比重が大きい収入を加えて、各ルールセットがそれぞれ別の形で効くようにします。いずれもワールドと模範解答のすべての数値を変えるので、全面的な再調整が必要です。

**更新（ルールシード）：解決済み。** ワールドではなく候補を再調整して解決しました。基準点はA社スコアの点数で 745 / 760 / 775 から抽選され（B社では `derive_params` により 800 / 815 / 830）、延滞のない申込者482人の8–19%（39–89人）がそれを下回ります。貸付が採算割れになるスコアのあたりに位置するので、悪い貸付を防ぐと同時に良い貸付も失わせます。収入上限は 50 / 65 / 80% から抽選され、35%のDSR上限でさえ債務のない顧客に認める額（収入の約88%）より低いので、公開設定ごとに対象顧客の最初の申込38–148件で枠を決めている項になります（C の使われていなかった120%はなくなりました）。信用情報機関も引き続き効いています。検証器の拘束チェックでは、hard/s30 の模範解答はもう一方の機関のもとで無効になります。実際のPDは引き続きA社スコアだけに従います。

### F6 — 同じ日の予算削減が、それまでの承認を違反に変えていた（中、確認済み）
`period_budget` は、その日に何も承認していなくても、累計にその日の承認額を足した値がその日の予算を超えると必ず違反とされていました。pace 3.0 の模範解答でこれを再現しました。medium/C では12日目の終わりまでに3,006,233を承認し、13日目の削減以降は何も承認していないのに、「2026-11-19: 3,006,233 approved in the period > budget 3,000,000」と判定されました。hard/C も3,025,764で同じでした。A と B では1日の上限が効くので、削減前の支出はどの pace でも同じです。

**状況：** 今回の変更で修正済み — ルールは、その日の承認によって累計がその日に適用中の予算を超えた日だけを違反とするようになりました（`day_total > 0 and total + day_total > budget(d)`）。表の項目はそのまま max(0, budget − total) = 0 です。要件（5つのロケールすべて）、ルールの説明、README は、削減が以前の確定した承認を取り消さず、それ以降の承認を止めることを明記するようになりました。`violating_examples` は、medium と hard のすべての設定とワールドで、ペース配分のない模範解答（残額を超えて承認することはない）がこのルールを破らないことを確かめるようになりました。公開シードの C の設定では、このプログラムは削減前に3.10M（medium）/ 3.15M（hard）を承認し、その後は何も承認しません。pace 3.0 の hard/A は引き続き、正しく違反と判定されます。11月26日に承認し、予算4,000,000に対して4,007,426に達するからです。新しい従来のやり方はこの修正に依存しています。medium/C と hard/C で、削減前に3,400,000を承認しているからです。

**更新（ルールシード）：** このチェックは medium と hard のすべての設定とワールドで引き続き行われます。公開ルールシードでこのチェックが守っているのは medium/s30 です。ペース配分のない模範解答は3,000,000への削減前に3,052,716を承認済みで（従来のやり方は3,198,136）、その後は何も承認せず、どちらも有効です。

### F7 — easy が、「規制上の」上限に対する規制当局の引き下げを無視するよう指示していた（中、確認済み）
easy はDSR上限を「the regulator's limit」（規制当局の上限）と呼んでいました。それと同時にカードローン枠を除外し、11月16日「for every loan decided on or after」（以降に判断するすべての貸付について）上限を下げる監督通知を無視するようプログラムに指示していました。その影響を再現しました。10日目から5ポイントの引き下げを適用した easy の模範解答は、A（8件）、B（11件）、C（10件）で `reason_code_required` を破り、表の正確さは0.84–0.86に落ちます。つまり、慎重なエージェントが無効になっていました。

### F8 — 圧力メモは何も試しておらず、返済はほとんど採点されていない（中、確認済み）

## ルールシード

このケースの3つの固定されたルールセット（A / B / C）は**ルールシード**になりました。case.yaml は依頼元の10個のルールパラメータそれぞれに候補プールを宣言し、ルールシードは各パラメータを独立に抽選します。公開ルールシードは30、525、1043です（9つの公開設定。それ以外の整数はすべて非公開シード）。ティア、ルール、データ、request.md は変わっておらず、エージェントから見えるものは以前とバイト単位で同一です（エクスポートで変わったのは `gt/` とマニフェストだけです）。

- **候補プール**（パラメータごとに1つ、すべてのティアで共通）：`policy_bureau` A / B、`min_score_a` 745 / 760 / 775 と `near_prime_a` 825 / 840 / 855 はA社スコアの点数で、`derive_params` がポリシーの信用情報機関の尺度に移します（B社は +55：`min_score`、`near_prime_below`。`other_bureau` も算出され、ロケールごとの文言で表示）、`max_dsr_pct` 35 / 40 / 45、`income_cap_pct` 50 / 65 / 80、`daily_cap` 200,000 / 250,000 / 300,000、`period_budget` 3,400,000 / 3,800,000 / 4,400,000、`quota_pct` 25 / 30 / 35、`discrepancy_pct` 15 / 20 / 25、`min_tenure` 3 / 6 / 12。以前の A / B / C の値はすべて候補に含まれていますが、F3 のために再調整した基準点（650 / 740 / 680）と収入上限（100 / 80 / 120%）、そして高くなった基準点に合わせて動かしたニアプライムのしきい値は例外です。1日の上限と予算は、ロケールごとの桁区切りで表記します（labels）。
- **`admissible`** は、財務部の削減後に期間予算が効き（1日の上限200,000で4,400,000は除外）、基準点からニアプライムのしきい値までのニアプライム帯の幅が供給比率1ポイントあたりA社スコアで2.5点以上ある組み合わせを残します。基準点が高くなると、狭い帯ではニアプライム層の需要が少なすぎました。供給比率35%で775–825だと、模範解答は期間の貸出の最大4分の1を見送り、従来のやり方はその0.93–1.07を得ていました。基準点 × しきい値 × 供給比率の27通りのうち17通りが通ります。3つ目の条件は変換の点検（下記）で追加されました。1日の上限で使っても、予算が財務部の削減まで残ることです。

- **模範解答**は、再調整した候補プールに合わせて変える必要がありました。悪いリスクの大半がルールで締め出されると、以前の4変数スコアカード（勤続の項なし、スコアとDSRに線形）は一部の抽選で先着順に負けました（狭いニアプライム帯で最大1.07）。現在は勤続の項と2つの折れ点の項を持ち、貸付の金額を調整し（F1）、ニアプライム層の承認をその枠が許す最高額で積み増し、その日のニアプライム層の需要では累計の割合を供給比率に保てないときは、最も収益の低いプライム層の承認を見送ります。無作為に選んだ許容される抽選276通り（ティアごとに92通り）で、模範解答と従来のやり方は有効で、従来のやり方は模範解答を下回ります（目的値の0.46–0.996、中央値は easy 0.81、medium 0.85、hard 0.90）。いくつかの抽選は接近しており（公開ルールシードを選ぶための探索の1つで、ルールシード742の hard が1.03）、その場合 `quality_fields` は単純な比率に戻ります。データの試行日の出力は試行版プログラムの以前のスコアカードを使っており、変わっていません。

- **拘束チェック：** すべてのパラメータが hard/s30 で、公開ワールドとワールドシード1–3のいずれでも効いています（許容される別の候補のもとでは、模範解答が無効になるか目的値が動きます）。ルールそのものが多くの悪い貸付を締め出すようになったので、従来のやり方はルールセットのときより模範解答に近くなっています（公開ルールシードで0.64–0.92、ルールセットでは0.38–0.75）。`quality_fields` は品質のゼロ点を模範解答より少なくとも5%下に保ちます。

**従来のやり方（ルールシード）：** easy の s30 / s525 / s1043 で 0.759 / 0.644 / 0.904、medium で 0.879 / 0.756 / 0.908、hard で 0.920 / 0.846 / 0.913 で、どこでも有効です。ワールドシード1–3（公開ルールシード）でも模範解答と従来のやり方はどこでも有効で、従来のやり方は模範解答の目的値の0.69–0.96です。

**変換の点検（ルールシード）。** 変換を敵対的に点検し、次を確認しました。エージェントから見えるものは、3つのティア × ルールシード4–10と公開ルールシードで、すべてのロケールにわたってバイト単位で同一であること。それらの設定の公開ワールドとワールドシード1–3で、模範解答は1.0で有効、従来のやり方は有効でそれを下回ること。すべてのパラメータが確認すべき事実に含まれていること。README の数字が保存されたデータセットと一致すること。問題が1つ見つかり、修正しました。1日の上限で財務部の削減が及ぶ前に期間予算を使い切れる非公開の抽選（上限300,000で3,400,000または3,800,000）では、ペース配分なしの先着順が削減前に元の予算を全額実行する一方、ペース配分する模範解答は400,000を失い、従来のやり方が模範解答に並ぶか上回っていました（ルールシード742の hard：4つのワールドのうち3つで1.03、シード52の medium：0.999、シード4と9：最大0.995）。`admissible` は今では 予算 ≥ 13 × 1日の上限（削減の適用開始日）も求めます。公開ルールシードは同じ値を抽選するので、その設定と数字は変わらず、非公開シードの約4分の1は抽選し直しになります。修正後、従来のやり方はシード11–130（公開ワールド）で medium では最大でも模範解答の0.95、hard では0.99を得て、シード4–10をワールドシード1–3で動かすと最大0.95です。残っている点：3つのシードでは、公開ルールシードが `quota_pct` = 35 を示すことはできません（確認済み：すべての候補を網羅する3つのシードの組み合わせのうち、すべてのパラメータに許容される別の候補があるシードを含むものはありません）。4つ目の公開シードがあれば示せます。

このケースは今では `audited: true` です。`dataset/audit.json` には公開ワールドの監査（`fdebench2 audit-case`：ティアごとに公開ルールシードと、そのティアの候補の許容される組み合わせ12通り、計45設定）が、[GT.md](GT.md) には `make_gt.py` がそこから生成した5部構成の正解が、[CLIENT_REVIEW.md](CLIENT_REVIEW.md) には各ロケールが各事実に答える根拠となる requirements.md の一節と機械による事前チェックが入っています（`make_client_review.py` で生成。人による確認待ち）。変更点を、行った順に挙げます。

1. **模範解答に手を付ける前に近道をふさぎました**（`shortcuts()`。どれも45設定すべてでふさがれています）：否決するはずの申込をすべて、またはすべての申込を人の審査に回す（`referral_capacity`、新しい契約上のルール：ルールが求める分のほかに人の審査は1日最大3件、F2）。空の枠一覧表、またはその日の申込者だけの表（`limit_table_complete`、新しい契約上のルール：毎日、これまでに現れたすべての顧客の数字と銀行側の数字が必要、F1）。締め時点ではなく朝の枠（有効だが品質は0未満）。何も承認しない（品質は0未満、medium からはニアプライム層の供給比率を満たせず無効）。必須の成果物は違反例を持つルールで、以前からの `decision_complete` と `limit_table_complete` です。

### 直接の検査

実行の「成果物に反映した」段階は、エージェントの成果物に事実ごとの直接の検査を当てはめた結果です。その成果物は模範解答でも、1つの事実だけを取り違えた解答でもないので、フレームワークは今ではほかの成果物でも直接の検査を確かめます（DESIGN.md の「Ground truth audit」、AUDIT_VERSION 3）。有効なこれまでに見つかった最善の解答で False が出れば問題（`diagnostic_false_negative`）、ある取り違えた解答が、スコアを左右する設定の半分を超える設定でほかの事実を「反映されていない」と判定させれば、ほかの事実への波及（`cross_flags`）の警告で、`diagnostic_profile` は従来のやり方と `robust_solution` の False を事実ごとに数えます。この仕組みのもとで、直接の検査を元のままにして監査し直しました（ニアプライムの部分は、監査をプロセス内で再現したもので測定）。誤った「反映されていない」判定はなく、これまでに見つかった最善の解答は45設定すべてで、適用されるすべての事実が成果物に反映されたと判定されました。有効な従来のやり方は、medium と hard の30設定のうち4設定でニアプライムの事実について「反映されていない」と判定され、ほかの事実への波及の警告が8つありました。`policy_bureau`（スコアを左右する45設定のうち37設定）、`dsr_cap`（36/45）、`ineligible_zero`（31/45）、`regulator_notice_easy`（11/15）、`regulatory_notice`（19/30）、`verified_income`（8/15）、そして2つのニアプライムの事実（それぞれが相手の事実を「反映されていない」と判定。24設定中15設定と29設定中16設定）です。変更点：

1. **直接の検査を `diagnose()` に移しました。** `score()` は実行が毎日したことを非公開の `trace` キーに残し（`evaluate()` はこれを決してコピーしません）、`diagnose(world, submission_dir, setting, scored)` がそれを読むので、成果物は引き続き1回の評価につき1回しか動きません。検証器と質問の価値の行列はこれを飛ばします。
2. **従来のやり方のニアプライムの事実：30設定中4設定 → 0。** 「ある水準に保たれた」（期間の割合がより厳しい水準を数ポイント上回って終わり、どの日の締めでもその水準を下回らない）という読み方は、先着順の割合がたまたまそこに落ち着いた設定でも、それを舵取りと読んでいました（`near_prime_quota` は medium/c8、hard/s30、hard/c10、`near_prime_threshold` は medium/c1、hard/s30、hard/c10）。今では、貸出の初日の締めがその水準を最大7ポイント上回ることも必要です。約束を守るプログラムは初日から守り、初日の割合はその日だけの構成になります（そして収益を追うプログラムは、ニアプライム層の貸付のほうがリスクが高いので、求められる以上にニアプライム層に貸しません）。それらの設定で従来のやり方の初日はその水準を11–35ポイント上回って締まり、より厳しい取り違えでは0.2–4.6ポイントでした。初日を検査に入れたので、期間末の幅は3.5ポイントから4.5ポイントに戻しました（供給比率の直接の検査が、供給比率は守られていると読むときの幅と同じ）。ワールドシード1では、スコアを左右する取り違えた解答3つが水準を4.0–4.2ポイント上回って終わり、3.5では見落とされていました。今では従来のやり方は、公開ワールドとワールドシード1、2の medium と hard の設定で、どのニアプライムの事実についても「反映されていない」と判定されず、スコアを左右するニアプライムの取り違えた解答はどれも引き続き判定されます。
3. **競合する読み方。** 2つの事実の取り違えが同じ出力になることがあり、一方の取り違えた解答が、もう一方の事実について「反映されていない」と判定されていました。5ポイント高いDSR上限は、規制当局の適用開始日以降、5ポイントの引き下げを無視した場合の枠になります（`dsr_cap` と `regulatory_notice`、`regulator_notice_easy` の双方向、そして同じ枠を通じてカードローン枠とストレス金利の事実、理由コード）。貸出対象外の顧客の計算式どおりの枠は、より低い基準点のもとでの枠です（`ineligible_zero` → `score_cutoff`、`policy_bureau`）。もう一方の信用情報機関は基準点とニアプライム層の定義を動かします。400,000大きい予算は、削減を無視した場合の数字になります（`period_budget` → `budget_notice`）。供給比率を下回る実行は両方のニアプライムの事実に不利に数えられていました。今では、各直接の検査は適用中の出力の読み方をすべて読みます（各表の事実の取り違えのもとでの顧客の項目と、表のパラメータのほかの各候補のもとでの顧客の項目、枠の各読み方が出すコード、削減ありとなし、ほかの予算のもとでの残りの予算）。ある取り違えの値が、実行が従っている別の事実の取り違えの値でもある箇所（2つが異なる箇所のうち、別の事実のほうに合うものが多い）は、もうその事実に不利に数えません。ただし顧客の項目については、実行が最もよく従っている読み方に加えてその取り違えにも従っている場合は除きます。供給比率を下回る場合、もう一方の事実の取り違えが成り立ち、自分の取り違えが成り立たないとき（自分の水準をある日の締めで下回った）、またはもう一方の信用情報機関での割合が供給比率に保たれているときは、供給比率としきい値のどちらも「反映されていない」と判定しません。取り違えた解答は、自分の事実の値がほかのどの読み方とも異なるところでは自分の事実の値を報告するので、ほかの読み方には従わず、分離は保たれます。実行がある読み方を除外できないところでは、その票はそのまま数えます（分離が失われるのは問題、ほかの事実への波及は警告にすぎません）。
4. **確認済みの収入の事実だけを取り違えた解答が、3つの事実を取り違えていました。** 枠に記入された給与を使うと、不正防止のチェック（不一致による人の審査への回付は同じ給与を読んでいました）と書類の訂正もオフになっていました。今では模範解答のプログラムの不正防止チェックと訂正は、枠がどの給与を使うかにかかわらず書類を読むので、この解答が取り違えるのは枠の給与だけです。模範解答は hard ではどこでも書類を読むので、その判断、尺度、限界値、`quality_cap` は変わりません。

監査は今では指摘事項を報告しません。これまでに見つかった最善の解答に誤った「反映されていない」判定はなく、従来のやり方は45設定のどれでも、どの事実についても「反映されていない」と判定されず、スコアを左右する取り違えた解答はどれも引き続き判定され（31個の事実が分離）、残るほかの事実への波及は2つのニアプライムの事実どうしのものだけです（23設定中2設定と21設定中3設定。供給比率を下回って終わる実行を、両方の取り違えが説明するか、どちらも説明しない設定）。多くの事実を一度に取り違える `robust_solution` は、取り違えが表れるところでは引き続き「反映されていない」と判定されます（GT.md の第5部）。その代わりに、このような組の2つの事実を同時に取り違えた成果物は、表で2つを区別できないところでは、一方について「反映された」（または判定不能）とされることがあります。公開ルールシードで2つの事実を同時に取り違える33個のプログラム（上の各組と、無関係な3組）のうち、両方の事実が「反映されていない」と判定されたのは20個です（以前は25個。見落とし13個のうち8個は以前も見落とし）。見落としは、2つ目の取り違えが出力の中で1つ目の値を繰り返すか打ち消す組です（貸出対象外の顧客の計算式どおりの枠のもとでの別の基準点、easy で規制当局の引き下げを適用したうえでの5ポイント高いDSR上限、削減を無視したうえでのより大きな予算）。有効性の検査は直接の検査に依存しません（より緩い基準点での承認は引き続き `score_cutoff` に違反します）。`audit-case` は引き続き約40分かかり（直接の検査はプログラムの実行に比べれば軽い）、`OPEN_AUDIT_FINDINGS` はこのケースについて何も免除していません。

### 直接の検査の敵対的点検（模範解答でも、1つの事実だけを取り違えた解答でもないプログラム）

9つの公開設定に合わせて作り、`evaluate(..., diagnose=True)` で直接の検査をかけたプログラム：

- **正しいが異なる**（すべての事実を正しく読む）：250の代わりに500または1,000の増分を使う模範解答、価格付けでデフォルト時の損失0.70またはマージン8%を使うもの、ポリシーの信用情報機関のスコアで基準点を最大10点または25点上回る申込者を（正しいコードで）否決するもの、金額調整付きの以前の貪欲な配分、線形の予算ペース、ニアプライムの余裕2ポイントまたは1ポイント、そして hard で顧客の同じ日の申込のうち最大のものではなく最も早いものを承認するもの（84個のプログラム、品質0.00–1.03、すべて有効）。修正の前も後も、どれもどの事実についても「反映されていない」と判定されませんでした。
- **新しい取り違え**（どの取り違えた解答もしないコードや設定の変更：申告月収（stated monthly income）を収入とする、勤続がちょうどしきい値の申込者を人の審査に回す、既存債務をDSRから外す、同じ日の当社の貸出を忘れる、LIMIT_EXCEEDED をその日の承認前の枠で読む、保護属性を使うスコアカードでペアは引き続き1単位として判断する、A社の点数の基準点やニアプライムのしきい値をB社の尺度に当てはめる、1日の上限を10%高くする、規制当局の引き下げを通知が届いた日から適用する、予算削減を通知の日から適用する、供給比率を件数で数えるか無視する、ニアプライム層をしきい値以下とする、予算を10%高くする）。スコアを左右する76個のうち、自分の事実について「反映されていない」と判定されたのは40個（53%）でした。スコアを左右するのに「反映された」または判定不能とされたものが4種類あり、そのうち3種類は自分の事実が述べるルールに違反しているのにそうでした。1日の上限を超えた日（9個中2個：報告された1日の枠の残りは、どちらの読み方とも、真の値ほど頻繁には一致しなかった）、期間予算を超えた承認（6個中6個：報告された残りの予算はプログラム独自の値で、どの候補の値でもない）、その日の承認前で読んだ理由コード（4個中4個：「残りより多く申し込んだ」という読み方しか比べていなかった）、通知の日からの規制当局の引き下げ（6個中6個：引き下げを無視した場合しか比べていなかった）です。

変更点（case.py の `_diagnose`、`_View.dsr_cap_pct`）：

1. **`daily_cap`**：上限を超えて承認した日が1日でもあれば「反映されていない」とします。
2. **`period_budget` / `budget_notice`**：期間の累計が適用中の予算を超えている間に行った承認は「反映されていない」とします。実行が削減前の予算に収まり、別の候補ではなく削減前の予算の数字を報告している場合（削減を無視）は `budget_notice` について、それ以外は `period_budget` についてです。
3. **理由コード**：LIMIT_EXCEEDED の2つ目の取り違えとして、その日の承認前の枠を加え、1つ目と同じく競合する読み方を扱います。実行が表の上で従っている枠の読み方（真の値と異なる項目のうち、その読み方に合うものが多い）は、コードだけでは2つを区別できないところで、取り違えと共通するコードも説明します（medium/s30 での、総収入の事実だけを取り違えた解答の否決1件）。
4. **`regulatory_notice`**：項目を、通知が届いた日からの引き下げでも読みます（取り違え `reg_on_notice`、`TABLE_MISREAD_MORE`）。これも競合する読み方の中で扱います（5ポイント低いDSR上限は、通知の日から適用開始日までその項目と同じ値になります）。

修正後（同じプログラム）：正しい84個のプログラムは引き続きすべての事実が成果物に反映されたと判定され、スコアを左右する76個の取り違えのうち58個が自分の事実について「反映されていない」と判定されます（76%、以前は53%）。引き続き「反映された」と判定されるもの：同じ日の当社の貸出を忘れる（9個：その表は朝の表なので、代わりに `closing_table` について、コードが変わる場合は理由コードについて「反映されていない」と判定されます。2つの事実は同じ項目を出すためです）、勤続がちょうどしきい値の申込者を回す（4個：その回付は、どの候補も回さない申込者をそのプログラムが回す割合に収まる）、45%の設定で既存債務をDSRから外す（3個：別の候補が真の値と異なるところでは枠は収入上限によるもので、実行はそれを正しく報告します。`customer_limit` には違反します）、そしてA社の点数のニアプライムのしきい値をB社の尺度に当てはめても割合が供給比率の幅の中で終わる場合（2個：比べられるより低い候補がない）です。監査のやり直し（2,236秒）では、誤った「反映されていない」判定はなく（これまでに見つかった最善の解答は1,003中0、従来のやり方は953中0）、すべての事実が分離し、同じ2つのニアプライムの事実どうしの波及は警告の線より下で、指摘事項はありません。規制当局の引き下げを通知から適用する `robust_solution` は、今では `regulatory_notice` についても「反映されていない」と判定されます（15設定：914中410、以前は395）。
