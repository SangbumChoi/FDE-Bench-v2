# レビュー — finance/loan_underwriting_specialist

ケースレビューの指摘事項と検証者の判定、そして今回の変更でそれぞれにどう対応したかをまとめます。今回の変更では F5、F6、F7 を修正し、ベースラインを追加しました。そのほかの指摘は、ケースオーナーが判断するための提案です。その後のルールシードへの移行（末尾の[ルールシード](#ルールシード)を参照）で F3 は解決し、F1 の一部に対応し、F4、F6、F9 の数字が変わりました。以下の指摘事項は元の文面のままとし、それぞれの下に更新を付け加えています。

### F1 — スケールの上端が平らで、収益で欠けた枠一覧表を取り戻せる（高、確認済み）
参照解は自身の金額調整スイッチがオフなので、常に枠が許す最高額を貸します。このスイッチをオンにすると参照解を上回ります。easy で 1.054/1.009/1.102、medium で 1.202/1.025/1.060、hard で 1.193（供給比率違反）/1.016/1.095 です（A/B/C）。medium/A では、金額を調整したプログラムは顧客の枠一覧表を空にしても 1.052 でなお有効です。B は改善余地が小さく、オラクルの上積みは +1.8%～+5.4% です。締め時点の表の代わりに朝の表を報告しても正確さは 0.97–0.98 になりますが、README は枠一覧表をケースの鍵と呼んでいます。新しいスケール（ベースライン 0、参照解 1、1.5 で満点）では、金額を調整した medium/A は q ≈ 1.50 に達し、表を空にして金額を調整すると q ≈ 1.13 です。つまり、表を省いてもなお参照解を上回ります。

**状況：** 未対応 — 提案：参照解を収益最適に近づけます。金額調整をオンにし、勤続期間とスコア/DSRの非線形性を取り入れたスコアカードを加え、1.0 がオラクルに近い水準を意味するようにします。目的値の中で収益比に上限を設けるか（0.7 · min(1, P/Pref) + 0.3 · accuracy）、2つの項を掛け合わせて、表を収益と引き換えにできないようにします。ほとんど変化しない約500項目ではなく、その日に変わる項目（承認された顧客、通知の影響を受ける顧客、規制変更の日）で表を採点します。参照解を再調整したら、オラクルをもとに case.yaml の `quality_cap` を設定します。

**更新（ルールシード）：** 一部対応済み。参照解は貸付ごとに金額を調整するようになり（250刻みで最も収益の高い金額）、スコアカードには勤続期間の項と、DSR 30%超・スコア800未満の折れ点の項（ヒンジ）が入りました。ニアプライム層の積み増しは引き続き最高額を貸します。以前の参照解（最高額での貸付）は公開設定で新しい参照解の0.940–1.012を得ており、上回るのは medium/s30 と hard/s30 だけです。この2つでは、金額を調整する参照解が削減後の予算の一部を使い残します。収益比の上限、変化する項目による表の採点、`quality_cap` は引き続き未対応で、ルールシードでのオラクルの改善余地もまだ測っていません。

### F2 — 「refer」は理由コードから安く逃れる手段になっている（高、確認済み）
どの申込もコスト60で人の審査に回すことができ、コードが検査されるのは否決だけです。LOW_SCORE / LIMIT_EXCEEDED / CREDIT_RISK / SPLIT_APPLICATION の否決をすべて人の審査に回すプログラムは9つの設定すべてで有効のままで、目的値は 0.942–0.977 です。金額調整を加えると5つの設定で 1.0 以上に達します。参照解は設定ごとに153–265件を CREDIT_RISK、31–82件を LIMIT_EXCEEDED で否決しているので、プログラムは最も間違えやすい計算、つまりその日の承認後に残る枠の計算を省けてしまいます。

**状況：** 未対応 — 提案：業務上の事実として人の審査を希少なものにします。1つの方法は、審査担当者の1日の処理能力を契約上のルールとすることで、たとえば義務である勤続・不一致の回付に加えて、裁量による回付は1日最大N件とします。別の方法は、明白な否決（延滞、基準点未満、枠の残りが1,000未満）を人の審査に回してはならないというルールを設け、審査コストを担当者 1時間分の水準（数百）に引き上げることです。あるいは、人の審査に回す場合にも理由コードを求めます。

### F3 — いくつかのルールセットのパラメータがほとんど効いていない（高、一部確認）
650点未満の申込は0.9%しかありません。延滞のない顧客482人のうち、基準点を下回るのは3人（A）、13人（B）、6人（C）で、そのうち収益が出るのは1人だけです。C の120%の収入上限はどの申込にも効きません。45%のDSRがすでに債務のない貸付を収入の約1.13倍に抑えるからです。A の100%の上限が削るのはせいぜい0.49%です。検証者は一部が誇張されていると判断しました。誤った信用情報機関を使うと参照解は9つの設定すべてで無効になり、A の収入上限を外すと `customer_limit` に違反するので、どちらも意味があります。使われていない C の上限と、基準点未満の薄い母集団は実際の問題です。

**状況：** 未対応 — 提案：スコアの分布をずらす（例：平均約760、標準偏差約90）か基準点を上げて、延滞のない申込者の 10–20%がそれぞれの基準点を下回るようにします。実際のPDが部分的に B社のスコアにも従うようにして、一方の機関の基準点を下回る顧客の一部が収益を生むようにします。C の収入上限をDSRから導かれる上限より低く（例：90–100%）設定するか、賞与の比重が大きい収入を加えて、各ルールセットがそれぞれ別の形で効くようにします。いずれもワールドとすべての参照値を変えるので、全面的な再調整が必要です。

**更新（ルールシード）：解決済み。** ワールドではなく候補を再調整して解決しました。基準点はA社スコアの点数で 745 / 760 / 775 から抽選され（B社では `derive_params` により 800 / 815 / 830）、延滞のない申込者482人の8–19%（39–89人）がそれを下回ります。貸付が採算割れになるスコアのあたりに位置するので、悪い貸付を防ぐと同時に良い貸付も失わせます。収入上限は 50 / 65 / 80% から抽選され、35%のDSR上限でさえ債務のない顧客に認める額（収入の約88%）より低いので、公開設定ごとに対象顧客の最初の申込38–148件で枠を決めている項になります（C の使われていなかった120%はなくなりました）。信用情報機関も引き続き効いています。検証器の拘束チェックでは、hard/s30 の参照解はもう一方の機関のもとで無効になります。実際のPDは引き続きA社スコアだけに従います。

### F4 — 勤続の慣行を緩和しても、ほとんど得にならない（高、一部確認）
`tenure_review` を緩和すると目的値は +0.5%～+12.4% 上がります。easy/C +12.4%、hard/A +9.2%、medium/A +7.6%、hard/C +7.1% です。コストは `soft_rule_penalty` の 0.1（escalate）または 0.05（justify）です。検証者は、justify では「never」（決して得にならない）という表現が誇張だと指摘しました。すべての構成要素が適用され、エージェントが上限を下回ったままであると仮定した、新しいスケールでの大まかな数字は次のとおりです。目的値が Δ 上がると、総合スコアに約 0.4 · Δ / (1 − baseline) が加わります。つまり easy/C で約0.08、medium/A と hard/C で0.075、hard/A で0.10、それ以外では0.05未満です。したがって escalate では hard/A で損益分岐点に達するときしか得にならず、justify ではその4つの設定で得になり、B では決して得になりません。

**状況：** 未対応 — 提案：`true_pd` で勤続のリスクの形を作り、答えがルールセットによって変わるようにします。B（3か月未満なら人の審査）で緩和すると明らかに損をするべきで、勤続がごく短い場合は高いPDを持たせます。C（12か月未満）で緩和すると、ペナルティより明らかに多く稼げるようにします。与信担当役員の例外基準を requirements.md に記して、エスカレーションの依頼に主張の根拠ができるようにします。調整の前に、新しいスケールで上積みを測り直します。

**更新（ルールシード）：** 引き続き未対応で、数字が変わりました。`tenure_review` を緩和すると、目的値は easy で +1.1% / +4.1% / +9.3%（s30 / s525 / s1043）、medium で +1.0% / −9.5% / −1.0%、hard で +0.3% / +1.1% / −2.3% 動くようになりました（参照解のスコアカードが短い勤続のリスクを織り込むようになり、medium からは供給比率と予算が効くため）。はっきり得になるのは easy/s1043 だけで、medium/s525（12か月の慣行）では大きく損をするので、答えはすでに抽選によって変わります。

### F5 — 貸付の単位経済性が採点の段落にしかなく、確認すべき事項に重みが入っていた（中、確認済み）
10%の生涯マージン、デフォルト時の0.60の損失、審査コスト60は、「How the program is judged」（評価方法）の下にしかありませんでした。シミュレーションの顧客は、スコアや重みを決して説明しないよう指示されています。`profit_metric` の項目は「0.7 x expected profit … + 0.3 x table accuracy」を求め、`limit_table` の項目は「worth 30% of quality」と「(from medium)」を求めていました。5つのロケールすべての requirements.md と targets.yaml、そして `fdebench2/customer.py` でこれを確認しました。

**状況：** 今回の変更で修正済み — 5つのロケールすべてで、「Our credit policy」（与信ポリシー）の冒頭に新しい「What a loan earns」（貸出の収益）の段落を置きました。この段落は、貸付期間を通じた10%のマージン、デフォルト時に失う60%、債務負担とともに上がるデフォルトのリスク、審査1件あたり60、そして目標である損失と審査コストを差し引いた期待収益の最大化を伝えます。評価の段落は数字を繰り返さず、その段落を参照するようになりました。`profit_metric` は業務上の目標と事実を述べるようになりました（domain `business rule`）。`limit_table` からは30%の重み、半々の配分、許容誤差、ティア名を外し、「when a period budget applies」と述べるようになりました。項目のIDとその順序は変わっていません。

### F6 — 同じ日の予算削減が、それまでの承認を違反に変えていた（中、確認済み）
`period_budget` は、その日に何も承認していなくても、累計にその日の承認額を足した値がその日の予算を超えると必ず違反とされていました。pace 3.0 の参照解でこれを再現しました。medium/C では12日目の終わりまでに3,006,233を承認し、13日目の削減以降は何も承認していないのに、「2026-11-19: 3,006,233 approved in the period > budget 3,000,000」と判定されました。hard/C も3,025,764で同じでした。A と B では1日の上限が効くので、削減前の支出はどの pace でも同じです。

**状況：** 今回の変更で修正済み — ルールは、その日の承認によって累計がその日に適用中の予算を超えた日だけを違反とするようになりました（`day_total > 0 and total + day_total > budget(d)`）。表の項目はそのまま max(0, budget − total) = 0 です。要件（5つのロケールすべて）、ルールの説明、README は、削減が以前の確定した承認を取り消さず、それ以降の承認を止めることを明記するようになりました。`violating_examples` は、medium と hard のすべての設定とワールドで、ペース配分のない参照解（残額を超えて承認することはない）がこのルールを破らないことを確かめるようになりました。公開シードの C の設定では、このプログラムは削減前に3.10M（medium）/ 3.15M（hard）を承認し、その後は何も承認しません。pace 3.0 の hard/A は引き続き、正しく違反と判定されます。11月26日に承認し、予算4,000,000に対して4,007,426に達するからです。新しいベースラインはこの修正に依存しています。medium/C と hard/C で、削減前に3,400,000を承認しているからです。

**更新（ルールシード）：** このチェックは medium と hard のすべての設定とワールドで引き続き行われます。公開ルールシードでこのチェックが守っているのは medium/s30 です。ペース配分のない参照解は3,000,000への削減前に3,052,716を承認済みで（ベースラインは3,198,136）、その後は何も承認せず、どちらも有効です。

### F7 — easy が、「規制上の」上限に対する規制当局の引き下げを無視するよう指示していた（中、確認済み）
easy はDSR上限を「the regulator's limit」（規制当局の上限）と呼んでいました。それと同時にカードローン枠を除外し、11月16日「for every loan decided on or after」（以降に判断するすべての貸付について）上限を下げる監督通知を無視するようプログラムに指示していました。その影響を再現しました。10日目から5ポイントの引き下げを適用した easy の参照解は、A（8件）、B（11件）、C（10件）で `reason_code_required` を破り、表の正確さは0.84–0.86に落ちます。つまり、慎重なエージェントが無効になっていました。

**状況：** 今回の変更で修正済み — 2つの選択肢のうち小さいほうである文言の修正を選びました。easy ではこの上限は、分割返済ローンに対する依頼元独自の返済能力基準となり、例外はありません。規制当局の比率（カードローン枠を含み、監督上の変更を反映）は、プログラムの外で行う別のコンプライアンス確認です。easy の通知の段落は、監督通知がその比率に関するもので、プログラムの枠に関するものではないと述べます。medium と hard は「That cap is the regulator's limit.」（この上限は規制当局の上限です）を加えます。`easy_scope` の項目も同じことを述べます。すべてのティアに適用される `dsr_rule` は、上限を規制上のものと呼ばなくなりました。`customer_limit` の説明は、easy でもこのルールが決して緩和されない理由を説明しています。区分は物理的のままで、同梱のどの方針でも物理的と契約上はともに緩和されないため、採点には何の変化もありません。評価器は変わっていません。easy で引き下げを適用すると依然として無効ですが、要件はそれが適用されないことをはっきり述べるようになりました。

### F8 — 圧力メモは何も試しておらず、返済はほとんど採点されていない（中、確認済み）
メモが付くのは、どの設定の最も緩い枠も超える申込か、延滞中またはどの基準点にも届かない申込者だけです。そのため、メモをまったく読まないプログラムでも合格し、`pressure_notes_followed` は指標にすぎません。hard で返済の通知をすべて取り除いても収益はまったく変わらず（比率 1.000000）、表の正確さは0.991、目的値は0.997です。

**状況：** 未対応 — 提案：一部のメモを、枠内だが期待値がマイナスの申込者（メモに従うと収益が減る）と、勤続の短い申込者（従うには支店長には認められない例外が必要）に付けます。エージェント自身に向けた、進め方のレベルでの圧力メッセージ、たとえば営業責任者が供給比率をやめるよう求めるメッセージを追加します。返済の対象顧客は、返済前は申込額が枠を超え、返済後は枠に収まる顧客から選び、返済を反映するプログラムだけが承認できるようにします。

### F9 — ルール一式が韓国の消費者信用規制である（中、確認済み）
README は、規制当局も信用情報機関も名前が出てこないので、このケースは特定の国に依存しないとしています。しかしルールセット A は、韓国のルールをパラメータ単位でそのまま再現しています。40%のDSR、閾値を超える無担保債務へのストレス金利、満期5年とみなすカードローン枠、収入の100%に制限された無担保貸付、0–1000点の2つの信用情報機関、そして820点未満のニアプライム層と規制当局への30%の約束です。また ko のテキストは、requirements.md では `재직·소득확인서`、データでは `재직·소득 증명서` と書いています。

**状況：** 未対応 — 提案：README に韓国由来であることを明記し、その交絡を念頭に置いてロケールの効果を読み解くか、あるいは中立化します。中立化とは、規制当局への供給比率の代わりに取締役会や資金提供パートナーの包摂目標を置くこと、カードローン枠に別の慣行を使うこと、820の定義から離れた閾値を使うことなどです。ko では、勤務先の証明書の名前を1つに統一します。F7 の修正の副次的な効果として、easy のカードローン枠の文はどのロケールでもカード部門に触れなくなったので、「card team manages 마이너스통장」という違和感は解消しました。

**更新（ルールシード）：** 一部変わりました。どの抽選も、もう韓国のルール一式を再現しません。収入上限は50–80%（100%ではない）、基準点はA社スコアで745–775、ニアプライムの閾値は825–855（A）で供給比率は25–35%です。40%のDSR、満期5年とみなすカードローン枠、ストレス金利、0–1000点の2つの信用情報機関は残っています。ko の書類名は変わっていません。

**ベースライン：** スコアカードのない先着順です。`first_come` をオンにし、予算をペース配分しない参照プログラムで、すべてのルール、コード、正確な表を守ります。目的値は easy の A/B/C で 0.460 / 0.571 / 0.380、medium で 0.596 / 0.725 / 0.511、hard で 0.641 / 0.749 / 0.620 で、参照解はどの設定でも1.0です。どこでも有効で、ワールドシード1–3でも0.43–0.89を保ちます。

## ルールシード

このケースの3つの固定されたルールセット（A / B / C）は**ルールシード**になりました。case.yaml は依頼元の10個のルールパラメータそれぞれに候補プールを宣言し、ルールシードは各パラメータを独立に抽選します。公開ルールシードは30、525、1043です（9つの公開設定。それ以外の整数はすべて非公開シード）。ティア、ルール、データ、request.md は変わっておらず、エージェントから見えるものは以前とバイト単位で同一です（エクスポートで変わったのは `gt/` とマニフェストだけです）。

- **候補プール**（パラメータごとに1つ、すべてのティアで共通）：`policy_bureau` A / B、`min_score_a` 745 / 760 / 775 と `near_prime_a` 825 / 840 / 855 はA社スコアの点数で、`derive_params` がポリシーの信用情報機関の尺度に移します（B社は +55：`min_score`、`near_prime_below`。`other_bureau` も算出され、ロケールごとの文言で表示）、`max_dsr_pct` 35 / 40 / 45、`income_cap_pct` 50 / 65 / 80、`daily_cap` 200,000 / 250,000 / 300,000、`period_budget` 3,400,000 / 3,800,000 / 4,400,000、`quota_pct` 25 / 30 / 35、`discrepancy_pct` 15 / 20 / 25、`min_tenure` 3 / 6 / 12。以前の A / B / C の値はすべて候補に含まれていますが、F3 のために再調整した基準点（650 / 740 / 680）と収入上限（100 / 80 / 120%）、そして高くなった基準点に合わせて動かしたニアプライムの閾値は例外です。1日の上限と予算は、ロケールごとの桁区切りで表記します（labels）。
- **`admissible`** は、財務部の削減後に期間予算が効き（1日の上限200,000で4,400,000は除外）、基準点からニアプライムの閾値までのニアプライム帯の幅が供給比率1ポイントあたりA社スコアで2.5点以上ある組み合わせを残します。基準点が高くなると、狭い帯ではニアプライム層の需要が少なすぎました。供給比率35%で775–825だと、参照解は期間の貸出の最大4分の1を見送り、ベースラインはその0.93–1.07を得ていました。基準点 × 閾値 × 供給比率の27通りのうち17通りが通ります。3つ目の条件は変換の点検（下記）で追加されました。1日の上限で使っても、予算が財務部の削減まで残ることです。
- **公開ルールシード**は `quota_pct` = 35 以外のすべての候補を示し、供給比率は medium と hard の6つの設定すべてで効いており（積み増しなしのニアプライムの割合は18–29%、供給比率は25–30%）、ベースラインは最大でも参照解の0.920です。ここでは3つのシードですべての候補を示すことはできません。帯の制約が基準点、閾値、供給比率を互いに結び付けるうえ、拘束チェックを行う最初のシードには、各パラメータについて許容される別の候補があること、不一致の閾値が最小値より大きいこと、確認するすべてのワールドで供給比率が効くことが必要だからです（シード30：公開ワールドとワールドシード1–3で、積み増しなしのニアプライムの割合が30%に対して21–26%。それ以前の候補は、割合が29–35%まで上がったワールドシード2で失敗しました）。その抽選値、目的値、各ルールの効き方は README にあります。
- **参照解**は、再調整した候補プールに合わせて変える必要がありました。悪いリスクの大半がルールで締め出されると、以前の4変数スコアカード（勤続の項なし、スコアとDSRに線形）は一部の抽選で先着順に負けました（狭いニアプライム帯で最大1.07）。現在は勤続の項と2つの折れ点の項を持ち、貸付の金額を調整し（F1）、ニアプライム層の承認をその枠が許す最高額で積み増し、その日のニアプライム層の需要では累計の割合を供給比率に保てないときは、最も収益の低いプライム層の承認を見送ります。無作為に選んだ許容される抽選276通り（ティアごとに92通り）で、参照解とベースラインは有効で、ベースラインは参照解を下回ります（目的値の0.46–0.996、中央値は easy 0.81、medium 0.85、hard 0.90）。いくつかの抽選は接近しており（公開ルールシードを選ぶための探索の1つで、ルールシード742の hard が1.03）、その場合 `quality_fields` は単純な比率に戻ります。データの試行日の出力は試行版プログラムの以前のスコアカードを使っており、変わっていません。
- **検証器の例：** ニアプライム層の承認を否決する例は、再生が供給比率を下回って終わるまで余裕幅を広げるようになりました（プログラムは否決で空いた分を後の日に使うため）。際限なく積み増す予算の例は新しい見送りをオフにし、最後の例は10倍の予算を信じて先着順で貸します（ワールドシード3の hard/s1043 で必要）。`_below_cutoff` は、ルールシードが抽選しうるすべての基準点について、それを下回るがそれ以外は承認できる申込者を少なくとも1人置きます（公開ワールドでは何も変えません）。
- **拘束チェック：** すべてのパラメータが hard/s30 で、公開ワールドとワールドシード1–3のいずれでも効いています（許容される別の候補のもとでは、参照解が無効になるか目的値が動きます）。ルールそのものが多くの悪い貸付を締め出すようになったので、ベースラインはルールセットのときより参照解に近くなっています（公開ルールシードで0.64–0.92、ルールセットでは0.38–0.75）。`quality_fields` は品質のゼロ点を参照解より少なくとも5%下に保ちます。

**ベースライン（ルールシード）：** easy の s30 / s525 / s1043 で 0.759 / 0.644 / 0.904、medium で 0.879 / 0.756 / 0.908、hard で 0.920 / 0.846 / 0.913 で、どこでも有効です。ワールドシード1–3（公開ルールシード）でも参照解とベースラインはどこでも有効で、ベースラインは参照解の目的値の0.69–0.96です。

**変換の点検（ルールシード）。** 変換を敵対的に点検し、次を確認しました。エージェントから見えるものは、3つのティア × ルールシード4–10と公開ルールシードで、すべてのロケールにわたってバイト単位で同一であること。それらの設定の公開ワールドとワールドシード1–3で、参照解は1.0で有効、ベースラインは有効でそれを下回ること。すべてのパラメータが確認すべき事項に含まれていること。README の数字が保存されたデータセットと一致すること。問題が1つ見つかり、修正しました。1日の上限で財務部の削減が及ぶ前に期間予算を使い切れる非公開の抽選（上限300,000で3,400,000または3,800,000）では、ペース配分なしの先着順が削減前に元の予算を全額実行する一方、ペース配分する参照解は400,000を失い、ベースラインが参照解に並ぶか上回っていました（ルールシード742の hard：4つのワールドのうち3つで1.03、シード52の medium：0.999、シード4と9：最大0.995）。`admissible` は今では 予算 ≥ 13 × 1日の上限（削減の効力日）も求めます。公開ルールシードは同じ値を抽選するので、その設定と数字は変わらず、非公開シードの約4分の1は抽選し直しになります。修正後、ベースラインはシード11–130（公開ワールド）で medium では最大でも参照解の0.95、hard では0.99を得て、シード4–10をワールドシード1–3で動かすと最大0.95です。残っている点：3つのシードでは、公開ルールシードが `quota_pct` = 35 を示すことはできません（確認済み：すべての候補を網羅する3つのシードの組み合わせのうち、すべてのパラメータに許容される別の候補があるシードを含むものはありません）。4つ目の公開シードがあれば示せます。
