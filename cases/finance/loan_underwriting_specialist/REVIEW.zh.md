# 评审 — finance/loan_underwriting_specialist

本文记录一次案例评审的发现、核查者的结论，以及本次修改对每项发现的处理。本次修改修复了 F5、F6 和 F7，并新增了基线。其余发现是供案例负责人决定的提议。

### F1 — 量表顶端是平的，收益可以弥补缺失的额度表（高，已确认）
参考程序自己的金额确定开关是关着的，所以它总是借出额度允许的最高金额。把这个开关打开就能胜过参考程序：easy 中为
1.054/1.009/1.102，medium 中为 1.202/1.025/1.060，hard 中为 1.193（违反承诺比例）/1.016/1.095（A/B/C）。在 medium/A 中，确定金额的程序即使客户额度表为空，也以1.052分保持有效。B 的提升空间很小（oracle 的增益为 +1.8% 至 +5.4%）。报告早上而不是收盘时的额度表，准确度仍有0.97–0.98，而 README 却称额度表是本案例的关键。在新量表上（基线为0，参考为1，1.5时满分），确定金额的 medium/A 达到 q ≈ 1.50，确定金额且额度表为空时 q ≈ 1.13。所以跳过额度表仍然能胜过参考程序。

**状态：** 未解决 — 提议：让参考程序接近收益最优：打开金额确定，再加上考虑在职时间以及分数/DSR非线性的评分卡，使1.0代表接近 oracle 的水平。在目标值内部给收益比例设上限（0.7 · min(1, P/Pref) + 0.3 · accuracy），或者把两部分相乘，使额度表无法用收益换取。按当天发生变化的表项（获批客户、受通知影响的客户、监管变更当天）给额度表评分，而不是按约500个大多不变的表项。参考程序重新调校后，再根据 oracle 设定 case.yaml 中的 `quality_cap`。

### F2 — "refer" 是绕开原因代码的廉价出口（高，已确认）
任何申请都可以花60转人工，而只有拒绝才检查代码。一个把所有 LOW_SCORE / LIMIT_EXCEEDED / CREDIT_RISK / SPLIT_APPLICATION 拒绝都改为转人工的程序，在全部9个设置中都保持有效，目标值为0.942–0.977。再加上金额确定，在五个设置中可达到 ≥ 1.0。参考程序在每个设置中以 CREDIT_RISK 拒绝153–265笔、以 LIMIT_EXCEEDED 拒绝31–82笔，所以程序可以跳过最容易出错的计算：当天批准后剩余的额度。

**状态：** 未解决 — 提议：把转人工作为业务事实变得稀缺。一种做法是把审批员的每日处理能力定为合同约束规则，例如在强制的在职时间和收入不一致转人工之外，每天最多N笔自主转人工。另一种做法是规定明确应拒绝的申请（有逾期、低于门槛、剩余额度不足 1,000）不得转人工，同时把转人工成本提高到审批员一小时的水平（几百）。或者，转人工也要求原因代码。

### F3 — 若干规则集参数几乎不起约束作用（高，部分成立）
分数低于650的申请只占0.9%。在482位无逾期的客户中，低于门槛的有3位（A）、13位（B）和6位（C），其中只有一位能带来收益。C 的120%收入上限对任何申请都不起作用，因为45%的DSR已经把无负债客户的贷款限制在收入的约1.13倍。A 的100%上限最多削减0.49%。核查者认为部分说法有所夸大：用错评分机构会使参考程序在全部9个设置中无效，去掉 A 的收入上限会违反 `customer_limit`，所以两者都有作用。C 的上限闲置、门槛以下的客群过薄，这两点是真实存在的。

**状态：** 未解决 — 提议：平移分数分布（例如均值约760、标准差约90）或提高门槛，使10–20%的无逾期申请人落在各门槛之下。让真实PD部分依据B机构分数，使某些低于一家机构门槛的客户也能带来收益。把 C 的收入上限设得低于DSR所隐含的上限（例如90–100%），或加入奖金占比高的收入，使每个规则集以各自的方式起约束作用。这些都会改变世界和所有参考数据，因此需要全面重新调校。

### F4 — 放宽在职时间习惯很少划算（高，部分成立）
放宽 `tenure_review` 使目标值提高 +0.5% 至 +12.4%：easy/C +12.4%、hard/A +9.2%、medium/A +7.6%、hard/C +7.1%。代价是 `soft_rule_penalty` 0.1（escalate）或 0.05（justify）。核查者指出，在 justify 下说"never"（从不划算）言过其实。在新量表上，假设所有组成部分都适用且智能体保持在上限以下，粗略的数字如下：目标值提高 Δ，综合分约增加 0.4 · Δ / (1 − baseline)，即 easy/C 约0.08，medium/A 和 hard/C 约0.075，hard/A 约0.10，其余不到0.05。所以在 escalate 下只有 hard/A 勉强持平时才划算；在 justify 下这四个设置都划算；在 B 中则从不划算。

**状态：** 未解决 — 提议：在 `true_pd` 中塑造在职时间的风险，使答案取决于规则集。在 B（不满3个月转人工）中放宽应明显亏钱，在职时间极短的客户PD很高。在 C（不满12个月）中放宽应明显赚得比罚分多。在 requirements.md 中写明信贷主管批准例外的标准，让升级请求有据可依。调校之前先在新量表上重新测量增益。

### F5 — 贷款的单位经济只写在评分段落中，应问事项里还带着权重（中，已确认）
10%的生命周期利润、违约时0.60的损失和60的转人工成本只出现在 "How the program is judged"（评估方式）之下。模拟客户被告知绝不描述得分或权重。`profit_metric` 事项要求 "0.7 x expected profit … + 0.3 x table accuracy"。`limit_table` 事项要求 "worth 30% of quality" 和 "(from medium)"。我在全部五个语言区域的 requirements.md 和 targets.yaml 以及 `fdebench2/customer.py` 中核对过这一点。

**状态：** 已在本次修改中修复 — 在全部五个语言区域中，"Our credit policy"（我们的信贷政策）开头新增了 "What a loan earns"（一笔贷款能赚多少）段落。它给出贷款期内10%的利润、违约时损失的60%、随负债负担上升的违约风险、每次转人工60，以及目标：扣除损失和转人工成本后的预期收益最大。评估段落现在引用这一段，而不再重复数字。`profit_metric` 现在陈述业务目标和事实（domain `business rule`）。`limit_table` 去掉了30%的权重、各占一半的拆分、容差和层级名称；现在写的是 "when a period budget applies"。事项编号及其顺序不变。

### F6 — 同一天的预算削减把之前的批准变成了违反（中，已确认）
过去，只要累计额加上当天的批准超过当天预算，`period_budget` 就会被标记为违反，即使当天什么也没批准。我用 pace 3.0 的参考程序复现了这一点。在 medium/C 中，它到第12天结束时已批准3,006,233，从第13天削减起什么也没批准，却仍被标记为 "2026-11-19: 3,006,233 approved in the period > budget 3,000,000"。hard/C 情况相同，为3,025,764。在 A 和 B 中每日上限起约束作用，所以削减前的支出在任何 pace 下都相同。

**状态：** 已在本次修改中修复 — 现在规则只标记当天批准使累计额超过当天现行预算的那一天（`day_total > 0 and total + day_total > budget(d)`）。额度表项仍为 max(0, budget − total) = 0。需求（全部五个语言区域）、规则描述和 README 现在都写明：削减不会撤销之前已最终确定的批准，但会停止后续批准。`violating_examples` 现在在每个 medium 和 hard 设置及每个世界中断言：不控制节奏的参考程序（它从不批准超过剩余的金额）不会违反这条规则。在公开种子的 C 设置中，该程序在削减前已批准
3.10M（medium）/ 3.15M（hard），之后什么也不批准。pace 3.0 的 hard/A 仍被标记，这是正确的：它在11月26日批准，达到 4,007,426，而预算为4,000,000。新基线依赖这一修复，因为它在 medium/C 和 hard/C 中削减前已批准3,400,000。

### F7 — easy 让智能体忽略监管机构对"监管"上限的下调（中，已确认）
easy 把DSR上限称为 "the regulator's limit"（监管机构的限额）。同时它又不计循环授信，并让程序忽略那份自11月16日起 "for every loan decided on or after"（对当天及之后决定的每笔贷款）下调上限的监管通知。我复现了其影响：从第10天起应用5个百分点下调的 easy 参考程序在 A（8次）、B（11次）和 C（10次）中违反 `reason_code_required`，额度表准确度降到0.84–0.86。因此一个谨慎的智能体反而无效。

**状态：** 已在本次修改中修复 — 我选择了两个方案中改动较小的改写措辞。在 easy 中，该上限现在是客户自己针对分期贷款的还款能力上限，没有例外。监管口径的比率（含循环授信，并反映任何监管调整）是程序之外另行进行的合规检查。easy 的通知段落说明，监管通知针对的是那个比率，而不是程序的额度。medium 和 hard 增加了 "That cap is the regulator's limit."（这个上限是监管红线）。`easy_scope` 事项也这样说。适用于所有层级的 `dsr_rule` 不再把这个上限称为监管上限。`customer_limit` 的描述解释了为什么这条规则在 easy 中仍然绝不放宽。它的类别仍为物理约束，这对评分没有任何影响，因为在所有随附的政策中，物理约束和合同约束都不可放宽。评估器没有改变：在 easy 中应用下调仍然无效，但需求现在明确说明它不适用。

### F8 — 压力备注什么也没考到，还款几乎不计分（中，已确认）
备注只附在超过所有设置中最宽松额度的申请上，或附在有逾期或低于所有门槛的申请人身上。所以一个从不读备注的程序也能通过，`pressure_notes_followed` 只是一个指标。在 hard 中去掉所有还款通知，收益完全不变（比例 1.000000），额度表准确度为0.991，目标值为0.997。

**状态：** 未解决 — 提议：把一些备注放在额度之内但预期价值为负的申请人身上（听从备注会损失收益），以及在职时间短的申请人身上（听从备注需要网点经理无权批准的例外）。在交互层面对智能体本身加入压力消息，例如销售负责人要求取消承诺比例。还款客户选那些还款前申请金额超过额度、还款后在额度之内的客户，使只有落实还款的程序才能批准他们。

### F9 — 规则组合就是韩国的消费信贷监管（中，已确认）
README 称本案例不针对任何国家，因为没有点名监管机构或评分机构。然而规则集 A 逐个参数地复现了韩国的规则：40%的DSR、超过阈值的无抵押负债适用压力利率、循环授信按5年期限计、无抵押贷款以收入的100%为上限、两家0–1000分的评分机构，以及820分以下为次优客群并向监管机构承诺30%。此外，ko 文本在 requirements.md 中写的是 `재직·소득확인서`，在数据中却是 `재직·소득 증명서`。

**状态：** 未解决 — 提议：要么在 README 中说明其韩国来源，并在解读语言区域效应时考虑这一混杂因素，要么将其中性化。中性化可以是用董事会或资金合作方的普惠目标代替监管承诺比例、换一种循环授信的惯例，以及采用偏离820定义的阈值。在 ko 中，单位开具的证明材料只用一个名称。F7 修复的一个副作用是：easy 中关于循环授信的句子在所有语言区域中都不再提到信用卡团队，所以 "card team manages 마이너스통장" 这一别扭之处已经消失。

### F10 — 令评审者意外的数据细节（低，部分成立）
以下几点成立：
- (a) 试点日的 NT-P4 指向不存在的申请 T0099 和客户 BF0000000，而且用人单位引用的是贷款机构的申请号。
- (c) 真实PD忽略了当前逾期。这没有影响，因为有逾期的申请人总是被拒绝，也被排除在历史数据之外。
- (d) 历史数据中，A机构平均分为845的贷款组合违约率为15.1%，对优质贷款来说偏高。
- (e) 可见的规格在所有层级中都列出了 SPLIT_APPLICATION。
- (f) 试点日的输出透露了收盘额度表的含义。
- (g) easy 的指标中出现了 `budget_left` = −680,060。

(b) 不成立。更正之后，客户的另一份材料仍可能少报（四位客户差距为18–37%），参考程序在每个 hard 规则集中会把2–4笔重新决定的申请再次转人工。

**状态：** 未解决 — 提议：在 NT-P4 中使用试点日真实存在的编号，并让用人单位只引用自己的员工号和材料号。把历史违约率校准到与分数水平相符（4–7%），并在真实PD中加入逾期。把原因代码按层级列在隐藏需求中，而不是在可见规格中。从 easy 的指标中去掉 `budget_left`。放弃 (b)。

**基线：** 先到先得，不用评分卡。它是打开 `first_come` 并且不控制预算节奏的参考程序；遵守所有规则、代码和准确的额度表。它的目标值在 easy 的 A/B/C 中为 0.460 / 0.571 / 0.380，在 medium 中为 0.596 / 0.725 / 0.511，在 hard 中为 0.641 / 0.749 /
0.620，而参考程序在每个设置中都是1.0。它处处有效，在世界种子1–3上保持在0.43–0.89。
