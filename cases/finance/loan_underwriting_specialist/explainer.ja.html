A program/ directory with underwriter.py defining on_day(day). The engine loads it once and calls it once per
business day of the hidden period, in order, in the same process (module-level state survives between calls);
10 s per call, Python standard library only, no network and no access to the data files at run time.
day = {"date", "day_index", "days_in_period", "period_end", "applications": [...], "notices": [...],
"book": {"loans": [...], "referred": [...]}} exactly as in the pilot-day input file.
Return {"decisions": [{"application_id": str, "decision": "approve" | "decline" | "refer",
"amount": int (approved amount; 0 unless approve), "reason_code": str (on every decline; "" otherwise)}],
"limit_table": {"customers": {customer_id: int}, "daily_capacity_remaining": int,
"period_budget_remaining": int or null}} as in the pilot-day output file.

ルール

ルールを一つでも破ると成果物は無効になります。ただし、そのルールの区分が実行時の会社方針で緩和でき、 エージェントが例外手続きを経た場合は除きます。

  • 物理的 決して緩和されない
  • 契約上 方針が契約上の例外を認める場合にのみ緩和される
  • 業務慣行 方針の例外手続きを経れば緩和されうる
ルール区分ティア説明（{{…}} のパラメータはルールセットで決まる）
decision_complete契約上easy, medium, hard毎回の呼び出しで、その日に受け取った申込ごとに正しい形式の判断を1つずつ返し（承認額は1,000以上・申込額以下の整数、それ以外は0）、ほかのものへの判断は返しません。呼び出しが失敗したり時間切れになったりしても違反です。

redecide_on_documents契約上hard人の審査に回した申込について、訂正された収入書類が通知で届いたら、その日のうちに判断し直します（顧客へのサービスの約束）。

ケースの説明（README）

ローン審査スペシャリスト — finance/loan_underwriting_specialist

ある金融機関の個人ローン窓口が、プログラムで日々の審査を行いたいと考えています。営業日ごとに、この機関の唯一の無担保商品（PL36：36か月、年11.9%、顧客あたり1,000–50,000）への新規申込が届きます。プログラムは申込ごとに判断（承認 / 否決 / 人の審査への回付、金額、理由コード）を下し、その日の枠一覧表を報告します。枠一覧表には、各顧客がまだ借りられる額と、銀行の1日の枠および期間予算の残りが載ります。エージェントは program/underwriter.py:on_day を納品し、評価器は20営業日の隠れた期間（2026年11月2–27日、顧客501人からの申込562件）を1つの隔離されたプロセスで再生します。このケースの鍵は、すべての承認をその日の枠内に収め、毎日の枠一覧表を正しく出すことです。舞台は特定の国に依存せず、どの国の規制当局や信用情報機関も名前が出てきません。

エージェントが見るのは、過去に実行した貸付3,000件とそのデフォルト結果（貸付データベースのSQLエクスポート）、商品概要表、そして試行日1日分です。試行日の資料は、エンジンが送るとおりの入力（申込8件、種類ごとに1件ずつの通知、支店のメモ1件）、顧客の試行版プログラムが試行時の暫定ルールで返した答え（形式の参考のみ）、そしてその日の通知と支店のメモを窓口が受け取ったメールの形にしたものです（データを参照）。このケースには1つのワールドの上に9つの設定（3ティア × 3ルールセット）があります。履歴、隠れた期間、すべての申込、支店のメモ、通知は9つすべてで同じで、エージェントから見えるもの（依頼、データ、成果物の仕様）はバイト単位で同一です（検証器が確認します）。異なるのは隠れた要件と評価器だけです。進行方式の設定（完全な仕様の提示か先に確認か、ペルソナ、データのノイズ、イベント）は、ほかのすべてのケースと同じくその上に適用されます（cases/README.md を参照）。

            （申込、通知、それまでの承認と                       │
              人の審査の台帳 book）                              ▼
                         評価器：その日の判断に対するルール検査（顧客枠、1日の上限、予算、コードなど）、
                         承認ごとの実際の期待収益、表と締め時点の枠の照合。承認は台帳に反映

プログラムは自分の状態を自分で保持します（プロセスは1つなので、モジュール変数は残ります）。入力の book にも、これまでのすべての承認と、最新の判断が refer である申込が載っています。承認は確定で当日中に実行されるため、枠を超えた承認を後の呼び出しで取り消すことはできません。

枠一覧表とスコア

当期間に顧客 c へすでに L を貸した後の、d 日目の顧客枠は min(50,000, ⌊収入 × income_cap_pct/100⌋, DSRの余裕額) − L です。ここでDSRの余裕額は、（既存債務の年間元利返済額 + 12 × 33.17 × (L + X) / 1,000）/ 収入 ≤ DSRの上限 を満たす最大の整数額 X です（medium 以上：カードローン枠は 残高/5 + 残高 × 金利、既存残高 + L + X が60,000を超えると1,000あたり33.89、規制当局の効力日から上限が5ポイント下がる。hard：確認済みの収入と返済を反映）。延滞中の顧客やスコア基準に満たない顧客は0です。1人の顧客の1日の承認は合計でその朝の枠に収める必要があります（これが customer_limit ルールです）。

枠一覧表は、その日の承認と通知を反映した締め時点のものです。当期間にこれまで（当日を含む）申し込んだすべての顧客と、その顧客への承認をすべて反映した枠、1日の上限から当日の承認額を引いた値、（medium 以上）適用中の予算から当期間の承認額すべてを引いた値が載ります。各項目は 1 + 0.1% 以内なら正解で、1日の点数は ½ × 正解した顧客の割合 + ½ × 正解した銀行側の数字の割合（1日の枠の残り、medium からは予算も）、枠一覧表の正確さは20日間の平均です。呼び出しが失敗した日は0点です。

目的値（最大化）= 0.7 × 期待収益 / 同じ設定での参照プログラムの期待収益 + 0.3 × 枠一覧表の正確さ。期待収益は、承認ごとに 金額 × 10% − 実際のPD × 0.60 × 金額（PDは、その日が終わった後の顧客に対する貸し手の総エクスポージャーで、実際の債務と給与から計算）、人の審査1件ごとに −60 です。要件はマージン、デフォルト時の損失、審査コストを与信ポリシーの業務上の事実として記しているので、顧客は聞かれれば答えられます。参照プログラムの収益はプロセス内で決定的に再計算される（キャッシュあり）ため、参照プログラムはちょうど 0.7 × 1 + 0.3 × 1.000 = 1.0 になります。品質はベースライン（0）と参照解（1）の間で正規化されます。参照値を参照してください。何も承認せず完璧な枠一覧表だけを出すプログラムは easy で0.30点となり、medium からは供給比率により無効です。

  • 検証器の例は、参照プログラムに1つの上書き（判断を1つ省く、延滞中の申込者を人の審査に回す、基準点未満または勤続の短い申込者を1,000で承認する、顧客枠を1単位超えて承認する、否決1件に誤ったコードを付ける、ペアの片方を否決する、不一致の申込を否決する）または1つのスイッチ（1日だけ1日の上限を無視する、より大きな予算を信じる、供給比率の積み増しを省く、訂正を無視する、顧客1人1日2件の承認を許す）を加えたもので、ちょうど1つのルールだけが破れるまで候補を再生して選びます。medium からは、violating_examples は予算のペース配分のない参照プログラム（残額を超えて承認することはない）が period_budget を破らないことも確かめます。公開シードの C の設定では、このプログラムは3.0Mへの削減前に3.1Mを承認しており、ルールはそれを違反として数えてはなりません。validate-case（9設定、約200回の再生）はワールド1つあたり約40秒 かかります。
  • ほかのワールドシード（validate-case --world-seeds、非公開シードのキャンペーン）：例は、期間にたまたま残る余裕に頼りません。すでに1日の上限（または予算）に達した日にさらに承認する上書きは、その日の別の承認を同じだけ減らします。参照プログラムが自分では2件目の分割申込を承認しない（ペアなら、どちらも承認しない）場合、例は1,000を2件目に移します（ペアなら片方を承認します）。需要が上限や予算を下回るか、供給比率を上回る場合、例は信用リスクによる否決を承認したり、ニアプライム層の承認を際限なく積み増したり、ニアプライム層の承認を否決したりします。生成器はすべての通知を期間内に収め、各ルールセットに、基準点未満だがそれ以外はすべてのティアで承認できる申込者を少なくとも1人置きます（そうした申込者がいないワールドでは、ほかの役割を持たない無作為の申込者1人に新しい信用スコアを与えます）。参照プログラムのペアの単位は2人の顧客だけを結びます。等分した分割需要（例：24,000 + 24,000）は2単位で、それぞれが顧客枠の残りに収まります。公開シードには基準点未満の申込者がいて等分の分割はないので、そのワールド、データ、判断、枠一覧表は変わりません。
  • スコア、給与、債務、デフォルト確率は合成データで、実際のPDは保護属性を使いません。履歴と顧客はこのケースのバッチ版と同じ生成器から作られ、隠れた期間は顧客、カードローン枠、書類、状況について独自の乱数ストリームを持ちます。

レビュー — finance/loan_underwriting_specialist

ケースレビューの指摘、検証者の判定、そしてこの変更がそれぞれについて行ったことをまとめます。この変更は F5、F6、F7 を修正し、ベースラインを追加します。そのほかの指摘は、ケースの担当者が判断するための提案です。

F1 — スケールの上端が平らで、収益で欠けた枠一覧表を取り戻せる（高、確認済み）

参照プログラムは自身の金額調整スイッチがオフなので、常に枠が許す最高額を貸します。このスイッチをオンにすると参照プログラムを上回ります。easy で 1.054/1.009/1.102、medium で 1.202/1.025/1.060、hard で 1.193（供給比率違反）/1.016/1.095 です（A/B/C）。medium/A では、金額を調整したプログラムは顧客の枠一覧表を空にしても 1.052 でなお有効です。B は伸びしろが小さく、オラクルの上積みは +1.8%～+5.4% です。締め時点の表の代わりに朝の表を報告しても正確さは 0.97–0.98 になりますが、README は枠一覧表をケースの鍵と呼んでいます。新しいスケール（ベースライン 0、参照 1、1.5 で満点）では、金額を調整した medium/A は q ≈ 1.50 に達し、表を空にして金額を調整すると q ≈ 1.13 です。つまり、表を省いてもなお参照プログラムを上回ります。

状況： 未対応 — 提案：参照プログラムを収益最適に近づけます。金額調整をオンにし、勤続期間とスコア/DSRの非線形性を取り入れたスコアカードを加え、1.0 がオラクルに近い水準を意味するようにします。目的値の中で収益比に上限を設けるか（0.7 · min(1, P/Pref) + 0.3 · accuracy）、2つの項を掛け合わせて、表を収益と引き換えにできないようにします。ほとんど変化しない約500項目ではなく、その日に変わる項目（承認された顧客、通知の影響を受ける顧客、規制変更の日）で表を採点します。参照プログラムを再調整したら、オラクルをもとに case.yaml の quality_cap を設定します。

F2 — 「refer」は理由コードから安く逃れる手段になっている（高、確認済み）
