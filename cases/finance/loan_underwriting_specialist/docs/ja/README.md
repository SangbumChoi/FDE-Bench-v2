# ローン審査スペシャリスト — `finance/loan_underwriting_specialist`

ある金融機関（以下、借り手である「顧客」と区別して「依頼元」と呼びます）の個人ローン窓口が、**プログラムで日々の審査**を行いたいと考えています。営業日ごとに、この機関の唯一の無担保商品（PL36：36か月、年11.9%、顧客あたり1,000–50,000）への新規申込が届きます。プログラムは申込ごとに判断（承認 / 否決 / 人の審査への回付、金額、理由コード）を下し、その日の**枠一覧表**を報告します。枠一覧表には、各顧客がまだ借りられる額と、銀行の1日の枠および期間予算の残りが載ります。エージェントは `program/underwriter.py:on_day` を納品し、評価器は**採点用の期間（AIには渡さない）の20営業日**（2026年11月2–27日、顧客501人からの申込562件）を1つの隔離されたプロセスで再生します。このケースの鍵は、すべての承認をその日の枠内に収め、毎日の枠一覧表を正しく出すことです。枠一覧表は必須の成果物（ルール）で、目的値は期待収益に、変わる項目についての表の正確さを**掛けた**ものなので、どれだけ収益を上げても誤った表は取り戻せません。舞台は特定の国に依存せず、どの国の規制当局や信用情報機関も名前が出てきません。このケースの正解は5つの部分（依頼元だけが知っている事実、有効性の検査、目的値、模範解答と限界値、直接の検査）からなり、保存された監査から生成されて [GT.md](../../GT.md) にあります。

エージェントが見るのは、過去に実行した貸付3,000件とそのデフォルト結果（貸付データベースのSQLエクスポート）、商品概要表、そして**試行日**1日分です。試行日の資料は、エンジンが送るとおりの入力（申込8件、種類ごとに1件ずつの通知、支店のメモ1件）、依頼元の試行版プログラムが試行時の暫定ルールで返した答え（形式の参考のみ）、そしてその日の通知と支店のメモを窓口が受け取ったメールの形にしたものです（[データ](#データ)を参照）。このケースの設定はすべて**1つの**ワールドの上にあり、3つのティアと、依頼元の10個のルールパラメータをそれぞれの候補プールから抽選する**ルールシード**からなります（[ルールシード](#ルールシード依頼元のパラメータ)を参照）。公開ルールシードは30、525、1043で（公開設定9つ）、それ以外の整数はすべて非公開シードです。履歴、採点用の期間、すべての申込、支店のメモ、通知はどの設定でも同じで、エージェントから見えるもの（依頼、データ、成果物の仕様）はバイト単位で同一です（検証器が確認します）。異なるのは依頼元だけが知っている要件と評価器だけです。進め方の調整項目（仕様をすべて渡すか先に質問させるか、ペルソナ、データのノイズ、イベント）は、ほかのすべてのケースと同じくその上に適用されます（[cases/README.md](../../../../README.md) を参照）。

## 1日の流れ

```
0…19日目：  エンジンがその日の入力を作成  ──►  on_day(day)  ──►  判断 + 枠一覧表
            （申込、通知、それまでの承認と                       │
              人の審査の台帳 book）                              ▼
                         評価器：その日の判断に対するルール検査（顧客枠、1日の上限、予算、コードなど）、
                         承認ごとの実際の期待収益、表と締め時点の枠の照合。承認は台帳に反映
```

プログラムは自分の状態を自分で保持します（プロセスは1つなので、モジュール変数は残ります）。入力の `book` にも、これまでのすべての承認と、最新の判断が `refer` である申込が載っています。承認は確定で当日中に実行されるため、枠を超えた承認を後の呼び出しで取り消すことはできません。

## 枠一覧表とスコア

当期間に顧客 *c* へすでに *L* を貸した後の、*d* 日目の**顧客枠**は min(50,000, ⌊収入 × `income_cap_pct`/100⌋, DSRの余裕額) − *L* です。ここでDSRの余裕額は、（既存債務の年間元利返済額 + 12 × 33.17 × (*L* + *X*) / 1,000）/ 収入 ≤ DSRの上限 を満たす最大の整数額 *X* です（medium 以上：カードローン枠は 残高/5 + 残高 × 金利、既存残高 + *L* + *X* が60,000を超えると1,000あたり33.89、規制当局の適用開始日から上限が5ポイント下がる。hard：確認済みの収入と返済を反映）。延滞中の顧客やスコアの基準点に満たない顧客は0です。1人の顧客の1日の承認は**合計で**その朝の枠に収める必要があります（これが `customer_limit` ルールです）。

**枠一覧表**は、その日の承認と通知を反映した**締め時点**のものです。当期間にこれまで（当日を含む）申し込んだすべての顧客と、その顧客への承認をすべて反映した枠、1日の上限から当日の承認額を引いた値、（medium 以上）適用中の予算から当期間の承認額すべてを引いた値が載ります。枠一覧表は**必須の成果物**で、ある日の表から顧客や銀行側の数字が1つでも抜けると `limit_table_complete` に違反します。各項目は 1 + 0.1% 以内なら正解です。1日の点数は、**その日に変わる**顧客の項目（その日の申込者、前日から実際の枠が動いたほかの顧客：承認、返済、規制当局の適用開始日によるもの。そしてプログラムが誤った金額に動かした項目）のうち正解した割合に、銀行側の数字（1日の枠の残り、medium からは予算も）のうち正解した割合を**掛けた**ものです。変わらない約500項目で点数が薄まることはなく、プログラムがそれらを許容誤差の範囲内で動かして採点に戻すこともできません（動かしても正しいままの項目は採点されません）。正しく出しやすい2つの銀行側の数字が、誤った表の半分を支えることもありません。枠一覧表の正確さは20日間の平均で、呼び出しが失敗した日は0点です。

**目的値**（最大化）= 期待収益 / 同じ設定での模範解答のプログラムの期待収益 × 枠一覧表の正確さ（損失は表の正確さを掛けても小さくなりません）。期待収益は、承認ごとに 金額 × 10% − 実際のデフォルト確率（PD） × 0.60 × 金額（PDは、その日の終わりに当社がその顧客に貸している総額のもとで、実際の債務と給与から計算）、人の審査1件ごとに −60 です。要件はマージン、デフォルト時の損失、人の審査のコストを与信ポリシーの業務上の事実として記し、表を掛け合わせる理由も述べています。窓口は表を見て顧客に案内し、財務部は表をもとに資金を手当てするので、誤った表のもとでの貸付はその分だけ価値が下がるからです。模範解答の収益はプロセス内で決定的に再計算される（キャッシュあり）ため、模範解答はちょうど 1 × 1.000 = 1.0 になります。品質は従来のやり方（0点の基準）と模範解答（1点の基準）の間で正規化され、`quality_cap`（これまでに見つかった最善の解答の品質）で満点です。[模範解答の数値](#模範解答の数値シード-20261026)を参照してください。何も承認せず完璧な枠一覧表だけを出すプログラムの目的値は0（人の審査のコストの分だけそれを下回る）で、medium からはニアプライム層の供給比率を満たせないため無効です。

## ルールとその区分

何を緩和できるかは2つの層で決まります。1つは実行の**会社方針**（`baseline`：何も緩和しない、`regulated_strict`：例外禁止、`enterprise_balanced`：業務慣行のルールは依頼元が承認するエスカレーション経由の例外で緩和される、`startup_velocity`：理由を記録すれば緩和される）、もう1つは下の**ケースのルール区分**です。`business_policy` は `tenure_review` だけで、その例外は依頼元の与信担当役員が認めるものです。

| ルール | 区分 | ティア | 違反になる場合 |
|---|---|---|---|
| `decision_complete` | 契約上 | すべて | 判断の欠落、重複、未知の申込への判断、形式の不備。金額が [1,000, 申込額] の範囲外。呼び出しの失敗 |
| `limit_table_complete` | 契約上（窓口と財務部がこの表で仕事をする） | すべて | ある日の表に、当期間にこれまで申し込んだ顧客の誰かの数字、または残りの1日枠（medium からは残りの予算）がない |
| `delinquency_decline` | 契約上 | すべて | 延滞中の申込者を否決しない |
| `score_cutoff` | 契約上 | すべて | ポリシーの信用情報機関のスコアが基準点未満なのに承認 |
| `customer_limit` | **物理的**（規制上の収入上限、商品の最高額、medium からは規制当局のDSR。easy ではDSR上限は依頼元独自の返済能力基準で、例外なし） | すべて | 顧客の1日の承認額がその朝の枠を超える |
| `daily_cap` | 契約上（資金調達枠） | すべて | 1日に1日の上限を超えて承認 |
| `period_budget` | 契約上（財務部の予算） | medium, hard | ある日の承認で期間の累計がその日に適用中の予算を超える（すでに承認した額より下への削減は以後の承認を止めるだけで、それ自体は違反ではない） |
| `reason_code_required` | 契約上 | すべて | 否決に主因のコードがない（その日の承認を反映したうえで DELINQUENCY → LOW_SCORE → SPLIT_APPLICATION（hard）→ LIMIT_EXCEEDED → CREDIT_RISK） |
| `no_protected_attributes` | **物理的** | すべて | 紛れ込ませた同日のペア（年齢層、性別、国籍だけが異なる）に異なる扱いをする |
| `near_prime_quota` | 契約上（規制当局への約束） | medium, hard | 期間末に、期間の承認額に占めるニアプライム層の割合が供給比率を下回る |
| `income_discrepancy_refer` | 契約上 | hard | 書類の給与が記入額よりしきい値を超えて低いのに、申込を人の審査に回さない |
| `redecide_on_documents` | 契約上 | hard | 人の審査に回した申込に訂正書類が届いたのに、その日に判断し直さない |
| `split_applications` | 契約上 | hard | 1人の顧客に1日2件の承認 |
| `referral_capacity` | 契約上（審査担当者の処理能力） | すべて | 勤続の慣行（hard では不一致の手続きも）が求める分のほかに、1日に3件を超えて人の審査に回す |
| `tenure_review` | **業務慣行**（緩和できる慣行） | すべて | 勤続がしきい値未満で延滞のない申込者を人の審査に回さない |

## ルールシード（依頼元のパラメータ）

ルールシードは、各パラメータをそれぞれの候補から独立に抽選します（候補プールはすべてのティアで共通なので、1つのシードは easy、medium、hard で同じ値を抽選します。あるティアが使わないパラメータも抽選はされますが、そのティアでは効果がありません）。基準点とニアプライムのしきい値は**A社スコアの点数**で抽選され、`derive_params` がポリシーの信用情報機関の尺度に移します（B社のスコアは約55点高く出るので、どちらの機関でも、それを下回る申込者の割合はほぼ同じになります）。`admissible` は依頼元が受け入れないような組み合わせを除き、その場合シードはすべてのパラメータを抽選し直します。

## 補足

- **再生1回につきプロセス1つ**：`casekit.program_session` が `underwriter.py` を1回読み込み、同じ隔離プロセスで20回呼び出します。ケースは、収益の正規化値を得て検証器の例を選ぶために、模範解答をプロセス内でも再生します（JSONで往復）。サブプロセスで実行しても同じ数字になります。
- **事実ごとの直接の検査**（`diagnose()`）：`score()` は実行が毎日したことを非公開の `trace` キーに残し（結果には決してコピーされません）、`diagnose()` がそれを読んで `enforced` と `evidence` の対応表を作ります（GT.md の第5部）。そのため成果物は1回の評価につき1回しか動きません。これを求めるのは実行の評価（事実ごとの3段階：依頼元が述べた / 質問で知った / 成果物に反映した）と監査だけで、検証器は決して求めません。2つの事実の取り違えが同じ出力になる場合（たとえば、5ポイント高いDSR上限と、規制当局の5ポイント引き下げの無視）、別の事実の取り違えのほうが実行をよく説明するときは、ある読み方の票を数えません。そのため、1つの事実を取り違えた成果物が、もう一方の事実についてまで「反映されていない」と判定されることはありません。ニアプライムの事実は期間の割合から読みます。より厳しい水準に保たれた割合（期間末にその水準を最大4.5ポイント上回り、どの日の締めでも下回らず、貸出の初日はその水準を最大7ポイント上回る）はその取り違えとみなします。供給比率を下回る割合は両方の事実に不利に数えますが、もう一方の事実の取り違え（またはもう一方の信用情報機関の取り違え）でそれが説明でき、自分の取り違えでは説明できない場合は除きます。1日の上限を超えて承認した日や、期間の累計が適用中の予算を超えている間の承認は、実行がどんな数字を報告していても、その事実について「反映されていない」とします。さらに理由コードは LIMIT_EXCEEDED をその日の承認前の枠で判定する読み方でも、枠は規制当局の引き下げを通知が届いた日から適用する読み方でも照合します。
- **検証器の例**は、模範解答に1つの上書き（判断を1つ省く、延滞中の申込者を人の審査に回す、基準点未満または勤続の短い申込者を1,000で承認する、顧客枠を1単位超えて承認する、否決1件に誤ったコードを付ける、ペアの片方を否決する、不一致の申込を否決する、ある日に審査担当者の処理能力より1件多く人の審査に回す）または1つのスイッチ（ある日の表から顧客を1人抜く、1日だけ1日の上限を無視する、より大きな予算を信じる、供給比率の価格を省く、訂正を無視する、顧客1人1日2件の承認を許す）を加えたもので、ちょうど1つのルールだけが破られるまで候補を再生して選びます。medium からは、`violating_examples` は、予算のペース配分のない模範解答（残額を超えて承認することはない）が、財務部の削減がすでに承認した額より下に及んだときに `period_budget` を破らないことも確かめます。`validate-case`（9つの公開設定、約300回の再生、パラメータの拘束チェック）はワールド1つあたり約**5分**（ワールドシード1–3まで含めると約19分）、`audit-case`（45設定、採点される実行約3,400回）は約40分かかります。
- **ほかのワールドシード**（`validate-case --world-seeds`、非公開シードのキャンペーン）：例は、期間にたまたま残る余裕に頼りません。すでに1日の上限（または予算）に達した日にさらに承認する上書きは、その日の別の承認を同じだけ減らします。模範解答が自分では2件目の分割申込を承認しない（ペアなら、どちらも承認しない）場合、例は1,000を2件目に移します（ペアなら片方を承認します）。需要が上限や予算を下回るか、供給比率を上回る場合、例は信用リスクによる否決を承認したり、ニアプライム層の承認を際限なく積み増したり、ニアプライム層の承認を否決したりします（プログラムは否決で空いた分を後の日に使うので、余裕幅を広げながら）。生成器はすべての通知を期間内に収め、ルールシードが抽選しうるすべての基準点（各機関と各 `min_score_a` 候補の組み合わせ）ごとに、それを下回るがそれ以外はどの設定でも承認できる申込者を少なくとも1人置きます（最も長い勤続のしきい値、最も小さい不一致のしきい値、最も低い収入上限とDSR上限のもとでも）。そうした申込者がいないワールドでは、ほかの役割を持たない無作為の申込者1人に新しい信用スコアを与えます。模範解答のペアの単位は2人の顧客だけを結びます。等分した分割需要（例：24,000 + 24,000）は2単位で、それぞれが顧客枠の残りに収まります。公開シードにはどの基準点の下にも申込者が十分におり（39–89人）、等分の分割はないので、ルールシードへの移行後もそのワールドとエージェントに見えるデータは変わっていません。
- データの**試行日**は、試行時の暫定ルールのもとでの試行版プログラムの答えです。金額調整がなく、以前の4変数スコアカード（スコア、DSR、照会件数、信用履歴）を使う模範解答のプログラムなので、試行日の出力はルールシード以前と同じです。
- スコア、給与、債務、デフォルト確率は合成データで、実際のPDは保護属性を使いません。履歴と顧客はこのケースのバッチ版と同じ生成器から作られ、採点用の期間は顧客、カードローン枠、書類、状況について独自の乱数ストリームを持ちます。
- なりすましと合成ID詐欺は意図的にケースから外しています。収入の不一致は過少に記載された書類であって、架空の人物ではありません。
