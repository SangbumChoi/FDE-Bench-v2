A program/ directory with strategy.py defining on_day(day). The engine loads it once and calls it once per
hidden session after the close, in order, in the same process, so module-level state survives from one call to
the next; 10 s per call, Python standard library only, no network and no data files at run time.
day = {"market": {...}, "portfolio": {...}, "notices": [...]} exactly as in the sample call file.
Return {"orders": [...], "status": {"stock_weights": {ticker: percent}, "sector_weights": {sector_code: percent},
"buying_power": number, "drawdown_pct": number}} as in the sample output file.
An order is {"ticker": str, "side": "buy" | "sell", "qty": int, "at": "open" | "p10"} ("at" defaults to "p10");
at most one order per ticker per session; orders execute in the next session, sells before buys.

주식 매매 전략가 — finance/stock_trading_strategist

한 데스크가 가상의 아든 거래소에서 고객의 소규모 계좌를 운용하며, "지수를 그냥 보유하는 것보다 나은 매매 프로그램, 고객의 지시와 저희 한도는 지키면서 매일 계좌가 그 한도에 비해 어디쯤 있는지도 알려 주는 프로그램"을 요청합니다. 에이전트는 4개 업종 16개 종목의 1년치 합성 과거 데이터(250거래일, 2025년 6월 2일~2026년 5월 15일: 종목별 시가, 개장 10분 후 가격, 종가, 거래량, 그리고 지수, 기업행위, 거래정지, 분기 실적발표), SQL 덤프로 된 데스크 데이터베이스, 데스크의 메일, 호출 예시와 반환 예시를 받고(데이터 파일 참고), 프로그램 program/strategy.py:on_day를 납품합니다. 평가기는 그 뒤에 이어지는 숨은 80거래일(2026년 5월 18일~9월 4일)을 격리된 프로세스 하나에서 재생합니다. 계좌는 현금 10,000,000으로 시작합니다. 모든 가격은 합성 데이터이며 거래소는 특정 국가와 관계가 없습니다.

이 케이스의 핵심은 날짜가 정해진 고객의 지시와 한도를 지키면서(위반이 하나라도 있으면 프로그램은 무효) 지수를 이기고, 일별 상태표를 보고하는 것입니다. 케이스에는 하나의 월드 위에 9개 설정(티어 3개 × 규칙 세트 3개)이 있습니다. 과거 데이터, 숨은 기간, 날짜가 정해진 모든 통지는 9개 설정에서 모두 같고, 에이전트가 보는 것(요청, 데이터, 산출물 명세)은 바이트 단위까지 동일합니다(검증기가 확인합니다). 다른 것은 숨은 요구사항과 평가기뿐입니다. 진행 방식(engagement) 설정은 모든 케이스와 마찬가지로 그 위에 적용됩니다(cases/README.md 참고).

상태표와 점수

표는 방금 일어난 마감 시점의 계좌를 나타냅니다(그 거래일의 체결, 기업행위, 지급을 반영한 뒤, 새 주문을 내기 전).

  • stock_weights: 보유 종목별 평가액(주식 수 × 마지막 체결 종가, 현재 주식 수 기준)이 equity에서 차지하는 비율(%);
  • sector_weights: 보유분이 있는 업종코드별 합계;
  • buying_power: 결제 완료 현금 + next_date까지 사용 가능해지는 미결제 매도대금에서, (medium 이상) 통지는 받았지만 아직 지급하지 않은 고객 출금액(이번 마감 시점 기준 금액)을 뺀 값, 최소 0;
  • drawdown_pct: 100 × (1 − (자산 + 지금까지의 지급액) / 모든 마감 시점에 걸친 그 합계의 최고치, 시작 시점의 10,000,000 포함).

비중과 낙폭은 0.05포인트, 매수 여력은 1 + 0.1% 안이면 맞은 것으로 봅니다. 하루의 점수는 네 부분(맞은 종목 비중의 비율, 맞은 업종 비중의 비율, 매수 여력, 낙폭)의 평균이고, 표의 정확도는 80번 호출의 평균입니다(실패한 호출은 0점).

목표(최대화) = 0.8 × 수익 점수 + 0.2 × 표 정확도. 최종 가치 = 9월 4일의 최종 순자산(마지막 마감 시점의 현금 + 미결제 대금 + 보유분에서 수수료와, medium 이상이면 매도 거래세를 뺀 값) + 고객에게 지급한 모든 현금. 수익 점수 = (최종 가치 − 첫 거래일 p10에 사서 보유한 지수) / 그 설정에서 참조 프로그램이 거둔 같은 초과분(프로세스 안에서 결정적으로 다시 계산)이며, 지수보다 낮으면 0입니다. 참조 프로그램이 지수를 앞선 폭이 500,000(자본의 5%, MIN_EDGE)에 못 미치거나 지수에 뒤지는 경우 — 다른 월드 시드에서는 실제로 일어납니다(시드 2의 지수는 숨은 기간에 48% 오릅니다) — 비교 기준을 지수 대신 참조 프로그램의 최종 가치보다 500,000 낮은 수준으로 두어, 수익 점수가 정의되고 계좌 가치에 따라 증가하도록 합니다. 이 월드에서는 모든 참조 프로그램이 지수를 5.8%–13.5% 앞서므로 비교 기준은 지수입니다. 참조 해답의 점수는 정확히 0.8 × 1 + 0.2 × 1.000 = 1.0입니다. 지수를 보유하면 0.2 × 표 점수가 됩니다. 기준선(baseline_solution, reference/baseline.py)은 엔지니어가 없을 때 데스크가 가진 것입니다. 계좌를 현금으로 두고 주문을 내지 않으며 올바른 표를 보고합니다(medium부터는 매수 여력에서 대기 중인 출금을 뺍니다). 모든 설정에서 유효하며 점수는 0.24–0.32입니다(비용을 빼면 지수는 시작 자본보다 0.7% / 0.9% 낮게 끝나고, 참조 해답의 초과분은 5.8%–13.5%입니다). 품질은 둘 사이에서 정규화됩니다: q = (목표값 − 기준선) / (1 − 기준선). 따라서 아무것도 하지 않으면 0, 참조 해답은 1입니다. 다른 월드 시드에서는 참조 해답이 현금보다 낮게 끝날 수 있습니다(예: 시드 3, 7, 42에서 9개 설정 중 6–9개). 그 경우 기준선이 참조 해답보다 나쁘지 않으므로 프레임워크는 단순 비율로 돌아갑니다(REVIEW.md, F1 참고).

  • 10분 관행을 없앤 이유: 그것은 예전의 완화 가능한 규칙이었습니다. 대량 주문 승인이 업무 관행(business-policy) 규칙이 된 지금, 완화 가능한 관행이 하나 더 있으면 완화의 가치가 흐려지고, 단순한 계약상 규칙으로 두면 고정 비용만 더할 뿐입니다. 시가 단일가 매매(스프레드 없음)는 이제 에이전트가 찾아낼 수 있는 체결 방식의 선택지입니다.
  • 유동성을 고려한 규모 결정이 필요한 이유: 정리 기한(계약상)과 대량 주문 기준(업무 관행)이 함께, 계좌가 어떤 종목이든 보유할 수 있는 양에 상한을 둡니다. 어떤 종목이든 컴플라이언스가 추가하는 종목이 될 수 있기 때문입니다. 엄격한 정책 아래의 프로그램은 이에 맞춰 규모를 정해야 하고, 완화를 허용하는 정책 아래에서는 에이전트가 데스크 헤드에게 예외를 요청해 전체 포지션을 보유할 수 있습니다. 이것이 완화가 이득이 되는 이유입니다(+28%에서 +90%).
  • 월드는 팩터 모델입니다. 시장, AR(1) 업종·종목 드리프트(참조 해답이 활용하는 모멘텀), 개별 노이즈로 이루어지며, 하루는 밤사이 갭, 첫 10분, 나머지 장으로 나뉩니다. 여기에 거래정지, 기업행위, 실적발표, 급락, ZENT의 인수 갭, 하락장과 회복이 각자의 난수 스트림으로 더해집니다. 종목코드와 거래소는 가상입니다.

여러 하위 주장은 맞습니다. 기준 × 기한(기한 안에 다 팔 수 있는 종목의 양)은 A / B / C에서 하루 거래량의 0.18 / 0.20 / 0.18입니다. 출금액 차이는 5% 미만입니다(2.50 / 2.58 / 2.59–2.62 M). 유보분은 호출 23–31에만 들어가며 목표값의 약 0.6%입니다. 리스크 한도 축소를 무시해도 hard/B와 hard/C에서는 유효하고, 출금을 무시해도 hard/C에서는 유효합니다. 서킷브레이커는 참조 해답의 주문을 하나도 거부하지 않습니다. 핵심 주장은 성립하지 않았습니다. 각 규칙 세트의 매매제한 목록을 서로 바꿔 넣어도 18개 교차 조합이 모두 다른 규칙(대량 주문, 정리, 종목 한도, 업종 한도, 출금)에서 무효로 남습니다.

상태: 미해결 — 제안: 유동성 곱의 간격을 벌려서(예: 4%×2 = 0.08, 6%×3 = 0.18, 9%×4 = 0.36) 규칙 세트마다 규모 결정이 실제로 달라지게 합니다. 출금 기준이 더 중요해지게 합니다. 자본의 %, 누적 최고치의 %, 또는 고정 금액에 수수료를 더한 것을 서로 다른 시차를 두고 통지하는 식입니다. 한도 축소와 지급의 일정을 잡아서 낙폭을 관리하는 계좌에도 구속력이 있게 합니다. 예를 들어 계좌가 다시 투자된 회복 국면에 축소가 효력을 갖게 합니다. 적용 중인 모든 규칙이 각 설정에서 참조 해답을 실제로 구속하는지 확인하는 검증기 검사를 추가합니다.

F7 — easy 티어의 범위 문장에 대량 주문 규칙이 빠져 있었음 (중간, 확인됨)

easy 요구사항에는 "이번 라운드는 매매의 기본, 매매제한 목록(추가 포함), 현황표만 봅니다"라고 되어 있었습니다. 하지만 large_order_approval은 easy에서도 적용되고 검사되며, easy 범위 질문 목표에도 들어 있습니다. "이번 라운드에는 무엇이 평가되나요?"라는 질문에 그 문장으로 답하는 고객은 이 규칙을 빠뜨릴 수 있습니다. 하위 티어의 문장들도 하네스 메모처럼 읽혔습니다("아직 적용하지 않습니다", "아직 점검하지 않으며").

상태: 이번 변경에서 수정됨 — 다섯 로캘 모두에서 easy 문장은 이제 고객이 말할 법한 형태로 바뀌었습니다: "이번 첫 라운드는 고객의 투자 지침 없이 돌려 보는 시험 운용입니다. 매매의 기본, 매매제한 목록(추가 포함), 위의 대량 주문 승인 규칙, 상태표만 봅니다…". medium 문장은 이제 "고객의 최대 낙폭 한도는 실제 계좌에 적용되는 것이라 이번 라운드의 백테스트에는 적용하지 않으며, 메모도 이번 라운드와 관계가 없습니다."입니다. 규칙과 채점은 바뀌지 않았습니다.

F8 — 몇몇 사실이 비현실적임 (중간, 확인됨)

영어 request.md는 "a small proprietary book … for a client"라고 하지만, 자기자본 계좌(prop book)는 고객 계좌가 아니며, 다른 로캘은 고객의 계좌라고 합니다. 시가총액이 약 8B인 종목들이 하루에 주식의 약 0.05%만 거래됩니다(VOLUME_SCALE 0.06). 심어 둔 드리프트 때문에 보이는 1년 동안 DUNE +335%, CURA +177%, FERN −81%가 됩니다. 시범 운용은 "저희가 운용하는 모든 계좌에 적용"되는 정책 아래에서 평균 거래량의 36%인 LUMO 40,000주를 삽니다. 서킷브레이커 거래일의 시세에는 마감까지 매매가 중단되었는데도 시가와 p10이 있고 거래량이 3배입니다. 영어는 매도 측 세금을 "sales tax"라고 부릅니다.

상태: 미해결 — 제안: request.md에서 관리형 고객 계좌(managed client account)라고 부릅니다. request.md는 모든 설정에서 같으므로 이렇게 바꿔도 됩니다. 종목을 소형주로 만들거나, 현실적인 회전율과 함께 계좌를 더 크게 만듭니다. MU_SD를 줄여서 모멘텀이 연간 한 자릿수 알파를 내게 합니다. 시범 운용의 규모를 기준 안으로 맞춥니다. 서킷브레이커 거래일의 시세는 종가 단일가만 보여 주게 합니다(open = p10 = close, 단일가 거래량). 세금 이름을 "transaction tax on sales"나 "stamp duty"로 바꿉니다. 대부분 데이터와 참조 수치를 바꾸므로 F2와 함께 다루는 것이 맞습니다.

F9 — 한국어 용어가 일관되지 않음 (낮음, 확인됨)

한국어 텍스트는 요구사항과 질문 목표에서 desk head를 데스크장이라고 불렀지만, 메일 발신자와 서명에서는 데스크 헤드라고 했습니다. status table은 요구사항에서 현황표였지만 요청, 데이터베이스 주석, 시범 운용 메일에서는 상태표였습니다. restricted_list_history에 관한 문장은 테이블 자체가 해제되었다고 읽혔습니다. drawdown은 손실 한도 / 손실폭이었고, 세금은 한국의 법정 세목 이름인 증권거래세였습니다.

상태: 이번 변경에서 수정됨 — 한국어 요구사항과 질문 목표는 이제 데스크 헤드, 상태표, 최대 낙폭 한도 / 낙폭, 매도 거래세를 씁니다. 테이블 문장은 이제 "…테이블에 있는 항목은 모두 이전에 해제된 것입니다"입니다. ja/zh/es에도 같은 점검을 해 보니 같은 두 가지 불일치가 있었고, 이제 에이전트가 보는 메일과 데이터베이스의 용어를 씁니다. ja는 デスク責任者, ステータス表(이전: デスク長, 状況表), zh는 交易台主管, 状态表(이전: 交易台负责人, 状况表), es는 "tabla de estado"(이전: "tabla de situación"; "jefe de la mesa"는 원래 일관됨)입니다. 보이는 데이터는 바뀌지 않았습니다. 소유자에게 남긴 일: zh는 drawdown mandate를 回撤授权("낙폭 승인")으로 옮기는데, 最大回撤限制가 더 자연스럽게 읽힐 것입니다.

F10 — 일부 질문 목표는 데이터에서 읽어낼 수 있음 (낮음, 일부 확인됨)

보이는 시범 운용 메일에는 "전체 모드(매도 시 거래세 0.2%, T+2 결제)"라고 적혀 있습니다. 시범 운용의 체결 내역은 스프레드 없는 시가 체결과 0.04% 수수료를 보여 줍니다(539.33 = 0.0004 × 20,000 × 67.4163). 하지만 검증 담당자는 데이터만으로 완전히 답이 나오는 질문 목표는 없다는 것을 확인했습니다. 메일은 다른 모드가 있음을 암시하고(easy는 간이 모드로 돌아감), 최소 수수료, p10의 반스프레드, 매도 우선 체결은 데이터에 없습니다. 숨은 기간과 설정별 참조 프로그램은 설계상 저장소에 들어 있습니다.

상태: 미해결 — 제안: fills, costs, settlement를 확인형 목표로 표시해 질문하거나 NOTES.md에 명시적으로 적으면 점수를 주거나, 시범 운용 메일에서 파라미터를 빼냅니다. 비공개 시드가 작동하게 되면(F1), dataset/hidden과 dataset/gt를 공개 릴리스에서 제외합니다. 예를 들어 릴리스 아티팩트로 따로 배포하거나 해시만 배포합니다.

기준선: 계좌는 현금으로 남아 주문을 내지 않고 올바른 상태표를 보고합니다(reference/baseline.py). 목표값은 0.243 / 0.242 / 0.242(easy A/B/C), 0.269 / 0.286 / 0.274(medium), 0.274 / 0.288 / 0.323(hard)으로, 모든 설정에서 1.000인 참조 해답의 24–32%입니다.
