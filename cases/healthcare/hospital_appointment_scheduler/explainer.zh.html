层级

层级适用内容
easy每日预约的核心：初诊 = 连续两个号源，复诊 = 一个；科室对应；不早于最早可约日期；紧急预约时限；紧急预留号 （上午时段的前两个号源到前一天为止留给紧急申请）；市民日假日有一个科室停诊，而出诊表里仍列着它；初诊每天的 现场翻译人数；调整预约的提前通知期；候诊名单的优先顺序；复诊约给上次接诊医生（可放宽）；每日现况表。缺勤和 翻译通知、转诊单有效期、抽血、爽约和重复申请不在范围内。
medium在 easy 基础上，加上会过期的转诊单、在检验科每日上限内于就诊至少一个工作日前进行的空腹抽血、医生缺勤（缺勤 医生的预约须在提前通知期内调整）以及翻译请假（当天少一名翻译）。

医院预约专员 — healthcare/hospital_appointment_scheduler

一家中等规模的门诊医院希望预约处 每天通过程序运转。每个工作日，程序拿到当天新的预约申请、当天的通知（患者取消预约、医生 病休或开会、翻译请假、工作人员备注）、今天的到诊情况，以及当前的预约簿和候诊名单（即它自己此前决定的结果）。程序把申请约进 医生在接下来十个工作日里空闲的20分钟号源，为受通知影响的预约重新安排，用候诊名单填补空出的号源，并按科室报告 每日现况表。 智能体交付 program/scheduler.py:on_day；评估器在一个隔离的进程里回放 20个工作日的隐藏时段（2026年11月9日 – 12月4日： 新申请1,184条，开始时候诊45条、已预约359条）。本案例的核心是 号源利用率：在医生的时间里看尽可能多的患者，同时不违反任何 规则。案例不针对任何国家：没有国家医保方或付费方的规则。

智能体看到的是预约系统的纯文本 SQL 导出（五个科室的14位医生及其语言和每周出诊时段、出诊表、四周的申请和预约及其结果 —— 1,074个预约，在已就诊或爽约的预约中有22%爽约 —— 取消、到诊、候诊名单的历史，以及11月9日起已约上的359个预约）、预约处收到的 邮件（缺勤、翻译请假、工作人员备注、一条院长熟人的请求，以及门诊部办公室的通知：11月23日市民日，出诊表没有为此修改），以及 一天的 试点日 数据：一份与引擎发送的完全相同的输入（每种通知各一条，一条熟人备注）和客户的试点程序按其临时规则给出的答复 （仅供参考格式）。本案例在 同一个 世界上有九个设置（3个层级 × 3个规则集）：历史、隐藏时段、每条申请、取消意向、通知和备注 在九个设置中都相同，智能体看到的内容（需求、数据、交付物规格）逐字节一致（由校验器检查）。不同的只有隐藏需求和评估器。与所有 案例一样，交接方式的各项设置叠加在其上（见 cases/README.md）。

现况表（按科室，在当天的动作执行之后，针对预约范围 d+1…d+10）：

  • free_slots：该科室医生出诊表中没有预约、任何人都可以约的号源 —— 不是预留号，不在市民日停诊的科室，（medium 及以上） 也不在已通知的缺勤日；

评审结果（REVIEW）

评审 — healthcare/hospital_appointment_scheduler

案例评审的发现（F1–F9）、核查者的结论，以及本次修改对每一项做了什么。除非另有说明，数字均为种子 20261116 下的结果；"q" 是 归一化质量（基线 0，参考解 1）。

F1 — 利用率已到顶，紧凑排号收益很小（高，部分成立）

容量约为每天79个号源，需求约83–86个，所以参考解在 easy 和 medium 中已填满98%的号源。我们所知最好的有效变体（紧凑排号；在 hard 中再加上更低的超额预约阈值和真实爽约率）只给目标值带来 +0.1% 到 +1.5%，相对新基线为 q = 1.005–1.056。有效程序的得分仍 分布在约0.79到1.0之间，但差距来自几个粗粒度的杠杆（是否放开预留号、D10 的备注、到底超不超额预约），而不是紧凑排号。原先 "在1.0处被截断"的问题随新量表消失了，但现在政策上限1.5已够不着：已知的有效程序拿到的质量分都不超过约70%。

状态： 未解决 — 提议：先决定这里是否应能衡量更好的优化。如果应当，就让排号更难而不是降低需求（更多绑定某位医生的复诊、 翻译和抽血集中的日子、长短不一的就诊时长），并加入更强的参考解或上界，使紧凑排号和前瞻能让得分变动几个百分点。如果不应当， 就把 case.yaml 中的 quality_cap 设为约1.1，让达到已知最佳水平的程序拿满分。

F2 — 超额预约用不到逐个患者的爽约估计（高，已确认）

把所有符合条件的复诊号源都超额预约到上限（阈值0），在 hard A/B/C 中得 0.999 / 1.005 / 1.000（q 0.997 / 1.015 / 1.000），全部 有效；阈值0.10略高于参考解，不超额预约则为 0.943–0.952。所以超不超额预约很重要（约5%），但 hard 层级本想考查的风险筛选并不 重要。在本次修改之前，10对12的权衡只以得分权重的形式写出，而模拟客户可能不会透露它。

状态： 未解决 — 提议：让风险筛选决定得分：提高冲突成本（或加上医生加班成本），使一刀切的超额预约明显净亏，并拉大爽约率的 分布，使有选择的超额预约明显胜出。在 validate-case 中加一项检查：阈值为0的程序至少比参考解低3%。（本次修改在 F6 下已经把这一 权衡作为业务事实写进 hard 需求：两位患者都来时医生会拖延，这比空一个号源的损失稍大。）

F3 — 规则集的数值不起作用或只朝一个方向起作用（高，已确认）

urgent_days 取 1、3 或 10，在全部九个设置中都得到目标值 1.0000 且没有违反：紧急申请总是本地语言、不需要抽血、对象就是明天， 而且只在明天的预留号无人动用时才生成。在本次修改之前，把所有数值都取最保守的值（翻译2、检验科5、超额预约1、提前通知4、紧急1） 在9个设置中有8个有效，得分0.98–1.00，所以区分规则集的只有 waitlist_order（以及微弱的 closed_dept）。F8 修复后，这个保守 组合在9个中有8个无效（waitlist_priority：没用上的翻译和检验科名额不再为被跳过的患者免责），但仅提前通知4 + 超额预约1 + 紧急1 仍在9个中有6个有效，得分0.988–1.000。
