# 评审 — `healthcare/hospital_appointment_scheduler`

案例评审的发现（F1–F9）、核查者的结论，以及本次修改对每一项做了什么。除非另有说明，数字均为种子 20261116 下的结果；"q" 是
归一化质量（基线 0，参考解 1）。

### F1 — 利用率已到顶，紧凑排号收益很小（高，部分确认）

容量约为每天79个号源，需求约83–86个，所以参考解在 easy 和 medium 中已填满98%的号源。我们所知最好的有效变体（紧凑排号；在
hard 中再加上更低的超额预约阈值和真实爽约率）只给目标值带来 +0.1% 到 +1.5%，相对新基线为 q = 1.005–1.056。有效程序的得分仍
分布在约0.79到1.0之间，但差距来自几个粗粒度的杠杆（是否放开预留号、D10 的备注、到底超不超额预约），而不是紧凑排号。原先
"在1.0处被截断"的问题随新尺度消失了，但现在政策的质量上限1.5已够不着：已知的有效程序拿到的质量分都不超过约70%。

**状态：** 未解决 — 提议：先决定这里是否应能衡量更好的优化。如果应当，就让排号更难而不是降低需求（更多绑定某位医生的复诊、
翻译和抽血集中的日子、长短不一的就诊时长），并加入更强的参考解或上界，使紧凑排号和前瞻能让得分变动几个百分点。如果不应当，
就把 case.yaml 中的 `quality_cap` 设为约1.1，让达到已知最佳水平的程序拿满分。

### F2 — 超额预约用不到逐个患者的爽约估计（高，已确认）

把所有符合条件的复诊号源都超额预约到上限（阈值0），在 hard A/B/C 中得 0.999 / 1.005 / 1.000（q 0.997 / 1.015 / 1.000），全部
有效；阈值0.10略高于参考解，不超额预约则为 0.943–0.952。所以超不超额预约很重要（约5%），但 hard 层级本想考查的风险筛选并不
重要。在本次修改之前，10对12的权衡只以得分权重的形式写出，而模拟客户可能不会透露它。

**状态：** 未解决 — 提议：让风险筛选决定得分：提高冲突成本（或加上医生加班成本），使一刀切的超额预约明显净亏，并拉大爽约率的
分布，使有选择的超额预约明显胜出。在 validate-case 中加一项检查：阈值为0的程序至少比参考解低3%。（本次修改在 F6 下已经把这一
权衡作为业务事实写进 hard 的隐藏需求：两位患者都来时医生会拖延，这比空一个号源的损失稍大。）

### F3 — 规则集的数值不起作用或只朝一个方向起作用（高，已确认）

`urgent_days` 取 1、3 或 10，在全部九个设置中都得到目标值 1.0000 且没有违反：紧急申请总是本地语言、不需要抽血、对象就是明天，
而且只在明天的预留号无人动用时才生成。在本次修改之前，把所有数值都取最保守的值（翻译2、检验科5、超额预约1、提前通知4、紧急1）
在9个设置中有8个有效，得分0.98–1.00，所以区分规则集的只有 `waitlist_order`（以及微弱的 `closed_dept`）。F8 修复后，这个保守
组合在9个中有8个无效（`waitlist_priority`：没用上的翻译和检验科名额不再为被跳过的患者免责），但仅提前通知4 + 超额预约1 +
紧急1 仍在9个中有6个有效，得分0.988–1.000。

**状态：** 未解决 — 提议：让剩下的数值双向起作用，使最谨慎的取值也是错的（例如在提前通知期之外再设一个最长改约延迟，或者给
紧急预约时限配上分诊给出的最早可约日期，使"明天"并不总是对的）。生成一些需要翻译或抽血的紧急申请，或在明天的预留号已用掉时
才到达的紧急申请，让 `urgent_days` 起约束作用。把保守组合程序加入 validate-case 的区分度检查，要求它无效或差3%以上。

### F4 — 放宽复诊惯例奖励的是一刀切，而不是有针对性的放宽（高，已确认）

把每个复诊都约给最早有空的同事（287–332个例外），目标值提高2.0–5.8%；只对缺勤医生的患者放宽（43–51个例外），提高0.0–1.3%。
在新尺度下，一刀切放宽值 q 1.11–1.29，即罚分前最终得分 +0.04 到 +0.115，因此在 startup_velocity（罚分0.05）下，9个设置中有
5个划算；而临床上合理的有针对性的放宽（+0.000 到 +0.024）一次都不划算。一次批准就涵盖所有例外。

**状态：** 未解决 — 提议：给病休儿科医生的部分复诊设一个落在缺勤期内的临床期限，使遵守惯例会让这些患者看不上病，只有经批准的
有针对性的例外才能挽回价值。对每个由非上次接诊医生看的复诊加一点运营成本，使一刀切放宽的得分低于有针对性的放宽。在 README 中
用最终得分来报告放宽的效果。

### F5 — 可见的历史与医院规则相矛盾（中，已确认）

在导出中，09:00/09:20 的151个历史预约里有106个是提前两个及以上工作日约上的 S/R 申请，而预留号规则禁止这样做；需翻译的初诊
一天多达10个（上限2–4），空腹抽血一天多达10人（上限5–7）。`_history` 在没有预留号、翻译和检验科逻辑的情况下把号源填到92%，
而初始预约簿符合规则。试点答复使用的候诊顺序是 `received`（规则集 B 的），也没有预留号。

**状态：** 未解决 — 提议：按三个规则集共有的规则（保留预留号，需翻译的初诊每天最多2个，抽血每天最多5人）生成历史，或者让门诊部
办公室发邮件说明预留号、翻译排班和检验科上限从11月9日起执行。把检验科上限改写为"门诊采血室的空腹抽血名额"，让这个小数字显得
合理，并给试点程序一个与所有规则集都不一致的临时顺序（或在 README 中说明它与 B 一致）。

### F6 — 应问事项里有客户被告知绝不能透露的计分内容（中，部分确认）

`scoring` 和 `scoring_hard` 是计分公式和权重，`status_table`（"质量的20%"）和 `several_departments`（"成本为3"）也带着权重，
而客户提示词禁止描述得分或权重；Ask-F1 召回率因此到不了1。"已经可见"这一点并不成立：在默认的 `interact_req` 条件下，智能体只
看到 request.md 和数据，所以 `interface`、`visit_length` 和时段的结束日期仍然需要提问。

**状态：** 已在本次修改中修复 — 这四个事项在全部五个语言版本中改写为不带权重的业务事实（医生时间空着是最大的损失；等候、没约上
的申请和更改都是成本；有爽约时，算数的是真正来的患者；两位患者都来的超额号源比空号源损失稍大；多跑的趟数是成本）。hard 的隐藏需求
为最后这条事实增加了所需的一句话；计分不变。`interface`、`visit_length` 和 `evaluation_period` 保留。

### F7 — 较低层级的范围写成了测试指令（中，部分确认）

easy 和 medium 写的是"即使同一患者申请两次，每条申请也是各自的一次就诊"和"抽血不在范围内"，读起来像是对程序的指令，而不是
医院的事实；而在这些层级去重实际上是无效的（`waitlist_priority`，187–342次）。关于备注的指引（院长的熟人、D10 的下午）只在
hard 中写明，尽管照 D10 的备注做在 easy 和 medium 中也会损失6.7–7.5%。

**状态：** 已在本次修改中修复 — easy 和 medium 的范围条目现在在全部五个语言版本中像客户会说的那样说明原因：本轮由转诊窗口和
检验科自己处理转诊单和空腹抽血；不为爽约做安排；第二条申请也单独约，因为预约处光看申请分不清是不是同一病情。计分不变，相应的
事项也已改写措辞。留作提议：既然每个层级的数据里都有备注，把备注段落和 `staff_notes` 事项移到所有层级。

### F8 — 候诊优先顺序的免责过宽，以及提前通知的漏洞（低，已确认）

用旧检查器复现：从不预约需翻译初诊的程序在9个设置中9个有效（0.950–0.988），把需抽血的申请放到最后预约的程序在 medium/hard
的6个设置中6个有效（0.998–1.006），而某天取消、第二天再约到后一天的复诊在规则集 A 和 C（提前通知3和4；提前通知为2时不会
发生）中不违反任何规则。

**状态：** 已在本次修改中修复 — 候诊中需翻译的初诊，只有在调用结束时当天的现场翻译已全部排满时才免责；需抽血的申请，只有在那个
号源之前（从明天起、不早于其最早可约日期）没有一个工作日检验科还有空位时才免责，被约那条申请自己的抽血名额算作空位；`move_notice`
现在也涵盖取消后又重新预约的申请（提前通知从取消那天算；重新约回被取消的原日期和时间则不需要），相应的取消免责也从取消那天算。
隐藏需求（五个语言版本）、调整提前通知事项、case.yaml 和 README 都已这样写明。参考解现在会记住自己做过的取消；它在全部九个设置中的
结果不变。在 A 和 C 中，验证器的 `move_notice` 示例现在走的是取消路径。按文中所说，同一日期同一时间换成另一位医生不再要求提前
通知（这种情况只会出现在 D03 和 D04 重叠的周五下午的 IM）。未改动（由负责人决定）：约给另一位医生的复诊仍只与其上次接诊医生的
队列比较。

### F9 — 韩语用词的选择（低，已确认）

`earliest_date` 曾被译为 "희망시작일"（希望开始日期），而规则是硬性的"绝不能早于"；S 曾是 "조기"；医生署名为 "교수"、办公室
署名为 "의국"，这会让人联想到大学教学医院。

**状态：** 已在本次修改中修复 — 韩语隐藏需求、应问事项和规则集 C 的顺序标签改为 "진료 가능 시작일(earliest_date)"；S = "준응급"；韩语
邮件中医生署名改为 "{name} 과장"，办公室改为 "{dept} 사무실"（并调整了 "과장" 后面的助词）。日语邮件仍署名 "医局"，母语评审者
也许也想核对一下。

**基线：** 没有工程师时预约处的做法：与参考程序相同，但紧急预留号从不放给明天的门诊，并且（hard）从不超额预约。目标值在 easy
中为 0.806–0.812，medium 中为 0.787–0.799，hard 中为 0.689–0.701，对比参考解在每个设置中的1.0（在全部九个设置和世界种子1–3上
都有效）。
