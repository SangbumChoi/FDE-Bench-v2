# レビュー — `healthcare/hospital_appointment_scheduler`

ケースレビューの指摘事項（F1–F9）と検証者の判定、そして今回の変更でそれぞれにどう対応したかをまとめます。特に断りのない数値は
シード 20261116 のもので、「q」は正規化品質（ベースライン 0、参照解 1）です。

### F1 — 稼働率が上限に張り付いており、パッキングで得られるものが少ない（高、一部確認）

受け入れ能力は1日約79枠、需要は約83–86なので、参照解は easy と medium ですでに枠の98%を埋めています。私たちが知る最良の有効な
変種（パッキング。hard ではより低いオーバーブッキングのしきい値と真の無断欠席率も使う）でも目的値は +0.1% から +1.5% しか
上がらず、新しいベースラインに対しては q = 1.005–1.056 です。有効なプログラムは依然として約0.79から1.0まで散らばっていますが、
その差はパッキングではなく、いくつかの大まかなレバー（確保枠を解放するか、D10 のメモ、そもそもオーバーブッキングするか）から
生じています。当初の「1.0で頭打ち」という点は新しいスケールで解消しましたが、今度は方針の上限1.5に届きません。知られている
有効なプログラムで、品質点の約70%を超えるものはありません。

**状況：** 未対応 — 提案：まず、ここでより良い最適化を測れるようにすべきかを決めます。そうするなら、需要を減らすのではなく
配置を難しくし（特定の医師に結びついた再診を増やす、通訳や採血が集中する日をつくる、診療時間を混在させる）、より強い参照解か
上界を加えて、パッキングや先読みでスコアが数パーセント動くようにします。そうしないなら、case.yaml の `quality_cap` を約1.1に
設定し、知られている最良の水準のプログラムが満点を得られるようにします。

### F2 — オーバーブッキングに患者さんごとの無断欠席の推定が要らない（高、確認済み）

条件を満たす再診の枠を上限まですべてオーバーブッキングすると（しきい値0）、hard の A/B/C で 0.999 / 1.005 / 1.000
（q 0.997 / 1.015 / 1.000）となり、すべて有効です。しきい値0.10では参照解をわずかに上回り、オーバーブッキングしなければ
0.943–0.952 です。つまり、オーバーブッキングするかどうかは重要（約5%）ですが、hard ティアで試すはずのリスクの選別は重要では
ありません。この変更までは、10対12の損得はスコアの重みとしてしか書かれておらず、シミュレーションの顧客はそれを明かさない
可能性がありました。

**状況：** 未対応 — 提案：リスクの選別でスコアが決まるようにします。重なったときのコストを上げる（または医師の残業コストを
加える）ことで一律のオーバーブッキングを明確な純損失にし、無断欠席率のばらつきを広げて、選別的なオーバーブッキングが明確に
上回るようにします。しきい値0のプログラムが参照解より少なくとも3%低くなることを validate-case で確認します。（この変更では
F6 の一環として、すでに hard の要件にこの損得を業務上の事実として書いています。2人とも来ると外来が押し、それは空き枠より少し
大きな損失です。）

### F3 — ルールセットの数値が効いていないか、一方向にしか働かない（高、確認済み）

`urgent_days` = 1、3、10 のどれでも、9つの設定すべてで違反なしに目的値1.0000になります。緊急の依頼は常に現地の言語で、採血が
不要で、翌日が対象であり、翌日の確保枠が手つかずのときにしか生成されないからです。この変更の前は、すべての数値を最も慎重な値
（通訳者2、検査室5、オーバーブッキング1、予告4、緊急1）にすると9つの設定のうち8つで 0.98–1.00 の有効な結果になったため、
ルールセットを分けていたのは `waitlist_order`（と弱く `closed_dept`）だけでした。F8 の修正後、その慎重な組み合わせは9つのうち
8つで無効になりました（`waitlist_priority`: 使われていない通訳者や検査室の空きが、飛ばされた患者さんの免除理由にならなくなった）
が、予告4 + オーバーブッキング1 + 緊急1 だけなら、まだ9つのうち6つで 0.988–1.000 の有効な結果になります。

**状況：** 未対応 — 提案：残りの数値を両方向に効くようにし、最も慎重な値も誤りになるようにします（たとえば予告期間と並べて
取り直しの最大遅延を設ける、またはトリアージ上の受診可能日を持つ緊急の予約期限を設けて「翌日」が常に正解にならないようにする）。
通訳や採血が必要な緊急の依頼、あるいは翌日の確保枠がすでに使われているときに届く緊急の依頼をいくつか生成し、`urgent_days` が
効くようにします。慎重な組み合わせのプログラムを validate-case の区別性チェックに加え、それが無効か3%を超えて悪くなることを
求めます。

### F4 — 再診の慣行の緩和が、的を絞った緩和ではなく一律の緩和に報いている（高、確認済み）

すべての再診をいちばん早い同僚に予約すると（例外287–332件）目的値は2.0–5.8%上がり、不在の医師の患者さんに限って緩和すると
（例外43–51件）0.0–1.3%上がります。新しいスケールでは一律の緩和は q 1.11–1.29、つまりペナルティ前の最終スコアで +0.04 から
+0.115 の価値があり、startup_velocity（ペナルティ0.05）のもとでは9つの設定のうち5つで得になります。一方、臨床的に妥当な
的を絞った緩和（+0.000 から +0.024）は一度も得になりません。1回の承認ですべての例外がカバーされます。

**状況：** 未対応 — 提案：病欠中の小児科医の再診の一部に、不在期間内の臨床上の期限を設け、慣行を守るとその患者さんたちが受診
できず、的を絞った承認済みの例外だけがその価値を取り戻せるようにします。前回担当医以外の医師が診た再診1件ごとに小さな運営
コストを加え、一律の緩和が的を絞った緩和より低いスコアになるようにします。README では緩和の効果を最終スコアで報告します。

### F5 — 見える履歴が病院のルールと矛盾している（中、確認済み）

エクスポートでは、09:00/09:20 の履歴の予約151件のうち106件が2営業日以上先に予約された S/R の依頼で、これは確保枠のルールが
禁じるものです。通訳が必要な初診は1日10件（上限2–4）、空腹時採血は1日10件（上限5–7）に達しています。`_history` は確保枠・
通訳・検査室のロジックなしに枠を92%埋めていますが、初期の予約台帳はルールに沿っています。試行版の回答は待ちリストの順序
`received`（ルールセット B のもの）を使い、確保枠がありません。

**状況：** 未対応 — 提案：3つのルールセットに共通するルール（確保枠を守る、通訳が必要な初診は1日最大2件、採血は1日最大5件）の
もとで履歴を生成するか、外来管理室のメールで、確保枠・通訳者の勤務表・検査室の上限は11月9日から始まると伝えます。小さな数字が
もっともらしくなるよう、検査室の上限を「外来採血室の空腹時採血の枠」と言い換え、試行版にはどのルールセットとも一致しない暫定の
順序を与えます（または README に B と一致すると書きます）。

### F6 — 顧客が決して明かさないよう指示されている採点内容が確認すべき事項に入っていた（中、一部確認）

`scoring` と `scoring_hard` はスコアの式と重みであり、`status_table`（「品質の20%」）と `several_departments`（「コストは3」）にも
重みが入っていました。一方、顧客のプロンプトはスコアや重みの説明を禁じているので、Ask-F1 の再現率は1に届きませんでした。
「すでに見えている」という前提は成り立っていませんでした。既定の `interact_req` 条件では、エージェントが見るのは request.md と
データだけなので、`interface`、`visit_length`、期間の終わりはやはり質問する必要があります。

**状況：** 今回の変更で修正済み — 4つの事項を5つのロケールすべてで、重みを含まない業務上の事実として書き直しました（医師の時間が
空くことが最大の損失である、待ち・予約されない依頼・変更はコストである、無断欠席があるときに数えるのは実際に来る患者さんである、
2人とも来るオーバーブッキング枠は空き枠より少し大きな損失である、余分な来院はコストである）。hard の要件には最後の事実に必要な
1文が加わり、採点は変わっていません。`interface`、`visit_length`、`evaluation_period` は残しています。

### F7 — 下位ティアの範囲が試験の指示のように書かれていた（中、一部確認）

easy と medium には「同じ患者さんが2回依頼しても、依頼ごとに別の受診とする」と「採血は範囲外」とあり、病院の事実というより
プログラムへの指示のように読めました。実際、そこで重複を除くと無効になります（`waitlist_priority`、187–342件）。メモの扱い
（院長の知人、D10 の午後）は hard にしか書かれていませんが、D10 のメモに従うと easy と medium でも6.7–7.5%を失います。

**状況：** 今回の変更で修正済み — easy と medium の範囲の項目は、5つのロケールすべてで、顧客が言うように理由を述べるようになり
ました。今回は紹介窓口と検査室が紹介状と空腹時採血を自分で扱う、無断欠席は見込まない、予約係は依頼だけでは同じ症状か分からない
ので2回目の依頼にも別の予約を取る、というものです。採点は変わらず、対応する事項の文言も直しました。提案として残したもの：メモは
どのティアのデータにも入っているので、メモの段落と `staff_notes` の事項をすべてのティアに移すこと。

### F8 — 待ちリストの優先順位の免除が緩く、予告に抜け穴がある（低、確認済み）

旧チェッカーで再現した結果：通訳が必要な初診を一度も予約しないプログラムは9つの設定のうち9つで有効（0.950–0.988）、採血が必要な
依頼を最後に予約するプログラムは medium/hard の6つの設定のうち6つで有効（0.998–1.006）で、ある日に取り消して翌日にその次の日へ
取り直した再診は、ルールセット A と C（予告3と4。予告2では起こりえない）でどのルールにも違反しませんでした。

**状況：** 今回の変更で修正済み — 待っている通訳が必要な初診は、その日の対面通訳者が呼び出しの終わりにすべて埋まっている場合に
だけ免除されます。採血が必要な依頼は、その枠より前の営業日（明日以降、受診可能日以降）に検査室の空きのある日が1日もない場合に
だけ免除され、予約されたほうの依頼自身の採血の枠は空きとして数えます。`move_notice` は、取り消したあとで取り直した依頼も扱う
ようになりました（予告は取り消した日から。取り消した元の日時にもう一度入れる場合は不要）。対応する取り消しの免除も取り消した日
から数えます。要件（5つのロケール）、移動の予告の事項、case.yaml、README にそう書きました。参照解は自分の取り消しを覚えるように
なり、結果は9つの設定すべてで変わっていません。A と C では、検証器の `move_notice` の例は取り消しの経路になりました。同じ日付・
時刻で別の医師に移す場合は、文面のとおり予告を求めなくなりました（これは D03 と D04 が重なる金曜午後の IM でしか起こりえません
でした）。変更しなかったもの（ケースオーナーの判断）：別の医師に予約された再診は、引き続き前回担当医の待ち行列とだけ比べます。

### F9 — 韓国語の用語の選び方（低、確認済み）

`earliest_date` は「희망시작일」（希望開始日）と訳されていましたが、ルールは「それより前には決して入れない」という厳格な条件です。
S は「조기」で、医師は「교수」、事務局は「의국」と署名していましたが、これは大学の教育病院を連想させます。

**状況：** 今回の変更で修正済み — 韓国語の要件、確認すべき事項、ルールセット C の順序ラベルで「진료 가능 시작일(earliest_date)」、
S =「준응급」、韓国語のメールで医師は「{name} 과장」、事務局は「{dept} 사무실」（「과장」のあとの助詞も調整）にしました。日本語の
メールはまだ「医局」と署名しているので、ネイティブのレビュアーにこちらも確認してもらうとよいでしょう。

**ベースライン：** エンジニアがいない場合の予約係のやり方です。参照プログラムと同じですが、緊急用確保枠は翌日の外来分として
解放されることがなく、（hard では）どの枠も二重に予約しません。目的値は easy で 0.806–0.812、medium で 0.787–0.799、hard で
0.689–0.701 で、参照解はどの設定でも1.0です（ベースラインは9つの設定すべてとワールドシード1–3で有効）。
