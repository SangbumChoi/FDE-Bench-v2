# 蓄電池運転オペレーター — `energy_utilities/battery_dispatch_operator`

スペインの太陽光・蓄電サイト（リャノ・ベルデ：蓄電池と 30 MWp の太陽光発電所が1つの連系点と1つの計量器を共用しています）にある 40 MWh / 20 MW の蓄電池のオペレーターが、来週、つまり2027年3月22日（月）から28日（日）までに蓄電池をいつ充電・放電すべきかを「一番収益が上がるように」計画するようエージェントに依頼します。成果物は `dispatch.csv`（`timestamp,charge_mw,discharge_mw`）で、週の現地時刻の15分区間ごとに1行です。計画は、エージェントが見る予測とは異なる、その週の実際の価格で精算されます。採点器は充電率を15分区間ごとにシミュレーションし、その設定のすべてのルールを確認します。

このケースには**設定**があります。ティア3つ × 公開ルールシード3つ（141、70、334）です。**エージェントはどの設定でも同じ依頼と同じデータを見ます**（検証器が、プロンプトと作業領域がバイト単位で同一であることを確認します）。設定によって変わるのは、どのルールが適用されるかと、顧客がエンジニアに伝えなければならない運用値です。ルールシードは各値を候補のプールから互いに独立に抽選するため、それ以外のシードはすべて独自の正解を持つ非公開の設定になります。進め方の調整項目（完全な仕様を渡すか先に質問させるか、顧客のペルソナ、データのノイズ、イベント）は、ほかのすべてのケースと同様にその上に適用されます（[cases/README.md](../../README.md) を参照）。

## ティア

| ティア | 適用される内容 | ルール |
|---|---|---|
| easy | 中核となる問題です。保証上の充電率の範囲、出力上限、方向別の効率、週の終了時の充電率、変更後の送電上限（手元の契約書より低い）、夏時間への切り替えを扱います。要件は顧客の言葉で、今回の最初の計画ではオフピーク受電のルール（いつでも最大 20 MW まで系統から受電可能）、夕方の予備、劣化を外すと述べています。 | `soc_limits`, `power_limits`, `export_cap`, `end_soc` |
| medium | easy に運用ルールを加えます。オフピーク時間帯のみの系統受電、夕方の非常用予備（比率と時間帯）、充放電量 1 MWh あたりの劣化コストです。 | + `grid_charging_window`, `evening_reserve` |
| hard | medium に日付の決まった通知3件を加えます。変電所工事が早めに終わり（ある日から契約書の 30 MW に戻る）、配電事業者（DSO）がある日の夕方（18:00–21:00）にサイトの送電を制限し、ある日の 08:00 から 20:00 まではインバーター点検で蓄電池が停止します。顧客は、夕方のピークで予備を売るようにというトレーディング部門の要求も伝えますが、これは承認された例外があるときにしか認められません（予備は唯一の緩和可能なルールです）。 | + `dso_limit`, `maintenance_outage` |

## パラメータ

各パラメータはルールシードごとに独立に抽選されます（case.yaml の `params:`）。あるティアで使わないパラメータには、プレースホルダーの候補が1つ（`any`、`none` または 0）だけあります。

| パラメータ | easy | medium | hard | 何が変わるか |
|---|---|---|---|---|
| `soc_window` | 10-90, 15-85, 5-95 | 同じ | 同じ | 保証上の充電率の範囲、40 MWh に対する %。5-95 は仕様書にあるメーカーの範囲で、残りの2つはそれより狭い範囲です。 |
| `efficiency` | 92/92, 95/89, 90/94 | 同じ | 同じ | 充電 / 放電の片道効率、%。どの組み合わせでも仕様書の往復 84.6% になるため、方向別にどう分かれるかは顧客にしか分かりません。 |
| `end_soc` | 50, 40, 30 | 同じ | 同じ | 最後の15分区間の後の最低充電率、%。週は先週の記録の終わりと同じく 50% から始まるため、待機のベースラインはどの設定でも有効です。 |
| `export_cap` | 18, 15, 12 | 同じ | 同じ | 変電所工事の期間中の変更後の送電上限、MW（契約書では 30）。蓄電池の 20 MW を下回るため夕方の売電も制限し、これを超える太陽光は蓄電池が吸収しない限り出力抑制されます。 |
| `import_window` | any | 00-06, 01-05, 02-08 | 同じ | この時間帯（現地時刻）に始まる15分区間でのみ系統から受電します。 |
| `reserve_pct` | 0 | 20, 30, 15 | 同じ | 夕方の予備、40 MWh に対する %。 |
| `reserve_window` | none | 17-21, 18-22, 16-20 | 同じ | 予備の時間帯：この時間帯の15分区間の各境界で充電率を確認します。 |
| `degradation` | 0 | 5, 15, 25 | 同じ | 計量点での充電量と放電量の合計 1 MWh あたりの EUR で、利益から差し引きます。 |
| `works_end` | none | none | 2027-03-26, 2027-03-24, 2027-03-27 | その日の 00:00 から契約書の送電上限 30 MW に戻ります。 |
| `dso_day` | none | none | 2027-03-23, 2027-03-25, 2027-03-27 | DSO が送電を制限する日、18:00–21:00。 |
| `dso_mw` | none | none | 10, 5, 8 | DSO の送電上限、MW（夕方のピークでの売電を制限します）。 |
| `outage_day` | none | none | 2027-03-24, 2027-03-22, 2027-03-26 | その日の 08:00 から 20:00 まで蓄電池が停止します。 |

`derive_params` は、テキストに書かれる値を加えます。`soc_min`、`soc_max` とその MWh 値（`soc_min_mwh`、`soc_max_mwh`）、百分率と小数で表した効率（`eta_charge`、`eta_discharge`。es では小数点にコンマを使用）、`end_soc_mwh`、`reserve_mwh`、そして各時間帯の最初と最後の15分区間（`import_from`、`import_last`、`reserve_from`、`reserve_to`）です。`admissible` は、保証の下限以下の予備（15-85% の範囲での 15% の予備）を除外します。日付は `labels` によってロケールごとに表記されます。

**拘束性**（検証器、hard/s141、ワールドシード 20270322、1、2、3）：どのパラメータも正解を変えます。別の候補にすると、`soc_window`、`export_cap`、`import_window`、`reserve_pct`、`reserve_window`、`works_end`、`dso_day`、`dso_mw`、`outage_day` では参照解が無効になります。`efficiency` と `end_soc` では、別の候補での参照解がこの参照解を 1.7–5.1% 上回ります。`degradation` では目的値が 38–84% 変わります。

## エージェントが確認すべきこと

- **すべてのティア：** 効率が方向別にどう分かれるか（仕様書には往復効率しかない）、保証上の充電率の範囲（仕様書にあるのはメーカーの範囲）、週の終了時の充電率、現在の送電上限（契約書は古い）、精算は15分単位なのに価格ファイルは1時間単位であること、3月28日の夏時間への切り替え（668行）、「収益」が何を意味するか（太陽光単独と比べた利益で、送電と受電は計量どおり）。
- **medium と hard：** オフピーク受電時間帯、夕方の予備の比率と時間帯、劣化コスト。
- **hard：** その週を変える通知があるかどうか。通知は3件あり、それぞれに独自の日付があります（DSO の通知には上限値もあります）。また、予備についてのトレーディング部門の要求をどう扱うかも確認が必要です。予備は会社の方針であり、承認された例外（`request_exception`）だけがそれを解除できます。

先週の記録（`dispatch_log_last_week.csv`）は、先週のプランナーが先週の慣行（10–90%、片道 92% ずつ、開始と終了は 50%、17:00–21:00 に 20% の予備、00:00–06:00 の受電、25 MW の上限）で計画したものです。どの公開設定でも、その値の少なくとも1つは誤っています。以前の固定された問題の計画は、25 MW の上限がどの候補よりも高いため、9つの設定すべてで無効です。顧客に確認せずに記録から慣行を読み取るエージェントは失敗します。

## ルール

| ルール | 区分 | ティア | 求められること |
|---|---|---|---|
| `soc_limits` | 物理的 | すべて | 各15分区間の後、充電率が 40 MWh の `soc_window` 以内。充電と放電にはその設定の効率を適用 |
| `power_limits` | 物理的 | すべて | 充電と放電はそれぞれ 0–20 MW、1区間で両方は行わない、系統からの受電は最大 20 MW |
| `export_cap` | 契約上 | すべて | 放電中は 太陽光 + 放電 − 充電 ≤ `export_cap` MW（hard：`works_end` 00:00 からは 30 MW） |
| `grid_charging_window` | 契約上 | medium, hard | 系統からの受電（太陽光を超える充電）は `import_window` に始まる区間のみ |
| `end_soc` | 契約上 | すべて | 50% で始め、週を `end_soc` 以上で終える |
| `evening_reserve` | 業務慣行（緩和可能） | medium, hard | 毎日、`reserve_window` の15分区間の各境界で充電率 `reserve_pct` 以上 |
| `dso_limit` | 契約上 | hard | `dso_day` 18:00–21:00 は、放電中 太陽光 + 放電 − 充電 ≤ `dso_mw` MW |
| `maintenance_outage` | 物理的 | hard | `outage_day` 08:00 から 20:00 までは充電も放電も行わない |

充電率は 0.02 MWh（容量の 0.05%）の誤差内で確認されるため、小数第2位や第3位に丸めた計画が丸めだけを理由に無効になることはありません。品質は実際の価格での蓄電池の利益です。15分区間ごとに、サイトの送電収入（価格 × 0.25 × min(正味出力, 送電上限)）から系統からの受電コストを引き、太陽光発電所だけで得られたはずの収入（価格 × 0.25 × min(太陽光, 送電上限)）を引き、さらに充電量と放電量の合計 1 MWh あたり `degradation` EUR を引きます。ある区間の送電上限は `export_cap` で、工事の終了後は 30 MW、DSO の制限時間帯は `dso_mw` です。

## 含まれる状況

- **古くなった文書。** 系統連系契約では 30 MW ですが、変電所工事により送電上限が 12–18 MW に引き下げられています。hard では工事が早めに終わり、ある日から契約書が再び正しくなります。
- **仕様書と顧客のモデルの違い。** 仕様書には往復 84.6% と充電率 5%–95% とありますが、顧客は方向別の効率で計算し、保証範囲はそれより狭いこともあれば、そうでないこともあります。
- **単位と時刻。** 価格は1時間単位ですが、精算は15分単位です。3月28日（日）に時計が1時間進む（EU の夏時間、3月の最終日曜日）ため、週は15分区間668個になります。その日の 02:00–02:45 の行があるファイルは致命的です。
- **出力抑制される太陽光。** 送電上限が 12–18 MW で太陽光が 30 MWp なので、蓄電池が吸収しない限り日中の出力の多くが抑制されます。そのエネルギーは無償です。これは、プランナーが無駄にしてはならない主な価値の源泉です。
- **オフピーク受電時間帯**（medium、hard）。太陽光からの充電はいつでも可能ですが、系統からの充電はその時間帯のみです。
- **日付の決まった通知**（hard）。文書には載っていない、特定の時間帯についての変更が3件あります。
- **緩和可能なルールへの圧力**（medium、hard：予備。hard：トレーディング部門の要求）。予備を緩和すると、参照解は +4% から +19%、予測ベースの LP は +0% から +13% の上積みになります。予備が 30% のときに最も得になります。
- **価格の不確実性。** 実際の価格は予測に日ごとのバイアスと時間ごとのノイズを加えたもの（下限 0）で、エージェントは予測だけをもとに計画します。

確認すべき事項は13個です。すべてのティアで `efficiency`、`soc_window`、`start_end_soc`、`export_cap`、`grid_charging`、`quarter_settlement`、`dst_clock`、`profit_scoring`（8個）、medium から `evening_reserve` と `degradation`（10個）、hard で `works_end`、`dso_limit`、`maintenance_outage`（13個）です。

## 参照解とベースライン

参照解は、予測価格に対する1日2サイクルの貪欲法ルールです。毎日、受電時間帯の中で最も安い夜間の15分区間で満充電し、最も高い午前の区間（06:00–11:00）で売ります。続いて、最も安い晴天の区間16個（09:00–17:00）で充電し直します。いつでも受電できる場合は系統からも充電し、抑制されるはずの太陽光は常に吸収します。最後に、15:00 以降の最も高い区間で売ります。ある区間で売るのは、その価格がそのサイクルの平均購入価格を往復効率で割った値に劣化コストの2倍を加えたものを上回る場合だけです。送電上限が 20 MW 未満の区間では MW を少なく見積もるため、そこではより多くの区間を使います。記録を作った先週のプランナーに比べて、改良点が2つあります。

- 夜間の充電は、午前の売電では空かない日中の再充電分のために余地を残します。抑制されるはずの太陽光のためには常に、日中が夜間より安いときは再充電の全量のために残します。夜間の充電率は、予備の時間帯までに再充電で入る量（80% として計算）の分だけ、予備と終了目標を下回っても構いません。
- 予備の時間帯が終わると、予備も売ります。

予備を守り、停止中の区間は飛ばし、最終日は目標で終わるように計画します。先週の値で先週用のスイッチを入れると、以前の固定された参照解を正確に再現します（18,084.35 EUR）。

ベースラインは運転計画のないサイトです。蓄電池は週の間ずっと 50% で待機し、発電所は太陽光だけを売るので、蓄電池の利益はどの設定でも **0.00 EUR** です（有効：何も動かず、50% を超える終了目標もありません）。ベースラインが 0 なので、正規化品質は参照解に対する単純な比と同じです。

## 補足

- 合成された、または検証されていない値です。価格、太陽光出力、送電上限の変更、効率、劣化コスト、受電時間帯、予備の方針、日付の決まった通知は設計上の選択であり、測定値ではありません。
- 太陽光のプロファイルは理想化されています。DC 定格 30 MWp をそのまま出し切り、太陽の南中は現地時刻 12:45（夏時間への切り替え後は 13:45）で、CET を使うスペインのサイトより早くなっています。
- ケースレビューで挙がった未解決の設計上の論点（品質上限、日次のプログラム成果物、契約上のルールの文書上の根拠）は REVIEW.md にあります。
