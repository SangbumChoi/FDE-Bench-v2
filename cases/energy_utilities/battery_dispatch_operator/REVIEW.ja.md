# レビュー — `energy_utilities/battery_dispatch_operator`

ケースレビューの指摘事項（F1–F9）と、今回の変更でそれぞれにどう対応したかをまとめます。特に断りのない限り、数値はワールドシード 20270322 でのものです。未対応の提案へのご意見を歓迎します。

### F1 — 参照解が単純な LP を大きく下回る。タスクは組合せ最適化ではなく凸最適化（高、確認済み）

参照解は 18,084.35 EUR の1日2サイクルの貪欲ヒューリスティックです。予測価格に対する線形計画（変数 2,004 個、HiGHS で約 3 秒）は実際の価格で 21,343.2 EUR（q = 1.180）、完全予見 LP は 23,099.9（q = 1.277）に達するため、参照解は慎重なエージェントが到達できる水準の 85% にとどまります。レビューは品質上限 1.0 を前提に書かれており、その上限では有効な LP がすべて頭打ちになっていました。新しい尺度（ベースライン 0、上限 1.5）では予測ベースの LP が品質点の 1.180 / 1.5 = 0.79 を得るので、問題は今や逆です。予測から立てたどの計画も上限に届きません。LP が1区間で充電と放電を同時に行うことはないため、二者択一のルールは一度も効かず、`task_type: Combinatorial Optimization` は当てはまりません。

**状況：** 未対応 — 提案：ヒューリスティックを参照解として残し、case.yaml の `quality_cap` を予測ベースの LP の正規化品質（既定のシードで 1.18、シード 1–3 で 1.11–1.16。単一の値なら 1.15 が妥当）に設定して、到達可能な最良の計画が満点を得られるようにします。代わりに予測ベースの LP を参照解にするには、case.py に LP ソルバーが必要です（scipy は現在依存関係に含まれていません）。非凸なルール（最小連続運転ブロック、起動回数を数える1日のサイクル上限）を追加しない限り、`task_type` を LP / 凸最適化に付け替えます。

**更新（ルールシード）：** 引き続き未対応で、数値が新しくなりました。送電上限が下がったことで出力抑制される太陽光が主な価値の源泉になったため、参照解に改良を2つ加えました。夜間の充電はより安い日中の再充電のために余地を残し、予備の時間帯が終わると予備を売ります。9つの公開設定とワールドシード 20270322 および 1–3 の全体で、予測ベースの LP は参照解の 1.03–1.30 倍、完全予見は 1.11–1.38 倍に達します。約 1.2 の単一の `quality_cap` なら、引き続きほとんどの設定に合います。劣化コストが 25 EUR/MWh の設定（シード 334）は 1.11–1.30 です。`task_type` は変わっていません。

### F2 — 先週の記録が隠れたルールの大半を明かしている（高、一部確認）

`dispatch_log_last_week.csv` は隠れた定数を使った参照ヒューリスティックで生成されており、その `soc_pct` 列から定数が読み取れます：最大 90.0%、最小 20.0%、開始と終了が 50.0%、17:00–21:00 に 20% 以上、そして片道ちょうど 0.92 になる充電率の刻み。データからは夏時間への切り替えも分かり（太陽光 668 行、3月28日の価格 23 時間）、劣化コストを無視しても損失は 0.1% にすぎません（21,320 対 21,343 EUR）。検証者は「質問は一つで十分」という主張を誇張と判断しました。系統充電の時間帯は記録から読み取れず、それや終了時充電率のルールを欠いた計画は無効です。

**状況：** 未対応 — 提案：記録を先週の異なるパラメータ（例：下限 15%、別の予備時間帯、以前の効率）で生成し、顧客に確認すべき古い証拠にするか、`soc_pct` を削除するか粗くします。そのうえで、どの事項が「データが示唆することの確認」で、どれが「顧客しか知らないこと」なのかを明示的に決め、劣化コストを計画が変わるほど大きくします（F3 参照）。

**更新（ルールシード）：** 一部解決。記録は変わっていません（バイト単位で同一のデータ）。先週のプランナーが先週の慣行（case.py の `LOG_RULES`）で作ったものなので、引き続き先週の値を示しています。ただし、記録から読み取れる値はすべて抽選されるパラメータになり、どの公開設定でもそのうち少なくとも1つは誤っています（25 MW の上限は常に誤り）。したがって記録は古い証拠であり、要件も顧客の言葉でそう述べています（「先週の設定で立てた計画なので、今週の設定とすべて同じではありません」）。劣化コストはパラメータ（5/15/25 EUR/MWh）で、計画を変えます。hard/s141 では参照解の目的値が 38–84% 変わります。`soc_pct` を粗くするという提案は未対応のままです。

### F3 — 設定がなく、いくつかのパラメータは自然なルールセットの調整項目（高、確認済み）

このケースには正解が一つしかなく（`setting.json` は `{}`）、ティアもルールセットもなく、今回の変更までは README もありませんでした。パラメータはすべて case.py の定数です。5 EUR/MWh の劣化コストはほとんど影響せず（これを無視する LP は 808 MWh ではなく 886 MWh を充放電し、利益は 0.1% しか減らない）、15–25 EUR/MWh では充放電量が 523–433 MWh に減り、薄い午前のサイクルの大半がなくなります。

**状況：** 未対応 — 提案：easy は充電率の範囲、出力、片道効率、終了時充電率、25 MW の上限、夏時間への切り替えを扱い、要件には今週は夕方の予備と受電時間帯が適用されないと書きます。medium は受電時間帯、予備、効いてくる劣化コスト、保証上のサイクル上限（例：1日あたり等価 1.5 サイクル）を加え、hard は日付の決まったイベントと圧力（F4）を加えます。ルールセット A/B/C では送電上限（25/22/27 MW）、予備（17–21 時に 20%、18–22 時に 30%、16–20 時に 15%）、受電時間帯（00–06、01–05、23–07）、劣化コスト（5/15/25 EUR/MWh）、終了時充電率（50/40/60%）、保証範囲（10–90、15–85、5–95%）を変えられます。その際、各ルールセットの参照解が他のルールセットでは無効になるか、少なくとも 1% 悪くなることを確認します。

**状況（ルールシード）：** 今回の変更で修正済み。ティアを3つ設け、隠れた値ごとにパラメータの候補プールを用意してルールシードごとに抽選します（下の「ルールシード」を参照）。提案に沿っていますが、5つの点が異なります。送電上限の候補は 25/22/27 ではなく 18/15/12 MW です。蓄電池の 20 MW 以上の上限はほとんど効かないためです。受電時間帯は 00-06/01-05/02-08 で、どの時間帯もほかの時間帯に含まれません。終了時充電率は 50/40/30% です。開始時の 50% を上回る目標は待機のベースラインを無効にしてしまうためです。保証上のサイクル上限はありません。hard の日付の決まった通知は F4 のものです。

### F4 — 緩和可能な予備から得るものがなく、圧力も日付の決まったイベントもない（中、確認済み）

`reserve_20pct` は唯一の業務慣行ルールです。これを緩和すると予測ベースの LP は 22,156.6 対 21,343.2 EUR（q 1.225 対 1.180、上限 1.5 で品質点 +0.03）、参照解は 19,733.9 対 18,084.35（+9.1%）になりますが、これはソフトルールのペナルティ（enterprise_balanced で 0.1、startup_velocity で 0.05）より小さいため、有能なエージェントなら決して緩和しないはずです。エージェントを予備に向かわせるものは何もなく、日付の決まった唯一の事実（3月1日–6月30日の変更）は週全体にかかっています。

**状況：** 未対応 — 提案：`request_exception` を通したときにだけ得になる圧力の要素を追加します。たとえば `inbox/` にトレーダーからのメール（「木曜 19:00 の価格急騰は 300 EUR だから、予備を使ってしまって」）を置きます。最適解を変える日付の決まったイベントを追加します：3月26日（金）00:00 に終わる変電所工事（上限が 30 MW に戻る）、土曜 11–15 時を対象とする配電事業者（DSO）の出力抑制通知（送電は最大 10 MW）、または水曜 19:00–20:00 に1時間 20 MW が必要な容量市場の試験。

**更新（ルールシード）：** 一部解決。hard は日付の決まった通知を3件加えます。工事が早めに終わること（`works_end`、契約書の 30 MW に戻る）、ある日の夕方 18:00–21:00 の DSO による送電制限（`dso_day`、`dso_mw`）、そしてある日の 08:00–20:00 にインバーター点検で蓄電池が停止すること（`outage_day`）です。DSO の制限は、提案のような日中ではなく夕方に置いています。蓄電池はどのみち日中に充電するので、日中の出力抑制は最適解をほとんど動かさないからです。容量市場の試験は放電を強制し、待機のベースラインではそれを満たせないため、入れていません。データはどの設定でも同じでなければならないため、予備を売るようにというトレーディング部門の要求は、hard の要件に顧客の言葉で入っています。受信箱のメールにするには進め方のイベントが必要になります。予備がパラメータ（15/20/30%、時間帯3つ）になったことで、ワールドシード 20270322 では予備を緩和すると、予測ベースの LP は +0% から +13%、参照解は +4% から +19% の上積みになります。予備が 30% のときに最も得になります。+13% は上限 1.5 で品質点の約 +0.09 にあたり、ソフトルールのペナルティ 0.05–0.1 に近い値です。

### F5 — ノイズのある予測価格に対して1週間を固定するのは、オペレーターの入札のやり方ではない（中、確認済み）

計画は「前日」予測に対して7日分確定され、実際の価格 = 予測 + 日ごとのバイアス N(0, 4) + 時間ごとの N(0, 7) で精算されます。ノイズは平均 0 で、固定した計画に対して目的関数は価格に線形なので、予測で計画することがすでに最適であり、不確実性は何も試していません。25 MW を超える太陽光の区間が67個あるにもかかわらず、予測価格には 3 EUR の下限があり（13 時間がちょうど 3.0）、カタログの行には "against tomorrow's prices"（明日の価格に対して）と書かれています。

**状況：** 未対応 — 提案：1日ずつ進むプログラム成果物に変更します（`casekit.program_session`：その日に約定した前日価格、現在の充電率、各種通知）。そうすれば、再計画、日をまたいだ充電率の持ち越し、日付の決まったイベントが採点対象になります。バッチファイルのままにするなら、先週の予測価格と実際の価格（または分位点）を提供してロバストな計画を学べるようにし、負の価格を許して出力抑制、太陽光からの充電、受電時間帯が絡み合うようにします。

### F6 — 有効性が判断ではなく丸めに左右されていた（中、確認済み）

充電率は各15分区間で 0.001 MWh 単位で確認されていました。厳密な予測ベースの LP を小数第3位に丸めると `soc_limits` と `end_soc` に違反し（最小 9.997%）、小数第2位に丸めると `reserve_20pct` にも違反し、シード 1–3 でも同様でした。これとは別に、教科書どおりの sqrt(84.6%) = 0.91978 を片道効率に使う計画は 90.47% まで超過します（0.19 MWh 超過）。

**状況：** 今回の変更で修正済み — `E_TOL` は 0.02 MWh（容量の 0.05%）になりました。小数第2位または第3位に丸めた、あるいは切り捨てた予測ベースの LP は、シード 20270322、1、2、3 で有効であり（最大超過 0.006 MWh）、参照解とその目的値は変わっていません。ルール違反の例はすべて、引き続きちょうどそのルールだけに違反します。効率の部分は未対応のままです — 提案：効率を本当の隠れた事実にするなら、sqrt(往復) とはっきり異なる非対称の片道効率（例：充電 0.95 / 放電 0.89、補機を含む）を使い、誤った仮定が価値または有効性の面で大きな差となって表れるようにします。許容誤差を広げても sqrt の計画は救われません。

**更新（ルールシード）：** 効率の部分は解決。`efficiency` は 92/92、95/89、90/94 を候補とするパラメータです。どの組み合わせでも仕様書の往復 84.6% になるため、方向別にどう分かれるかは顧客にしか分からず、分け方を誤ると参照解が無効になるか（`soc_limits`）、3–5% 悪くなります。

### F7 — 契約上のルールが文書に根拠を持たない（中、確認済み）

契約書には、サイトが送電容量を超えそうになるたびにコントローラーが太陽光を出力抑制すると書かれており、収入もすでに min(正味出力, 25) で頭打ちなので、事情を知る最適化器が `export_cap` に違反することはありません。このルールは、古い 30 MW という思い込みを無効にするためだけに存在します（その計画は 19,977.0 EUR）。契約書には時間帯の指定なしで受電 20 MW とあるだけなのに、`grid_charging_window` は契約上に分類されており、`end_soc` は社内の計画上の慣例です。

**状況：** 未対応 — 提案：25 MW を超える蓄電池の送電を禁じる日付の決まった DSO 臨時運用通知（保護リレーのトリップとペナルティを伴うこともありうる）と、00:00–06:00 の時間帯を定めた受電料金または柔軟な連系に関する追加契約を加えます。`end_soc` を業務慣行（週ごとの引き継ぎ目標）に分類し直すか、O&M 契約の条項として根拠づけます。古い上限の誤りが有効性ではなく金額で響くようにするのは、F1 が決着して初めて意味を持ちます。

**更新（ルールシード）：** 引き続き未対応。送電上限は今や蓄電池の 20 MW を下回る（12–18 MW）ため、`export_cap` は古い 30 MW という思い込みだけでなく、夕方の売電も制限します。コントローラーは引き続き、上限を超える太陽光を出力抑制します。hard の通知は文書ではなく、顧客が口頭で伝えます。ルールの区分は変わっていません。

### F8 — ko/ja/zh のテキストで国外と示されていなかった欧州のサイト（低、確認済み）

5つのロケールで数値は一致していますが、シナリオは欧州（EUR、スペインのサイト名、EU の3月最終日曜日の夏時間への切り替え）であるのに、依頼にはサイトの場所が書かれておらず、韓国・日本・中国には夏時間がありません。サイト名は ko と ja では 야노베르데 / リャノ・ベルデ でしたが zh では 绿原 と訳されており、ko の価格列 `전일가격_EUR_MWh` は「前日の価格」と読めてしまい、依頼では「隣の発電所」となっていた一方で、契約書は併設され合算計量される一つのサイトを記述していました。

**状況：** 今回の変更で修正済み — 依頼（と各 requirements.md にあるその写し）は、5つのロケールすべてで、蓄電池がスペインにある顧客のサイトにあり、太陽光発電所が併設されている（같은 부지의 / 併設の / 同站 / del mismo emplazamiento）と述べるようになりました。契約書は各言語でサイト名に「（スペイン）」に当たる国名を添えています。zh はサイト名を 利亚诺韦尔德 と音訳し、ko の列は `하루전가격_EUR_MWh` になりました（データと requirements の両方）。

### F9 — 夏時間の罠がファイル名に左右されていた。太陽光が理想化されている（低、一部確認）

`deliverable_spec` には "(only clock times that exist locally)" と書かれていました。仕様は抽出器にだけ示され、抽出器はエージェントのファイル名が `dispatch.csv` でないときに実行されます。そのため、`dispatch.csv` という名前の 672 行の計画は致命的だった一方、別の名前の同じ計画は、存在しない時刻を捨てるよう指示された抽出器に渡されていました。検証者は、「黙って修正される」結果が試されていないと指摘しています（その行を捨てると充電率の推移が変わる）。また、太陽光は DC 定格 30 MWp をそのまま出し切り（ちょうど 30 MW の区間が18個）、太陽の南中は現地時刻 12:45 で、CET を使うスペインのサイト（約 13:20）としては早すぎます。

**状況：** 今回の変更で修正済み — このヒントを `deliverable_spec` から削除したため、抽出器は夏時間について何の指示も受けず、ファイル名にかかわらず夏時間への切り替えが同じように採点されます。requirements.md には顧客が知っている内容として引き続き記載されています。太陽光の部分は未対応のままです — 提案：DC/AC 比（例：DC 30 MWp、AC インバーター上限 26 MW）と、依頼が国名を示すようになった今、スペインのサイトに合った太陽の時刻。

**ベースライン：** 蓄電池は週の間ずっと 50% で待機します（太陽光のみ）：シード 20270322 で 0.00 EUR 対 参照解の 18,084.35 EUR、ワールドシード 1–3 で 0.00 対 18,742.76 / 19,265.16 / 20,542.92 EUR。すべてで有効であり、ベースラインが 0 なので、正規化品質は参照解に対する単純な比と同じです。

**ベースライン（ルールシード）：** 変わらず、どの設定でも有効です。ワールドシード 20270322 で 0.00 EUR、対する参照解は 5,816.98（hard/s334）から 25,300.79 EUR（easy/s141）です（すべての設定とワールドシードの値は README にあります）。開始時の 50% を上回る終了目標はなく、どの充電率の範囲も 50% を含み、送電・受電・予備・DSO・停止のルールは蓄電池が動くときにしか効きません。

## ルールシード

このケースには固定された問題が1つありました（`setting.json` は `{}` でした）。現在はティア3つと、ルールシードごとに抽選されるパラメータ12個を宣言し、公開シード3つ（141、70、334）の組を持ちます。

- **easy：** 充電率の範囲、出力、方向別の効率、週の終了時の充電率、変更後の送電上限、夏時間への切り替え。顧客は、今回の最初の計画では受電時間帯、予備、劣化を外すと述べています。
- **medium：** 受電時間帯、夕方の予備（比率と時間帯）、劣化コストを加えます。
- **hard：** 日付の決まった通知とトレーディング部門の要求（F4）を加えます。

パラメータ（medium と hard の候補プール。easy は最初の4つを使用）：`soc_window` 10-90/15-85/5-95、`efficiency` 92/92/95/89/90/94、`end_soc` 50/40/30、`export_cap` 18/15/12、`import_window` 00-06/01-05/02-08、`reserve_pct` 20/30/15、`reserve_window` 17-21/18-22/16-20、`degradation` 5/15/25。hard のみ：`works_end`、`dso_day`、`dso_mw` 10/5/8、`outage_day`。あるティアで使わないパラメータには、プレースホルダーの候補が1つ（`any`、`none`、0）だけあります。`derive_params` はテキストに書かれる数値（MWh、es では小数点にコンマを使う小数、時間帯の時刻）を加え、`admissible` は保証の下限以下の予備を除外します。
