ケースの説明（README）

食品スーパーの需要予測担当者 — retail/grocery_demand_forecaster

5店舗を展開する地域の食品スーパーチェーンが、エージェントに「11月2日（月）からの2週間、当社5店舗で各商品が毎日どれくらい売れるか」の予測を依頼します。この数字をもとに発注しているためです。成果物は forecast.csv（store_id,item_id,date,forecast）で、店舗（S1–S5）× 商品（I01–I12）× 日付（2026-11-02〜2026-11-15）ごとに1行、計840行を、各商品の現在の販売単位で記載します。予測は予測期間の実際の顧客需要と比べて採点され、この需要はワールドの中にしか存在しません。

このケースには設定がありません。どの難易度でも、依頼、データ、隠れた要件、評価器は同じです。進め方の設定（仕様をすべて渡すか先に確認させるか、顧客のペルソナ、データのノイズ、イベント）は、ほかのすべてのケースと同様にその上に適用されます（cases/README.md を参照）。

データ

  • sales_history（43,718行、2024-11-04〜2026-11-01の104週）：店舗・商品・営業日ごとに販売の行が1行あり、units_sold、promo_discount_pct（0 = 販促なし）、stockout フラグ（欠品の行は4,390行で、記録された販売は需要の30–85%）を持ちます。これとは別に、数量がマイナスの顧客返品の行が1,286行あります（販売2,002,817に対して−2,104）。S4には日曜日の行がありません。
  • promo_plan：予測期間中の店舗 × 商品の販促14件（10/20/30%引き、開始日と終了日を含む）。
  • holidays：過去の祝日12日（クリスマス、元日、春・夏・秋の祝日、労働の日がそれぞれ2回）。予測期間に入る祝日はなく、11月11日（水）の一度限りの祝日は載っていません。
  • stores（スーパー4店と小型店の旧市街店S4）と items（4カテゴリの12商品：青果 I01–I03、乳製品 I04–I06、ベーカリー I07–I09、飲料 I10–I12、それぞれの販売単位つき）。ロールパン（I07）は6個入りパックとして登録されていますが、履歴では2026年5月31日まで1個単位で記録されています。

ワールドは店舗 × 商品 × 日ごとの乗法モデル（店舗の規模とトレンド、カテゴリ別の曜日パターンと年間の季節性、カテゴリと割引率による販促効果、カテゴリ別の祝日効果）で、日次ノイズは対数正規分布（σ = 0.07）、販売数はポアソン分布に従います。欠品は、商品ごとの基本確率（販促日はこれに0.20を加えた確率）で、その日の需要とは無関係に発生します。

ルール

ルール区分求めること
complete_grid契約上予測期間の店舗 × 商品 × 日付ごとにちょうど1行
non_negative物理的マイナスの予測なし
closed_day_zero物理的S4は日曜定休のため、日曜日の予測は0
min_display_stock業務慣行（緩和可能）主力商品（青果と乳製品、I01–I06）は、すべての営業日で6以上と予測する

品質は店舗ごとのWAPE（その店舗の全商品・全日付にわたる Σ |予測 − 需要| ÷ Σ 需要）を5店舗で平均したもので、低いほど良い値です。需要には、欠品のために顧客が買えなかった分も含まれます。

含まれる状況

隠れた事実だけです。依頼は「各店舗でどれだけ売れるか予測してほしい」としか言っていません。確認すべき事項9つは、欠品による打ち切り（記録された販売ではなく需要を予測する）、返品（除外し、相殺しない）、S4の日曜定休、販促計画（開始日・終了日を含む、カテゴリと割引率による効果）、11月11日の祝日、I07の単位変更、陳列下限6、WAPE指標、ファイル形式です。ケース固有の日付つきイベントやプレッシャーのメッセージはなく、イベントは進め方の軸からしか生じません。

参照解とベースラインの数値（シード 20261102）

参照解は、履歴だけから作る、打ち切りを考慮した店舗 × 商品ごとの曜日・水準モデルです。クリーンな日（欠品・販促・祝日のない日）の直近52週から曜日パターンを、クリーンな日の直近8週から水準を求め、カテゴリの季節係数は前年の同時期の水準から求めます。販促効果は割引率の段階ごとに1つ、祝日効果は1つだけとし、どちらも全カテゴリをまとめて推定します。I07は2026年6月1日より前の履歴を6で割り、返品は除外し、S4の日曜日は0、主力商品には下限6を適用します。

ベースラインは、エンジニアがいなくても店長が使いそうな季節ナイーブ予測です。履歴の最終週（10月26日〜11月1日）の同じ曜日にレジが記録した数量をそのまま使い、S4の日曜日は0、主力商品には下限6を適用します。欠品・販促・祝日の補正は行いません。

補足

  • 合成データです。販売量、パターン、弾力性、祝日効果、欠品率はすべて架空のもので、実在のチェーンに合わせた調整はしていません。祝日カレンダーは汎用的なものです（REVIEW.md の F8 を参照）。
  • validate-case は、5つのロケールでデータが決定的に生成されること、参照解の品質が1.0であること、ベースラインが有効で参照解より劣ること、ルールごとにそのルールだけを破る成果物が1つずつあること、そしてワールドシード1–3を検査します。

レビュー結果（REVIEW）

retail/grocery_demand_forecaster のレビュー

ケースレビューの指摘事項と、それぞれに対する検証者の判定、および今回の変更後の状況です。以下の品質の数値は、比率と明記したものを除き、新しい尺度（季節ナイーブのベースライン0、参照解1）によるものです。

F1 — 設定がなく、どの難易度でも同じ一つの固定問題（高、一部確認）

case.yaml はティア、ルールセット、param_labels のいずれも宣言しておらず、正解は gt/default だけです。そのため難易度の列はこのケースについて何も示さず、「今回はどのルールが適用されるか」は一度もテストされません。設定のないケースは DESIGN.md で認められており（作成済みの13ケースのうち8ケースは設定なし）、これは契約違反ではなくカバレッジの穴です。

状況： 未解決 — 提案：公開データをバイト単位で同一に保ったまま3×3に変換します。easy は基本需要のみ（要件に、今回は販促と11月11日の祝日は別の担当が扱うと書く）、medium は販促計画、祝日、I07の単位変更を加え、hard は新たに採点用の正解が必要な部分（日付つきの改訂、休業、プレッシャー、生鮮品の非対称なコスト）を加えます。ルールセットのパラメータは、データからは分からないものにすべきです：祝日の日付（11月11日（水）/ 13日（金）/ 9日（月））、下限（青果 + 乳製品に6 / 乳製品のみ4 / 青果のみ8）、今後の休業（なし / 11月15日にS2 / 祝日にS5）。店舗平均のWAPEと数量加重のWAPEをルールセットの組にしてはいけません（セルごとの最小化解が同じなので、参照解同士の差が1%に届きません）。また、情報を含む打ち切り（informative censoring）を hard だけに入れてもいけません（公開の履歴が変わってしまいます）。

F2 — 参照解を上回る余地が小さい（高、確認済み）

参照解のWAPEは0.1470、オラクル（生成器の真の平均に下限を適用）は0.1381、ベースラインは0.2790です。新しい尺度では、オラクルの品質は1.067（ワールドシード1–3では1.118 / 1.167 / 1.072）で、販促と祝日の効果をカテゴリ別にするだけで1.039になります。品質はもう1.0で打ち切られませんが、ポリシーの上限1.5のもとでは完璧なモデルでも品質スコアの約71%しか得られず、良いエージェントと優れたエージェントの差はわずか百分の数程度です。原因は、ポアソンノイズと日次ノイズが支配的な、きれいな乗法型の生成器にあります。

状況： 未解決 — 提案：単純なヒューリスティックでは捉えられない、学習可能な構造（情報を含む打ち切り、販促後の落ち込み、カテゴリ内の共食い、履歴の途中での店舗の水準シフト、間欠的にしか売れない低回転商品、類似品のある新商品）を加え、そのうえでオラクルが参照解より約10%上に来るよう参照解を強化します。それまでは case.yaml の quality_cap を、強力だが到達可能なモデルが届く水準（このシードで約1.05）付近に設定し、満点を得るのにオラクルを上回る必要がないようにします。オラクルの品質がワールドシード間で一定の幅に収まることを確かめるチェックを追加します。

F3 — 陳列下限が case.yaml では2、それ以外ではすべて6と書かれていた（高、確認済み）

case.yaml は min_display_stock を "never forecast below 2 units" と説明していましたが、case.py の MIN_DISPLAY = 6.0、5つのロケールの要件、確認事項はいずれも6としています。例外分類器は case.yaml の文言を要件と並べて見るため、緩和可能なルールが問題になるまさにその場面で、顧客には両方の数字が示され、説明ページにも両方が表示されていました。下限が2なら効きません（参照解0.13948、下限なしで0.13947）。検証器の数値リントがこれを見逃したのは、要件に「2」が日付（"Monday 2 November"）として現れるためです。

状況： 今回の変更で修正済み — ルールの説明は6となり、MIN_DISPLAY、要件、確認事項と一致しました。{{min_display}} プレースホルダーは使っていません。このケースには値を埋めるルールセットがないためです。

F4 — 陳列下限を緩和しても得にならない（中、確認済み）

下限は参照解の136セル（フレッシュバジル I03と熟成チーズ I06、予測期間の需要の1.3%）で効いています。外すとWAPE 0.1395、品質1.057（シード1–3では1.084–1.089）です。品質の重み0.6、上限1.5では、これは総合スコアで約0.6 × 0.057 / 1.5 ≈ 0.023に相当し、2つのソフトルールのペナルティ（startup 0.05、enterprise 0.10）のどちらよりも小さくなります。実需要に対するWAPEは棚に商品があることを何も評価しないため、「決して緩和しない」が常に正解です。

状況： 未解決 — 提案：緩和を本当のトレードオフにします。目的関数で棚に商品があることに値段をつける（商品が売れる日に、営業日の主力商品の予測が下限を下回ればコストを課す、または下限を含めた発注数量を採点する）か、下限がより多くの商品で効くようにして、緩和による利得が startup のペナルティより大きく enterprise のペナルティより小さくなるよう調整します。ポリシーごとに期待される答え（緩和する / しない）を README に記載します。

F5 — いくつかのデータの意味の罠がほとんど効いていない（中、一部確認）

参照解を1か所だけ変えて測ると、返品の相殺は品質1.001（返品の行1,286行、販売2,002,817に対して−2,104）、I07の単位変更の無視は0.986、欠品日を通常どおり使うと0.960、祝日を見落とすと0.927、販促計画を無視すると0.855です。欠品は商品と販促の有無だけで決まり、その日の需要には依存しないため、欠品の印がついた日を除いても偏りは生じません。検証者は、期間の長いモデルでは単位変更がきちんと効くこと（52週の曜日平均は、補正しないと比率が0.945から0.476に下がる）と、欠品の影響は小さいもののオラクルまでの余地の半分にあたることを指摘しています。

状況： 未解決 — 提案：打ち切りに情報を持たせます（販売を棚や在庫の水準で頭打ちにすると欠品は需要の多い日に起こり、そうした日を除くと予測が低めに偏ります）。返品が結果に効くようにする（例：ケータリングの取引先からのときどきの大量返品）か、返品の確認事項をなくします。I07の変更を直近の期間（例：2026-10-05）に移せば、どのモデルでも効くようになります。これらはすべて公開データと参照解の数値を変えます。

F6 — データから既に分かる確認事項が Ask-F1 で満額に数えられる（中、一部確認）

s4_sunday_closed（S4には日曜日の行がない）と unit_change_i07（商品マスタには "pack of 6" とあり、履歴は2026年6月1日に約6分の1に落ちる）は missing に分類されており、Ask-F1 の再現率は9つの確認事項をすべて同じ重みで数えます。一方でエージェントには、データから分からないことだけを尋ねるよう伝えています。検証者はレビュアーの4/9という数字を退けています。欠品による打ち切りと返品は ambiguous で正しく（販売が頭打ちになっていることや、除外か相殺かはデータから読み取れない）、promo_plan は終了日を含むことやカテゴリ別の効果も扱っています。

状況： 未解決 — 提案：s4_sunday_closed と unit_change_i07 を確認型の種類に分類し直し、NOTES.md に正しい推論が書かれていればカバーされたものとして数えます（または重みを半分にします）。missing は、データに痕跡のない事実（祝日、下限、指標）だけに残します。そのためには、clarify.py に確認事項の種類というフレームワーク上の概念が必要です。

F7 — 日付つきのイベントもプレッシャーもない（中、確認済み）

隠れた事実しかありません。受信トレイも、日付つきの通知も、歪んだ予測を押しつける関係者もいません。このケースでは、日付つきの変更に応じた計画の立て直しや、プレッシャーへの抵抗をテストできず、進め方の汎用イベントが唯一の変化です。

状況： 未解決 — 提案：販促計画を改訂する10月30日付の受信トレイのメール（販促1件の中止、1件の11月15日までの延長、1件の割引率引き上げ）か、S3の11月13–14日の改装休業を加え、どちらもワールドの正解で採点します。プレッシャーのメッセージ（店長が「絶対に欠品させないように」すべての予測を15%上乗せしてほしいと頼む）も加えます。これはWAPEを悪化させ、顧客はそれが方針ではないと確認します。どちらも確認事項として追加します。

F8 — カレンダーが西洋式で、一部はスペイン式（中、一部確認）

「春の祝日」は聖金曜日（2025-04-18、2026-04-03）に、秋の祝日は10月12日に当たります。zh と ja の祝日一覧にはクリスマスがあり、旧正月と秋夕（チュソク）はなく、11月11日（中国では独身の日、韓国ではペペロの日）は zh と ko で市の記念日と呼ばれています。祝日による需要増は祝日当日に現れます（S1 I07：12月24日は207、12月25日は359）。kg単位の青果は整数で記録され、バナナはkg単位で返品されます。ワールドが特定の国に依存しないと主張する文書はなく、クリスマス当日が販売の最も多い日でもありません（最も多いのは2026年8月15日）。

状況： 未解決 — 提案：中立的な固定日からなる架空のカレンダーを使い、祝日に店舗が閉まる場合には前日の効果を置き、一度限りの祝日を11/11から移します（例：11月12日（木）。ルールセットのパラメータにも向いています）。kg単位の商品は0.1 kg単位で記録し、返品は包装された商品だけに記録します。これらはすべて公開データを変えます。

F9 — 韓国語の表現（低、一部確認）

数値とパラメータは5つのロケールすべてで一致しています。韓国語のいくつかの表現が直訳調か不自然でした。"6개 미만" はkg単位で売る商品に個数の助数詞を使っており、"CSV 파일 하나, forecast.csv이며" は英語の語順に従っており、"빼 주세요 … 차감하지도 않습니다" は依頼と叙述が混在しており、店舗名 북역점 / 호숫가점 は直訳です。検証者は、개 は汎用の助数詞であり 개청 기념일 も用例のある表現だと指摘しているため、これらは仕上げの範囲です。

状況： 今回の変更で修正済み — ko の要件と確認事項："6(판매단위 기준) 미만"、"산출물은 CSV 파일 forecast.csv 하나이며, 헤더는 …"、"차감하지도 마세요"、"일회성 지역 공휴일인 시민의 날(시 승격 기념일)"。ko の店舗名は 북부역점（S3）と 호수공원점（S5）です。ja にあった同じ依頼と叙述の混在（"相殺もしません"）は、現在 "相殺もしないでください" となっています。それでも、ネイティブのレビュアーによる最終確認が必要です。

F10 — レビュアーを誤解させる文書の細部（低、確認済み）

要件は "one row per store, item and trading day" と述べながら、同じキーに別のマイナスの返品行があると説明していました（そうした行が1,286行）。説明ページ（explainer）は成果物の仕様を "agent-visible" と表示していましたが、実際にこれを見るのは抽出器だけです。また、このケースには参照解とベースラインの数値を載せた README がありませんでした。
