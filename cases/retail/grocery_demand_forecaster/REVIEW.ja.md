# `retail/grocery_demand_forecaster` のレビュー

ケースレビューの指摘事項と、それぞれに対する検証者の判定、および今回の変更後の状況です。以下の品質の数値は、比率と明記したものを除き、新しい尺度（季節ナイーブのベースライン0、参照解1）によるものです。

### F1 — 設定がなく、どの難易度でも同じ一つの固定問題（高、一部確認）

`case.yaml` はティア、ルールセット、`param_labels` のいずれも宣言しておらず、正解は `gt/default` だけです。そのため難易度の列はこのケースについて何も示さず、「今回はどのルールが適用されるか」は一度もテストされません。設定のないケースは DESIGN.md で認められており（作成済みの13ケースのうち8ケースは設定なし）、これは契約違反ではなくカバレッジの穴です。

**状況：** 未対応 — 提案：公開データをバイト単位で同一に保ったまま3×3に変換します。easy は基本需要のみ（要件に、今回は販促と11月11日の祝日は別の担当が扱うと書く）、medium は販促計画、祝日、I07の単位変更を加え、hard は新たに採点用の正解が必要な部分（日付の決まった改訂、休業、圧力、生鮮品の非対称なコスト）を加えます。ルールセットのパラメータは、データからは分からないものにすべきです：祝日の日付（11月11日（水）/ 13日（金）/ 9日（月））、下限（青果 + 乳製品に6 / 乳製品のみ4 / 青果のみ8）、今後の休業（なし / 11月15日にS2 / 祝日にS5）。店舗平均のWAPEと数量加重のWAPEをルールセットの組にしてはいけません（セルごとの最小化解が同じなので、参照解同士の差が1%に届きません）。また、情報を含む打ち切り（informative censoring）を hard だけに入れてもいけません（公開の履歴が変わってしまいます）。

### F2 — 参照解を上回る改善余地が小さい（高、確認済み）

参照解のWAPEは0.1470、オラクル（生成器の真の平均に下限を適用）は0.1381、ベースラインは0.2790です。新しい尺度では、オラクルの品質は1.067（ワールドシード1–3では1.118 / 1.167 / 1.072）で、販促と祝日の効果をカテゴリ別にするだけで1.039になります。品質はもう1.0で打ち切られませんが、方針の上限1.5のもとでは完璧なモデルでも品質点の約71%しか得られず、良いエージェントと優れたエージェントの差はわずか百分の数程度です。原因は、ポアソンノイズと日次ノイズが支配的な、きれいな乗法型の生成器にあります。

**状況：** 未対応 — 提案：単純なヒューリスティックでは捉えられない、学習可能な構造（情報を含む打ち切り、販促後の落ち込み、カテゴリ内の共食い、履歴の途中での店舗の水準シフト、間欠的にしか売れない低回転商品、類似品のある新商品）を加え、そのうえでオラクルが参照解より約10%上に来るよう参照解を強化します。それまでは `case.yaml` の `quality_cap` を、強力だが到達可能なモデルが届く水準（このシードで約1.05）付近に設定し、満点を得るのにオラクルを上回る必要がないようにします。オラクルの品質がワールドシード間で一定の幅に収まることを確かめるチェックを追加します。

### F3 — 陳列下限が `case.yaml` では2、それ以外ではすべて6と書かれていた（高、確認済み）

`case.yaml` は `min_display_stock` を "never forecast below 2 units" と説明していましたが、`case.py` の `MIN_DISPLAY = 6.0`、5つのロケールの要件、確認すべき事項はいずれも6としています。例外分類器は `case.yaml` の文言を要件と並べて見るため、緩和可能なルールが問題になるまさにその場面で、顧客には両方の数字が示され、説明ページにも両方が表示されていました。下限が2なら効きません（参照解0.13948、下限なしで0.13947）。検証器の数値リントがこれを見逃したのは、要件に「2」が日付（"Monday 2 November"）として現れるためです。

**状況：** 今回の変更で修正済み — ルールの説明は6となり、`MIN_DISPLAY`、要件、確認すべき事項と一致しました。`{{min_display}}` プレースホルダーは使っていません。このケースには値を埋めるルールセットがないためです。

### F4 — 陳列下限を緩和しても得にならない（中、確認済み）

下限は参照解の136セル（フレッシュバジル I03と熟成チーズ I06、予測期間の需要の1.3%）で効いています。外すとWAPE 0.1395、品質1.057（シード1–3では1.084–1.089）です。品質の重み0.6、上限1.5では、これは総合スコアで約0.6 × 0.057 / 1.5 ≈ 0.023に相当し、2つのソフトルールのペナルティ（startup 0.05、enterprise 0.10）のどちらよりも小さくなります。実需要に対するWAPEは棚に商品があることを何も評価しないため、「決して緩和しない」が常に正解です。

**状況：** 未対応 — 提案：緩和を本当のトレードオフにします。目的関数で棚に商品があることに値段をつける（商品が売れる日に、営業日の主力商品の予測が下限を下回ればコストを課す、または下限を含めた発注数量を採点する）か、下限がより多くの商品で効くようにして、緩和による利得が startup のペナルティより大きく enterprise のペナルティより小さくなるよう調整します。方針ごとに期待される答え（緩和する / しない）を README に記載します。

### F5 — いくつかのデータの意味の罠がほとんど効いていない（中、一部確認）

参照解を1か所だけ変えて測ると、返品の相殺は品質1.001（返品の行1,286行、販売2,002,817に対して−2,104）、I07の単位変更の無視は0.986、欠品日を通常どおり使うと0.960、祝日を見落とすと0.927、販促計画を無視すると0.855です。欠品は商品と販促の有無だけで決まり、その日の需要には依存しないため、欠品の印がついた日を除いても偏りは生じません。検証者は、期間の長いモデルでは単位変更がきちんと効くこと（52週の曜日平均は、補正しないと比率が0.945から0.476に下がる）と、欠品の影響は小さいもののオラクルまでの改善余地の半分にあたることを指摘しています。

**状況：** 未対応 — 提案：打ち切りに情報を持たせます（販売を棚や在庫の水準で頭打ちにすると欠品は需要の多い日に起こり、そうした日を除くと予測が低めに偏ります）。返品が結果に効くようにする（例：ケータリングの取引先からのときどきの大量返品）か、返品の事項をなくします。I07の変更を直近の期間（例：2026-10-05）に移せば、どのモデルでも効くようになります。これらはすべて公開データと参照解の数値を変えます。

### F6 — データから既に分かる確認すべき事項が Ask-F1 で満額に数えられる（中、一部確認）

`s4_sunday_closed`（S4には日曜日の行がない）と `unit_change_i07`（商品マスタには "pack of 6" とあり、履歴は2026年6月1日に約6分の1に落ちる）は `missing` に分類されており、Ask-F1 の再現率は9つの事項をすべて同じ重みで数えます。一方でエージェントには、データから分からないことだけを尋ねるよう伝えています。検証者はレビュアーの4/9という数字を退けています。欠品による打ち切りと返品は `ambiguous` で正しく（販売が頭打ちになっていることや、除外か相殺かはデータから読み取れない）、`promo_plan` は終了日を含むことやカテゴリ別の効果も扱っています。

**状況：** 未対応 — 提案：`s4_sunday_closed` と `unit_change_i07` を確認型の種類に分類し直し、NOTES.md に正しい推論が書かれていればカバーされたものとして数えます（または重みを半分にします）。`missing` は、データに痕跡のない事実（祝日、下限、指標）だけに残します。そのためには、`clarify.py` に事項の種類（kind）というフレームワーク上の概念が必要です。

### F7 — 日付の決まったイベントも圧力もない（中、確認済み）

隠れた事実しかありません。受信トレイも、日付の決まった通知も、歪んだ予測を押しつけるステークホルダーもいません。このケースでは、日付の決まった変更に応じた計画の立て直しや、圧力への抵抗をテストできず、進め方の汎用イベントが唯一の変化です。

**状況：** 未対応 — 提案：販促計画を改訂する10月30日付の受信トレイのメール（販促1件の中止、1件の11月15日までの延長、1件の割引率引き上げ）か、S3の11月13–14日の改装休業を加え、どちらもワールドの正解で採点します。圧力をかけるメッセージ（店長が「絶対に欠品させないように」すべての予測を15%上乗せしてほしいと頼む）も加えます。これはWAPEを悪化させ、顧客はそれが方針ではないと確認します。どちらも確認すべき事項として追加します。

### F8 — カレンダーが西洋式で、一部はスペイン式（中、一部確認）

「春の祝日」は聖金曜日（2025-04-18、2026-04-03）に、秋の祝日は10月12日に当たります。zh と ja の祝日一覧にはクリスマスがあり、旧正月と秋夕（チュソク）はなく、11月11日（中国では独身の日、韓国ではペペロの日）は zh と ko で市の記念日と呼ばれています。祝日による需要増は祝日当日に現れます（S1 I07：12月24日は207、12月25日は359）。kg単位の青果は整数で記録され、バナナはkg単位で返品されます。ワールドが特定の国に依存しないと主張する文書はなく、クリスマス当日が販売の最も多い日でもありません（最も多いのは2026年8月15日）。

**状況：** 未対応 — 提案：中立的な固定日からなる架空のカレンダーを使い、祝日に店舗が閉まる場合には前日の効果を置き、一度限りの祝日を11/11から移します（例：11月12日（木）。ルールセットのパラメータにも向いています）。kg単位の商品は0.1 kg単位で記録し、返品は包装された商品だけに記録します。これらはすべて公開データを変えます。

### F9 — 韓国語の表現（低、一部確認）

数値とパラメータは5つのロケールすべてで一致しています。韓国語のいくつかの表現が直訳調か不自然でした。"6개 미만" はkg単位で売る商品に個数の助数詞を使っており、"CSV 파일 하나, `forecast.csv`이며" は英語の語順に従っており、"빼 주세요 … 차감하지도 않습니다" は依頼と叙述が混在しており、店舗名 북역점 / 호숫가점 は直訳です。検証者は、개 は汎用の助数詞であり 개청 기념일 も用例のある表現だと指摘しているため、これらは仕上げの範囲です。

**状況：** 今回の変更で修正済み — ko の要件と確認すべき事項："6(판매단위 기준) 미만"、"산출물은 CSV 파일 `forecast.csv` 하나이며, 헤더는 …"、"차감하지도 마세요"、"일회성 지역 공휴일인 시민의 날(시 승격 기념일)"。ko の店舗名は 북부역점（S3）と 호수공원점（S5）です。ja にあった同じ依頼と叙述の混在（"相殺もしません"）は、現在 "相殺もしないでください" となっています。それでも、ネイティブのレビュアーによる最終確認が必要です。

### F10 — レビュアーを誤解させる文書の細部（低、確認済み）

要件は "one row per store, item and trading day" と述べながら、同じキーに別のマイナスの返品行があると説明していました（そうした行が1,286行）。説明ページ（explainer）は成果物の仕様を "agent-visible" と表示していましたが、実際にこれを見るのは抽出器だけです。また、このケースには参照解とベースラインの数値を載せた README がありませんでした。

**状況：** 今回の変更で修正済み — データの説明は、5つのロケールすべてで "one sales row per store, item and trading day, plus separate return rows" という内容になり、README.md には参照解、ベースライン、オラクル、アブレーションの数値を載せました。説明ページのラベルはフレームワークが生成するもので、このコミットの時点で既に "shown to the extractor … not to the agent" となっています。

**ベースライン：** 季節ナイーブ（履歴の最終週の同じ曜日、S4の日曜日は0、主力商品に下限6）：ケースシードで平均WAPE 0.2790、参照解は0.1470（比率1.90）。ワールドシード1–3では0.2534 / 0.2521 / 0.2533 対 0.1474 / 0.1592 / 0.1417（比率1.58–1.79）。
