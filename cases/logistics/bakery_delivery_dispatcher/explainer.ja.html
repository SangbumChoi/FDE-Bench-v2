ケースの説明（README）

ベーカリー配送の配車担当者 — logistics/bakery_delivery_dispatcher

あるベーカリーのセントラルキッチンは、毎朝4台の車両で各店舗にパンのトレーを届けています。顧客はエージェントに、 明日（月曜日）のルートを「店舗にトレーが間に合うように、またドライバーが必要以上に長く走らなくて済むように」組むよう 依頼します。成果物は routes.json で、使う車両ごとに出発時刻（HH:MM、省略時は05:00）と訪問順の店舗を記載します。 評価器はこの計画をワールドの移動モデルで走らせ、参照解と比べて採点します。

このケースには設定がありません。どの難易度でも同じ一つの固定問題です（ティアもルールセットもありません）。進め方の 設定（仕様をすべて渡すか先に確認させるか、顧客のペルソナ、データのノイズ、イベント）は、ほかのすべてのケースと同様に その上に適用されます（cases/README.md を参照）。このケースはフレームワークのテストフィクスチャ （tests/conftest.py）でもあるため、検証を高速なまま保つ必要があります。

データ

cafes（18店舗 C01–C18：x_km / y_km はキッチン (0, 0) からの相対位置、trays 8–30、tier premium/standard、opens、deliver_by、partner_brand）と vans（V1–V4、max_trays 120、冷蔵車はV4のみ） からなります。ファイル名、ヘッダー、ラベルはローカライズされています（매장목록.csv の 매장등급 = 프리미엄、 cafeterias.csv の categoria = premium）が、IDと数値はローカライズしません。休業中の店舗も普通の1行にすぎず、 休業していることは顧客だけが知っています。

ケースシード（20261025）では、営業中の17店舗にトレー356枚を届け、車両全体の積載能力は480枚です。提携店舗は 港町店（C05、標準店）、時計台店（C10、旗艦店）、競技場前店（C16、旗艦店）で、ほかの旗艦店はC01、C04、C07、C13です。

顧客が知っていること（隠れた要件）

  • 道路距離は直線距離の1.3倍です。速度は区間の出発時刻で決まり、07:00より前は時速30km、07:00以降は時速20km （朝の渋滞時間帯）です。荷下ろしには4分に、トレー1枚あたり0.2分を加えた時間がかかります。
  • opens より前に着いた車両は待ちます。deliver_by を過ぎた到着も受け入れられますが、遅れた1分ごとに、車両の 稼働3分と同じだけのコスト（クレーム、納品代金の値引き）がベーカリーにかかります。
  • 車両は05:00から出発し、09:30（ドライバーの勤務終了）までに戻ります。1台に積めるのは max_trays 枚までです。
  • 南山店（C11）は今週改装のため休業です。
  • partner_brand の店舗は提携先の冷蔵商品を扱うため、冷蔵車V4しか配送できません。
  • 各店舗は、1台の車両の1回の訪問でトレーをすべて受け取ります。
  • 会社の慣習：どのルートでも旗艦店が標準店より先です。

確認すべき事項は9つです：道路距離、速度、荷下ろし時間、勤務時間、休業店舗、コールドチェーン、1回の訪問、旗艦店優先、 遅延コスト。

closed_cafe物理的休業中の店舗（C11）には配送しません。

品質（低いほど良い）： 全車両が出ている時間（出発から帰着まで。まだ開いていない店舗での待ち時間を含む）の合計に、 店舗への到着が deliver_by を過ぎた分数の3倍を加えた値です。

含まれる状況

  • 隠れた事実： C11は今週休業ですが、データのどこにもそうは書かれていません。
  • データの意味： partner_brand = yes は冷蔵商品を意味するため、冷蔵車でしか配送できません。
  • 緩和されうる慣習： 旗艦店優先。このシードでは、この慣習のためにV4がC05より先にC16とC10を回ることになり、 ルールを守るどの計画でも、C05には deliver_by の07:30より約10分遅れて着きます。
  • トレードオフ： 遅く出発すれば、まだ開いていない店舗での待ちを避けられますが、07:00以降に始まる区間は遅くなり、 遅れた到着のコストは3倍です。
  • 日付の決まったイベントも、ステークホルダーからの圧力もありません（REVIEW.md の F8 を参照）。

参照解とベースライン

参照解（_solve）は、最小コストの実行可能挿入（提携店舗を先に、次にランク順、大きい店舗から）でルートを作ります。 貪欲な構築が行き詰まった場合は、提携店舗の実行可能な順序ごとにV4をその順序で始めてやり直し、さらに挿入順序をシャッフル してやり直します。その後、目的値が下がる間は訪問先を1つずつ移し替え、各ルートに5分刻みのグリッド上で最良の出発時刻を 与えます。

ベースライン（baseline_solution）は、エンジニアなしで配車担当者が自分で組む計画です。V4が提携店舗を受け持ちます （旗艦店を先に、最も早く戻れる順序で）。ほかの店舗は真西から始めてキッチンの周りを回る方位角の順に並べ、次の店舗が 入らなくなるまで（積載能力、09:30までの帰着）V1、V2、V3、そしてV4に順に積みます。各車両は旗艦店を先に回り、残りは 開店順に回ります。どの車両も勤務開始の05:00に出発し、deliver_by は考慮しません。店舗が余った場合は、次の店舗から 回り始めます（どの開始点でもうまくいかなければ、すべての車両を05:00に出発させて参照解のルートを走らせます。これは常に 有効で、これまでに作ったワールドでこれが必要になったものはありません）。

補足

  • 合成データです。位置、トレー数、開店時刻、速度、荷下ろし時間、遅延の重みは架空の値です。速度は区間の出発時刻に 応じて07:00で一段切り替わるだけで、時間依存の移動モデルではありません。
  • build_world は、参照ソルバーがすべてのルールを守る計画を見つけ、かつどのルールにもそのルールだけを破る計画が 見つかるまで、シードの乱数列から引き続けます。そのため、どのワールドシードでも使えるワールドができます。
  • validate-case は、参照解の品質が1.0であること、ベースラインが有効で参照解より悪いこと、ルールごとにそのルール だけを破る成果物が1つあること、5つのロケールでデータが決定的であること、そしてワールドシード1、2、3を確認します。

レビュー結果（REVIEW）

logistics/bakery_delivery_dispatcher のレビュー

ケースレビューの指摘事項（F1–F9）と検証者の判定、そして今回の変更でそれぞれにどう対応したかをまとめます。特に断りの ない限り数値はケースシード20261025のもので、「q」は正規化した品質（ベースライン0、参照解1）です。改善余地の数値は、 参照解から始めた焼きなまし法（simulated annealing）の探索（移し替え・交換・2-opt の操作、出発時刻は分単位）によるもので、 この探索はレビューの601.51と521.98を再現しました。

F1 — 休業店舗が別の店舗の名前で呼ばれていた（高、確認済み）

5つのロケールすべてが「Clock Tower café (C11)」（日本語版では「時計台店（C11）」）が休業だと書いていました。データでは Clock Tower は旗艦店で提携店舗のC10であり、C11は South Hill（남산점、南山店、Cafetería Colina Sur）です。名前に従って C11に配送しC10を飛ばしたエージェントは、無効な計画を提出することになりました。参照解をそのように書き換えると、 closed_cafe、serve_each_once（C10が未配送）、shift_window（V4の帰着が10:08）に違反します。有効かどうかが、 正しい質問をするかではなく、名前よりIDを信じるかどうかで決まっていました。

状況： 今回の変更で修正済み — 5つのロケールの requirements.md と targets.yaml は、データと同じ名前で店舗を呼ぶように なりました：South Hill café (C11)、남산점(C11)、南山店（C11）（ja、zh）、Cafetería Colina Sur (C11)。C10は営業を続けます。 5つのロケールすべてでこの不一致を検出していた検証器の name (ID) リントは、もう何も報告しません。

F2 — 参照解を上回る余地が小さい（高、確認済み）

探索はすべてのルールのもとで601.51に達し、参照解の625.55より3.8%低くなります。品質はもう1.0で切り詰められません。 新しいベースライン（963.09）に対してその計画は q = 1.07 となり、方針の品質上限1.5のもとで品質配点の0.71を得ます。参照解は 0.67です。レビューで使った単純な方位角スイープの計画に出発時刻の調整を加えたもの（686.39）は q = 0.82 です。したがって 単純な計画と熟練者の計画は区別できるようになりました（0、0.82、1.0、1.07）が、既知のルール順守計画で上限に近いものは ありません。

状況： 未解決 — 提案：参照解を強化する（交換・2-opt の操作、分単位の出発時刻：このワールドで約601.5）か、そのままにして case.yaml に quality_cap: 1.1 を設定し、既知の最良水準の計画が満点を得られるようにします。インスタンスを厳しくすれば （F3、F4）、計画の差はさらに広がります。

F3 — 旗艦店優先を破る利得はわずかで、しかも慣習が不利に働く箇所から生じていない（高、一部確認）
