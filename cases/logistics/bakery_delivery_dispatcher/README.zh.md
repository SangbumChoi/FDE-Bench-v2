# 面包店配送调度员 — `logistics/bakery_delivery_dispatcher`

一家面包店的中央厨房每天早上用四辆车把面包托盘送到各门店。客户请智能体规划明天（周一）的路线，"让门店按时拿到托盘，
司机也别在外面跑太久"。交付物是 `routes.json`：每辆用到的车给出出发时间（`HH:MM`，不填则为 05:00）和按到访顺序排列的
门店。评估器按该设置的行驶模型执行方案，并与参考解比较评分。

此案例有**设置**：3 个层级 × 规则种子（DESIGN.md，Settings）。数据和需求在所有设置下都相同；变化的只是客户的隐藏规则，
以及随之变化的正确方案。与所有案例一样，交接方式的各项调节（给出完整需求还是先澄清、客户人设、数据噪声、事件）叠加在
其上（见 [cases/README.md](../../README.md)）。它也是框架的测试夹具（`tests/conftest.py`、`tests/test_validator.py`），
因此它的验证必须保持快速。

## 层级

| 层级 | 适用的规则 | 不在范围内（由客户亲口说明） |
|---|---|---|
| **easy** | 配送路线的核心：本周每辆车的托盘上限、司机班次（05:00 起出发，班次结束前返回）、每家门店只送一次、本周停业的门店、恒定 25 公里/小时、迟到成本 | 合作方冷链（"这周冷藏商品由合作方自己配送……哪辆车都可以去这些店"）、旗舰店优先的习惯（"这周暂停"）、早高峰（"周一是学校假期"）、V2 的刹车检查（"安排在周二"） |
| **medium** | easy + 合作方冷链（合作品牌门店只能由冷藏车 V4 配送）+ 规则种子抽到时的旗舰店优先习惯 | 早高峰和 V2 的刹车检查，与 easy 相同 |
| **hard** | medium + 早高峰（`rush_start` 之前 30 公里/小时，从该时刻起 20 公里/小时，已在途中的路段同样适用）、一个带日期的事件（周一 V2 在修理厂待到 06:40），以及东湖店（C07）店长坚持要在 06:30 之前做第一站的施压（不是规则） | — |

## 参数（规则种子抽取的值）

每个参数都从该设置所在层级的候选池中独立抽取，与其他参数无关（`case.yaml` 的 `params:`）。

| 参数 | easy | medium | hard | 影响 |
|---|---|---|---|---|
| `closed_cafe` | C11, C03, C14 | 同左 | 同左 | 不得送货的门店（南山店 / 北站店 / 梧桐里店，各语言版本中都按数据中的名称称呼）；其余门店都必须送到 |
| `late_cost` | 3, 2, 5 | 同左 | 同左 | 迟到一分钟相当于车辆多少分钟的在外时间：目标值中的迟到权重 |
| `shift_end` | 09:30, 09:00, 10:00 | 同左 | 同左 | 所有车辆必须回到厨房的时间 |
| `van_capacity` | 100, 110, 120 | 同左 | 110 | 本周每辆车的托盘数（数据中的 `max_trays` 为 120；新的周转箱更占地方）。在 hard 中固定，因此其候选值在 medium 中比较 |
| `rush_start` | none | none | 07:00, 06:30, 07:30 | 车辆从 30 公里/小时降到 20 公里/小时的时刻（easy 和 medium 整个早上都是 25 公里/小时） |
| `premium_first` | false | true, false | true, false | 本周旗舰店优先的习惯是否有效 |

车辆、05:00 的开始时间、道路距离（直线距离的 1.3 倍）、卸货时间（4 分钟 + 每托盘 0.2 分钟）、V2 在修理厂待到 06:40
（hard）以及施压的门店（C07）都是固定的。`case.py` 不推导任何值，也不需要 `admissible()`：在 `build_world` 接受的每个
世界中，每种组合都可行（见下文）。

## 智能体必须问的事项

各层级的应问事项（`locales/<lang>/targets.yaml`）：

- **所有层级：** 道路距离（1.3 倍）、卸货时间、班次结束时间、停业门店（是哪一家）、每家门店只送一次、旗舰店优先的
  习惯（有效，还是本周暂停）、迟到成本（其权重），以及低于货架容量 120 时的托盘上限（`tray_limit`，抽到 100 或 110；
  hard 始终为 110）。
- **easy 和 medium：** 恒定的 25 公里/小时（`speed`）。
- **easy：** 本周任何车辆都可以给合作门店送货（`partner_this_week`）。
- **medium 和 hard：** 冷链（合作门店只能由 V4 配送）。
- **hard：** 早高峰及其开始时间（`rush_hour`）、V2 在修理厂待到 06:40（`workshop`），以及 C07 店长的要求不是规则
  （`manager_pressure`）。

因此 easy 和 medium 有 9 或 10 个应问事项，hard 有 12 个。

## 数据

`cafes`（18 家门店 C01–C18：`x_km` / `y_km` 为相对厨房 (0, 0) 的位置，`trays` 8–30，`tier` premium/standard，
`opens`，开门后 30、45 或 60 分钟的 `deliver_by`，`partner_brand`）和 `vans`（V1–V4，`max_trays` 120，只有 V4 是
冷藏车）。文件名、表头和标签都已本地化（`매장목록.csv` 中的 `매장등급 = 프리미엄`，`cafeterias.csv` 中的
`categoria = premium`）；编号和数字不做本地化，门店名称随编号而定（C11 始终是南山店）。停业的门店只是普通的一行：
只有客户知道它停业了。

在案例种子下，18 家门店共订 332 个托盘（去掉停业门店后为 309 到 318 个，车队总运力为 400 到 480 个托盘）。合作门店是
港口店（C05，标准店）、钟楼店（C10，旗舰店）和体育中心店（C16，旗舰店）；其余旗舰店为 C01、C04、C07 和 C13。C07 在
07:00 开门（08:00 前送达），因此按店长说的"06:30 之前"去送，意味着车辆要在她门口等半小时。

**使用哪些世界。** `build_world` 持续从种子的随机流中抽取，直到得到一个对规则种子可能抽到的每个设置（公开或私有）都
可用的世界：
1. 对每个层级，参考求解器在该层级最严格的组合下（100 个托盘、09:00 前返回，hard 中还有 06:30 开始的早高峰和 06:40 才能
   出发的 V2，该层级有的话还包括这一习惯和冷链）给全部 18 家门店送货。这个方案就是该层级的兜底方案：去掉停业门店后，它
   满足每个设置的规则（更晚的班次结束时间、更多托盘、更晚的高峰、没有这一习惯以及少一个站点，都不会让车辆更晚返回），
   因此每个设置都有一个有效方案。
2. 参数能改变答案：在每个层级的代表组合下，参考解有一辆车晚于最早的班次结束时间返回（hard），有一辆车的装载量超过最小的
   托盘上限（medium），迟到至少占目标值的 1%，并且比没有旗舰店优先习惯时至少贵 1%（hard）。
3. 在 hard 中，取 110 个托盘和 09:00 的班次结束时间，每条规则都有一个只违反它的方案。

约 9% 的抽取能通过；构建一个世界平均需要 0.8 秒（在世界种子 1–30 上最多 3.3 秒）。

## 规则

| 规则 | 类别 | 层级 | 含义 |
|---|---|---|---|
| `van_capacity` | 物理约束 | 全部 | 本周每辆车最多装 `van_capacity` 个托盘。 |
| `shift_window` | 物理约束 | 全部 | 车辆 05:00 或之后出发，`shift_end` 前回到厨房。 |
| `van_ready` | 物理约束 | hard | V2 不早于 06:40 出发（周一在修理厂）。 |
| `closed_cafe` | 物理约束 | 全部 | 不给 `closed_cafe` 送货。 |
| `serve_each_once` | 合同约束 | 全部 | 每家营业门店恰好送一次。 |
| `cold_chain` | 合同约束 | medium, hard | 合作品牌门店只能由冷藏车配送。 |
| `premium_first` | 业务惯例 | medium, hard，仅当 `premium_first` | 每条路线上旗舰店都排在标准店之前（在把业务惯例设为可放宽的政策下，可经例外流程放宽）。 |

**质量（越低越好）：** 所有车辆在外的总时间（从出发到返回，包括在尚未开门的门店等待的时间），加上门店晚于 `deliver_by`
送达的每一分钟乘以 `late_cost`。

## 包含的情境

- **隐藏事实：** 哪家门店停业；低于 `max_trays` 的本周托盘上限；班次结束时间；迟到权重；旗舰店优先的习惯是否有效；
  hard 中早高峰何时开始。
- **数据语义：** `partner_brand = yes` 表示冷藏商品，因此只能用冷藏车配送（medium、hard），但在 easy 中本周不是这样。
- **可以放宽的习惯：** 旗舰店优先（抽到时）。在代表组合的设置下，它占目标值的 27–28%，因此在业务惯例可放宽的政策下，
  经例外流程放宽它是划算的（REVIEW.md，F3）。
- **带日期的事件（hard）：** 周一 V2 在修理厂待到 06:40。
- **施压（hard）：** C07 店长要求 06:30 之前做第一站。客户说这不是规则；照办意味着要在一家 07:00 才开门的门店（案例种子）
  等待，并重排一条路线。
- **权衡：** 晚些出发可以避免在尚未开门的门店等待，但在 hard 中高峰开始后的路段更慢，而迟到的代价是车辆时间的
  `late_cost` 倍。

## 参考解与基线

**参考解**（`_plan`）用最便宜的可行插入来构建路线（适用冷链时先合作门店，再按等级，大店优先）；贪心构建陷入死局时，
依次以合作门店的每种可行顺序作为 V4 的起点重试，再用打乱的插入顺序重试；它还会从去掉停业门店的该层级兜底方案出发。每个
起点都通过逐个迁移单个站点来改进，其中较便宜的一个再经过 300 轮破坏与重建（ruin and recreate；取出 2–4 家相邻或随机的
门店，再用最便宜插入放回），并在 5 分钟的网格上为每条路线选出最佳出发时间。参考解对每个世界和每组规则值只计算一次。

**基线**（`baseline_solution`）是调度员在没有工程师的情况下自己排的方案：适用冷链时，V4 负责合作门店（旗舰店优先，按
最早返回的顺序）；其余门店从正西方向开始，按绕厨房一圈的方位角顺序排列，依次装上 V1、V2、V3，然后 V4，直到下一家装不下
为止（本周托盘上限、班次结束前返回）；每辆车先送旗舰店，其余按开门时间顺序；所有车辆都在班次开始的 05:00 出发（hard 中
V2 为 06:40），不考虑 `deliver_by`。如果有门店剩下，扫描就从下一家门店开始重来；如果没有任何起点可行，就让所有车辆尽早
出发，跑该层级兜底方案的路线（总是有效；目前还没有用到）。

## 备注

- 合成数据。位置、托盘数、开门时间、车速、卸货时间和迟到权重都是虚构的。在 hard 中，已在途中的路段在 `rush_start`
  时同样变速（路段出发得越晚，所需时间绝不会更短）。
- 引入规则种子后，参考解之上的提升空间尚未重新测量（REVIEW.md，F2）。
- `validate-case` 检查每个公开设置：参考解的质量为 1.0，基线有效且更差，每条适用的规则各有一个只违反该规则的交付物，
  五个语言版本的数据是确定性的，每个参数都起作用，每个设置下智能体看到的内容都相同，以及世界种子 1、2 和 3。
