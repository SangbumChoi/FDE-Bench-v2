# 面包店配送调度员 — `logistics/bakery_delivery_dispatcher`

一家面包店的中央厨房每天早上用四辆车把面包托盘送到各门店。客户请智能体规划明天（周一）的路线，"让门店按时拿到托盘，
司机也别在外面跑太久"。交付物是 `routes.json`：每辆用到的车给出出发时间（`HH:MM`，不填则为 05:00）和按到访顺序排列的
门店。评估器按世界的行驶模型执行该方案，并与参考解比较评分。

此案例没有设置：每个难度下都是同一个固定问题（没有层级，也没有规则集）。与所有案例一样，交接方式的各项调节（给出完整需求还是先澄清、客户人设、数据噪声、事件）叠加在其上（见 [cases/README.md](../../README.md)）。它也是框架的测试夹具
（`tests/conftest.py`），因此它的验证必须保持快速。

## 数据

`cafes`（18 家门店 C01–C18：`x_km` / `y_km` 为相对厨房 (0, 0) 的位置，`trays` 8–30，`tier` premium/standard，
`opens`，`deliver_by`，`partner_brand`）和 `vans`（V1–V4，`max_trays` 120，只有 V4 是冷藏车）。文件名、表头和标签都已
本地化（`매장목록.csv` 中的 `매장등급 = 프리미엄`，`cafeterias.csv` 中的 `categoria = premium`）；编号和数字不做本地化。
停业的门店只是普通的一行：只有客户知道它停业了。

在案例种子（20261025）下，营业门店共 17 家、356 个托盘，车队总运力为 480 个托盘。合作门店是港口店（C05，标准店）、
钟楼店（C10，旗舰店）和体育中心店（C16，旗舰店）；其余旗舰店为 C01、C04、C07 和 C13。

## 客户知道的内容（隐藏需求）

- 道路距离是直线距离的 1.3 倍。车速取决于路段的出发时间：07:00 之前为 30 公里/小时，07:00 起为 20 公里/小时（早高峰）。
  卸货需要 4 分钟，另加每托盘 0.2 分钟。
- 早于 `opens` 到达的车辆需要等待。晚于 `deliver_by` 到达也会收货，但每晚一分钟，面包店的损失相当于车辆多跑三分钟
  （投诉、货款折让）。
- 车辆最早 05:00 出发，09:30（司机下班）前返回；每辆车最多装 `max_trays` 个托盘。
- 南山店（C11）本周装修停业。
- `partner_brand` 门店销售合作方的冷藏商品，因此只能由冷藏车 V4 配送。
- 每家门店的全部托盘由一辆车一次送达。
- 公司习惯：每条路线上旗舰店都排在标准店之前。

共有 9 个应问事项：道路距离、车速、卸货时间、班次、停业门店、冷链、一次送达、旗舰店优先和迟到成本。

## 规则

| 规则 | 类别 | 含义 |
|---|---|---|
| `van_capacity` | 物理约束 | 每辆车最多装 120 个托盘。 |
| `shift_window` | 物理约束 | 车辆 05:00 或之后出发，09:30 前回到厨房。 |
| `closed_cafe` | 物理约束 | 不给停业门店（C11）送货。 |
| `serve_each_once` | 合同约束 | 每家营业门店恰好送一次。 |
| `cold_chain` | 合同约束 | 合作品牌门店只能由冷藏车配送。 |
| `premium_first` | 业务惯例 | 每条路线上旗舰店都排在标准店之前（在把业务惯例设为可放宽的政策下，可经例外流程放宽）。 |

**质量（越低越好）：** 所有车辆在外的总时间（从出发到返回，包括在尚未开门的门店等待的时间），加上门店晚于 `deliver_by`
送达的每一分钟乘以 3。

## 包含的情境

- **隐藏事实：** C11 本周停业；数据中没有任何地方提到这一点。
- **数据语义：** `partner_brand = yes` 表示冷藏商品，因此只能用冷藏车配送。
- **可以放宽的习惯：** 旗舰店优先。在这个种子下，它迫使 V4 先送 C16 和 C10、再送 C05，因此在每个合规方案中，C05 都比
  其 07:30 的 `deliver_by` 晚约 10 分钟送达。
- **权衡：** 晚些出发可以避免在尚未开门的门店等待，但 07:00 起出发的路段更慢，而迟到的代价是三倍。
- 没有带日期的事件，也没有利益相关方施压（见 REVIEW.md，F8）。

## 参考解与基线

**参考解**（`_solve`）用最便宜的可行插入来构建路线（先合作门店，再按等级，大店优先）；贪心构建陷入死局时，依次以合作门店的
每种可行顺序作为 V4 的起点重试，再用打乱的插入顺序重试。之后，只要目标值还在下降，就逐个迁移单个站点，并在 5 分钟的
网格上为每条路线选出最佳出发时间。

**基线**（`baseline_solution`）是调度员在没有工程师的情况下自己排的方案：V4 负责合作门店（旗舰店优先，按最早返回的顺序）；
其余门店从正西方向开始，按绕厨房一圈的方位角顺序排列，依次装上 V1、V2、V3，然后 V4，直到下一家装不下为止（运力、09:30
前返回）；每辆车先送旗舰店，其余按开门时间顺序；所有车辆都在班次开始的 05:00 出发，不考虑 `deliver_by`。如果有门店剩下，
扫描就从下一家门店开始重来（如果没有任何起点可行，就让所有车辆在 05:00 出发跑参考解的路线，这总是有效的；目前构建过的
世界都没有用到这一步）。

| 种子 20261025 | 目标值 | 路线分钟数 | 迟到分钟数 | 路线 |
|---|---|---|---|---|
| 参考解 | 625.55 | 592.74 | 10.94 | V1 06:20 C01 C04 C15 C08 · V2 06:00 C13 C07 C18 C06 · V3 05:45 C09 C03 C14 C02 C17 · V4 06:10 C16 C10 C05 C12 |
| 基线 | 963.09 | 897.53 | 21.85 | V1 C03 C14 C02 C17 · V2 C07 C13 C09 C18 C06 C12 · V3 C01 C04 C08 C15 · V4 C16 C10 C05，均为 05:00 出发 |

基线多出的成本大部分是等待：05:00 出发，车辆到达的是 06:00 以后才开门的门店。

**提升空间**（种子 20261025；"q" 为归一化质量，基线为 0，参考解为 1）。从参考解出发的模拟退火搜索（迁移、交换和 2-opt
操作，出发时间精确到分钟；这是分析脚本，不属于案例）在遵守全部规则时达到 601.51，q = 1.07，在政策的质量上限 1.5 下获得
质量分的 0.71（参考解为 0.67）。该方案的装载量为 89/85/115/67 个托盘，最晚返回时间为 09:21，因此运力和班次在这里都不
构成约束。放宽 `premium_first` 后，同一搜索达到 521.98 且没有迟到（q = 1.31），在四条路线中的三条上打破了这一习惯。

## 备注

- 合成数据。位置、托盘数、开门时间、车速、卸货时间和迟到权重都是虚构的；车速只是按路段出发时间在 07:00 发生一次阶跃，
  而不是随时间变化的行驶模型。
- `build_world` 会持续从种子的随机流中抽取，直到参考求解器找到遵守全部规则的方案，且每条规则都有一个只违反它的方案，
  因此任何世界种子都能得到可用的世界。
- `validate-case` 检查：参考解的质量为 1.0，基线有效且更差，每条规则各有一个只违反该规则的交付物，五个语言版本的数据
  是确定性的，以及世界种子 1、2 和 3。
