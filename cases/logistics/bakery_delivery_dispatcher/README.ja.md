# ベーカリー配送の配車担当者 — `logistics/bakery_delivery_dispatcher`

あるベーカリーのセントラルキッチンは、毎朝4台の車両で各店舗にパンのトレーを届けています。顧客はエージェントに、
明日（月曜日）のルートを「店舗にトレーが間に合うように、またドライバーが必要以上に長く走らなくて済むように」組むよう
依頼します。成果物は `routes.json` で、使う車両ごとに出発時刻（`HH:MM`、省略時は05:00）と訪問順の店舗を記載します。
評価器はこの計画をその設定の移動モデルで走らせ、参照解と比べて採点します。

このケースには**設定**があります。3ティア × ルールシードです（DESIGN.md、Settings）。データと依頼はどの設定でも同じで、
変わるのは顧客の隠れたルールと、それに応じた正しい計画だけです。進め方の調整項目（仕様をすべて渡すか先に質問させるか、
顧客のペルソナ、データのノイズ、イベント）は、ほかのすべてのケースと同様にその上に適用されます
（[cases/README.md](../../README.md) を参照）。このケースはフレームワークのテストフィクスチャ（`tests/conftest.py`、
`tests/test_validator.py`）でもあるため、検証を高速なまま保つ必要があります。

## ティア

| ティア | 適用されるルール | 対象外（顧客が自分の言葉で伝える） |
|---|---|---|
| **easy** | 配送ルートの基本：今週の1台あたりのトレー上限、ドライバーの勤務時間（05:00から出発し、勤務終了までに帰着）、1店舗1回の訪問、今週休業の店舗、一定の時速25km、遅延のコスト | 提携先のコールドチェーン（「今週は提携先が冷蔵商品を自分で届けます … どの車両が回っても構いません」）、旗艦店を先に回る慣習（「今週お休みです」）、朝の渋滞（「月曜日は学校が休み」）、V2のブレーキ点検（「火曜日に入っています」） |
| **medium** | easy ＋ 提携先のコールドチェーン（提携ブランドの店舗は冷蔵車V4だけが配送）＋ ルールシードの抽選で有効になった場合の旗艦店優先の慣習 | 朝の渋滞とV2のブレーキ点検（easy と同じ） |
| **hard** | medium ＋ 朝の渋滞（`rush_start` までは時速30km、そこからは時速20km、すでに走行中の区間にも適用）、日付の決まったイベント（月曜日はV2が06:40まで整備工場）、06:30より前に最初の訪問先にしてほしいと言い張る東湖店（C07）の店長からの圧力（ルールではない） | — |

## パラメータ（ルールシードが抽選する値）

各パラメータは、その設定のティアの候補プールから、ほかのパラメータとは独立に抽選されます（`case.yaml` の `params:`）。

| パラメータ | easy | medium | hard | 変わるもの |
|---|---|---|---|---|
| `closed_cafe` | C11, C03, C14 | 同じ | 同じ | 配送してはいけない店舗（南山店／北駅店／楓並木店。どのロケールでもデータどおりの名前）。それ以外の店舗にはすべて配送が必要 |
| `late_cost` | 3, 2, 5 | 同じ | 同じ | 遅れた1分が車両の稼働何分に相当するか：目的値の遅延の重み |
| `shift_end` | 09:30, 09:00, 10:00 | 同じ | 同じ | すべての車両がキッチンに戻っていなければならない時刻 |
| `van_capacity` | 100, 110, 120 | 同じ | 110 | 今週の1台あたりのトレー数（データの `max_trays` は120だが、新しい番重が場所をとる）。hard では固定なので、候補どうしは medium で比較 |
| `rush_start` | none | none | 07:00, 06:30, 07:30 | 車両が時速30kmから20kmに落ちる時刻（easy と medium は朝のあいだずっと時速25km） |
| `premium_first` | false | true, false | true, false | 今週、旗艦店優先の慣習が有効かどうか |

車両、05:00の勤務開始、道路距離（直線距離の1.3倍）、荷下ろし時間（4分 ＋ トレー1枚あたり0.2分）、06:40まで整備工場に
あるV2（hard）、圧力をかける店舗（C07）は固定です。`case.py` は値を何も算出せず、`admissible()` も必要ありません。
`build_world` が受け入れるどのワールドでも、すべての組み合わせが実行可能だからです（後述）。

## エージェントが確認すべきこと

ティアごとの確認すべき事項（`locales/<lang>/targets.yaml`）：

- **すべてのティア：** 道路距離（1.3倍）、荷下ろし時間、勤務終了時刻、休業店舗（どの店舗か）、1店舗1回の訪問、
  旗艦店優先の慣習（有効か、今週はお休みか）、遅延のコスト（その重み）、そして棚の120枚より少ない場合のトレー上限
  （`tray_limit`、100か110が抽選される。hard は常に110）。
- **easy と medium：** 一定の時速25km（`speed`）。
- **easy：** 今週はどの車両が提携店舗を回ってもよいこと（`partner_this_week`）。
- **medium と hard：** コールドチェーン（提携店舗はV4だけ）。
- **hard：** 朝の渋滞とその開始時刻（`rush_hour`）、06:40まで整備工場にあるV2（`workshop`）、C07の店長の要求が
  ルールではないこと（`manager_pressure`）。

したがって、確認すべき事項は easy と medium で9または10、hard で12です。

## データ

`cafes`（18店舗 C01–C18：`x_km` / `y_km` はキッチン (0, 0) からの相対位置、`trays` 8–30、`tier`
premium/standard、`opens`、開店の30分・45分・60分後のいずれかである `deliver_by`、`partner_brand`）と `vans`
（V1–V4、`max_trays` 120、冷蔵車はV4のみ）からなります。ファイル名、ヘッダー、ラベルはローカライズされています
（`매장목록.csv` の `매장등급 = 프리미엄`、`cafeterias.csv` の `categoria = premium`）が、IDと数値はローカライズ
しません。店舗の名前はIDに従います（C11は常に南山店）。休業中の店舗も普通の1行にすぎず、休業していることは顧客だけが
知っています。

ケースシードでは、18店舗の注文はトレー332枚です（休業店舗を除くと309～318枚で、車両全体の積載能力は400～480枚）。
提携店舗は港町店（C05、標準店）、時計台店（C10、旗艦店）、競技場前店（C16、旗艦店）で、ほかの旗艦店はC01、C04、C07、
C13です。C07は07:00に開店する（08:00までに配送）ので、店長の言う「06:30より前」に従うと、車両がその店の前で30分
待つことになります。

**どのワールドを使うか。** `build_world` は、ルールシードが抽選しうるすべての設定（公開でも非公開でも）で使える
ワールドが得られるまで、シードの乱数列から引き続けます：
1. ティアごとに、参照ソルバーがそのティアの最も厳しい組み合わせ（トレー100枚、09:00までに帰着、hard では06:30からの
   渋滞と06:40からのV2、そのティアにあれば慣習とコールドチェーン）で18店舗すべてに配送します。この計画がそのティアの
   フォールバック計画です。休業店舗を除いてもあらゆる設定のルールを守るので（勤務終了が遅い、トレーが多い、渋滞が遅い、
   慣習がない、訪問先が1つ少ない、のいずれでも車両の帰着が遅くなることはない）、どの設定にも有効な計画があります。
2. パラメータが答えを変えられます。各ティアの代表の組み合わせで、参照解には最も早い勤務終了時刻より後に帰着する車両が
   あり（hard）、最も小さいトレー上限を超えて積む車両があり（medium）、遅延が目的値の1%以上を占め、旗艦店優先の慣習が
   ない場合より1%以上高くつきます（hard）。
3. hard でトレー110枚、勤務終了09:00のとき、どのルールにもそのルールだけを破る計画があります。

引いたワールドの約9%が条件を満たし、ワールド1つの構築には平均0.8秒かかります（ワールドシード1–30で最大3.3秒）。

## ルール

| ルール | 区分 | ティア | 意味 |
|---|---|---|---|
| `van_capacity` | 物理的 | すべて | 今週は車両1台に積めるトレーは最大 `van_capacity` 枚です。 |
| `shift_window` | 物理的 | すべて | 車両は05:00以降に出発し、`shift_end` までにキッチンへ戻ります。 |
| `van_ready` | 物理的 | hard | V2は06:40より前には出発しません（月曜日は整備工場にあります）。 |
| `closed_cafe` | 物理的 | すべて | `closed_cafe` には配送しません。 |
| `serve_each_once` | 契約上 | すべて | 営業中の全店舗にちょうど1回ずつ配送します。 |
| `cold_chain` | 契約上 | medium, hard | 提携ブランドの店舗には冷蔵車だけが配送します。 |
| `premium_first` | 業務慣行 | medium, hard, `premium_first` の場合 | どのルートでも旗艦店が標準店より先です（業務慣行を緩和可能とする方針のもとでは、例外手続きを経て緩和されうる）。 |

**品質（低いほど良い）：** 全車両が出ている時間（出発から帰着まで。まだ開いていない店舗での待ち時間を含む）の合計に、
店舗への到着が `deliver_by` を過ぎたすべての分数の `late_cost` 倍を加えた値です。

## 含まれる状況

- **隠れた事実：** どの店舗が休業か、`max_trays` より少ない今週のトレー上限、勤務終了時刻、遅延の重み、旗艦店優先の
  慣習が有効か、hard では渋滞がいつ始まるか。
- **データの意味：** `partner_brand = yes` は冷蔵商品を意味するため、冷蔵車でしか配送できません（medium、hard）。
  ただし easy では今週はそうではありません。
- **緩和されうる慣習：** 旗艦店優先（抽選された場合）。代表の組み合わせの設定では目的値の27–28%のコストになるので、
  業務慣行が緩和可能な方針のもとでは、例外手続きを経て緩和するほうが得になります（REVIEW.md、F3）。
- **日付の決まったイベント（hard）：** 月曜日はV2が06:40まで整備工場にあります。
- **圧力（hard）：** 06:30より前に最初の訪問先にしてほしいというC07の店長の要求。顧客はこれをルールではないと言います。
  従うと、07:00に開店する店舗（ケースシード）で待つことになり、ルートを1つ組み直すことになります。
- **トレードオフ：** 遅く出発すれば、まだ開いていない店舗での待ちを避けられますが、hard では渋滞開始後の区間が遅くなり、
  遅れた到着には車両の稼働時間の `late_cost` 倍のコストがかかります。

## 参照解とベースライン

**参照解**（`_plan`）は、最小コストの実行可能挿入（コールドチェーンが適用される場合は提携店舗を先に、次にランク順、
大きい店舗から）でルートを作ります。貪欲な構築が行き詰まった場合は、提携店舗の実行可能な順序ごとにV4をその順序で
始めてやり直し、さらに挿入順序をシャッフルしてやり直します。また、休業店舗を除いたティアのフォールバック計画からも
始めます。各開始点は訪問先を1つずつ移し替えて改善し、そのうち安いほうをさらに破壊と再構築（ruin and recreate）300回
（隣接する、または無作為の2–4店舗を取り出し、最小コスト挿入で戻す）で改善し、各ルートに5分刻みのグリッド上で最良の
出発時刻を与えます。参照解はワールドとルールの値ごとに一度だけ計算します。

**ベースライン**（`baseline_solution`）は、エンジニアなしで配車担当者が自分で組む計画です。コールドチェーンが適用される
場合はV4が提携店舗を受け持ちます（旗艦店を先に、最も早く戻れる順序で）。ほかの店舗は真西から始めてキッチンの周りを回る
方位角の順に並べ、次の店舗が入らなくなるまで（今週のトレー上限、勤務終了までの帰着）V1、V2、V3、そしてV4に順に積み
ます。各車両は旗艦店を先に回り、残りは開店順に回ります。どの車両も勤務開始の05:00に出発し（hard ではV2は06:40）、
`deliver_by` は考慮しません。店舗が余った場合は、方位角順の次の店舗から回り直します。どの開始点でもうまくいかなければ、
すべての車両をできるだけ早く出発させてティアのフォールバック計画のルートを走らせます（常に有効で、これまで必要に
なったことはありません）。

## 補足

- 合成データです。位置、トレー数、開店時刻、速度、荷下ろし時間、遅延の重みは架空の値です。hard では、すでに走行中の
  区間でも `rush_start` で速度が変わります（区間を遅く始めたほうが所要時間が短くなることはありません）。
