# `logistics/bakery_delivery_dispatcher` のレビュー

ケースレビューの指摘事項（F1–F9）と検証者の判定、そして今回の変更でそれぞれにどう対応したかをまとめます。特に断りの
ない限り数値はケースシード20261025のもので、「q」は正規化品質（ベースライン0、参照解1）です。改善余地の数値は、
参照解から始めた焼きなまし法（simulated annealing）の探索（移し替え・交換・2-opt の操作、出発時刻は分単位）によるもので、
この探索はレビューの601.51と521.98を再現しました。

### F1 — 休業店舗が別の店舗の名前で呼ばれていた（高、確認済み）

5つのロケールすべてが「Clock Tower café (C11)」（日本語版では「時計台店（C11）」）が休業だと書いていました。データでは
Clock Tower は旗艦店で提携店舗のC10であり、C11は South Hill（남산점、南山店、Cafetería Colina Sur）です。名前に従って
C11に配送しC10を飛ばしたエージェントは、無効な計画を提出することになりました。参照解をそのように書き換えると、
`closed_cafe`、`serve_each_once`（C10が未配送）、`shift_window`（V4の帰着が10:08）に違反します。有効かどうかが、
正しい質問をするかではなく、名前よりIDを信じるかどうかで決まっていました。

**状況：** 今回の変更で修正済み — 5つのロケールの requirements.md と targets.yaml は、データと同じ名前で店舗を呼ぶように
なりました：South Hill café (C11)、남산점(C11)、南山店（C11）（ja、zh）、Cafetería Colina Sur (C11)。C10は営業を続けます。
5つのロケールすべてでこの不一致を検出していた検証器の `name (ID)` リントは、もう何も報告しません。

**ルールシード：** 休業店舗はパラメータになりました（C11、C03、C14のいずれか）。各候補のどのロケールでの表記も
case.yaml の `params.closed_cafe.labels` から取られ、データがそのIDに付けている名前です（どのワールドでも店舗の名前は
IDに従います）。したがって、どの店舗が抽選されてもこの修正は保たれます。hard ティアで圧力をかける店舗C07も、データ
どおりの名前で呼んでいます。`name (ID)` リントは、どの公開設定でも何も報告しません。

### F2 — 参照解を上回る改善余地が小さい（高、確認済み）

探索はすべてのルールのもとで601.51に達し、参照解の625.55より3.8%低くなります。品質はもう1.0で切り詰められません。
新しいベースライン（963.09）に対してその計画は q = 1.07 となり、方針の品質上限1.5のもとで品質点の0.71を得ます。参照解は
0.67です。レビューで使った単純な方位角スイープの計画に出発時刻の調整を加えたもの（686.39）は q = 0.82 です。したがって
単純な計画と熟練者の計画は区別できるようになりました（0、0.82、1.0、1.07）が、既知のルール順守計画で上限に近いものは
ありません。

**状況：** 未対応 — 提案：参照解を強化する（交換・2-opt の操作、分単位の出発時刻：このワールドで約601.5）か、そのままにして
case.yaml に `quality_cap: 1.1` を設定し、既知の最良水準の計画が満点を得られるようにします。インスタンスを厳しくすれば
（F3、F4）、計画の差はさらに広がります。

**ルールシード：** 参照解はティアのフォールバック計画からも始めるようになり、移し替えの後に破壊と再構築（ruin and
recreate）を300回加えます。上の数値は以前の単一の問題のもので、新しいルールのもとでの改善余地は測っていません。
引き続き未対応です。

### F3 — 旗艦店優先を緩和しても利得はわずかで、しかも慣習が不利に働く箇所から生じていない（高、一部確認）

`premium_first` を緩和すると、探索は遅延なしで521.98（q = 1.31）に達し、ルールを守る最良の計画より13.2%低くなります。
ルールを守るどの計画でも、V4がC16とC10を先に回らなければならないため、C05には約10分遅れて着きます（参照解のV4：C16
06:19、C10 07:00、C05 07:40）。新しい尺度では、以前の「1.0で切り詰められる」という論拠はなくなりました。4つのスコア要素を
すべて数えると（品質の重み0.6）、慣習を緩和すれば、ルールを守る最良の計画に比べてペナルティ前の最終スコアが0.094上がります。
ペナルティを差し引くと、`enterprise_balanced`（ペナルティ0.1）では−0.006、`startup_velocity`（0.05）では+0.044です。
参照解と比べると、`enterprise_balanced` で+0.023になります。最良の緩和計画は、V4だけでなく4ルートのうち3ルートで慣習を
緩和しています。

**状況：** 未対応 — 提案：よく根拠づけられた例外がここで得になるべきかを決めます。得になるべきなら、慣習のコストを具体的
かつ局所的にします。たとえば提携SLA（「提携店舗は遅れた1分ごとに当社に費用を請求します」）を設け、ルールを守るV4のルート
が緩和したルートより明らかに高くつくようにし、その業務上の理由こそがエージェントの示すべき理由になるようにします。
README の緩和前後の数値（601.51 対 521.98）は最新に保ちます。得になるべきでないなら、衝突をなくす（たとえばC05の
`deliver_by` を遅くする）か、慣習を契約上のルールにして、緩和しても決して正味の利得が出ないようにします。

**ルールシード：** 慣習はパラメータになりました。medium と hard では有効か無効かを抽選し、easy では無効です。有効な
場合のコストは以前よりずっと大きく、ケースシードで参照解の目的値の27.5%（hard/s5）と28.4%（medium/s5）になります。
配送期限の幅が狭くなったためです。業務慣行が緩和可能な方針のもとでは、承認された例外で慣習を緩和すれば明らかに得に
なります。このパラメータが結果を左右するよう、`build_world` は hard の代表の組み合わせで少なくとも1%を求めます。
緩和がこれほど得になるべきかどうかは、引き続き未対応です。

### F4 — 積載能力、勤務時間、1回訪問の事項が最良の計画を左右しない（中、一部確認）

ルールを守る最良の計画では、積載量は120に対して89/85/115/67枚、最も遅い帰着は09:30に対して09:21です。営業中の店舗の
需要は、車両全体の積載能力480枚に対して356枚です。成果物には訪問先ごとの数量がないため、`one_visit` の事項は計画を
変えられません（店舗を2回書けば、それだけで `serve_each_once` 違反です）。どちらのルールも、弱い計画では実際に制約に
なります。ベースラインのスイープは、まさに積載能力か勤務時間に引っかかったときに次の車両へ移ります。`van_capacity` には
確認すべき事項がありません（`max_trays` はデータにあります）。

**状況：** 未対応 — 提案：物理的ルールが強い計画にも効くようにしたいなら、どれか1つが最適解で制約になるようにします。
勤務終了を09:00にするか、需要を車両全体の積載能力の90%近くにします。ルールを守るV4のルートは67枚しか積まないので、V4を
小さくしても効果はありません。`one_visit` の事項をなくすか、訪問先ごとのトレー数を書く分割配送を認めて、その事実が成果物を
変えるようにします。

**ルールシード：** 一部解決。勤務終了時刻（09:00、09:30、10:00）と今週のトレー上限（100、110、120。データに見える
`max_trays` の120より少ない隠れた事実で、新しい深型の番重のためと説明しています）がパラメータになり、`build_world` は
これらが答えを変えうるワールドだけを残します。hard の代表の組み合わせの参照解には09:00より後に帰着する車両があり、
medium の代表の組み合わせの参照解には100枚を超えて積む車両があるので（ケースシード：09:03と103枚）、どちらもそこで
結果を左右します。`van_capacity` には、120より少ない場合は常に確認すべき事項（`tray_limit`）があるようになりました。
`one_visit` の事項は変わっていません（未対応）。

### F5 — 遅延コストが採点ルールとしてしか示されていなかった（中、確認済み）

遅れた分数にかかる3倍の重みは「評価の概要」の下にしかありませんでした。顧客プロンプトは重みの説明を禁じており、データの
説明には `deliver_by` が「店舗が受け入れられる最も遅い到着時刻」とあるだけでした。エージェントがこのトレードオフを知る
かどうか、そして `lateness` の事項を満たせるかどうかは、シミュレーションの顧客が自らの指示を破るかどうかにかかって
いました。

**状況：** 今回の変更で修正済み — 5つのロケールのデータの説明は、`deliver_by` の行のすぐ後に、このコストを業務上の事実と
して記載するようになりました（日本語版）：「遅れて着いても受け取ってもらえますが、コストがかかります。店舗への到着が
`納品期限` を1分過ぎるごとに、車両の稼働3分と同じだけのコスト（店舗からのクレーム、納品代金の値引き）がかかると見て
います。」「評価の概要」の節は変わっておらず、これを管理者の口調に改めるかどうかはケースオーナーに委ねます。

**ルールシード：** 重みはパラメータ `late_cost`（2、3、5のいずれか）になり、データの説明、評価の節、`lateness` の
事項で同じように示されます。

### F6 — 一部のワールドシードで生成器が落ちていた（中、確認済み）

レビューの時点で、参照ソルバーはワールドシード1–30のうち5つで例外を出し、そのうち3つのワールドには有効な計画が
ありませんでした。提携とランクの役割がインデックスで固定されていたためです。

**状況：** 再現せず — 以前のコミット "Bakery dispatcher: work on any world seed"（adb576f）により、`build_world` は参照解が
有効な計画を見つけ、かつどのルールにもそのルールだけを破る計画が見つかるまでシードの乱数列から引き続けるようになり、
構築も提携店舗の実行可能な順序ごとに、さらにシャッフルした順序でやり直すようになりました。ワールドシード1–50はすべて
構築でき、`validate-case --world-seeds 1,...,50` も参照解、違反例、新しいベースラインのすべてで通ります。役割は今も
インデックスで固定されていますが、引き直しがその問題を解決しています。

**ルールシード：** `build_world` は、各ティアの最も厳しい組み合わせ（ティアのフォールバック計画）でも有効な計画があり、
どのパラメータも影響しうるワールドであることも求めるようになりました（後述の「ルールシード」を参照）。引いたワールドの
約9%が条件を満たし、1ワールドあたり平均0.8秒です。ケースシードとワールドシード1–30は構築でき、
`validate-case --world-seeds 1,...,20` は通ります。ケースシードのデータもそれに伴って変わりました。

### F7 — 営業時間中の配送、速度の段差、地区名（中、一部確認）

車両は店舗の開店まで待ち、`deliver_by` は開店の45–90分後ですが、実際のベーカリー配送はふつう開店前に届きます。速度は
区間の出発時刻だけで決まります。06:59に始まる区間は最後まで時速30kmで走り、07:00に始まる区間は50%長くかかります。
地区名は座標と合っていません（北駅店は y = −10.27、南山店は y = +6.05）。ただし、+y が北だとはデータのどこにも書かれて
いません。検証者はこれらを欠陥ではなく現実性に関する判断とみなしています。ルールは明示されており、どのエージェントにも
等しく適用されるからです。

**状況：** 未対応 — 提案：ケースを作り直すなら（F8）、`opens` を受け取り時間帯（「スタッフの在店開始」）に変え、
`deliver_by` を開店時刻以前にし、区間の途中で変わる（または06:45–07:15にかけて徐々に変わる）速度を使い、地区名を座標から
割り当てます。いずれもデータと参照解を変えるため、パッチではなくF8の再設計と一緒に扱うべきです。

**ルールシード：** 一部対応済み。hard では、すでに走行中の区間でも `rush_start` で速度が変わるようになりました
（遅く始めた区間のほうが短時間で済むことはありません）。easy と medium は一定の時速25kmです。`deliver_by` は開店の
30分・45分・60分後のいずれかになったので（以前は45分・60分・90分後）、遅延は実際のトレードオフになります。`opens` を
受け取り時間帯にすることと、座標からの地区名の割り当ては行っていません（未対応）。

### F8 — 設定がなく、隠れた事実しかない（中、確認済み）

このケースにはティアもルールセットもないため、どの難易度の列も同じ問題を採点しています。3種類の状況のうち隠れた事実
（C11の休業、コールドチェーンの意味、旗艦店優先の慣習）しかなく、日付の決まったイベントもステークホルダーからの圧力も
ありません。また、フレームワークのテストフィクスチャ（`tests/conftest.py`）でもあるため、変更のコストが高くなります。

**状況：** 未対応 — 提案：まずフィクスチャのテストを小さな専用ケースに移します。次に、データをバイト単位で同一に保った
まま3ティア × 3ルールセットに切り替えます。Easy：移動モデル、勤務時間、休業店舗、遅延コストを扱い、コールドチェーンと
旗艦店優先は今週は対象外と明記します。Medium：コールドチェーン、渋滞時の速度、旗艦店優先（緩和可能）を加えます。Hard：
日付の決まったイベント（V2が06:40まで整備工場にある、または注文が倍になって積載能力が制約になる）と圧力のメッセージ
（自店を最初にしろと迫る旗艦店の店長）を加えます。ルールセットでは、どの店舗が休業か、勤務終了時刻、遅延の重み、渋滞の
開始時刻を変えられます。V4の容量を隠すと、データに見える `max_trays` と矛盾するため、隠れた事実（「今週はV4の冷蔵棚が
故障しています」）として示すべきです。

**状況（ルールシード）：** 解決済み — 3ティアと、ルールシードが抽選する6つのパラメータに切り替えました。日付の決まった
イベントは06:40まで整備工場にあるV2、圧力は東湖店（C07）の店長の要求で、どちらも hard にあります。後述の
「ルールシード」を参照してください。トレー上限は、V4だけでなくすべての車両についての隠れた事実（新しい番重）として
示しています。フィクスチャのテストはこのケースのまま残し、最小限の更新にとどめました。

### F9 — 07:00の境界の韓国語表現と列名1つ（低、確認済み）

韓国語の標準的な用法では `07:00 이전` / `07:00 이후` はどちらも07:00を含むため、ちょうど07:00に始まる区間が両方の速度帯に
入っていました。出発時刻を分単位で指定できるので、このケースは実際に起こりえます。列名 `최종도착` は期限ではなく
「最終到着」と読めてしまいます。数値は5つのロケールで一致しています。

**状況：** 今回の変更で修正済み — ko/requirements.md と ko/targets.yaml は「07:00 전에 출발하는 구간은 시속 30km, 07:00부터
출발하는 구간은 시속 20km」と書くようになりました。韓国語の列名は、データ（case.py）とその列に触れるすべての韓国語テキスト
で `납품마감` に改められました。

**ルールシード：** 速度の文は新しいモデルに合わせて書き直し（easy と medium：一定の時速25km、hard：
`{{rush_start}} 전까지는 시속 30km, {{rush_start}}부터는 시속 20km`）、境界があいまいにならないようにしています。
`납품마감` は変わっていません。

**ベースライン：** 配車担当者が自分で組む計画（V4が提携店舗を受け持ち、残りはキッチンの周りの方位角で分けてV1、V2、V3、
そしてV4に積みます。旗艦店を先に、次に開店順。すべての車両が05:00に出発）：シード20261025で、参照解の625.55に対して
963.09（×1.54）。ワールドシード1、2、3では、それぞれ568.06に対して1,292.28、779.02に対して1,192.03、560.91に対して
1,402.46です。シード1–50全体ではどのワールドでも有効で、参照解の×1.37～×4.16（中央値×2.19）です。

## ルールシード

このケースは、固定された一つの問題からルールシードの方式（DESIGN.md、Settings）に移りました。case.yaml に3つの
ティアがあり、ルールシードがティアごとの候補プールからそれぞれ独立に抽選する6つのパラメータがあります。データと
`request.md` はどの設定でも同じで、要件、確認すべき事項、ルール、採点は抽選された値に従います。

- **ティア。** Easy：今週のトレー上限、勤務時間、1回の訪問、休業店舗、一定の時速25km、遅延のコスト。要件は顧客の
  言葉で、今週は提携先が冷蔵商品を自分で届けること、旗艦店優先の慣習はお休みであること、月曜日は朝の渋滞がないこと
  （学校が休み）、V2のブレーキ点検は火曜日であることを伝えます。Medium はコールドチェーンと、抽選された場合の慣習を
  加えます。Hard は朝の渋滞（`rush_start` までは時速30km、そこからは時速20km、走行の途中でも適用）、06:40まで整備
  工場にあるV2（新しいルール `van_ready`）、C07の店長からの圧力（ルールではない。事項 `manager_pressure`）を加えます。
- **パラメータ。** `closed_cafe`（C11、C03、C14。ロケールごとの表記は labels による）、`late_cost`（3、2、5）、
  `shift_end`（09:30、09:00、10:00）、`van_capacity`（easy と medium は100、110、120、hard は110なので medium で
  比較）、`rush_start`（easy と medium は none、hard は07:00、06:30、07:30）、`premium_first`（easy は false、medium
  と hard は true か false）。算出値はなく、すべての組み合わせが許容されます。
- **公開パネル。** ルールシード5、13、58：すべての候補が現れ、シード5が medium と hard の代表の組み合わせ（最も遅い
  勤務終了、最も大きいトレー上限、残りは最初の候補）を抽選します。
- **どの設定にも有効な計画がある。** `build_world` は18店舗すべてが営業している状態で各ティアの最も厳しい組み合わせを
  解き、その計画をティアのフォールバック計画として保持します。休業店舗を除いても、そのティアのどの抽選（非公開シードを
  含む）でも有効です。参照解は貪欲な構築からだけでなく、この計画からも始めます。
- **すべてのパラメータが結果を左右する**（`build_world` が受け入れるどのワールドでも）：休業店舗と渋滞の開始時刻は
  常にそうであり、勤務終了時刻、トレー上限、遅延の重み、慣習は、`build_world` がこれらで代表の組み合わせの参照解が
  変わるワールドだけを残すからです（hard で09:00より後に帰着する車両、medium で100枚を超えて積む車両、目的値の1%以上の
  遅延、hard で1%以上のコストになる慣習）。ワールドのフィルタは候補プールに対してのみ調整されています。
- **データの変更。** `deliver_by` は開店の30分・45分・60分後のいずれか（以前は45分・60分・90分後）で、新しいフィルタに
  伴ってどのシードでも受け入れられるワールドが変わったため、ケースシードのデータとすべての数値が上の指摘事項とは
  異なります。
- **ベースライン。** 引き続き配車担当者のスイープです（コールドチェーンが適用される場合はV4が提携店舗を受け持ち、
  すべての車両が05:00に出発、hard ではV2は06:40）。確認したすべての設定（ケースシードとワールドシード1–30、ルール
  シード5、13、58と101–105）で有効で、参照解の1.17～9.76倍です。
- **テスト。** `tests/test_validator.py` はこのケースを高速なフィクスチャとして使い続けます。仕込んだベースラインと
  例の上書きが設定の引数を受け取り、2つのアサーションが設定ごとのメッセージに合わせてあります。
  `tests/test_end_to_end.py` と `tests/test_isolation.py` は `NativeCase.write_reference` で参照解を書き出し、実行
  フォルダを探す前に仕様のルールシードを確定させます。`tests/test_rule_seeds.py` はこのケースを「設定のないケース」
  として使っていましたが、今はそのために設定のない最小限の case.yaml を書き出します。

  （F4）、受け取り時間帯と地区名（F7）。
