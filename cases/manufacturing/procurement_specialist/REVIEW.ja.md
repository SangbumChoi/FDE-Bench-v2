# レビュー：manufacturing/procurement_specialist

ケースレビューの指摘事項（F1–F10）と、各変更がそれぞれの指摘事項にどう対応したかをまとめます。数値は、指摘事項に別途記載がない限り、その数値を報告した変更の後のシード 20261123 のものです。正解の監査までは、仕入先の価格メールとそのルールはケースオーナーのものだったので変更していませんでした。監査では、ケースオーナーの依頼でこれを置き換えました（下記）。

### 正解の監査

ケースオーナーは、どの設定でもデータと依頼が同じ1つのワールドを保ち、顧客だけが知っている要件が答えを決める形のまま、正解と採点を強化するよう依頼しました。GT.md（`gt_report.py` が `dataset/audit.json` から生成）はティアごとに5つの部を示し、CLIENT_REVIEW.md は、事実ごとに、シミュレーションの顧客が各ロケールで何をもとに答えるかを一覧にしています（人による確認待ち）。`audited: true` により、validate-case は監査の結果を合格の条件にします。変更点は次のとおりです。

- **価格メールが答えを変えるようになりました（F3、F8 の一部）。** C01/S03 の通知（`supplier_price_email.txt`、購買部門自身のアドレス、週コード W4、英語のファイル名1つ）を、仕入先のドメインから送られたロケールごとの `.eml` ファイル3通のやり取りである `mail/` に置き換えました。Nara Display（S08）は、最も高価な部品で購買金額の約3分の1を占めるディスプレイモジュール C06 を、12月9日（水）以降に受領する発注から12%値上げし、1月からさらに8%を提案します。顧客は12%を受け入れて8%は保留し、仕入先が確認します。承認済みか承認待ちかは、やり取りの中に書かれています。顧客だけが知っている事実は、発注を月曜日に出すことです。そのため W3（12月7日）は旧価格のままで、W4 が新価格の最初の発注週です（新しい事実 `price_rise_week`）。模範解答は今、S08 への後の週の C06 の発注を W3 に前倒しします。日付を W3 と読むと、測定した easy の15設定のうち9設定と medium の15設定のうち3設定で品質の尺度の10–23%を失います。hard では供給割当（ディスプレイは月3,500個）のため発注を前倒しする余地がないので、週を読み違えても hard のどの設定でも失うのは10%未満で、この事実は hard ではAIが確認すべき事実ではありません（hard の要件には残っています）。依頼文のメールの一文と、要件のメールの段落は、5つのロケールすべてで変わりました。
- **欠品待ちを基板単位に（F4）。** 部品を待って1週待つ基板1枚に10,000 KRW（納期遅延の違約金と残業）がかかり、部品ごとに数えます。不足1個のコストは 10,000 KRW / その部品の基板当たり個数です。顧客の経済感覚では、6 KRW のコンデンサが1個足りなくても、ディスプレイが足りないのと同じく基板は止まります。部品ごとに数えると、複数の部品が同時に足りない週を多めに数えますが、hard の厳密な期待値は保てます。安い部品の不足が高くつくようになったため、約束どおりの日付で立てた顧客自身の計画は、hard で模範解答に対して60–90%悪くなりました（何も測れないほど品質の尺度の幅が広い）。そこで hard の従来のやり方は、供給が不安定になったときに購買担当者がすること、つまりすべてのリードタイムに1週を足すことにしました（README の従来のやり方の説明）。公開ルールシードでの hard の品質の尺度の幅は8.6–19.2%です。
- **事実を1つずつに分割（F6）。** 複数の事柄をまとめた19の事実を25に分けました。`round_scope_easy` と `round_scope_medium` は `scope_list_prices`、`scope_no_flash_change`、`scope_on_time`、`scope_no_allocation` に、リードタイムの事実は `lead_time_business_days`、`scope_whole_weeks`、`holiday_weeks` に、`monthly_budget_cap` は `budget_hard_cap` と `budget_month` に、`dual_source_critical` は `dual_source_two` と `max_share` に、`cost_model` は `shortfall_cost` と `backlog_cost`（hard）に、`engineering_change` は `eco_switch` と `eco_c04_exempt` に分けました。`bom_explosion` は、部品が基板を作る週に必要であること（組立のための前倒しなし）を明記するようになりました。`param:` のリンク：`usd_planning_rate`、`quality_hold`、`safety_stock`、`max_share`。削除したもの（背景としてのみ残し、読み違えても尺度の10分の1未満しか失わない）：`resistor_reels`（公開ルールシードで失う点数0.01–0.13）、保管コストの重み（0–0.04）、`expected_cost`（その唯一の読み違えは、`supplier_lateness` の取り違えた解答がすでに扱っている）、easy での `usd_planning_rate`（easy で測定した15設定のどれでも、誤ったレートはスコアを左右しない。medium では15設定のうち2設定でスコアを左右するので、medium の事実として残る）。5つのロケールの targets.yaml はすべて同じ id を持ちます。範囲の絞り込みには、ストーリーの中で理由が付きました（数量割引には未締結の基本契約が必要、設計部門がまだ C25 を認定中、経営陣はまず確定した日程での計画を求めている）。
- **どの事実もスコアを左右し、直接の検査も付きます。** パラメータでない事実にはそれぞれ自然な読み違えがあり（case.py の `MISREADINGS`：リードタイムを暦日とする、W2 を12月とする、審査中の仕入先を認める、easy でフラッシュの変更を適用する、値上げを W3 からとする、…）、それがプランナーにとっても採点器にとっても設定の見え方を切り替えます。その事実だけを取り違えた解答は、その見え方で立てた模範解答で、模範解答自身の計画がその読み違えの下で有効かつ安ければそちらを採ります（ヒューリスティックの揺れをスコアへの影響として数えないためです）。どの事実も、それが適用されるすべてのティアで、測定した設定の少なくとも1つでスコアを左右します。`score()` は事実ごとに `enforced` を報告し、模範解答を、スコアを左右する取り違えた解答すべてから区別します（GT.md の第1部と第5部）。（2回目：`shortfall_cost` の読み違えは実際には安全在庫を測っていたので置き換えました。直接の検査は、模範解答と取り違えた解答以外の計画には信頼できません。下記を参照。直接の検査の回：`diagnose()` に置き換え、読み違えごとのプランナーの計画に対するリグレットで判定します。）
- **近道をふさぎました。** `no_orders`、`express_only`、`express_split`、`ignore_budget`、`all_upfront`、`no_buffers`、`critical_only` は、39設定すべてで無効になるかスコアが0.5以下です。以前の `no_safety_stock` は hard の1つの組み合わせ（安全在庫0.5週）で0.58でした。不確実性を本当に無視する近道は両方のバッファ（安全在庫と安全リードタイム）を捨てるもので、これはどこでもふさがれています。必須の成果物のための新しいルールは要りません。2社購買により空の計画や一部だけの計画は無効になり、欠品待ちのコストが抜け落ちた部品を罰します。（2回目：近道を3つ追加し、すべてふさがれています。`no_safety_stock` を測り直すと、hard/c4 で依然0.582です。）
- **尋ねない解法。** `robust_solution` はフラッシュの変更がある場合とない場合の両方に備え、納入実績と供給割当を使い、値上げを W3 からと読み、抵抗の在庫を個数と読み、抽選されるすべてのルールについて最も厳しい候補で計画します（安全在庫1.5週、上限70%、1ドル = 1,500ウォン、すべての候補の保留を避ける）。どの設定でも有効ですが、品質点はほとんど得られません。質問の価値は0.99（easy）、1.00（medium）、0.96（hard）です。その大部分は安全在庫の水準だけで決まります。顧客の水準より少なく計画すると致命的で（不足1個・1週あたり標準原価の1.5倍）、多く計画すると重要部品の所要量のおよそ1週分のコストがかかります。（2回目：これは置き換えられました。依頼文の自然な読み方で立てるプランナーは hard でずっと多くを得ます。下記を参照。）
- **模範解答、限界値、品質上限（F2）。** 模範解答は15の変種の後に、評価回数6,000回に固定した局所探索（決定的）を行います。公開ルールシードで最良の変種より2.2–5.4%安く、値上げ前にディスプレイを買うのはこの探索です。`best_known_solution`（4つの出発点からのより広い探索、評価60,000回）はさらに0.3–3.2%安く（品質1.03–1.31、中央値1.106）、HiGHS で解く線形緩和 `objective_bound` は、模範解答より easy で4–7%、medium で9–12%、hard で18–20%低くなります（最小発注数量と価格の段階は緩和。混合整数版は medium と hard では遅すぎました）。`quality_cap: 1.11`。（2回目：限界値には、部品の最後の週より後に届く発注の列が加わりました。有効な計画がそうした発注を出すことがあるためです。）
- **狭い尺度を解消しました。** 225通りの組み合わせすべてで、従来のやり方は模範解答より、このワールドでは少なくとも6.0%（easy）、7.8%（medium）、8.6%（hard）、ワールドシード 1、2、3 では少なくとも5.0%悪くなります（最小は5.02%で、ワールド 3、hard、安全在庫1.5週で Hanbit Electronics が保留）。模範解答と従来のやり方はすべて有効です。このケースはもう `validate.OPEN_NARROW_SCALES` に入っていません。
- **データとテスト。** 予算を同じルールで再調整しました（12月 475 → 480 M）。`tests/test_procurement_price_email.py` は C06/S08 の値上げ（W4 から1.12倍、価格と予算の両方、そして計画レート1,320では W4 から S04 がより安いディスプレイの供給元になること）を確認するようになりました。`tests/test_validator.py` は es/targets.yaml を、削除された `expected_cost` ではなく最後の事実の id である `eco_c04_exempt` で切り詰めます。

### 正解の監査、2回目（敵対的チェック）

2人目のエンジニアが、報告は楽観的だという前提で、1回目の主張をそのブランチのコードで再実行しました。1回目の各項目の状況と、変わった点を示します。尋ねない解法の代案と近道の試行は、監査の39設定でケース自身の採点器で採点しました。その他の数値は保存された監査のものです。

- **尋ねない解法：hard では過大評価（修正済み）。** 最初の `robust_solution` は、一度も尋ねない計画のうち最も強いものではありませんでした。フラッシュの変更がある場合とない場合の両方に備え（10週間ずっと C04 と、W6 から C25）、Nara Display の値上げを W3 からと読み、安全在庫1.5週で計画して、0.009 / 0.000 / 0.043（easy / medium / hard）を得ていました。ところが依頼文自体が、BOM には設計部門のフラッシュの変更がすでに入っていること、供給が不安定なので納入実績と供給割当の通知を送ったことを述べています。ティアに依存しない尋ねない読み方の、同じ39設定での品質点の平均（easy / medium / hard。いずれも最も厳しい割合の上限、最も高いドルのレート、すべての候補の保留で計画）：
  - 自然な読み方（変更を適用し、実績と割当を使う）で安全在庫0.5 / 1 / 1.5週：0 / 0 / 0.628、0 / 0 / 0.656、0 / 0 / 0.518（C04 を10週間ずっと使う easy と medium のすべての設定で無効：W6 から C04 がなくなり、仕入先が1社だけになる）；
  - 見つかった中で最良の、両方に備える計画（両方のフラッシュ、easy では短い週も数量割引もなし）で0.5週：0.058 / 0.001 / 0.346、1週：0.055 / 0.015 / 0.308；
  - 依頼文に反して変更を無視し、0.5週：0.315 / 0.095 / 0（hard のすべての設定で無効：C25 を一度も買わない）、1週：0.263 / 0.126 / 0；
  - 自然な読み方で値上げを W4 ではなく W3 からとした場合：hard で0.611。抵抗の在庫をリール単位と読んだ場合：hard で0.534（模範解答は遅延に対して抵抗を買い足りず、リールを読み違えて抵抗を多く発注するプランナーはそれを免れる）。
  最も厳しい安全在庫で計画するのは、平均では最良ではありません。すべての重要部品を1週分多く買うコストは、顧客がより多くを求める設定で防げる安全在庫不足のコストより大きいからです。`robust_solution` は今、依頼文の自然な読み方に安全在庫の中間の候補（1週）を組み合わせたもので、依頼文の読み方どおり、どのティアでも同じです。変更を無視する読み方も39設定全体ではほぼ同じくらいの成績ですが（品質点の平均0.158対0.151）、依頼文に反します。質問の価値は1.00（easy）、1.00（medium）、0.34（hard）です（1回目は0.99、1.00、0.96）。抽選されるパラメータだけの価値は変わりません（0.72、0.76、0.46）。質問が必要だという主張はどのティアでも成り立ちますが、hard ではその大きさは0.96ではなく約3分の1です。今回の範囲を正しく推測したプランナー（easy と medium で変更を無視する）でも、質問の価値は0.68（easy）と0.87（medium）残ります。
- **安全在庫不足のコストの取り違えた解答は、別の事実を測っていました（修正済み）。** その読み違え「安全在庫不足にはコストがかからない」は、プランナーに安全在庫を削り取らせました。これは安全在庫不足の値段ではなく `safety_stock` の事実で、easy と medium のすべての設定で失う点数は1.0でした。水準は聞いたが値段は聞いていないエージェントなら、安全在庫を下限として守るはずです。その読み違え（`shortfall_floor`、安全在庫不足を部品のコストの20倍とする）では、easy と medium のどの設定でも尺度の10分の1は失わず（最大0.09）、hard では9設定中8設定で失います（失う点数0.05–0.33）。hard では納入の遅れのために下限を守るのが高くつくからです。`shortfall_cost` は今、hard だけの事実です（en の targets.yaml で `tiers: [hard]`）。1.5倍は背景として easy と medium の要件に残ります。事実の数：easy 16、medium 17、hard 18（id は25）。安全在庫不足を部品自身のコスト（1倍）とする場合も測りました。easy では15設定中10設定でスコアを左右しますが、medium では15設定中1設定、hard では9設定中1設定だけで、下限より自然な読み方でもありません。
- **限界値は、有効な計画が出しうる発注を除外していました（修正済み）。** LP には部品の最後の週より後に届く発注の列がありませんでしたが、そうした発注は実際の計画では予算、供給割当、割合の上限に数えられます（割合のルールを満たすためだけに買う2社目の供給元）。それがないと割合の行がルールより厳しくなりうるので、LP が緩和であることは証明されていませんでした。そうした発注は今、在庫に影響しない列として入り、docstring にその論拠（有効な計画はすべて、その目的値以下で LP の実行可能解になる）を記しています。39設定のどれでも値は動かなかったので（そうした発注は緩和の助けにならない）、差は3.6–7.4%（easy）、8.9–12.2%（medium）、17.9–19.5%（hard）のままで、今回作ったどの計画も限界値を上回りません。
- **近道（確認済み、3つ追加）。** 新たに試した極端に単純な計画は、すべてふさがれています。`copy_demand`（毎週の総所要量をリードタイム分前倒しで発注し、在庫と未入荷発注を差し引かない：39/39で無効、予算）、`constant_orders`（部品ごとの週平均の正味所要量を W1-W8 の毎週発注：39/39で無効）、`baseline_breaks`（顧客の MRP で、得になる明細をすべて数量割引まで切り上げる：品質は最大0.002。従来のやり方の明細が安く割引に届くことはほとんどない）。3つとも今は `shortcuts()` に入っています。試したが残さなかったもの：承認済みのすべての見積を最小発注数量で W1 に発注する（39/39で無効、予算）、2社購買なしの模範解答のプランナーに、上限が必要とする最小限の2社目の数量を補ったもの（easy 8/15、medium 8/15、hard 9/9で有効、hard では品質が最大1.0）。後者はすべてのルールを守る安い計画で、近道ではありません。hard では供給割当と保留がすでに数量を分散させているので、割合のルールのコストは小さいのです（`dual_source_two` は hard の9設定中4設定でスコアを左右します）。1回目の判断どおり未対応のまま：安全在庫なしで安全リードタイムありの模範解答のプランナーは、hard/c4（安全在庫0.5週、Mirae Semicon が保留）で0.582です。両方を捨てる `no_buffers` が近道のままです。
- **事実を一つだけ取り違えた解答（確認済み）。** どれも見え方のスイッチを1つだけ切り替え、模範解答がその読み違えの下で有効かつ安ければ模範解答を採ります。安全在庫不足のコストを除けば、どれもエージェントが見るものの自然な読み違えです（暦日、組立のための前倒し、W2 を12月、値上げを W3 から、審査中の仕入先、計画全体での最小発注数量、累積の数量割引、データに見えるとおりの今回の範囲）。`backlog_piece`（1個・1週あたり部品のコストの5倍）は最初の版自身の値段で、その倍率は恣意的ですが、この事実が決めるのは基板単位か部品1個単位かなので、残しています。

### 正解の監査、直接の検査

フレームワークは今、事実ごとの直接の検査を求められた場合にだけ計算し（`diagnose()`、DESIGN.md の「Ground truth audit」）、監査は、模範解答でも取り違えた解答でもない成果物でそれを確かめます。すべての事実を知っている、有効なこれまでに見つかった最善の解答が、適用中の事実について反映されていないと判定されることがあってはなりません。2回目の直接の検査はこの確認に通りませんでした。同じ39設定と同じ計画で、これまでに見つかった最善の解答を657の事実と設定の組のうち125で、顧客の MRP（従来のやり方）を657のうち228で、反映されていないと判定しました。変更点は次のとおりです。

- **必要なときだけ計算。** score() はもう `enforced` を報告しません。evaluate() が求めたとき（監査、実行の採点）に `diagnose(world, submission_dir, setting, scored)` が報告します。読み違えごとの模範解答のプランナーの計画（取り違えた解答の計画で、`ablations()` が監査にも渡します）は設定ごとに一度だけ計画され、ワールドシードと抽選されたパラメータをキーにしてモジュール内にキャッシュされます。easy の設定で最初に直接の検査をする計画は24秒、次からは0.05秒です。validate-case はもう直接の検査を計算しません。同じマシンで同じ負荷のもと続けて実行して、今回の出発点のコミットの174秒に対して98秒です（監査は1,529秒かかります）。
- **読み違えごとのプランナーの計画に対するリグレット。** ある読み方の下での計画のリグレットは、その読み方での模範解答と取り違えた解答の計画のうち良いほうからの距離です（まず違反したルール、次に目的値を、品質の尺度で測ります）。計画が、読み違えの下より顧客の読み方の下で多くのルールに違反するとき、または、その事実についてこれまでに見つかった最善の計画より実質的に悪く（リグレット、つまり最善の計画に対する損失が0.05を超える）、そのリグレットの少なくとも半分を読み違えで説明できるとき、その事実は反映されていないと判定します。2回目の提案、つまりリグレットの差が尺度の5%を超えることだけを条件にすると、顧客の MRP を657の事実と設定の組のうち72で、これまでに見つかった最善の解答を3で、まだ反映されていないと判定しました。弱い計画の損失には、読み方ごとに異なる値段が付くからです（hard の従来のやり方の一律1週のリードタイムは、より大きな安全在庫、1個単位のより高い欠品待ち、あるいは納期どおりの仕入先のように見えます。そのロット・フォー・ロットの計画は、ディスプレイを W3 に前倒しで買うことも、明細を割引まで切り上げることもありません）。また、これまでに見つかった最善の解答がプランナーを上回る幅は、読み方によって異なります。実質的なリグレットを条件にすると、これまでに見つかった最善の解答は外れ、読み違えがリグレットの半分を説明することを条件にすると、従来のやり方は外れます。
- **計画の形（品質保留、割合の上限）。** どちらにも、同じ欠陥のある計画の形のチェックがありました。別の候補でだけ保留になる仕入先から何も買っていないか、すべての重要部品をより厳しい候補の上限以下に収めていて、模範解答がそうしていなければ、その仕入先やその余地が計画に必要だったかどうかにかかわらず、反映されていないと判定していました（従来のやり方の保留で39設定中18、割合の上限で12）。リグレットだけではこれを置き換えられません。そうした制約を守る計画はどちらの読み方でも同じスコアなので、そのリグレットの差はこれまでに見つかった最善の計画どうしの差になり、その制約を守るすべての計画で同じだからです。保留については、計画がそれをコストを払って守っていることも条件にしました。別の候補の仕入先がその保留期間中に何も納入せず、しかもその時期に入荷する明細をその仕入先に切り替えれば尺度の0.5%以上節約できる場合です。割合の上限については、どの計画の形もうまくいきません。上限70%に対するプランナー自身の計画では、最大の割合が61%から70%までばらつき、より厳しい上限の2ポイント以内に抑えられた仕入先を、コストを払っている場合に限って調べるテストでは、スコアを左右する3つ（medium/c5、c8、c9）を見逃しました。そこでは、リグレットの半分という規則が決めます。
- **実行不可能な読み違え。** hard/c2 と hard/c3 では、`c04_critical` の読み方の下で C04 を2社目から買える計画がないため、読み違えたプランナーは局所探索で改善する前のロット・フォー・ロットの変種に戻り、その失う点数（0.31と0.71）の大半は局所探索がないことによるものでした。リグレットで読み違えのせいにできたのは、尺度の0.03と0.10だけでした。代替の計画（`_plan_anyway`）にも、「それ以外は模範解答と同じくらい良い」という条件どおり模範解答の局所探索を適用するようにしました。失う点数は0.06と0.35になり、`eco_c04_exempt` は hard の9設定中8設定でスコアを左右します（以前は9）。読み違えのすべてのルールを守る計画が知られていない場合、そのリグレットはルールを1つ破る計画に対して測るので、条件は0.05だけです。
- **結果（保存された監査）。** どの事実も、模範解答を、スコアを左右する取り違えた解答すべてから区別します。これまでに見つかった最善の解答は657中0、従来のやり方は657中0、`robust_solution` は657中63です（hard 以外でもフラッシュの変更に従うので `scope_no_flash_change` が30中30、`dual_source_two` が39中30、安全在庫の中間の候補で計画するので `safety_stock` が39中3）。すべての事実を知っていて、そのどちらでもない計画でも確認しました。すべての設定でのプランナーの、局所探索で改善する前の15の変種（有効な計画386個、品質 −0.65 から0.86、中央値0.50）は、6,556の事実と計画の組のうち29で反映されていないと判定されます（以前の直接の検査では2,189）：`price_rise_week` 18（W3 にディスプレイを前倒しで買わない：旧価格を使わない）、`scope_no_allocation` 9（今回は適用されない供給割当の範囲内に収まっている）、`max_share` と `usd_planning_rate` が1ずつ。
- **ほかの事実への波及（警告8件）。** 事実どうしがルールを共有していると、ある事実を取り違えた解答は、それがスコアを左右するほとんどの設定で、ほかの事実も反映されていないと判定させます。月次予算を超える計画は、予算を目安とみなす読み方に合い、W2 を12月とすれば収まる場合は月の読み方にも合います（`budget_month`、`price_breaks`、`scope_list_prices`、`usd_planning_rate` の取り違えた解答。月、価格、レートを読み違えて使いすぎるもの）。2社購買のルールを破る計画は、1社購買の読み方に合い、それは割合の上限も外します（`max_share` のより緩い上限、C04 を1社から買うか C25 を一度も買わないフラッシュの変更の取り違えた解答）。そして hard では、遅延へのバッファを持たない計画は欠品待ちを抱え、1個単位の値段ならそれが安く見えます（`supplier_lateness`）。これらは、何がルール違反の原因であれ計画に表れていることなので、実行の段階別の集計（ファネル）では、別の事実を読み違えた計画について、こうした事実を反映されていないと記すことがあります。
- **限界。** 読み違えにしかない制約（より厳しい割合の上限、easy と medium での供給割当）を守り、その制約が模範解答のプランナーに生むコストの2倍以下しか失わない計画は、その余地が必要だったかどうかにかかわらず、反映されていないと判定されます。事実が与える機会（W3 での Nara Display の旧価格、数量割引）を使わない計画は、それがリグレットの半分を説明すれば、反映されていないと判定されます。直接の検査は計画を読むのであって、プランナーの意図を読むのではありません。しきい値（尺度の0.05、リグレットの半分、保留の0.5%）は、このワールドの39設定で決めました。（下記の敵対的チェックで狭めました。）

### F4 — 欠品待ちが基板ではなく部品1個単位で値付けされている（高、一部確認）

**状況：** 未対応 — 提案：欠品待ちを基板・週あたりで値付けします。一つの方法は、不足1個あたり `board_penalty / qty_per_board` とし、`board_penalty` を基板の材料費の5倍か、明示したマージンにすることです。これなら部品ごとに分離できるので、厳密な期待値計算はそのまま使えます。もう一つの方法は、生産数を部品間の最小値としてシミュレーションすることです。いずれの場合も予算と模範解答を再調整し、`cost_model` の事実に基板あたりの生産停止コストを明記します。

**状況（正解の監査）：** 解決。欠品待ちは基板・週あたり（10,000 KRW）で値付けし、部品ごとに、不足1個につき 10,000 / 基板当たり個数として数えます。事実 `backlog_cost`（欠品待ちが起こる hard）がそれを述べます。hard の従来のやり方は、すべてのリードタイムに1週を足すようになりました（そうしないと、そのライン停止のために hard の品質の尺度の幅が60–90%になっていました）。

### F5 — ルールセットが入れ子になっており、予算が効くのは主に11月と B だけ（中、確認済み）
