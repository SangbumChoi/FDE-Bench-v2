FDE-Bench v2

FDE-Bench v2 — direction, positioning and critique

Status: October 2026. This document says what the benchmark is for, where it sits among current agent evaluations, what it does that others do not, where it is still weak, and what to do next. It is written to guide new cases (the catalog has 76 planned roles) and the first live campaigns. Facts about other work come from the research notes summarized in §9; items marked (unverified) were not checked against a primary source.

1. What FDE-Bench v2 measures

A forward-deployed engineer (FDE) turns an under-specified client request into a working deliverable inside the client's rules. FDE-Bench v2 measures four abilities on the same trajectory, separately:

AbilityQuestionMeasured by
ElicitDid the agent find out this client's rules and parameters?Ask-F1 against clarification targets (judges see the client's answers); the share of runs valid under every rule seed of a tier ("all valid across rule seeds")
OperationalizeDid the deliverable actually enforce what was learned, including on hidden and future inputs?Validity against hard rules; program deliverables run on hidden, dated inputs
OptimizeWithin the rules, how good is the result?Quality normalized between a naive baseline (0) and a reference solution (1), uncapped; full credit at the quality cap
Hold the lineUnder pressure, temptation or a profitable shortcut, did it follow the client's rules and the company policy for exceptions?Rule violations on pressure items; bent rules only with an approved exception for that rule

…and how these change with the customer language, the agent's protocol language, the company policy, the engagement (full spec / must clarify / messy) and the harness (one reference loop and four vendor CLIs on the same client channel).

One-sentence positioning. FDE-Bench v2 is a procedurally generated, multilingual benchmark of deliverable-level FDE work. It holds the agent's view fixed while varying the hidden ground truth (difficulty tier × rule seed), so it can isolate whether agents elicit, operationalize and honour a client's rules, including in programs that run on hidden, dated inputs. It does this across customer and protocol languages, company policies and vendor harnesses on one client channel.

2. Lineage and neighbours

  • Baidu FDE-Bench (arXiv 2610.14539, Oct 2026) introduced the FDE framing: 49 real customer projects (optimization and ML), hidden information revealed by a simulated customer, quality relative to the customer-accepted FDE solution, DSR, pass^3, Ask-F1 with a judge panel, case-cluster bootstrap CIs. Best quality was 0.551 and best DSR 6.12%; 78.5% of zero scores were constraint violations, and agents sometimes asked about a rule and then failed to enforce it. Its stated limits: a static customer, fixed data, two task families, no human customers.
  • v2 keeps the metric vocabulary (quality vs reference, DSR, Ask-F1, pass^k, Interact-Req) so results are comparable in kind. It shares no code or data: every case is original and generated from a seed (the original cases could not be redistributed). v2 is a successor in design, not a fork.
  • What v2 adds to that framing: counterfactual ground truths over a fixed view, rule classes with company policies and exception processes, dated events and pressure items, program deliverables run day by day, five natively authored languages on two axes, and harness comparison through one client channel.
  • Name collision. Another, unrelated "FDE-Bench" (arXiv 2609.27571, Sep 2026) evaluates deployment configuration (Docker, Compose, Kubernetes). Cite v2 with its full name and repository.
  • Closest neighbour: τ^τ-Bench (arXiv 2609.04611, Sep 2026). A coding agent builds a customer-service agent from business records and a client with hidden requirements (fixed fact IDs), and the built agent is scored on held-out simulated users. It compares Claude Code, Codex, Kimi Code and OpenCode and keeps 53 private tasks. Best result is 23.9% against an 82.2% oracle reference, from one trial per configuration with no CIs. v2 shares the "program on hidden inputs + hidden requirements + harness comparison" core and differs in counterfactual settings, policies, multilinguality and dated events.

4. What is distinctive

  1. Counterfactual ground truths over a byte-identical view. The same data and request carry a correct answer for every tier and rule seed, and a private rule seed draws one that is published nowhere. A good score across rule seeds requires eliciting the parameters; priors and memorized answers cannot get there. The validator enforces both halves (identical view; every parameter changes the answer in every tier where it varies).
  2. Programs on hidden, dated inputs. The agent ships code that runs day by day on a period it never saw, with regulator changes, absences and cancellations arriving as notices. This tests whether elicited rules are operationalized, which is exactly where Baidu found agents failing.
  3. Rules with classes and company policies. Physical rules never bend; contractual and business rules bend only through the policy's exception process, and an approval covers one named rule. The same run is re-scored under several policies without re-running.
  4. Two-axis multilinguality. Customer language × protocol language, authored natively in zh, en, ko, ja and es, including the data labels and file names.
  5. Pressure inside productive work. Integrity is measured on the same trajectory as capability.
  6. Auditability. Every case stores its data, hidden inputs and ground truth per setting (dataset/) and an explainer page; the validator keeps both in sync with the generator.

5. Design commitments for every new case

These are the rules new cases follow (the new-case scaffold encodes them):

  1. One seeded world; the agent's data and request are the same in every setting.
  2. Three tiers that change which rules apply, and rule parameters that a rule seed draws from candidate pools (params:, with a public panel in rule_seeds:); every parameter binds in every tier where it has more than one candidate, so each draw has its own answer.
  3. Every rule has a class; exactly one business rule is the bendable habit, and bending it must matter: its measured gain should be positive in some settings and negative in others, never fixed by the formula.
  4. Situations of all three kinds: hidden facts, dated events, pressure or temptation. Pressure reaches the agent (not only a program at run time), and every hidden fact bites: ignoring it makes the deliverable invalid or measurably worse.
  5. Deterministic outcome scoring against the world; no LLM judge for quality.
  6. Two anchors: a baseline (the client's own way without an engineer, quality 0) and a solid reference (quality 1.0), with the headroom above the reference measured and reported; rules that bind; numbers for every public setting.
  7. Client-native formats (CSV, xlsx, SQL dumps, e-mails, folders), five natively written locales; the scenario's country is stated, or localized, in every locale.
  8. The client knows business facts (goals, costs, trade-offs), never the evaluation; a target that the data already settles is a confirmation, not a hidden fact.
  9. The case works on other world seeds (validate-case checks seeds 1–3 by default), so evaluation can use private worlds.

Forecasting and other ML cases. A forecast has no single correct answer: many models are reasonable, and one realized future mixes skill with luck. Such cases follow four rules instead of "match the reference":

  • Score the expected loss, not one draw. The world knows the demand distribution it samples from, so the scorer computes the deliverable's expected loss under it (exactly, or over many sampled futures). The result is deterministic and its optimum is known: the Bayes forecast of the true process. That optimum, not a reference heuristic, sets quality_cap; seasonal naive is the baseline.
  • The client's decision picks the loss. Absolute error is minimized by the median, squared error by the mean, a newsvendor cost with under- and over-stock prices by a quantile. Which one applies is a business fact to elicit (what a lost sale costs against an unsold unit), so a good model scored under the wrong loss is worse, for a reason the client can explain.
  • Rules constrain decisions, not forecasts. A shelf minimum, case-pack sizes or a delivery capacity apply to an order plan derived from the forecast; a forecast itself should never be "invalid" for being low. Ask for both (forecast and order) or score the order only.
  • Elicitation is about the target. The hidden facts are what is being forecast (demand or recorded sales when stockouts censor it, units or kilograms, returns netted or not), the calendar (holidays, promotions, closures) and the horizon. Each changes the expected loss measurably, which the validator can check with ablations; the model family is left entirely to the agent.

6.2 Open (ordered by importance)
  1. No live run yet. No API keys in the build environment; vendor CLI flags and docker isolation are unverified. Headroom, signal-to-noise and null-agent scores are therefore unknown.
  2. Simulated-client validity is unmeasured. Over-cooperation, leakage per locale and sensitivity to the client model need an audit and a small human-client calibration.
  3. Statistical power. 13 cases, all with settings. Settings and seeds are clustered within cases, so they do not replace more cases. The axis grid multiplies cells faster than evidence.
  4. Headroom and bite are not yet measured per case. The scale now credits beating the reference, but whether each hidden fact and the bendable rule move the score by a meaningful amount is still a per-case property (§10). Proposed: an ablations() hook checked by the validator.
  5. No human baseline. References are written with full knowledge of the ground truth.
  6. Synthetic realism and language quality. Requirements reflect the authors' research, not elicited practice; locale texts were written by models and need native review.
  7. Open binding findings. A parameter the client states changes no reference in some tiers: bi's reward for "don't know" in easy and medium, bakery's lateness cost in easy and its shift end in easy and medium on world seeds 2 and 3, resume's interview date in medium on world seed 3. They are validator warnings (validate.OPEN_BINDING_FINDINGS) until each owner decides. Loan and hospital also vary parameters in tiers where nothing uses them (warnings).
  8. Cost reporting covers client, extractor and judges; a CLI solver's own tokens are not parsed yet.
  9. Open network in the agent container. Model APIs need egress; an allowlist needs a proxy. Web search should be off or logged per harness.

7. How to run and report an evaluation (protocol)

  • Primary metrics: final score and its components; validity; normalized quality (baseline 0, reference 1, uncapped) next to the plain ratio to the reference; DSR (normalized quality ≥ 1); all valid across rule seeds (valid under every rule seed of the tier); Ask-F1; propensity (violations on pressure items, reported separately).
  • Settings: report per tier (difficulty), each case's score the mean over its rule seeds, then the mean over cases. Use private rule seeds (rule_seeds: [...] in the campaign; the same seeds for every system): the public panel's answers are in the repository and are for development and the explainers.
  • Worlds: report on private world seeds; the public seed is for development and the explainers.
  • Repetition: trials: 3 or more per (case, setting) for pass^k (τ-bench estimator over trials); noise seeds vary the hand-over and are not trials. World robustness (valid across world seeds) is a separate quantity; do not call it pass^k. Report run statuses and keep harness or infrastructure errors out of means.
  • Uncertainty: case-cluster bootstrap intervals; compare systems with paired, within-case differences. Pre-register the primary contrasts (e.g. harness effect at fixed model; Korean vs English customer) instead of reading the full grid.
  • Harness disclosure: model, harness, version, flags, tool access (web search off or logged), budgets.
  • Cost: tokens and dollars for the solver, the client, the extractor and the judges; wall-clock.
  • Simulator disclosure: client model, persona, engagement; judge models (not from the solver's family).

10. Case-level critique (appendix)

An independent reviewer read each of the 13 cases (code, data, five locales, stored dataset) and a second agent tried to refute every finding by re-running the reviewer's evidence. 121 findings: 82 confirmed, 39 confirmed in part, none refuted (the verifiers were lenient: read "partly" as "the direction is right, a detail is overstated"). Each case's findings, with what was fixed and what is left as a proposal, are in its REVIEW.md and in the "Review findings" section of its explainer.html.

10.3 What this changes in the direction
  • Headroom is part of validity. A score that saturates at a modest reference cannot measure the thing the benchmark claims (optimization on top of elicitation). Precedents: RE-Bench scores 0 = starting solution and 1 = reference with no cap; DSBench's Relative Performance Gap normalizes between a baseline and the best human; the deployment FDE-Bench's release gate rejects tasks that do-nothing or stub baselines solve.
  • Every hidden fact and every bendable rule must bite, measurably. The review found many facts that change no answer and bendable rules whose payoff is fixed by the scoring formula. The next case-authoring contract adds an ablations() hook next to violating_examples(): for each quality-relevant target, a deliverable that ignores only that fact, which the validator requires to be invalid or to lose at least 3% normalized quality; and for the bendable rule, the measured gain of the best bent deliverable per setting, which should be positive in some settings and negative in others.
  • The client knows business facts, not the evaluation. Costs, margins and trade-offs belong in the client's business knowledge; formulas and weights do not.
  • Calibrate each case against its best known solution. A single quality cap is wrong for every case: the room between the reference and the best possible answer ranges from 1% to more than 20%. Each case should report its best known normalized quality (an exact optimum where one is cheap, an LP or perfect answer otherwise) and set quality_cap from it, so full credit means "as good as is known".
  • Robustness across worlds is part of the case, not the seed. The stock case's reference loses to cash on many generated worlds; a case's anchors (baseline, reference) must hold on the private seeds it will be evaluated on, which the validator's seed panel now checks for three seeds and should check for more before a campaign.
